# campaign_driver v2 改进清单（战役收尾后实施）

> 2026-08-28 三分片并行实测复盘。当前版保留（利大于弊：CPU/GPU 流水线互补、
> 故障隔离、断点细粒度）。以下 4 项按优先级排序。

## 1. work-conserving 顺序（消灭分片饿死，最高优先）
现状：分片严格按序走切片，遇到排队中的扫描件就整体阻塞（A 实测饿 45 分钟）。
改法：预检后把切片分两池——文本件立即顺序入库；扫描件全部投递后**先继续
处理后面的文本件**，切片尾部统一收割 GPU 结果（文件化结果本就无序依赖）。
收益：分片 CPU 不再空转；总工期不变，CPU 侧吞吐提高。

## 2. 投递按 PDF 指纹去重（重启幂等）
现状：submit 无去重（同 PDF 重复投递=重复 OCR，靠文件化结果兜底但浪费排队位）。
改法：job 文件名带 file_hash，submit 前查 pending+done 已存在则跳过。
收益：重启/重跑零重复投递；purge-before-restart 不再必要。

## 3. 收割改轮转调度（防头部阻塞）
现状：全局 FIFO，先投递者先收割，后投分片系统性靠后。
改法：收割时按「分片轮转 + 各分片队首优先」取结果，或给 job 文件带 shard
优先级标记。收益：三组分片完成时间均衡，监控和续跑更可控。

## 4. 守护进程架构：3 守护 → 单守护并发 2
现状：3 个守护进程共享一张卡，各持模型上下文（实测 5.4/16GB 尚有余量）。
改法：单守护进程内部起 2 个解析线程（GPU 串行化由进程内锁保证）。
收益：显存减半冗余、消除进程间 GPU 争抢；保留并发 2 掩盖单件 IO 停顿。

## 不改项
- 三分片并行架构本身：保留。
- SQLite WAL 三写者：实测 0 错误（bulk delete 后写事务极短），不改。
- E8/E9/E10 三修复已固化，v2 重构时必须带回归测试（tests/test_pipeline.py 8 项）。

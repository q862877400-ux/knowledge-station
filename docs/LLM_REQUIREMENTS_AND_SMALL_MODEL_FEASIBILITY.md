# 批次 6 交付：LLM 需求分析 + 内嵌小模型可行性报告

> 业主问题（2026-09-12）：「分析我们这个项目对大模型的需求，有没有可能内嵌一个小模型」。
> 本文为研究性交付（无代码改动），供业主拍板。结论先行：**技术上可行但强烈不建议全内嵌；
> 建议分层——检索/分类用本地小模型，取证问答保留云端 DeepSeek，理由如下。**

---

## 1. 项目对大模型的需求盘点（4 个消费面）

| # | 消费面 | 代码位置 | 用途形态 | max_tokens | 温度 | 延迟要求 |
|---|--------|----------|----------|-----------|------|----------|
| 1 | **问答主链**（聊天答案） | `src/core/llm/deepseek_client.py` `stream_chat_completion`（系统提示 §6.2 规则 1-9：引用角标、模态保留、追问 JSON、常识标注） | 流式生成，多轮历史（≤4 轮，每条 300 字截断），证据 8 条×800 字符 | 1024 | 0.1 | 用户对话体感（流式掩盖首字延迟） |
| 2 | **取证答案 ks_answer** | `src/core/llm/ks_answer.py` `FORENSIC_SYSTEM_PROMPT`（三段式：依据→推导→结论；**只输出一个 JSON 对象** `{"derivation","conclusion"}`，引用标记 `[[c:i]]`） | 结构化 JSON 输出 + typed_verifier 核验 | ~1024 | 0.1 | 工具超时 120s 内完成检索+推理+核验 |
| 3 | **合规引擎**（义务清单等） | `src/core/compliance/engine.py:188` | 结构化短答（150 tok） | 150 | 0.0 | 批处理，可慢 |
| 4 | **找标分类 discover** | `src/core/update/discover.py:348`（LLM 按需分类与口语清洗） | 结构化分类（200 tok） | 200 | 0.0 | 批处理，可慢 |

**共同特征**（这决定了模型选型的硬约束）：

1. **中文法规域长上下文**：证据段（8 条 × 800 字符 ≈ 6400 字符）+ 系统提示（约 1500 字，含 9 条硬规则）+ 多轮历史 → 单次输入典型 8-10K 中文字符（≈12-16K token）。**小参数模型的主要瓶颈就在这**：长上下文里的「针」（具体条款号、数值、单位、模态词）提取精度随参数量下降而非线性上升的幻觉率。
2. **模态词零改写**：应/宜/严禁/不得/必须必须原样保留强度——这是合规场景的生命线。模态词改写 = 意义反转 = 事故。DeepSeek-chat 在 0.1 温度下此约束可靠；7B 级模型在长上下文偶发漂移。
3. **数值精度**：GB 条款的数值限值（浓度 %LEL、高度 m、距离 mm）不可编造。typed_verifier（数值/模态/法理核验）是引擎自带的第二道闸——**即使换小模型，核验层仍然兜底**，但核验失败的答案会降级为「核验未通过」提示，可用性下降。
4. **JSON 单对象输出**：ks_answer 要求恰好两个字段的裸 JSON。结构化指令遵循是参数敏感型能力（14B 以下模型的 JSON 模式失守率显著）。
5. **流式**：消费面 1 需要流式首字延迟 ≤3s（体感线）。
6. **额度成本**：当前用量（个人研究员日常）远低于成本敏感线；egress_audit 落库每次 payload 可追责。

## 2. 「内嵌小模型」的三个档位评估

### 档位 A：全内嵌（取证问答也本地跑）——❌ 不建议

| 维度 | 评估 |
|------|------|
| 精度 | **过不了取证门禁**。要达到「模态词零改写 + 数值零编造 + 12K token 中文长上下文针提取」，实测下限在 32B+（Qwen2.5-32B-Instruct / GLM-4-32B 级）；7B/14B 级在证据 8 条长上下文下的条款号幻觉率会让三段式取证退化 |
| 硬件 | 32B 量级 INT4 量化仍需 ~20GB 显存或 64GB 内存 CPU 推理（慢）；本机 GPU（ MinerU 已经在用）叠加 20GB 常驻会挤压 OCR 通道 |
| 维护 | 模型文件 +20GB 进仓库/交接链；huggingface 下载、量化版本、推理引擎（llama.cpp/ollama）三条新依赖链 |
| 结论 | **精度不达标 + 硬件冲突 + 依赖链膨胀**，三重否决 |

### 档位 B：分层内嵌（结构化短任务本地、长上下文取证留云端）——✅ 推荐（若要做）

- **可本地化的**：消费面 3（compliance 150tok）+ 消费面 4（discover 200tok）——都是「短输入短输出、温度 0、结构化分类」，4B-8B 级（Qwen2.5-7B / 4B INT4，4-6GB）即可胜任，且这两面本就是批处理不赶时间。
- **留云端的**：消费面 1（问答流式）+ 消费面 2（ks_answer 取证）——长上下文 + 模态/数值零漂移 + 流式，云端 DeepSeek 是当前精度-成本-延迟最优解。
- **实现形态**：`KS_LLM_BASE_URL` 已支持任意 OpenAI 协议端点 → 本地 ollama/vLLM 起一个 7B，把 compliance/discover 的 client 指过去（引擎侧只需按消费面分组读两套 base_url/model 配置——改动面小，`config.py` 加一对 `KS_LLM_STRUCT_*` 变量即可）。
- **成本收益**：省的只是批处理面的小额 token；换来 4-6GB 模型常驻 + 一条新依赖链。**个人研究员用量下收益为负**；若未来批处理放量（万级文档的找标分类），再启用。

### 档位 C：零内嵌 + 现状优化——✅ 当前最优（建议维持）

- 已有的降本机制已经覆盖主要浪费：历史截断（4 轮×300 字）、证据截断（800 字符）、egress 审计、未配置时明确报错不空转。
- DeepSeek-chat 单价在同类里已是最低档；本项目用量（问答 + 批处理分类）月成本远低于任何本地方案的硬件折旧。
- **可选微优化**（不换模型）：discover/compliance 的结构化短任务在 DSH 侧已有便宜工具（模型自身的工具调用）——不适用，这两个面在引擎内部，与 DSH 无关，维持现状。

## 3. 与 OCR 通道的类比（为什么 OCR 能全本地而 LLM 不建议）

项目已把 OCR 做成「云优先本地兜底」（MinerU 云/本地双通道）——因为 OCR 是**任务单一、精度可客观验证**（字符比对）的封闭任务。LLM 取证问答是**开放生成 + 域约束**任务：约束（模态词、数值、引用标记）的遵循率是统计性的，无法像 OCR 那样逐字验证兜底。**typed_verifier 能拦住错的，但拦不住「拦太多导致可用答案变少」**——这正是档位 A 的隐性失败模式。

## 4. 建议（供业主拍板）

1. **维持档位 C（零内嵌）**——当前个人研究员用量与精度要求下最优。
2. 若希望降低对云端的依赖（断网可用性/隐私），做**档位 B 分层内嵌**：批处理面（compliance/discover）指向本地 ollama 7B，取证面留 DeepSeek。改造量：`config.py` 一对变量 + 两个调用点换 client，约半天工作量，随时可启动。
3. **不建议档位 A**——32B 级精度下限的硬件/维护代价与本项目「轻量可交接」的定位冲突。
4. 无论选哪档：**typed_verifier 核验层不动**——它是换模型时的安全网，任何「小模型答案」也必须过核验才可呈现。

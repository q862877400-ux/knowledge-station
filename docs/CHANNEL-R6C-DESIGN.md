# R6c 设计：五类监控打通 + 巡检降级链来自台账（只出设计，不动代码）

- 状态：**设计稿**（2026-09-18，R6a/R6b 之后；本文只是下一步的"怎么打"，不含实现）
- 上游：`docs/CHANNEL-COVERAGE-PLAN.md` §4 的 R6 行（R6c = 五类监控打通）与 §6 的 R5/R6 轮次台账
- 验收（照搬 plan，不改口径）：**五类各有一条端到端用例**；**巡检降级链来自台账**

## 1. 现状（都是本仓可核对的事实）

| 事实 | 位置 |
|---|---|
| 巡检按标准号选链：前缀规则 `_PREFIX_ROUTE` + 固定兜底 `_FALLBACK` | `src/core/update/channels/routing.py` |
| 兜底链的**唯一所有者**是 `routing.fallback_chain()`（R6b 起，inspector 向它取） | 同上 + `inspector._FALLBACK_CHAIN` |
| 台账的 `wiring` 是**反查 routing 得出**的（不是驱动 routing） | `src/core/update/channel_seed.json` 的生成说明 |
| 台账里**部分**渠道声明了它能回答哪几类问题：`answers_json`——**实测只有 68/131 条有**（`发布` 63 / `修订` 30 / `废止` 27 / `现行性` 26 / `编号核验` 30），集中在 internal(16)/law(27)/std_*(19)/aggregator(6)，tool 类基本没有 | 种子记录（`channel_seed.json`） |
| 探针只回答"这个渠道今天能不能抓到东西"（`state`），**不回答**"五类问题有没有答案" | `channel_probe.py` 的模块 docstring |

⇒ 结论：**零件差一层，且差一块数据**——缺的是"按问题选渠道"这一层；
而且"哪条渠道能答哪几类"这份声明**只覆盖一半渠道**，R6c 必须先把它补齐（或明确"不参与五类"），
否则"按问题选链"只对一半台账有效。

## 2. 五类问题的定义（先钉语义，再谈实现）

| 类 | 一句话 | 谁能答（现状） | 反面（不许混） |
|---|---|---|---|
| 发布 | 这个号**什么时候发布**的 | ndls / std.samr / 公告源 | 不是"我们什么时候入库的" |
| 修订 | 有没有**新版**（代替关系） | ndls（代替链）/ hbba / ttzb | 不是"文本被我们改过" |
| 废止 | 有没有**废止/作废**日期与依据 | ndls / official_gb / dbba / hbba | 不是"我们把它移出收藏" |
| 现行性 | **今天**的法律状态（现行/将被代替/尚未生效） | ndls 为首选；govcn 只答"政策库里提没提到" | 不是"文件存在与否"（存在≠现行） |
| 编号核验 | 这个号**是否存在于权威库、写法是否规范** | official_gb / std.samr / dbba / 各国标库 | 不是"我们库里的写法对不对"（那是我们自己的清洗问题） |

⚠ 五类里 **编号核验最容易被做假**：只要"库里能搜到这个号"就给绿——但搜到的是**我们自己的库**。
所以这一类的判据必须落在**外部权威源**上（探针 + 适配器返回的 `source_channel`）。

## 3. 设计（三件事，按依赖排序）

### 3.1 台账作为"链"的**事实来源**（不把规则搬进数据库）

> ⚠ **本节已按实测修正一次（2026-09-18，快照工具当场抓到）**：第一版规则是"台账里
> `wiring='wired'` 且 `enabled=1` 的都进兜底链"。跑 `scripts/chain-snapshot.py` 立刻看到
> **9/9 个样例号的链都变了**——因为 `wired` 里混着**前缀专用**渠道（`dbba`/`hbba`/`mee`/`ndls`/`ttbz`）。
> 两个后果都是真问题：① 泛查链从 2 条变 7 条（每号最多 7 次请求，巡检预算与耗时都变）；
> ② 语义错位（`dbba` 只答 DB 地标号，拿它试 ISO 号是白跑）。
> ⇒ **"接在链上"（wired）≠"是兜底成员"（roster）**，台账今天没有区分这两者的字段。
> **所以本节的规则改成：成员资格是显式名单，台账只做"过滤 + 报告"。**

- **留在代码里**：`_PREFIX_ROUTE`（"GB 50xxx 走 ndls"这类**规则**）——它是判断逻辑，不是可用性事实。
- **成员资格（roster）是显式数据**：缺省仍是 `routing.fallback_chain()`（今天那两棒）；
  把某个专用渠道**提升**为兜底成员是一次**独立的行为改变**，必须单独一步 + 快照差异 + 理由
  （例如"泛查时也值得试 ndls"——但要付"每号多一次请求"的代价）。
- **台账做两件它能作准的事**：
  1. **硬过滤**：`enabled=0`（人工停用）与 `wiring='broken'`（已知失效）**不进链**；
  2. **报告**：`ledger_chain_report()` 列出"可提升为兜底成员的候选"（台账 wired + 代码里有适配器
     但不在名单里）与"台账说 wired、代码里没有该适配器"（G23 的教训：**报错，不静默跳过**）。
- **`state` 只报告不过滤**：探针判 `down` 的 13 条里混着瞬时/WAF/我方 TLS 指纹三类
  （R3d、R6a 实测）⇒ 按一次探针踢渠道会让**链随探针抖动**，那是另一个决策（要更硬的证据，
  如连续 N 次 down）。
- **读表时机**：巡检**批次开始时读一次**，批内复用（一个批次一个口径）；探针/写接口改动台账后
  **失效缓存**。
- ⚠ **循环问题**（不写清就会做出一个"回声"）：台账的 `wiring` 是 R2 反查 `routing` 得来的
  ⇒ 拿它当链的来源，链只能等于 routing 原来的链，台账成了回声。所以本设计只用它做
  "broken 过滤"与"候选报告"，**不用它决定谁能进链**。
- **落地顺序**：先合 `ledger_chain.py`（只算不改，已完成）+ `scripts/chain-snapshot.py`，
  看过快照差异后再单独一步把 inspector 接上去；接的时候要配"链快照"用例
  （给定台账行断言链）+ 一条真机用例（当前库过滤后 = 今天的链）。


### 3.2 "按问题选渠道"（五类打通的核心）

- **前置已完成（R6c-1，2026-09-18）**：`src/core/update/channel_answers.json` 把 131 条**逐条**声明齐了
  （68 条 R1 声明 + 45 条本轮逐条判 + 18 条规则判"不参与"），每条带 `basis`（可追回调研文档/适配器）
  与 `confidence`。⚠ 其中 68 条是 **R1 调研期声明、标 `medium`**（本轮未逐条复核；升 high 需适配器代码级证据）。
- **两条口径（本轮定的，别再吵）**：
  1. **mock/fixture 才供数的字段不算能力**（反例 `ch:discover_search`：卡片契约读 `status`，真实通路不解析）；
  2. `answers: []` 有两种含义——**非状态渠道**（聚合/下载/工具）与**页面取不到、能力未证实**
     （403/404/JS 空壳）；分辨看 `basis` 与台账 `state`，**别把后者读成"这条渠道没用"**。
- 由能力表生成**问题→渠道**的映射（派生物）：`{"废止": [...], "现行性": [...]}`；
  选渠道时**两根轴都要看**：能答这一类（`answers`）**且**探针没判死（`state`）
  ——`channel_answers.channels_for(cls, only_ok=True)` 就是这件事。
- 巡检对每个号：先算"这一号要回答哪几类"（默认五类；业主可按号声明子集），
  再按"该类 → 候选渠道"∩"链"选渠道；**每类各自记结论**，而不是像今天只记一个 `change_type`。
- **答不出来要如实说**：某类没有可用渠道时记 `unanswerable`（不是 `not_found`）——
  `not_found` 的意思是"问了权威源，它说没有这个号"，两者混在一起会让业主以为"查过了"。


### 3.3 事件与四色的口径（不推翻既有映射，只补维度）

- `update_change_event` 已有 `change_type` / `color` / `source_channel`。R6c **不新增列**：
  每类一条事件，`source_channel` 记"这条结论是哪条渠道给的"（这正好复用 R6a 的探针台账）。
- 四色映射保持 `inspector` 现有口径（§10.94 起冻结），R6c 只把"五类都答过了吗"作为**附加条件**
  写进终态恒等式：有 `unanswerable` 的号**不算 done**（与"红黄绿灰=total"并列，不是替代）。

## 4. 验收用例（五条，离线为主）

1. **发布**：喂 ndls 的搜索 JSON fixture ⇒ 事件 `change_type='new_version'`（或 `no_change`），
   `source_channel='ndls'`，且**日期取自响应**（不是本地时间）。
2. **修订**：喂"代替链"fixture ⇒ `superseded` + 新号出现在证据里。
3. **废止**：喂 `a000=作废` + 废止日期 fixture ⇒ `withdrawn` + 日期进证据。
4. **现行性**：同一号在 ndls 说"现行"、govcn 没提到 ⇒ 结论**只认权威源**（govcn 的 miss 不改判）。
5. **编号核验**：号在外部库里不存在 ⇒ `unanswerable`/`not_found` **分开断言**（不许都记 not_found）。
   再加一条**链来自台账**的用例：把某渠道 `enabled=0` ⇒ 链里立刻没有它。

## 5. 明确不做（避免范围蔓延）

- **不引入外部依赖**（`changedetection.io` 之类）——§7 的 D 条已定。
- **不在探针里做发现**（`discover(since)` 是 G12，属另一件）。
- **不逐省适配**（dbba 统一平台，§7 第 4 条已定）。
- **不改四色映射**（除上面的"附加条件"），也不动 SSE。

## 6. 风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| 链改成台账驱动后**变短**（把 seed_only 排除） | 巡检覆盖率下降、有的号变 `unanswerable` | 先跑"链快照"对比：改动前后逐号打印链，人工确认差异 |
| 台账被人工改坏（停用太多） | 巡检大面积失败 | 停用是显式动作 + 面板可见（R4b 的列）+ 批次日志记录"本次链" |
| 五类各记一条事件 ⇒ 事件量 ×N | 库压力与面板噪声 | 先在一个号上量（一期只对 tier0 生效），量完再定批量口径 |
| `answers_json` 是**调研期声明**，可能与实测不符 | 按它选链 = 信一份未复核的声明 | 生成映射时**带上探针 `state`**：`answers_json` 只是候选，`state != ok` 的候选降权并记原因 |
| `answers_json` **只覆盖 68/131 条** | "按问题选链"对一半台账无效 | R6c 第一步就是补齐这份声明（见 §3.2 前置），补不齐的显式标"不参与五类" |

### 3.2.1 实现计划（R6c-3，**2026-09-18 已交付**；本节的 5 条规则已全部实现并有用例）

**目标**：把"这一号该问谁"变成可调用的一层，**先只读**（不改巡检行为），等用例与真机对照齐了再接线。

**新模块** `src/core/update/channels/question_router.py`（纯函数优先，便于离线测）：
**已交付**：`channels_for` / `route_report` / `unanswerable_classes`（后两个是交付时补的——
"候选为空"有三种原因，只回一个空列表会让调用方把结构性缺口与"今天全挂"写成同一句话）。
用例 `tests/test_question_router.py` **20 条**；给人看的脚本 `scripts/question-route.py`。
真机量到的三件事（含 **GB/T 从未进 ndls**，6129/6417 条）见 `CHANNEL-COVERAGE-PLAN.md` 的 R6c-3 条目。

```python
def channels_for(classes: Iterable[str] | None = None, standard_no: str = "", *,
                 rows=None, only_ok: bool = True,
                 table=None, chain=None) -> dict[str, list[str]]:
    """五类 → 候选渠道（按链的顺序排）。classes 缺省 = 五类全要。"""
```
（`table`/`chain` 是交付时加的两个**注入点**：离线测不该连库；R6c-4 换链源时从这里进来。）

规则（每条都要有用例）：
1. **候选 = 能答这类（`channel_answers`）∩ 在链上（`routing.select_chain`）**；
2. `only_ok=True` 时再滤掉**探针判死**（`state == "down"`）的渠道
   ——⚠ **只滤 `down`**：`unknown`/无探针**不滤**（没有证据说它死了，滤掉等于凭空缩链）；
3. **顺序**：链里的先后就是优先次序（前缀专用渠道天然排在兜底棒前面）；
4. **答不出来要如实说**：某类候选为空 ⇒ 该类的结论是 `unanswerable`（**不是** `not_found`）；
5. ⚠ **`tool` 类渠道永不出现在候选里**（它们的 `answers` 是空的，规则上就排除了）。

**明确不做（交付时确认过的两条，别在 R6c-4 之前偷偷加）**：
- 本模块**不**滤 `enabled=0` / `wiring=broken`——那是"链"的职责（`ledger_chain` 已在做），
  两处都滤就是两个所有者；R6c-4 换链源后由链负责；
- 本模块**不**自己声明能力、也**不**决定链长什么样（唯一所有者分别是 `channel_answers.json` 与 `routing`）。

**巡检侧怎么用**（下一步）：
- 每个号先问 `channels_for(需要哪几类, no)`；对**每一类**沿候选链试，**每类各自记一条事件**
  （复用现有 `update_change_event`，`source_channel` 记"这条结论是谁给的"）；
- 某类所有候选都失败/为空 ⇒ 写 `unanswerable` 类结论，**不写 `not_found`**；
- 终态恒等式加一条**附加条件**：有 `unanswerable` 的号**不算 done**（与"红黄绿灰=total"并列，不替代）。

**验收用例（先离线，再一条真机）——5 条全部落地（`tests/test_question_router.py`）**：
1. `channels_for(["废止"], "GB 18218-2018")` 返回非空、且**不含**任何 `tool:` ✅；
2. 把某候选渠道在台账里设 `state="down"` ⇒ 它从候选里消失（`only_ok=True` 生效），
   但 `answers` 声明**不受影响**（两根轴分开）✅；
3. 构造"某类没有任何渠道能答" ⇒ 返回空列表（调用方据此写 `unanswerable`）✅
   ——并且**三种空因分开断言**（`no_capability`/`off_chain`/`all_down`）；
4. 某类的候选顺序 = 该号 `select_chain` 的顺序（前缀专用在前）✅；
5. **真机**：对 3 个真实号**独立复算**逐条一致 ✅（弃用"与 `answers-matrix.py` 对得上"这个说法：
   matrix 打的是**全局能力**（131 条，含不在任何链上的渠道），路由结果是它的**子集**，
   所以用例断言的是"**子集 + 逐条等于 独立复算的 能力∩链**"——原写法会把"子集"误报成"相等"）。

**明确不做**：不改 `inspector` 的选链（那是 R6c-4，且要先看过 R6c-2a 的快照差异）；
不新增表/列；不引入新依赖。

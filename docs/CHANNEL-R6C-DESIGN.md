# R6c 设计：五类监控打通 + 巡检降级链来自台账（只出设计，不动代码）

- 状态：**设计稿**（2026-09-18，R6a/R6b 之后；本文只是下一步的"怎么打"，不含实现）
- 上游：`docs/CHANNEL-COVERAGE-PLAN.md` §4 的 R6 行（R6c = 五类监控打通）与 §6 的 R5/R6 轮次台账
- 验收（照搬 plan，不改口径）：**五类各有一条端到端用例**；**巡检降级链来自台账**

## 1. 现状（都是本仓可核对的事实）

| 事实 | 位置 |
|---|---|
| 巡检按标准号选链：前缀规则 `_PREFIX_ROUTE` + 固定兜底 `_FALLBACK` | `src/core/update/channels/routing.py` |
| 兜底链的**唯一所有者**是 `routing.fallback_chain()`（R6b 起，inspector 向它取） | 同上 + `inspector._FALLBACK_CHAIN` |
| 台账的 `wiring` 是**反查 routing 得出**的（不是驱动 routing） | `src/core/update/channel_seed.json` 的生成说明 |
| 台账里**部分**渠道声明了它能回答哪几类问题：`answers_json`——**实测只有 68/131 条有**（`发布` 63 / `修订` 30 / `废止` 27 / `现行性` 26 / `编号核验` 30），集中在 internal(16)/law(27)/std_*(19)/aggregator(6)，tool 类基本没有 | 种子记录（`channel_seed.json`） |
| 探针只回答"这个渠道今天能不能抓到东西"（`state`），**不回答**"五类问题有没有答案" | `channel_probe.py` 的模块 docstring |

⇒ 结论：**零件差一层，且差一块数据**——缺的是"按问题选渠道"这一层；
而且"哪条渠道能答哪几类"这份声明**只覆盖一半渠道**，R6c 必须先把它补齐（或明确"不参与五类"），
否则"按问题选链"只对一半台账有效。

## 2. 五类问题的定义（先钉语义，再谈实现）

| 类 | 一句话 | 谁能答（现状） | 反面（不许混） |
|---|---|---|---|
| 发布 | 这个号**什么时候发布**的 | ndls / std.samr / 公告源 | 不是"我们什么时候入库的" |
| 修订 | 有没有**新版**（代替关系） | ndls（代替链）/ hbba / ttzb | 不是"文本被我们改过" |
| 废止 | 有没有**废止/作废**日期与依据 | ndls / official_gb / dbba / hbba | 不是"我们把它移出收藏" |
| 现行性 | **今天**的法律状态（现行/将被代替/尚未生效） | ndls 为首选；govcn 只答"政策库里提没提到" | 不是"文件存在与否"（存在≠现行） |
| 编号核验 | 这个号**是否存在于权威库、写法是否规范** | official_gb / std.samr / dbba / 各国标库 | 不是"我们库里的写法对不对"（那是我们自己的清洗问题） |

⚠ 五类里 **编号核验最容易被做假**：只要"库里能搜到这个号"就给绿——但搜到的是**我们自己的库**。
所以这一类的判据必须落在**外部权威源**上（探针 + 适配器返回的 `source_channel`）。

## 3. 设计（三件事，按依赖排序）

### 3.1 台账作为"链"的**事实来源**（不把规则搬进数据库）

- **留在代码里**：`_PREFIX_ROUTE`（"GB 50xxx 走 ndls"这类**规则**）——它是判断逻辑，不是可用性事实。
- **移到台账**：
  1. **兜底链** = 台账里 `wiring='wired'` 且 `enabled=1` 的兜底渠道（按 `priority` 或现有顺序）；
  2. **跳过条件** = `wiring='broken'`（在链上但实测不工作）与 `enabled=0`（人工停用）的渠道**不进链**。
- **冲突不许静默**（G23 的教训）：台账说有、`ADAPTER_CLASSES` 里没有该名字 ⇒ 批次开始写一条
  `event_log`，并把这条渠道标 `suspicious`（"台账说它在链上，代码里没有它"），**不静默跳过**。
- **读表时机**：巡检**批次开始时读一次**，批内复用（一个批次一个口径）；探针/写接口改动台账后
  **失效缓存**。取舍：多花一次读表，换"批内链一致 + 不会每号一次查询"。
- ⚠ 这条改动会**改变巡检行为**（链可能变短/变长）⇒ 必须配"链快照"用例：
  给定种子 + 台账状态，断言 `select_chain()` 的结果；再加一条**真机**用例（当前库的链 = 预期）。

### 3.2 "按问题选渠道"（五类打通的核心）

- **前置**：把 `answers_json` 从 68/131 补到"全覆盖或显式不参与"——每一类都要能回答
  "这一号该问谁"；补的时候**逐条写依据**（调研文档的哪一节 / 哪次实测），不许按类别想当然。
- 由种子的 `answers_json` 生成**问题→渠道**的映射（派生物，不新增真相）：
  `answers: {"废止": ["ndls","dbba","hbba",…], "现行性": [...]}`。
- 巡检对每个号：先算"这一号要回答哪几类"（默认五类；业主可按号声明子集），
  再按"该类 → 候选渠道"∩"链"选渠道；**每类各自记结论**，而不是像今天只记一个 `change_type`。
- **答不出来要如实说**：某类没有可用渠道时记 `unanswerable`（不是 `not_found`）——
  `not_found` 的意思是"问了权威源，它说没有这个号"，两者混在一起会让业主以为"查过了"。

### 3.3 事件与四色的口径（不推翻既有映射，只补维度）

- `update_change_event` 已有 `change_type` / `color` / `source_channel`。R6c **不新增列**：
  每类一条事件，`source_channel` 记"这条结论是哪条渠道给的"（这正好复用 R6a 的探针台账）。
- 四色映射保持 `inspector` 现有口径（§10.94 起冻结），R6c 只把"五类都答过了吗"作为**附加条件**
  写进终态恒等式：有 `unanswerable` 的号**不算 done**（与"红黄绿灰=total"并列，不是替代）。

## 4. 验收用例（五条，离线为主）

1. **发布**：喂 ndls 的搜索 JSON fixture ⇒ 事件 `change_type='new_version'`（或 `no_change`），
   `source_channel='ndls'`，且**日期取自响应**（不是本地时间）。
2. **修订**：喂"代替链"fixture ⇒ `superseded` + 新号出现在证据里。
3. **废止**：喂 `a000=作废` + 废止日期 fixture ⇒ `withdrawn` + 日期进证据。
4. **现行性**：同一号在 ndls 说"现行"、govcn 没提到 ⇒ 结论**只认权威源**（govcn 的 miss 不改判）。
5. **编号核验**：号在外部库里不存在 ⇒ `unanswerable`/`not_found` **分开断言**（不许都记 not_found）。
   再加一条**链来自台账**的用例：把某渠道 `enabled=0` ⇒ 链里立刻没有它。

## 5. 明确不做（避免范围蔓延）

- **不引入外部依赖**（`changedetection.io` 之类）——§7 的 D 条已定。
- **不在探针里做发现**（`discover(since)` 是 G12，属另一件）。
- **不逐省适配**（dbba 统一平台，§7 第 4 条已定）。
- **不改四色映射**（除上面的"附加条件"），也不动 SSE。

## 6. 风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| 链改成台账驱动后**变短**（把 seed_only 排除） | 巡检覆盖率下降、有的号变 `unanswerable` | 先跑"链快照"对比：改动前后逐号打印链，人工确认差异 |
| 台账被人工改坏（停用太多） | 巡检大面积失败 | 停用是显式动作 + 面板可见（R4b 的列）+ 批次日志记录"本次链" |
| 五类各记一条事件 ⇒ 事件量 ×N | 库压力与面板噪声 | 先在一个号上量（一期只对 tier0 生效），量完再定批量口径 |
| `answers_json` 是**调研期声明**，可能与实测不符 | 按它选链 = 信一份未复核的声明 | 生成映射时**带上探针 `state`**：`answers_json` 只是候选，`state != ok` 的候选降权并记原因 |
| `answers_json` **只覆盖 68/131 条** | "按问题选链"对一半台账无效 | R6c 第一步就是补齐这份声明（见 §3.2 前置），补不齐的显式标"不参与五类" |

## 二、我们现在的交互是什么（一手，来自代码）

```
DSH 会话里提问
├─ 输入框上方：KsScopeChip（显示当前口径/范围）
├─ 斜杠命令：/forensic · /bookmarks · /materials
└─ 右侧栏【只有一个 tab：证据】
     └─ KsEvidenceTab（128.9 KB / 1600+ 行）内部三模式：
          ├─ 文件目录（KsFilesView）
          ├─ 收藏（KsBookmarksView）
          └─ 正文（KsDocTextView）+ PDF 查看器 + 底部工具条

设置区（settings.section）里 4 个折叠类目：
   ├─ 效力报告（KsReportPanel）
   ├─ 参考资料/材料平面（KsMaterialsPanel）
   ├─ 渠道台账（KsChannelsPanel）
   └─ 入库（KsIngestPanel）
```

**结构性问题（这就是要重做的原因）**

1. **没有"本轮"这一层**：WeKnora 的来源/产物/追问都挂在**这一轮回答**上；我们的证据 tab 是**全局浏览器**，看完答案想知道"这轮用了哪几条"，没有对应面板。
2. **日常能力被埋进设置**：效力报告、参考资料、入库都在 `settings.section` 里 —— 它们是每天要用的，不是设置项。（WeKnora 把知识库/Agent 做成独立页面 + 对话内可达。）
3. **一个巨型 tab 承担三种模式**：128.9 KB 的单文件，认知负担重，且与"当前这轮对话"脱节。
4. **没有阶段进度**：我们明明有别人没有的**分型核验**这一段，却没在界面上显式呈现。
5. **没有追问建议**。
6. **没有"即问"通道**：想快速问一份文件必须先**入库**（进入向量索引）——这是个真实的体验断点。WeKnora 的临时附件把"即问"和"入库"明确分开。
7. **对话不可交付**：没有一键导出（我们有"研究报告 Markdown"的能力，却没接到对话上）。

## 三、重设计：一问一屏（Per-turn Workspace）

### 5 条原则

1. **右栏服务"这一轮"，而不是当"全库浏览器"**。回答出现时右栏默认切到「本轮」：这几条证据、命中原因、效力徽章、核验结论、追问建议。全库浏览降为二级。
2. **把埋进设置的日常能力搬出来**，按"使用频率"分家（见下表）。
3. **把我们的独有环节做成视觉主角**：每条证据盖**效力徽章**（现行/即将实施/已废止）+ **承重能力**（法条/本任务准则/仅参考），核验结果做成徽章行而不是日志。
4. **补三个原语**：阶段进度（含"核验中"这一段）、追问建议、**临时附件即问**（明确标注"仅本轮，不入库"）。
5. **对话可交付**：一键导出 Markdown（问题 → 三段式答案 → 引用：标准号-条款号+页码 → 核验结论）。

### 右栏一级 tab 从 1 个变 4 个（语义清晰，不再是巨型文件）

```
┌ 右栏 ───────────────────────────────────────────┐
│ [本轮]  [全库]  [效力]  [材料]                    │
├─────────────────────────────────────────────────┤
│ 本轮（默认，跟着当前回答走）                       │
│   ● 这一轮用了 3 条证据                           │
│     1. GB 51283-2020 第4.2.9条   exact ⭐ 现行有效 │
│        [点开原文] ← 跳 PDF 对应页 + 红箭头高亮      │
│     2. GB 50016-2014 第…          fts              │
│   ● 核验：数值 ✅ 模态 ✅ 例外 ✅（分型核验结果）    │
│   ● 追问：… ／ … ／ …                              │
│   ● 本轮产物：研究报告.md                          │
├─────────────────────────────────────────────────┤
│ 全库：文件目录 ⇄ 收藏 ⇄ 正文（原三模式，降为二级）   │
│ 效力：四色视图 + 时间窗 + 导出（从设置搬出）         │
│ 材料：项目 + 评审硬门（从设置搬出）                  │
└─────────────────────────────────────────────────┘
设置区只留：渠道台账（运维性质，低频）· 凭据 · 入库偏好
```

### 现有面板的映射（谁搬去哪、谁合并、谁保留）

| 现有 | 新位置 | 理由 |
|---|---|---|
| `KsEvidenceTab` 的三模式 | 合并为「全库」一个 tab（内部仍三模式） | 它们是"浏览"语义，不该占主位 |
| `KsReportPanel`（效力报告） | **定义成可按地址打开的 tab 类型**：从回答（出现"该标准已废止"时）、工具回执、斜杠命令一步可达，可停靠 | 它是数据视图不是设置；但够不上"每天看"（属巡检后的周期动作），**常驻一级 tab 会挤掉别的 tab** |
| `KsMaterialsPanel`（参考资料） | **暂不升**；先让"待评审 N 条"可见（待办角标） | 材料只有 `approved` 才进结论——**埋在设置里 = 没人回来点批准 = 材料永远不参与结论**（可预见的误解源）。但它**还没在真机跑过一次**（生产库无 `material*` 表），先给可见性、后给座位 |
| `KsIngestPanel`（入库） | **降为动作**：斜杠命令 + 拖拽入口 + 设置里的偏好 | 入库是"做一件事"，不是"看一个面板" |
| `KsChannelsPanel`（渠道台账） | 留在设置 | 运维性质、低频，符合"设置"语义 |
| 新增「本轮」 | 右栏默认 tab | 补上缺失的那一层（本轮证据/核验/追问/产物） |
| `KsScopeChip`（范围芯片） | 保留并强化：**每个回答上盖"这一轮的口径"章** | 防止用户忘了自己开着 forensic/材料绑定 |
| PDF 查看器 + 红箭头高亮 | **保留，不动** | 这是我们比 WeKnora 更强的地方（条款级 vs 分块摘要） |

### 宿主 tab 模型的约束（决定方案形态，2026-09-19 查证）

`@deepseek-ai/dsh-client-ui-sidebar-right` 的契约（`src/client/contract/slots.ts`）里：

- `'sidebar.right.pane.tab'` 是 **`kind: 'keyed'`**，按 **tab 类型定义的 `id`** 分发；原文注释：
  「A tab type registers here under its definition's `id` … **adding a type is a registration, never an edit here**」（第 44-55 行）；
- tab 是**按地址打开的记录**（`openResource(address)` / `openTab(kind, params)`），支持多 pane / 浮动 /
  `revealIfOpened` / `replaceTab`，每个 tab 还有 `title` 槽位与 `tab.menu.item` 动作菜单，
  另有可被替换的 guide tab。

⇒ **"把一个面板升为一级 tab"在宿主模型里说不通**：正确形态是「**定义成可按地址打开的 tab 类型**」，
并从回答、工具回执、斜杠命令处**一步直达**。**"从会话里点到"比"常驻一个 tab"更贴合宿主设计，也更省侧栏空间。**

### 三条"向宿主提议"的（我们改不了对话区）

- 阶段进度条与长等待提示（宿主对话流的进度语义）；
- 回答下方"本轮产物/追问建议"的挂载点；
- 对话导出 Markdown 的入口位置。

## 四、落地顺序（按"性价比"排，不按"看起来完整"排）

| 序 | 做什么 | 代价 | 收益 |
|---|---|---|---|
| 1 | **右栏加「本轮」tab**：本轮证据集 + 核验徽章 + 点开原文 | 纯前端（数据引擎已有：`latest_info`/证据集/核验结果） | 直接补上最大的结构性缺口，且强化我们最强的那一点 |
| 2 | **效力报告改为"按地址可直达"**：从回答/工具回执/命令一步打开并可停靠（`ctx.sidebarRight.openResource`，能力已在用）；材料先只加"待评审"可见性 | 前端为主（组件已存在，改挂载与入口） | 把周期要用的东西从设置里救出来，且不占常驻 tab 位 |

| 6 | 阶段进度 / 长等待提示 | 属宿主对话流，需提议 | 依赖宿主 |

## 五、知识库入口与「知识库管理」二级页（业主 2026-09-19 指定）

> 业主原话：把右侧栏那三个按钮里的「PDF 查看器」改成「**知识库**」；像「新建终端」那样旁边有个**下拉菜单**；
> 下拉里放**效力报告、文件导入**等作为二级目录；其中「**知识库管理**」这一页照 WeKnora 的
> `http://localhost/platform/knowledge-bases` 抄，默认两个自带文件夹（**法律法规**、**标准**），用户可自建（如**公司制度**）。

### 5.2 「知识库管理」二级页：照 WeKnora `KnowledgeBaseList` 抄什么

**抄（附出处，均为 `frontend/src/views/knowledge/KnowledgeBaseList.vue` 一手）**

| # | WeKnora 的做法 | 我们照抄成 |
|---|---|---|
| 1 | 顶部**新建按钮**（带 tooltip；受 `contributor` 角色门控） | 顶部「+ 新建文件夹」+ 搜索框。⚠ 我们的「新建」**只作用于用户文件夹**——自带两棵树是分类法的投影，**不可新建、不可改名、不可删**（见 5.3） |
| 2 | **可折叠分组 + 计数**：置顶 / 我的 / 他人 / 共享可编辑 / 共享只读 | **置顶 / 自带（法律法规 · 标准，逐层展开）/ 我建的**（无共享，故去掉两类；「导入来源」并入"我建的"更实在） |
| 3 | **卡片网格**，每卡：右上角浮动**星标**、标题、**「…」弹出菜单**（置顶/复制/设置/删除）、描述（无则"暂无描述"）、底部**徽标行** | ⚠ **要分两种渲染**：**自带两棵用「树」**（可逐层折叠，层级名即文件夹名，见 5.3）；**用户文件夹用「卡片网格」**（星标、标题、`…` 菜单 = 置顶/重命名/删除、描述、徽标 = 文档数 · 最近更新） |
| 4 | 加载时 **6 张骨架卡** | 同（树的骨架 = 骨架行） |
| 5 | 空状态引导新建 | 同 + 引导「文件导入」 |
| 6 | 新建对话框：名称 + 描述（其余是向量库/多模态/ASR/分块） | **只要名称 + 描述**（其余我们没有或已在设置里） |

**⚠ 与 WeKnora 最关键的形状差异**：它这一页是**扁平的 KB 卡片网格**（一个 KB = 一张卡，KB 内部的目录在详情页才看）。
而按业主 2026-09-19 的定调，我们的「知识库管理」**自带部分本身就是一棵可见的树**（几级目录 = 几层文件夹名）。
⇒ **抄它的"卡片的样式与菜单"，不抄它的"扁平"**；树的层级是我们的主体，不是藏在二级页里。

**不抄（并写清理由）**：向量库绑定、多模态 VLM、ASR、分块调试、Wiki 内容指令（我们没有这些概念）；
组织/共享/只读权限（我们没有多租户）。

### 5.3 数据模型：**几级目录 = 几层文件夹**（业主 2026-09-19 定调）

> 业主原话：**「法规标准的几级目录应该是对应知识库文件夹的不同层文件夹名字」**。

这一句把本设计最容易做错的地方**直接定死**：**不存在"另一套知识库文件夹层级"**。
`doc_catalog` 已经产出的那条分类路径，**就是**文件夹路径；文件夹名**就是**分类节点名。

| 层 | 「标准」下的文件夹名 | 「法律法规」下的文件夹名 | 出处 |
|---|---|---|---|
| 顶层（自带） | **标准** | **法律法规** | 业主指定 |
| 第 2 层 | L2 **CCS 24 大类**（如 `P 土木、建筑`） | L2 **效力等级**（法律 / 行政法规 / 部门规章…） | `doc_catalog.classify_document` 已分 |
| 第 3 层 | L3 **CCS 区间**（如 `P15/19 工程抗震工程防火人防工程`） | L3 **领域**（从 `domain_tags` 非 CCS 标签取首个） | 同上 |
| 叶 | L4 **CCS 具体类目**（如 `P16 工程防火`）+ 文档 | **文档叶**（法规无 L4） | `server.py:894-938` |

**⚠ 顶层名字的精确事实（一手核实，别想当然）**：后端返回的 top **正好两个**，不是三个也不是四个：
`{"top":"std","top_name":"国家标准·行业标准·团体标准"}`（`doc_catalog.py:291,299,302`）
与 `{"top":"law","top_name":"法律法规"}`（`:271,274`）。

⇒ **好消息**：业主说的"默认俩文件夹"**正好等于数据的两个 top**，**不需要造任何包装层**（我曾以为要在三个标准 top 之上再包一层「标准」，实测不存在）。
⇒ **但要决定显示名**：数据里那个长名 `国家标准·行业标准·团体标准` 作为**文件夹名太长**，
建议**显示名用「标准」**（`top` 键仍是 `std`），并在文件夹描述里写全称；
**这只是显示层改名，不是把层级数据改掉**——与硬约束 1 一致。
⚠ 若改成「标准」，则**必须同时**在左列（§7）显示同名，否则又违背"同一棵树"。

⇒ 于是「知识库管理」页里的树，和右栏左列的「文件目录」，是**同一棵树的两个投影**：

- **左列** = **浏览 + 筛选**（只读，服务"这一轮我该引谁"）；
- **知识库管理** = **组织 + 管理**（自带层禁改禁删；用户层可建 / 改名 / 删）。

**两条硬约束（否则一定漂移）：**

1. **不许为"知识库"另存一份层级数据。**
   自带的层级**必须**每次从 `GET /documents/categories` 派生——它已经是权威分类法的唯一实现
   （CCS 24 大类与**区间全表**在 `doc_catalog.py:22-42`）。
   若再建一张 `kb_folders` 表去描述「标准 → P 土木建筑 → …」，就等于有了**两套分类法**，
   以后改一处忘一处，必然出现「树里在 P16、文件夹里在 P15」。**这是本设计最危险的一步。**

2. **用户自建的是"另一棵树"，不是自带树的子层。**
   业主举的例子是「公司制度」——它既不属于 CCS，也不属于效力等级。
   ⇒ 用户文件夹与自带两棵树**平级**，是**真容器**（有独立 id，能改名 / 删除 / 被导入）；
   自带两棵树是**视图**（无 id，名字由分类法决定，不可改、不可删）。
   这恰好解掉了原先担心的"第四个重叠容器"：**不是加一个新容器，而是加一个新容器 + 两棵视图**。

**归属唯一性**：一个文档**要么**在自带树（**位置由分类决定**，用户不可拖），**要么**在用户文件夹（**位置由用户决定**）。
不允许"既在标准树里、又在我建的文件夹里"——否则"文件夹"立刻退化成标签，语义就乱了。
（若业主确实想要"把某个标准挑进自己的文件夹"，那是**收藏夹**的活，不是文件夹的活——收藏夹本来就支持跨夹多对多。）

### 5.4 落地顺序（等设计确认后再动）

1. tab 改名「知识库」（⚠ **是两处，不是一个开关**）：
   `ksSidebar.ts:179-180` 的 `evidenceTabTitle()` → `'PDF 查看器'`（tab 类型标题），
   与 `entry.ts:115-118` 的**地址派生**标题（`PDF 查看器 · 第N页`）。
   后者改完要保证「· 第N页」后缀还在；另 `ksSidebar.ts:201` 的侧栏开始页胶囊标题也走 `evidenceTabTitle`，会一起变（预期内）。
2. tab 顶栏加「▾」下拉，先只放**知识库管理 / 文件导入 / 效力报告**三条；
3. 「知识库管理」页**第一版只读**：把自带两棵树**逐层展开**（层级名即文件夹名，见 5.3）＋ 文档数 ＋ 最近更新；
   再把用户自建文件夹平级列在旁边；
4. 再加新建 / 重命名 / 删除**用户**文件夹（**自带两棵树禁改禁删**）；

⚠ 每一步都要单独过门禁：`plugin` smoke + `verify:commands` + `tsc`。**本页只做设计，未动代码。**

## 六、能力页：一个功能一张卡，点开是它自己的设置窗（业主 2026-09-19 指定）

> 业主原话：`/platform/agents` 这一页的结构思路也可以抄——**不是我们也要搞 agents**，而是说我们的
> 制度修订、自动生成检查清单、合同审计这些功能，都可以在这样一个页面里**对每一个单独功能留一个设置窗口**，
> 点一下就能设置各种东西，**而不是全部塞进设置按钮里**。

### 6.1 WeKnora 那一页的骨架（一手）

- `views/agent/AgentList.vue`（99.2 KB）：顶部新建按钮（`data-guide="agent-list-create"`）+ 加载时 **6 张骨架卡**
  + **可折叠分组**（`builtin` 自带 / `mine` 我的 / `tenantOthers` / `sharedEditable` / `sharedReadonly`）+ 卡片网格；
  点卡片 → `AgentEditorModal.vue`。
- `views/agent/AgentEditorModal.vue`（**248.2 KB**）：一个**带左侧导航分组的设置窗**；按 i18n 键去重后共 **17 组**：
  `agentType / tools / mcp / faq / fileTypes / imageUpload / audioUpload / dataAnalysis / chatParser /
  questionSuggestions / fallback / llmCallTimeout / promptNav / intentPrompts / selection / navGroups / desc`。
- ⇒ 两条可抄的结构：**「自带」本身是一个分组**；**每张卡点开就是"它自己的全部旋钮"**。

### 6.2 我们照这个思路做什么

把现在埋在一个设置栏目里的东西，改成 **能力页 = 每个功能一张卡 + 它自己的设置窗**：

| 卡（功能） | 引擎现状 | 它自己的设置窗里放什么 |
|---|---|---|
| 取证问答 | ✅ 已有 | 默认口径（轻/取证）· 冲突处理（全量列出 / 取一）· 排序红线开关 |
| 义务清单 → 检查表 | ✅ 引擎有、**界面没接** | 义务类型（应当/必须/禁止）· 范围（哪些文件夹）· 输出模板 · 是否带出处链接 |
| 合同审计 | ✅ 引擎有、**界面没接** | 审查类型 · 三色判定口径 · 依据范围 · 是否 LLM 精判 |
| 制度差距分析 | ✅ 引擎有、**界面没接** | 内部制度文件 · 对照范围 · 判定规则 · 输出 |
| 条款释义 / 批量问答 | ✅ 引擎有、**界面没接** | 单条/批量口径 · 输出格式 |
| 每日巡检 | ✅ 已有 | 时刻 · 渠道范围 · 失败重试 · 通知方式 |
| 材料评审 | 🟡 未真机跑过 | 轴 A/B 默认值 · 保留策略（**批准只能由用户做，此处不可配置**） |
| 文件导入 | ✅ 已有 | 默认落哪个文件夹 · Dry-Run 默认开关 · 分桶阈值 |

**分组**：`自带`（法规/标准相关的基础能力，不可删）· `我启用的` · `实验性`。

### 6.3 两条边界（否则等于把同一个病换个地方得）

1. **不要抄它的"17 组"**：248 KB 的设置窗正是"什么都往里塞"的后果。我们每个能力的窗
   **只放它自己的旋钮，3–6 组为上限**；超过就说明这个能力该拆。
2. **旋钮少于 3 个的能力不配独立窗口**：直接在**卡片上内联**（例如"条款释义"可能只有输出格式一个开关）。
   否则点开一个空窗，比塞在设置里更烦。

### 6.4 与既有设置的关系（收口）

`settings.section`「法规标准知识库」现有的六个类目**拆解**：

- 与**某个功能**相关的 → 移到该功能的设置窗（能力页）；
- **全局偏好**（红箭头定位开关等）与**凭据**（LLM / 云 OCR Key）→ 留在**设置**；
- **运维性质**（渠道台账）→ 留在**设置**。

⇒ 设置区从此只回答一个问题：「**这套系统的全局偏好与凭据**」；「某个功能怎么用」全部归到能力页。

### 6.5 落地顺序（先做不动的、再做能跑的、最后才搬设置）

1. **只读能力页**：把已有能力列成卡（`自带` / `我启用的` 分组），点开先只给「当前配置摘要 + 入口」，不做编辑；
2. 给**引擎已完备但界面没接**的三张卡（义务清单 → 检查表 / 合同审计 / 制度差距分析）**接上执行入口**
   —— 它们现在只能直接打 API，这是"最划算的一批活"；
3. 再逐个补各自的设置窗（每窗 3–6 组）；
4. **最后才拆设置区**（把现有六个类目搬走）—— 这一步影响面最大，放最后做，单独过门禁。

### 7.4 三个必须先说清的取舍（否则落地时一定翻车）

1. **第一版全部是"前端聚合"，零后端改动。**
   树端点已经把每个叶文档的 `domain_tags` / `legal_status` / `ccs_*` / `doc_type` 都下发了，所以
   「标签芯片」「效力筛选」「分类筛选」**都能纯前端在已拿到的树上算**（6417 条行的 JSON 量级可接受，且树已按目录稀疏化）。
   而且**过滤管线本身已经存在**（`KsFilesTab.tsx:144-178`），现在是"一个谓词"（搜索词），
   加筛选 = **往同一个 `useMemo` 里多叠几个谓词**，树渲染与剪枝逻辑一行不用改。
   只有两条**要动后端**：把 `standard_type`、`source` 加进那个 SELECT（各一行）。
   ⇒ 顺序上：**先做零改动的四轴，再看是否真需要另两轴。**

2. **我们的标签没有"表"，这是真缺口，必须诚实标注。**
   WeKnora 有独立标签实体 + 抽屉（新建 / 改名 / 删除 / 合并）。我们的标签是**存在每个文档行里的 JSON 串**：
   没有标签表、没有全局唯一性、没有重命名传播、没有"标签属于哪个库"。
   ⇒ 所以**标签编辑（新建/改名/删除）不是接线活**，而是要**新建一张标签表 + 写端点 + 迁移现有 JSON 串**。
   第一版**只做只读筛选**（从现有标签聚合出候选词）；「管理标签」抽屉列为**第二阶段**，单独设计，不顺手做。
   ⚠ 附带风险：`auto_tag.py` 打的领域词与 `ccs_fetcher` 写的 `CCS:` 分类号**混在同一个 `domain_tags` 里**——
   CCS 标签是**分类号不是领域词**（`doc_catalog.py:11` 注释已承认要取"非 CCS 标签"）。
   ⇒ **筛选芯片必须把 `CCS:` 前缀的分流成独立轴**，否则领域筛选里会混进分类号。

3. **这是"列头"，不是新页面。**
   业主比作"PDF 浏览器旁边的目录的详细版"，而我们左列是**一个物理列、多种模式**：
   - **文件目录** = `KsFilesTab.tsx`（**独立组件**，不是 `KsEvidenceTab` 的内部片段）→ 全库四级树；
   - **正文 / PDF** = `KsEvidenceTab.tsx`（`:301` `toc` + `:836-844` 拉 `/{doc_id}/tree`）→ 本书章/小节 + 页码；
   - 另有收藏（`KsBookmarksTab.tsx`）。

   ⚠ **且它就是 §5.3 的那棵树**：左列的「文件目录」与「知识库管理」页用的是**同一个端点**
   （`GET /documents/categories`）、**同一套层级名**。⇒ 左列看到的 `P 土木、建筑` 与知识库管理页里的
   文件夹名**必须逐字一致**——**这是同一份数据的两个投影，不许各画一套**。谁改了分类法，两边同时变。

   ⚠ **且搜索框已经是宿主受控的**：`KsFilesTab.tsx:141-142` 注释「2026-10-28 四宫格统一搜索：catQuery 改由宿主受控传入」
   —— 也就是说**输入框是顶部四宫格那一个**，不是本列私有的。
   ⇒ 所以筛选芯片应当**挨着这个已有搜索**放（同一根列头），而**不要**再长出一个第二搜索框。

   ⇒ 正确形态：给这一列加**列头**（复用已有搜索 + 新增筛选芯片 + 视图切换），下面挂**当前模式**内容；
   **文件目录模式**用上面的轴筛；**正文/PDF 模式**列头退化为"**本书内搜索**"。
   这样既满足"详细版目录"，又**不新增第四个入口、不新增第二个搜索框**。

### 7.5 落地顺序（等设计确认后再动）

1. **筛选芯片条**（挨着已有搜索放；第一版只放**效力状态**一个轴）——纯前端，往 `KsFilesTab.tsx:144-178` 那个 `useMemo` 里叠谓词；

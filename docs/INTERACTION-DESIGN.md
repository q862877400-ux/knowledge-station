## 二、我们现在的交互是什么（一手，来自代码）

```
DSH 会话里提问
├─ 输入框上方：KsScopeChip（显示当前口径/范围）
├─ 斜杠命令：/forensic · /bookmarks · /materials
└─ 右侧栏【只有一个 tab：证据】
     └─ KsEvidenceTab（128.9 KB / 1600+ 行）内部三模式：
          ├─ 文件目录（KsFilesView）
          ├─ 收藏（KsBookmarksView）
          └─ 正文（KsDocTextView）+ PDF 查看器 + 底部工具条

设置区（settings.section）里 4 个折叠类目：
   ├─ 效力报告（KsReportPanel）
   ├─ 参考资料/材料平面（KsMaterialsPanel）
   ├─ 渠道台账（KsChannelsPanel）
   └─ 入库（KsIngestPanel）
```

**结构性问题（这就是要重做的原因）**

1. **没有"本轮"这一层**：WeKnora 的来源/产物/追问都挂在**这一轮回答**上；我们的证据 tab 是**全局浏览器**，看完答案想知道"这轮用了哪几条"，没有对应面板。
2. **日常能力被埋进设置**：效力报告、参考资料、入库都在 `settings.section` 里 —— 它们是每天要用的，不是设置项。（WeKnora 把知识库/Agent 做成独立页面 + 对话内可达。）
3. **一个巨型 tab 承担三种模式**：128.9 KB 的单文件，认知负担重，且与"当前这轮对话"脱节。
4. **没有阶段进度**：我们明明有别人没有的**分型核验**这一段，却没在界面上显式呈现。
5. **没有追问建议**。
6. **没有"即问"通道**：想快速问一份文件必须先**入库**（进入向量索引）——这是个真实的体验断点。WeKnora 的临时附件把"即问"和"入库"明确分开。
7. **对话不可交付**：没有一键导出（我们有"研究报告 Markdown"的能力，却没接到对话上）。

## 三、重设计：一问一屏（Per-turn Workspace）

### 5 条原则

1. **右栏服务"这一轮"，而不是当"全库浏览器"**。回答出现时右栏默认切到「本轮」：这几条证据、命中原因、效力徽章、核验结论、追问建议。全库浏览降为二级。
2. **把埋进设置的日常能力搬出来**，按"使用频率"分家（见下表）。
3. **把我们的独有环节做成视觉主角**：每条证据盖**效力徽章**（现行/即将实施/已废止）+ **承重能力**（法条/本任务准则/仅参考），核验结果做成徽章行而不是日志。
4. **补三个原语**：阶段进度（含"核验中"这一段）、追问建议、**临时附件即问**（明确标注"仅本轮，不入库"）。
5. **对话可交付**：一键导出 Markdown（问题 → 三段式答案 → 引用：标准号-条款号+页码 → 核验结论）。

### 右栏一级 tab 从 1 个变 4 个（语义清晰，不再是巨型文件）

```
┌ 右栏 ───────────────────────────────────────────┐
│ [本轮]  [全库]  [效力]  [材料]                    │
├─────────────────────────────────────────────────┤
│ 本轮（默认，跟着当前回答走）                       │
│   ● 这一轮用了 3 条证据                           │
│     1. GB 51283-2020 第4.2.9条   exact ⭐ 现行有效 │
│        [点开原文] ← 跳 PDF 对应页 + 红箭头高亮      │
│     2. GB 50016-2014 第…          fts              │
│   ● 核验：数值 ✅ 模态 ✅ 例外 ✅（分型核验结果）    │
│   ● 追问：… ／ … ／ …                              │
│   ● 本轮产物：研究报告.md                          │
├─────────────────────────────────────────────────┤
│ 全库：文件目录 ⇄ 收藏 ⇄ 正文（原三模式，降为二级）   │
│ 效力：四色视图 + 时间窗 + 导出（从设置搬出）         │
│ 材料：项目 + 评审硬门（从设置搬出）                  │
└─────────────────────────────────────────────────┘
设置区只留：渠道台账（运维性质，低频）· 凭据 · 入库偏好
```

### 现有面板的映射（谁搬去哪、谁合并、谁保留）

| 现有 | 新位置 | 理由 |
|---|---|---|
| `KsEvidenceTab` 的三模式 | 合并为「全库」一个 tab（内部仍三模式） | 它们是"浏览"语义，不该占主位 |
| `KsReportPanel`（效力报告） | **定义成可按地址打开的 tab 类型**：从回答（出现"该标准已废止"时）、工具回执、斜杠命令一步可达，可停靠 | 它是数据视图不是设置；但够不上"每天看"（属巡检后的周期动作），**常驻一级 tab 会挤掉别的 tab** |
| `KsMaterialsPanel`（参考资料） | **暂不升**；先让"待评审 N 条"可见（待办角标） | 材料只有 `approved` 才进结论——**埋在设置里 = 没人回来点批准 = 材料永远不参与结论**（可预见的误解源）。但它**还没在真机跑过一次**（生产库无 `material*` 表），先给可见性、后给座位 |
| `KsIngestPanel`（入库） | **降为动作**：斜杠命令 + 拖拽入口 + 设置里的偏好 | 入库是"做一件事"，不是"看一个面板" |
| `KsChannelsPanel`（渠道台账） | 留在设置 | 运维性质、低频，符合"设置"语义 |
| 新增「本轮」 | 右栏默认 tab | 补上缺失的那一层（本轮证据/核验/追问/产物） |
| `KsScopeChip`（范围芯片） | 保留并强化：**每个回答上盖"这一轮的口径"章** | 防止用户忘了自己开着 forensic/材料绑定 |
| PDF 查看器 + 红箭头高亮 | **保留，不动** | 这是我们比 WeKnora 更强的地方（条款级 vs 分块摘要） |

### 宿主 tab 模型的约束（决定方案形态，2026-09-19 查证）

`@deepseek-ai/dsh-client-ui-sidebar-right` 的契约（`src/client/contract/slots.ts`）里：

- `'sidebar.right.pane.tab'` 是 **`kind: 'keyed'`**，按 **tab 类型定义的 `id`** 分发；原文注释：
  「A tab type registers here under its definition's `id` … **adding a type is a registration, never an edit here**」（第 44-55 行）；
- tab 是**按地址打开的记录**（`openResource(address)` / `openTab(kind, params)`），支持多 pane / 浮动 /
  `revealIfOpened` / `replaceTab`，每个 tab 还有 `title` 槽位与 `tab.menu.item` 动作菜单，
  另有可被替换的 guide tab。

⇒ **"把一个面板升为一级 tab"在宿主模型里说不通**：正确形态是「**定义成可按地址打开的 tab 类型**」，
并从回答、工具回执、斜杠命令处**一步直达**。**"从会话里点到"比"常驻一个 tab"更贴合宿主设计，也更省侧栏空间。**

### 三条"向宿主提议"的（我们改不了对话区）

- 阶段进度条与长等待提示（宿主对话流的进度语义）；
- 回答下方"本轮产物/追问建议"的挂载点；
- 对话导出 Markdown 的入口位置。

## 五、知识库入口与「知识库管理」二级页（业主 2026-09-19 指定）

> 业主原话：把右侧栏那三个按钮里的「PDF 查看器」改成「**知识库**」；像「新建终端」那样旁边有个**下拉菜单**；
> 下拉里放**效力报告、文件导入**等作为二级目录；其中「**知识库管理**」这一页照 WeKnora 的
> `http://localhost/platform/knowledge-bases` 抄，默认两个自带文件夹（**法律法规**、**标准**），用户可自建（如**公司制度**）。

 ├ 效力报告          ← 现埋在设置区（KsReportPanel），按地址直达

### 5.2 「知识库管理」二级页：照 WeKnora `KnowledgeBaseList` 抄什么

**抄（附出处，均为 `frontend/src/views/knowledge/KnowledgeBaseList.vue` 一手）**

| # | WeKnora 的做法 | 我们照抄成 |
|---|---|---|
| 1 | 顶部**新建按钮**（带 tooltip；受 `contributor` 角色门控） | 顶部「+ 新建文件夹」+ 搜索框。⚠ 我们的「新建」**只作用于用户文件夹**——自带两棵树是分类法的投影，**不可新建、不可改名、不可删**（见 5.3） |
| 2 | **可折叠分组 + 计数**：置顶 / 我的 / 他人 / 共享可编辑 / 共享只读 | **置顶 / 自带（法律法规 · 标准，逐层展开）/ 我建的**（无共享，故去掉两类；「导入来源」并入"我建的"更实在） |
| 3 | **卡片网格**，每卡：右上角浮动**星标**、标题、**「…」弹出菜单**（置顶/复制/设置/删除）、描述（无则"暂无描述"）、底部**徽标行** | ⚠ **要分两种渲染**：**自带两棵用「树」**（可逐层折叠，层级名即文件夹名，见 5.3）；**用户文件夹用「卡片网格」**（星标、标题、`…` 菜单 = 置顶/重命名/删除、描述、徽标 = 文档数 · 最近更新） |
| 4 | 加载时 **6 张骨架卡** | 同（树的骨架 = 骨架行） |
| 5 | 空状态引导新建 | 同 + 引导「文件导入」 |
| 6 | 新建对话框：名称 + 描述（其余是向量库/多模态/ASR/分块） | **只要名称 + 描述**（其余我们没有或已在设置里） |

**⚠ 与 WeKnora 最关键的形状差异**：它这一页是**扁平的 KB 卡片网格**（一个 KB = 一张卡，KB 内部的目录在详情页才看）。
而按业主 2026-09-19 的定调，我们的「知识库管理」**自带部分本身就是一棵可见的树**（几级目录 = 几层文件夹名）。
⇒ **抄它的"卡片的样式与菜单"，不抄它的"扁平"**；树的层级是我们的主体，不是藏在二级页里。

**不抄（并写清理由）**：向量库绑定、多模态 VLM、ASR、分块调试、Wiki 内容指令（我们没有这些概念）；
组织/共享/只读权限（我们没有多租户）。

### 5.3 数据模型：**几级目录 = 几层文件夹**（业主 2026-09-19 定调）

> 业主原话：**「法规标准的几级目录应该是对应知识库文件夹的不同层文件夹名字」**。

这一句把本设计最容易做错的地方**直接定死**：**不存在"另一套知识库文件夹层级"**。
`doc_catalog` 已经产出的那条分类路径，**就是**文件夹路径；文件夹名**就是**分类节点名。

| 层 | 「标准」下的文件夹名 | 「法律法规」下的文件夹名 | 出处 |
|---|---|---|---|
| 顶层（自带） | **标准** | **法律法规** | 业主指定 |
| 第 2 层 | **CCS 24 大类**（如 `P 土木、建筑`） | **效力层级**（法律 / 行政法规 / 部门规章…） | `doc_catalog.classify_document` |
| 第 3 层 | **CCS 区间**（如 `P15/19 工程抗震、工程防火、人防工程`） | **法律部门**（A~G，如 `宪法与行政法`） | 同上 |
| 第 4 层 | **CCS 具体类目**（如 `P16 工程防火`） | **业务领域**（取 `domain_tags` 首个；无则 `未细分`） | 同上 |
| 叶 | 文档 | 文档 | `server.py:933-937`：**两棵树都恒定输出四层** |

> 🔧 **一处更正（独立验证者 b44 发现，我已复核）**：本文初稿把法规树写成「L2 效力等级 → L3 领域 → 文档叶，**无法规 L4**」——**是错的**。

1. **不许为"知识库"另存一份层级数据。**

2. **用户自建的是"另一棵树"，不是自带树的子层。**
   业主举的例子是「公司制度」——它既不属于 CCS，也不属于效力等级。
   ⇒ 用户文件夹与自带两棵树**平级**，是**真容器**（有独立 id，能改名 / 删除 / 被导入）；
   自带两棵树是**视图**（无 id，名字由分类法决定，不可改、不可删）。
   这恰好解掉了原先担心的"第四个重叠容器"：**不是加一个新容器，而是加一个新容器 + 两棵视图**。

**归属唯一性**：一个文档**要么**在自带树（**位置由分类决定**，用户不可拖），**要么**在用户文件夹（**位置由用户决定**）。
不允许"既在标准树里、又在我建的文件夹里"——否则"文件夹"立刻退化成标签，语义就乱了。
（若业主确实想要"把某个标准挑进自己的文件夹"，那是**收藏夹**的活，不是文件夹的活——收藏夹本来就支持跨夹多对多。）

### 6.3 两条边界（否则等于把同一个病换个地方得）

1. **不要抄它的"17 组"**：248 KB 的设置窗正是"什么都往里塞"的后果。我们每个能力的窗
   **只放它自己的旋钮，3–6 组为上限**；超过就说明这个能力该拆。
2. **旋钮少于 3 个的能力不配独立窗口**：直接在**卡片上内联**（例如"条款释义"可能只有输出格式一个开关）。
   否则点开一个空窗，比塞在设置里更烦。

### 6.4 与既有设置的关系（收口）

`settings.section`「法规标准知识库」现有的六个类目**拆解**：

- 与**某个功能**相关的 → 移到该功能的设置窗（能力页）；
- **全局偏好**（红箭头定位开关等）与**凭据**（LLM / 云 OCR Key）→ 留在**设置**；
- **运维性质**（渠道台账）→ 留在**设置**。

⇒ 设置区从此只回答一个问题：「**这套系统的全局偏好与凭据**」；「某个功能怎么用」全部归到能力页。

### 6.5 落地顺序（先做不动的、再做能跑的、最后才搬设置）

1. **只读能力页**：把已有能力列成卡（`自带` / `我启用的` 分组），点开先只给「当前配置摘要 + 入口」，不做编辑；
2. 给**引擎已完备但界面没接**的三张卡（义务清单 → 检查表 / 合同审计 / 制度差距分析）**接上执行入口**
   —— 它们现在只能直接打 API，这是"最划算的一批活"；
3. 再逐个补各自的设置窗（每窗 3–6 组）；
4. **最后才拆设置区**（把现有六个类目搬走）—— 这一步影响面最大，放最后做，单独过门禁。

|---|---|---|---|
| 类别 | `doc_type` | 标准 / 法规 | 树顶端已分（`doc_catalog.classify_document`） |
| **效力状态** | `legal_status` + `effective_from` | 现行 / 即将实施 / 已废止 / 被替代 | `resolve_status()`，目录端点已统一 |
| 效力层级 | `legal_hierarchy` | 法律 / 行政法规 / 部门规章 / … | 法规树 L2 已在用（`_HIER_TO_TIER`） |
| 分类 | `ccs_code` / `ccs_name` / `ics` | CCS 大类 / 区间 / 具体类目 | 标准树 L2–L4 已在用 |
| **领域标签** | `domain_tags`（JSON 列表） | 如 `["安全","消防"]`；CCS 标签形如 `CCS:P16 工程防火` | ⚠ **不作筛选轴**（§8.3）。界面上的"标签"是用户自建的**另一套**，见 §8.1 |
| 来源渠道 | `source` | 渠道名 | ⚠ **不在树端点 SELECT 里** |
| 强制 / 推荐 | `standard_type` | 强制 / 推荐 | ⚠ **同上，不在树端点 SELECT 里** |

### 7.4 三个必须先说清的取舍（否则落地时一定翻车）

1. **第一版全部是"前端聚合"，零后端改动。**
   树端点已经把每个叶文档的 `domain_tags` / `legal_status` / `ccs_*` / `doc_type` 都下发了，所以
   「标签芯片」「效力筛选」「分类筛选」**都能纯前端在已拿到的树上算**（6417 条行的 JSON 量级可接受，且树已按目录稀疏化）。
   判谓词 + 剪枝这段逻辑**已经写好了一份**（`KsFilesTab.tsx:144-178`）；把它**抽成不依赖组件的纯函数**，
   查看器继续调用（**外观一行不改**），知识库管理页也调用它。
   只有两条**要动后端**：把 `standard_type`、`source` 加进那个 SELECT（各一行）。
   ⇒ 顺序上：**先做零改动的四轴，再看是否真需要另两轴。**

2. **我们的标签没有"表"，这是真缺口，必须诚实标注。**
   WeKnora 有独立标签实体 + 抽屉（新建 / 改名 / 删除 / 合并）。我们的标签是**存在每个文档行里的 JSON 串**：
   没有标签表、没有全局唯一性、没有重命名传播、没有"标签属于哪个库"。
   ⇒ 所以**标签编辑（新建/改名/删除）不是接线活**，而是要**新建一张标签表 + 写端点 + 迁移现有 JSON 串**。
   第一版**只做只读筛选**（从现有标签聚合出候选词）；「管理标签」抽屉列为**第二阶段**，单独设计，不顺手做。
   ⚠ 附带风险：`auto_tag.py` 打的领域词与 `ccs_fetcher` 写的 `CCS:` 分类号**混在同一个 `domain_tags` 里**——
   CCS 标签是**分类号不是领域词**（`doc_catalog.py` 模块注释与 `_law_domain_doc` 都按"**非 CCS 标签**"取领域；
   ⚠ 注意该模块注释的层级描述本身也是旧口径，见 §5.3 的更正）。
   ⇒ ~~筛选芯片必须把 `CCS:` 前缀分流成独立轴~~ **此条已作废**：按 §8.3，自动打的 `domain_tags`
   不再作为界面的筛选轴，所以不存在"把 CCS 分类号混进领域词"的暴露面。
   ⚠ 但 `domain_tags` 里这个混装问题**在引擎里仍然存在**（`auto_tag` 的领域词 + `ccs_fetcher` 的 `CCS:` 分类号同一列），
   效力报告/义务/差距分析仍读它 —— **别因为界面不展示了就以为它好了**。

3. **这是"知识库管理页里的一屏"，不是查看器的列头升级。**
   查看窗口 + 它的目录**保留原样**（见本节开头的边界）。要设计的是**知识库管理界面**里
   打开一个库（法律法规 / 标准 / 用户自建）之后的那一屏：

   - **左**：这个库的**目录**——按 §5.3，**几级目录就是几层文件夹名**
     （标准：CCS 大类 → 区间 → 具体类目；法规：效力层级 → 法律部门 → 业务领域）；
   - **上**：**筛选与搜索**（标签芯片 + 效力 / 类别 / CCS 分类 + 按标准号或名称搜）；
   - **主体**：文档列表（**卡片 / 列表**两种视图切换）。
   - 这一屏**自带搜索框**——查看器那个是宿主受控的顶部四宫格搜索，属查看器，**不借**。

   ⚠ **与查看器共享的是"数据与分类法"，不是"外观"**：同一端点 `GET /documents/categories`、
   同一套层级名——**不许各画一套**。谁改了分类法，两边同时变（查看器那边只是**名字**跟着变，**形式不动**）。

   ⚠ **也不要在知识库管理里另造一个"文件目录"组件与查看器打对台**：逻辑共用（抽纯函数），呈现各是各的。

### 7.5 落地顺序（等设计确认后再动）

1. **知识库管理页 → 打开一个库 → 详情屏（只读）**：目录（文件夹层级）+ 文档列表 + **它自己的搜索框**——纯前端，先证明形状对；
2. **筛选芯片**（第一版只放**效力状态**一个轴）——纯前端；
3. **类别 / CCS 分类筛选**——纯前端；
4. **领域标签芯片**（多选 popup，抄 `KnowledgeTagFilter` 形状）——纯前端聚合，**先把 `CCS:` 前缀分流成独立轴**；
5. 到这一步**才**考虑改后端 SELECT（`standard_type` / `source` 各加一行）；
6. **标签编辑 / 标签表 = 独立一轮**，单独设计 + 单独门禁；
7. **查看器全程不动**：唯一可能被牵动的是「顶层显示名」（见 §5.3），那是**数据文案**，不是形式。

⚠ **抽共用纯函数那一步要格外小心**：必须先用既有 smoke 证明**查看器左列行为未变**（同输入同输出）。
否则就成了"为了复用，偷偷改了不该改的东西"——那正是业主这次叫停的事。

⚠ 每步单独过门禁（`plugin` smoke + `verify:commands` + `tsc`）。**本页只做设计，未动代码。**

> 业主原话（一次给了十几条，逐条落到下面）：
> 「**收藏功能就不要了，改成标签**，标签可以**跨知识库大文件夹**定，比如设一个标签叫『公司相关』，
> 把和公司相关的法规标准及公司制度都打上标签，**我搜索的时候就可以选择在这个标签下面进行对话**」；
> 「知识库界面**不用搜索**，文件夹可能就那么几个，有个**新建按钮**得了」；
> 「『公司制度』这类自建夹是跟自带两棵树**平级**，相当于就加在后面了」；
> 「知识库详情这个我喜欢，可以把**发布日期、生效日期、废止日期**啥的也加上」；
> 「领域标签你现在是给每个文件**自动打了几个标签**然后可以选，**我不喜欢**」；
> 「文件名前面要有**选择框、全选**…我一个全选，下面就出来一个**悬浮按钮条**，包括『已选X项 取消选择 / 批量打标签 /
> 移动到目录 / 批量删除』，然后每个文件名字后面就**常驻一个『+标签』按钮**，可以手动单个加标签」；
> 「搜标准号/名称**我同意**，但我想加一个**搜内容**…多个关键词用 **+** 号连接，用 **-** 号那就是**屏蔽**这个词，
> 比如 `安全+半导体-冶金`」。

### 8.1 「收藏 → 标签」：**底账已经就是标签的形状**（一手核实）

这是本轮最划算的一条：我们不需要新建一套标签系统，因为现有收藏夹**在数据层已经是标签**：

| 现成的东西 | 位置 | 它就是 |
|---|---|---|
| `user_bookmark_folder(folder_id, folder_name UNIQUE)` | `schema.sql:170-175` | **标签**（名字唯一 = 标签名唯一） |
| `user_doc_bookmark(doc_id, folder_id)` | `schema.sql:158-166` | **文档 ↔ 标签** |
| `user_bookmark(clause_key, folder_id)` | `schema.sql:147-155` | **条款 ↔ 标签** |
| `user_data.folder_scope(folder_id)` → `{doc_ids, clause_keys}` | `user_data.py:262-282` | **标签覆盖的文档集** |
| `ks_answer.py` 按 `folder_id` 过滤（`:645-648`、`:754`） | 引擎侧 | **「在这个标签下提问」已经是引擎能力** |
| `server.py:412-456` 命中体追加夹范围标记 | 引擎侧 | 同上 |

⇒ 所以「标签下面进行对话」**不是新能力**，是把既有「夹内提问」**换个名字接出来**。

**但有一处硬约束挡着「一个文档多个标签」**：`user_doc_bookmark` 上有 **`UNIQUE(doc_id)`**（`schema.sql:165`）
——今天**一个文档只能属于一个夹**。业主的例子（一条标准既是「公司相关」又是「动火作业」）要求多标签，
⇒ **必须去掉这个 UNIQUE**（真迁移，要单独一轮 + 迁移脚本 + 老库兼容）。

**改名面（实测计数）**：`收藏` 在 plugin 里 145 处 / 9 个文件，src 里 100 处 / 13 个文件；
`bookmark-folders` 路由在 `server.py` 39 处、`api.ts` 33 处。
⇒ 建议**内部表名/路由名先不动**（改名收益低、风险高），**只改用户看得见的词**（收藏 → 标签、收藏夹 → 标签），
把物理改名留到确有需要时。这是一次**有意识的取舍**，不是漏做。

### 8.2 自建夹与自带两棵树**平级**（业主确认）

业主原话已确认：自建夹「相当于就加在后面」。⇒ §5.3 的结论成立，**不做**成自带树的子层。
“知识库”页**去掉搜索框**，只留「＋ 新建文件夹」（文件夹就几个，搜索是多余的）。

### 8.3 详情屏：批次操作与手动标签（业主逐条指定）

- 每行**文件名前有勾选框**；列表头有**全选当前**；
- 有选中时出现**悬浮批量条**：`已选 X 项` · `取消选择` · `🏷 批量打标签` · `📁 移动到目录` · `🗑 批量删除`；
- **每行常驻「＋标签」**按钮 → 手动给单份加/去标签；
- 行上补 **发布 / 生效 / 废止** 三个日期（`doc_meta` 有 `published_at` / `effective_from` / `withdrawn_date`；
  ⚠ `withdrawn_date` **无数据通路**，是这个字段的既有缺口，不是本轮引入的）；
- **删掉"自动打的领域标签当筛选轴"**（业主明确不喜欢）。筛选轴改为：**效力状态 · 强制性/推荐性 · 我的标签**。
  ⚠ 引擎的 `auto_tag.py` / `ccs_fetcher` **不动**（`domain_tags` 还被效力报告/义务/差距分析用着），
  只是**不再把它当界面的筛选轴**。

### 8.4 「搜内容」与 `+` / `-` 语法：**今天是包含而不是屏蔽**（重要事实）

一手核实 `src/core/text_utils.py:1374-1402` 的 `fts_match_expr()`——它是 FTS5 MATCH 表达式的**唯一构造器**
（注释写"必须只有一个"，`clause_repo`/`hybrid_engine`/`material_repo` 共用）。它现在：

1. 先 `segment_for_fts`（jieba `cut_for_search`）；
2. 每个词**加引号**（因为裸 `-` 会被 FTS5 当语法：实测 `GB 30871-2022` → `no such column: 2022`，
   且这类错**会被兜底 except 吞成"没有命中"**）；
3. 用 **`OR`** 连接（注释解释：FTS5 多词是隐式 AND，自然语言提问会 0 命中）。

⇒ **推论（必须写清）**：今天输入 `安全+半导体-冶金`，`-` 会被规则 2/3 处理掉，
"冶金"**会作为正词被 OR 进去**——即**是"包含"，不是"屏蔽"**。业主想要的行为**今天不成立**，是真改动。

**改法（只改这一处 = 唯一构造器）**：在分词**之前**先解析 `+` / `-`，产出
`(正词组) NOT (屏蔽词组)`，因为 FTS5 的 `NOT` 是**二元**运算符（`a NOT b`）。
⚠ **两个坑必须处理**：
- `-` 也是标准号的一部分（`GB 30871-2022`）。⇒ 约定：**`-` 后紧跟数字时不算运算符**（保护标准号）；
- **只有 `-词` 没有正词**时，FTS5 的 `NOT` **缺左操作数**，是非法表达式。⇒ 需要单独定策略
  （先给"无正词"直接返回空并提示，或退化成拉全表再过滤）。**这个洞先记下来，别假装不存在。**

**「搜内容」是纯前端做不到的**：标题/标准号可以在已下发的树上筛（§7.1），
但**正文检索必须打引擎**（FTS5 + jieba），⇒ 需要一个**返回命中 `doc_id` 集合**的端点，
前端再拿这个集合去剪目录树。**这是一条真后端活**，与 §7「零后端改动的四轴」不同。

## 九、边界与不做的事

- **不照抄 WeKnora 的形态**：它是"知识库管理平台"，入口是知识库列表；我们是"取证工作台"，入口是问题。抄它的页面结构会丢掉我们的中心。

- **不做 PPT/多形态分发**（业主已明确：产出物只要 Markdown）。
- 本文是**设计**，不含实现；每条落地都要单独过门禁（`plugin` smoke + `verify:commands` + `tsc`）。

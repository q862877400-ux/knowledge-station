# 本地资料检索工具：下一步路线征询（v4）

## 0. 先读这一页

**这是什么**：一个跑在个人电脑上的工具。用户用大白话提问，系统在本机的资料库里找到对应的原文段落，并给出可以点开的出处。资料库目前主要是法规和国家标准，也允许用户放入自己的资料。

**现在最大的问题**：用户换一种说法提问，经常找不到正确的原文。下文的数字说明了问题的大小，但口径很细（见第三节），不要直接相互比较。

**目前没有一把可信的尺子**。我们用来衡量"找得准不准"的题库有两个问题：旧题库是用 AI 生成的提问做的，业主已在 2026-10-11 裁定废弃；新题库用真人提问来建，还没有完成。所以第三节的数字只能说明问题出在哪一层，**不能用来做精确的决策**。

**我们要你回答的**：在现有条件下，**下一步应该按什么顺序做，每一步怎样验收**。第六节列出一个主问题和三个子问题。

## 一、名词

| 词 | 意思 |
|---|---|
| **条款** | 法规或标准里一个有编号的最小单元，例如"GB 30871-2014 第 5.1.1 条" |
| **文档** | 一部法规、标准或制度文件，包含多条条款 |
| **提问** | 用户输入的问题。分两种：**术语式**（用文档里的词问）和**大白话**（用日常说法问） |
| **正确答案 / gold** | 对某道题来说，应该被找到的那条条款 |
| **题库（尺子）** | 一批"提问 + 正确答案"，用来衡量系统找得准不准 |
| **候选** | 检索阶段先挑出来的一批可能相关的条款 |
| **融合** | 把多条检索通道各自排出的名次合并成一个总名次（RRF 算法：只看名次，不看各通道原始分数） |
| **向量检索** | 把文字转成一串数字表示"意思"，按距离找相近的。能处理换说法，但排序不一定准 |
| **全文检索（FTS）** | 按字面找，只认字面相同，换说法就找不到 |
| **命中率@K** | 正确答案出现在前 K 名里的比例。"前五命中率"就是 K=5 |
| **Vector@1000** | 只看向量通道前 1000 名里有没有正确答案。这是一个中间指标，用户看不到 |
| **fused@20** | 融合后前 20 名里有没有正确答案。这是更接近用户所见的指标 |
| **fused@8** | 融合后前 8 名。系统最多把 8 条证据交给后面的答案生成，所以这是用户实际看到的范围 |
| **池中位数** | 融合前，候选池里的条数（中间值）。当前生产中约为 40 条 |
| **口径** | 一个数是怎么数出来的：分母是什么，哪些算命中。本文每个数都会写明口径 |
| **Jev** | 一个外部的合规判断服务。本机访问它返回 HTTP 451（地区限制） |

## 二、系统怎么工作

```text
用户提问
  │
  ├─ 1. 同时交给 6 条检索通道，各自排出一个名次
  │      A 条款号精确匹配（只在提问里出现条款号时开）
  │      B 全文按字面找（一直开）
  │      C 向量按意思找（一直开；全库逐条比对，约 1 秒）
  │      D 模态词，如"应、必须、不得"（只在提问里有这些词时开）
  │      E 法理要素（生产中关闭：调用点不传参；数据里只有 4.7% 的条款有这个字段）
  │      F 行为客体（生产中关闭：字段全库为空）
  │
  ├─ 2. 按名次做 RRF 融合，得到一个总名次（生产中候选池中位数约 40 条）
  │
  ├─ 3. 取前 20 名。重排模型已关闭（生产中不启用）。
  │      最多 8 条证据进入答案（fused@8）
  │
  └─ 4. 答案生成：把问题和这 8 条证据发给云端大模型（默认 DeepSeek），
         答案附出处。每次外发的完整内容都落库留痕。
```

**运行形态**：两个进程。① 宿主程序（DSH）里的一个插件，负责界面，并给 AI 提供 6 个工具；② 一个本地 Python 引擎，负责检索、入库和核验。引擎只允许一个实例，闲置 30 分钟自动关停，冷启动上限 60 秒。引擎自己会直接调用云端大模型。

**数据离开本机的三条路**：

| 去向 | 内容 | 是否留痕 |
|---|---|---|
| 问答时发给云端大模型 | 问题 + 8 条证据 | 是（已接） |
| 云解析（可选）发给云端 | 整份 PDF | 是（已接） |
| 从政府网站抓取法规原文 | 抓取请求 | **否（未接，待补）** |

### 3.4 换模型与查询改写的读数

（以下读数用的是旧题库中的 120 道题，即"headline 120"。）

- **换向量模型**：把现役的 `bge-small-zh-v1.5`（512 维，CPU 运行）换成 `Qwen3-Embedding-0.6B`（GPU 运行），Vector@1000 从 35.8% 到 68.3%，**+32.5 个百分点**。
- **查询加指令前缀**：再加 **+15.8 个百分点**（95% 置信区间 +9.4 到 +22.7）。
- **同模型升维到 1024**：+1.7 个百分点，不显著（p=0.73），放弃。
- **代价**：查询时嵌入增加约 31 毫秒；显存峰值约 1.16 GB；模型冷启动约 5 秒；全库重建约 1 小时（这是按已有速度推算的，没有实跑全量）。
- **⚠ 没有测过的一格**：换模型之后，用户看到的前 20 名（fused@20）会变成多少。现在的基线是 8.33%。
- 候选池放大的实验：池子里有正确答案的比例从 12.5% 升到 35.0%，但融合后前 20 名里的比例只从 8.33% 升到 10.00%。
- 查询改写（三种方法）：在前 20 名上都没有可用的收益（最好的一种 +0.8 个百分点）。
- 重排模型：+1.7 个百分点，p=0.5，不接入生产。

### 3.5 已试过、没有采用的方向

| 方向 | 结果 |
|---|---|
| 条款上下文拼进向量 | +0.8 个百分点，在噪声内 |
| 查询侧术语桥 | +3.5 个百分点，低于阈值，放弃 |
| 提高每路取数上限 | 前 20 名 +1.7 个百分点，放弃 |
| RRF 与"取最大"两种融合方式 | 未检出差异（只有 1 对翻转，样本不够断言"无差异"） |
| 外部词表（维基、大词林） | 不采用：维基重定向只有 1.5% 能接上国标术语 |

### 3.6 已知但还没解决的问题

1. **切分**。业主确认"怎么切没解决"。33.6% 的条款不足 40 字，很多只是单独切出来的标题行，它们和正文条款在同一个索引里竞争。**还没有测过它们挤掉了多少正确结果。**
2. **长条款的向量只看前半段**。向量只嵌入前 512 个字符（代码上限），而模型本身也只能处理 512 个 token。超过 512 字的条款占 2.06%。全文检索仍能覆盖这些字，但向量这一路看不到后面的内容。
3. **排序中的例外条款保护不生效**。在真实的调用路径里，例外条款会被最后的截断切掉。接入重排之前必须先修。
4. **合规判断已静默降级**。本机访问 Jev 返回 HTTP 451 后，合规判断退回到词表，界面上看不出来。在隐性合规的测试中，词表识别 1/8，Jev 识别 8/8。
5. **跨文档引用为零**。入库时只连接了同一篇文档内部的条款。扩展引用之后前 20 名的命中率没有变化，但 4 道定向题里有 2 道只有靠扩展才能找到。现有的题库看不见这种收益。
6. **同一标准号的多个版本没有区分**。例如 GB 30871-2014 与 GB 30871-2022 都标为有效，检索时会混在一起。
7. **抓取政府网站的原文没有留痕**。问答、云解析、分类三条外发路径都已留痕，唯独抓取政府网站这一条未接。

## 四、目标、约束与已定事项

**目标**：让不懂行的人用大白话提问，能定位到可以点开的原文。

**成功线与止损线：目前没有统一的标准。** 项目里有三套互相不一致的阈值，都是各自实验预先定下的：

- **2026-10-06 的基础层计划**：提升 < 3 个百分点不维护；3 到 5 只作辅助；> 5 才推广。
- **池深与融合实验（exp-15）**：提升 ≥ 6 个百分点推广；2 到 6 观察；< 2 放弃。
- **查询改写实验（exp-13/14）**：提升 ≥ 8.18 个百分点且 p < 0.05 才推广；0 到 8.18 观察；≤ 0 放弃。

另外，题库本身的分辨率：120 道题的分辨率约为 8.2 个百分点，即低于这个幅度的变化分不清真假。目前还**没有"大白话前 5 命中率要达到多少才算成功"的绝对目标值**。

**已定事项（不要再提议）**：

- 不做 Word 或 PPT 交付物。只输出 Markdown（Excel 导出仍在用）。
- 不做 bbox 高亮框，改用红色定位箭头。
- 不做人工标注的黄金题库。2026-10-07 业主裁定：放弃人工审核，改用外部高级 AI 复核，事实核查和语言部分分开做。
- 不做无留痕的外发。外发本身可以，但每次必须落库可审计。
- 不自己造有现成方案的轮子。有现成的读它、抄它；只能从零设计并长期维护的不做。
- 1,832 条大白话说法废弃（2026-10-11）。
- 两条独立线（政务问答采集、渠道台账）的产出融入主项目（2026-10-11）。
- "重建向量索引"不是硬约束（2026-09-30 解禁），但重建前必须先量它值不值。

**约束**：

- 检索和数据存储在本机。答案生成可以用云端大模型（默认 DeepSeek）。语料是否上传到云端由用户决定，但每次外发必须留痕。
- 请按**网络可用**来给方案，不需要设计离线降级。
- 单机，引擎只允许一个实例。
- 团队只有业主一人，加上 AI 编码代理，没有专职工程师。AI 代理不能长时间无人值守。
- 硬件：Intel i7-14700KF，63.8 GB 内存，NVIDIA RTX 4080 SUPER（16 GB 显存）。
- 可以引入第三方库，但优先用现成的。
- 每个阶段必须能单独验收，并且过程中保持自动检查全部通过。
- 没有的数据写进"缺数据清单"，不要猜。

**规模**：业主判断目标规模是**千万级条款**（"规模是千万级，这是事实"）。当前是 66 万条。"千万级"的数字来自业主的判断；另外有一个推算是"14 万份文档 × 每篇约 77 条 ≈ 1,075 万条"，但"14 万份"这个数没有可核实的来源，是此前推算时用的假设。如果规模真是千万级，向量全库扫描约需 16 倍时间（当前约 1 秒），每次全库重建约需 16 小时。

## 五、三个待判断的假设（不是结论）

1. **大白话找不到，主要卡在哪一层？** 候选包括：(a) 说法和原文用词不同，需要换词（表示层）；(b) 正确条文已经进入候选，但排不到前面（排序层）；(c) 题库里的"标准答案"本身定义得不对，例如说法并不在问那个概念（题库层）；(d) 切分把正确条款挤掉了；(e) 有些问题本来就超出库的范围，应该拒答。**目前的证据还不足以分出各自的份量。** 如果你认为根因在别处，请直接说。
2. **换模型是当前收益最大的单项改动。** 但它的收益可能主要体现在中间指标上，到用户看到的前 8 或前 20 名时大幅缩水。这一点没有测过。
3. **把真人提问融入主项目是低风险、高收益的。** 但这批数据偏科（税务类占 11.9%），而且政务提问多是办事类（"户口怎么落""营业执照怎么办"），与法规库的领域可能重合不多。

## 六、请回答的问题

### 主问题

**在现有条件下，下一步应该按什么顺序做？每一步怎样验收？**

请给出：
1. 推荐的执行顺序，以及为什么不是其他顺序；
2. 每一步的验收判据。每条判据请写成四段：① 判据（一句话，可以判真假）；② 检查方式（读什么、跑什么、比什么）；③ 通过条件（具体的数字或布尔条件）；④ 反向验证（怎样证明"如果把这一步的改动去掉，检查会失败"）；
3. 你建议采用三套阈值中的哪一套，或者给出一套新的成功线和止损线，并说明理由。

### 子问题一：要不要先造尺子？

目前没有可信的尺子。下一步是否应该先用真人提问建一把尺子？如果是，请说明：
- 怎样避开已知的三个陷阱：投诉举报类不能直接当题；偏科（税务类占 11.9%）；答复点名的文件和库里的版本可能不一致。
- 造出来之后，怎样证明这把尺子本身是可信的（例如防止为了它而调参数）。
- 如果你认为应该先做别的，请说明理由。

约 500 字。

### 子问题二：换模型的收益怎么算清楚？

不做全库重建的前提下，怎样估算换模型在用户看到的前 8 名和前 20 名上的收益？请说明：抽多少道题、用哪些题、要重算多少条向量、用什么口径，以及会不会高估收益。如果你认为这个杠杆不值得测，请直接说。

约 400 字。

### 子问题三：切分和长条款要不要先处理？

标题单独成块的短条款（33.6%）和超过 512 字的长条款（2.06%），是不是召回损失的主要原因？请说明：
- 在不重建全库的前提下，怎样测出它们挤掉了多少正确结果；
- 如果确实是主因，修法是什么，要不要改表结构，代价多大；
- 如果无法在不重建的前提下测出来，请直接说"答不了"，并说明需要哪一个数。

约 400 字。

### 回答的格式与出口

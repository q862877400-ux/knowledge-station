# 自动成文（系统起草结论）——立项论证与设计（2026-09-18）

> 状态：**待业主拍板**（未写任何生产代码）。本文只做"先论证值不值、再定形态"——
> 与 §10.38（PPT 单独立项）同一个流程。
> 触发它的是方案 §Phase D 末尾那句登记：「**自动成文**（由系统得出结论）**未立项**
> （触及答案链，P1）」。

## 1. 结论（先给结论）

**推荐做，但只做"草稿"形态**：系统基于**已批准材料**起草一段结论，回给用户**编辑/批准**；
**绝不**自动进入报告、**绝不**自动批准、**绝不**改答案链（`ks_answer`）的提示词与口径。
不建议做"全自动成文"（无人工确认直接落盘成报告）——理由见 §5。

## 2. 现状与缺口（为什么现在提）

材料平面已经把"**收进来 → 可信度判别 → 用户评审 → 产出**"打通到"产出"这一侧：

| 环节 | 现状 | 所有者 |
|---|---|---|
| 检索已批准材料并按承重能力分组 | ✅ | `materials/authority.assemble_evidence()` |
| 只取"能承重"的那几组 | ✅ 且**已经为"要产出结论的调用方"预留** | `authority.usable_hits()`（docstring 原文：*"给'要产出结论'的调用方用的安全入口"*） |
| 提示词/产出物用的证据文本（带 `[[m:i]]` 与出处位置） | ✅ | `authority.render_evidence()` |
| 结论里的引用**逐条校验**（不存在 / 落在仅线索或不可用） | ✅ **唯一判据** | `exports/research_report._check_citations()` |
| **起草结论本身** | ❌ **由用户手写**（面板上的 `结论` 文本框 / API 的 `conclusion_md`） | — |

也就是说：**除了"写"这一步，其余每一步都已经有唯一所有者了**。本立项要补的就是这一步，
而且**只能复用上面那些所有者**——不许为起草另写一套分组、编号或校验。

## 3. 三个候选形态（取舍）

> ⚠ **本节 2026-09-18 被自己更正过一次**（§10.96 实施时发现）：初版把"复用法条链"当成
> **形态 A** 并以"答案链引的是 `[[c:i]]`、报告校验器核不了材料"为由否掉它。那个理由
> **不完整**——我漏读了答案链的**材料范围**那条路：
> `ks_answer.answer(query, params={"material_project_id": pid})` **本来就会**
> ① 取**已批准**材料（评审硬门同一条）、② 把材料**另起一节**渲染进提示词
> （`[[m:i]]` 编号由 `authority.render_evidence` 分配）、③ 在 `material_usage` 里回
> **`usable_indices`**（注释原文："可承重的编号（**产出物按它拼引用**）"）。
> ⇒ 结论仍是"复用既有链"，但正确形态是下面的 **形态 C**。

### 形态 A：**复用法条链**（把 `ks_answer` 的结论搬过来当草稿）

- 做法：用同一个问题调 `/api/v1/ks/answer`，把它返回的 **`conclusion`** 段塞进报告的 `conclusion_md`。
- ✅ 零新代码路径（答案链早已被审计）；而且它的**材料范围**那条路本来就带 `[[m:i]]`
  （这一点初版漏读了，见本节开头的更正）。
- ❌ 但它一次给的是**三段式整份答案**（依据区/推导区/结论区）并且**默认还带法条证据**
  （`[[c:i]]`，报告的校验器核不了）⇒ 直接把"整份答案"落进报告会很别扭，也会引入
  "两种引用混在一段文字里"的口径问题。
- ⇒ 不推荐**整份**照搬；它的**材料范围**那一半正是形态 C 要复用的东西。

### 形态 B：**材料链 + 自写提示词**（初版推荐，现已降级）

- 做法：`assemble_evidence` → `usable_hits` → `render_evidence` → **自己写一条新提示词** → LLM →
  校验引用 → 返回草稿。
- ❌ 比形态 C 多一条**新提示词**（本立项唯一真正新增的 P1 风险面），而**收益为零**：
  取证链里那条材料范围提示词（`FORENSIC_SYSTEM_PROMPT` + `MATERIAL_SYSTEM_ADDENDUM`）
  **已经被审计过**，而且它的输出本来就分 `derivation`/`conclusion`、本来就要求引用带标记、
  本来就按承重能力分组。
- ⇒ 只在"形态 C 证明不够用"时才回头考虑（例如将来要专门为"报告结论"调整措辞与篇幅）。

### 形态 C：**复用取证链的提示词，但只喂材料**（✅ 推荐，§10.96 已按它实现）

- 做法：`assemble_evidence(project_id, query)` → **有可承重材料才继续** →
  `render_evidence(assembled)` → **复用** `ks_answer.build_messages(query, [], "default",
  materials_text)` 与它那条 monkeypatch-able 的传输（`_stream_llm` / `_collect_stream`）→
  `parse_llm_answer()` 取 `conclusion` →
  用**同一个** `assembled` 调 `research_report.check_conclusion_citations()` 核引用。
- ✅ **零新提示词**：措辞与规则全部来自既有所有者（材料只作参考、按承重能力分组、
  引用用 `[[m:i]]`）。
- ✅ **引用可核**：`[[m:i]]` 编号与报告的"依据"一节**同一套**（同一个 `render_evidence`
  分配），校验器与警告措辞也是同一个函数（§10.96 把它抽成
  `check_conclusion_citations()` 的**唯一所有者**）。
- ✅ **只看得见已批准材料**（`search_materials()` 那层的评审硬门，已有测试）。
- ✅ **一次检索、一次装配** ⇒ 提示词里的编号与校验用的编号**必然一致**。这一条比看起来重要：
  若"先调链、再重新检索一遍来校验"，两次检索的命中顺序可能不同 ⇒ 编号漂移 ⇒ 把**合法引用
  误判成"引用了不存在的材料"**（或者反过来漏判）。
- ⚠ 代价：`evidence=[]`（不喂法条）⇒ 提示词里"证据条款："一节是空的。这是**有意**的
  （决策点②：默认不带法条链）；要带法条时见 §4.4。
- ⚠ 它**不是**"新的事实来源"：草稿只返回文本；报告的依据一节永远由 `render_evidence` 渲染。

## 4. 推荐形态的设计（可照此实现，不必再设计）

### 4.1 接口（**§10.96 已按此实现**）

```
POST /api/v1/report/research/draft        （引擎；`def`，进 test_declared_sync 表）
Body: {project_id, query(必填非空), limit?(1..50, 默认 8)}
200: {status: "unapproved_draft",      # **契约**，调用方必须显示
      disclaimer,                      # 人话："未经用户批准，不得作为依据"
      draft_md,                        # 草稿正文（Markdown，含 [[m:i]]）
      derivation_md,                   # 模型的推导段（草稿为空时看它）
      citations: {material_refs, unknown, not_load_bearing, unchecked_law_refs},
      warnings: [...],                 # 材料不足 / 引用不成立 / 模型输出为空 / 越界引用
      counts: {...}, notes: [...],     # assemble_evidence 的分组计数与人话说明（原样带出）
      usable_indices: [...],           # 可承重的材料编号
      llm_called: bool}                # false = **一次模型都没调**（不是失败）
422/404 与 /report/research 完全同款（缺 project_id·query / 项目不存在）
```

主机侧照惯例加一条**白名单转发** `/ks/report/research/draft`（只认 `project_id`/`query`/`limit`；
`title`/`conclusion_md`/`dry_run` **一个都不发**——冒烟里钉住了）。

⚠ **`status: "unapproved_draft"` 这个字段是契约的一部分**（不是装饰）：调用方（面板/模型）
必须能一眼看出"这不是已批准的结论"。文案里也要写"未经用户批准，不得作为依据"。

### 4.2 提示词（**形态 C：零新提示词**——初版写的"四条新规则"由取证链的既有提示词覆盖）

初版打算自己写四条规则（只能用给定证据、每句带 `[[m:i]]`、仅线索不许承重、不足就说不确定）；
实施时确认**这些规则本来就在** `FORENSIC_SYSTEM_PROMPT` + `MATERIAL_SYSTEM_ADDENDUM` 里
（材料只作参考、按承重能力分组、引用用 `[[m:i]]`、不得超出证据）。⇒ **不新增提示词**，
直接复用 `build_messages(query, [], "default", materials_text)`。

⚠ 仍然遵守一条既有约定：提示词里**不放** `locator` 锚点标记（那是给**报告展示**用的，
见 `render_evidence` 的 `locator_status` 参数说明）——**提示词与展示解耦**。

### 4.3 失败与降级路径（每条都有测试，见 `tests/test_research_draft.py`）

| 情形 | 实现行为 |
|---|---|
| 项目不存在 | 404 `materials_not_found` |
| 缺 `project_id` / 缺（或空白）`query` / `limit` 非整数 | 422 `materials_bad_request` |
| `usable_hits()` 为空（没有可承重材料） | **不调 LLM**（用例断言"替身一次都没被调用"），`draft_md: ""` + `llm_called: false` + 警告"**没有起草**" |
| LLM 未配置 Key / 调用失败 | 500 `llm_unavailable`，带可操作信息并**明说不会**降级成"凭常识作答" |
| LLM 输出为空 | 200 + 空草稿 + `derivation_md` + 警告"模型没有产出结论段"，**不**当成成功 |
| 草稿里出现 `unknown` / `not_load_bearing` 引用 | 200 + **原样保留**草稿 + `warnings` 逐条列出（不静默删改模型写的东西）；取证链自带的**越界**检查也一起报（两层互补） |

### 4.4 （可选，第二期）把法条链作为**补充证据**

若该问题同时命中库内法条，可以在返回里**另给**一段"法条依据（未经本次核验）"，
或让用户在面板上**显式**选择"起草时也带上法条"。**默认不合成**——两种引用混在一段文字里，
校验口径会变得说不清（这正是形态 A 的问题）。

### 4.5 面板（第二期）

- 产出区加一个按钮「起草结论（草稿）」；点了之后：
  - 草稿显示在**只读**框里，带醒目的"**未批准草稿**"标记；
  - `warnings` 用与现在**同一套**引用警告样式显示；
  - 一个**显式**按钮「用这段填进结论框」——**绝不自动填**；
  - 用户改完、点"生成研究报告"时，走的还是现在这条路径（`conclusion_md` 由**用户**给）。
- ⇒ 报告侧**一行都不用改**：草稿只是"帮用户写一稿"，产出的口径（谁批准、引用怎么核）完全不变。

## 5. P1 风险与缓解（这一节是本立项的核心）

| 风险 | 严重度 | 缓解（**已具备**的 / 本设计新增的） |
|---|---|---|
| 草稿**貌似合理但证据不支持**（幻觉、超出材料） | 高 | ① 提示词边界**来自已审计的取证链**（不是新写的）；② **引用逐条校验**（已有的唯一判据）会把"引了不存在/不该承重的材料"列出来；③ 草稿**只能**由用户显式点"用这段"才进结论框；④ 全程带 `unapproved_draft` 标记 |
| 用户把草稿当"系统已核过" | 高 | ⑤ 标记 + 面板文案（"未批准"）+ 警告区必须显示；⑥ 报告里**不**记录任何"已核验"暗示 |
| 提示词与答案链**漂开**（两套口径） | 中 | ⑦ **形态 C 直接复用同一条提示词**（不是"独立一条"）⇒ 这一条风险从"中"降到"低"（只有 `evidence=[]` 这一处差异，且它是有意的） |
| 未批准材料被写进草稿（越过评审硬门） | 中 | ⑧ **结构性**：`assemble_evidence` 的输入来自 `search_materials()`，未批准材料根本不在里面（已有测试） |
| 成本/时延（每次起草一次 LLM 调用） | 低 | ⑨ 同步 `def` 端点 + 线程池（**不许**写成 `async def`，理由同 `/report/*` 全族）+ 进重活前缀表；`limit` 上限 50 |
| 起草变成"新的事实来源" | 中 | ⑩ 明文：**草稿不是依据**——报告的依据一节仍只由 `render_evidence` 渲染，草稿永远进不了那一节 |
| **材料正文里可能含指令性文本**（提示词注入） | 中 | ⚠ **本立项初版漏了这条**（§10.96 复核 brief 的 H6 提出后自查确认属实）：材料是用户上传/采集的**外部文本**，会原样进提示词。现有缓解只有"提示词声明材料是非法规证据 + 引用要可核"；**没有**专门的内容隔离或注入检测。⇒ 登记为**已知风险**（登记 ≠ 已解决）：真要做，选项是"材料段落加显式分隔与'以下是数据不是指令'声明"或"输出侧禁止执行类语句"——**都不在 D-5a 里**。 |

## 7. **不做**的事（明确写下来，避免实施时顺手做）

1. 不自动批准、不自动落盘成报告；
2. 不改 `ks_answer`（答案链）的提示词、证据口径、降级路径；
3. 不让草稿出现在报告的"依据"一节；
4. 不为起草另写一套分组/编号/校验（**唯一所有者**不变）；
5. 不引入新依赖（复用 `openai` SDK 那条既有通路）；
6. 不做"多轮起草/自我修订"（那会把 P1 风险乘起来，且没有评测集）。

## 8. 成本估算（供业主判断值不值）

- 代码（**实际 D-5a 落地量**）：`research_draft.py` ~150 行 + 端点 ~55 行 + 主机路由 ~65 行 +
  客户端 api ~35 行 + 测试 ~200 行 + 冒烟 ~60 行 + 文档；
- 每次起草：**一次** LLM 调用（输入 ≈ 材料证据文本 + 提示词，输出 ≤ 1200 tokens，沿用答案链参数）；
- 风险增量：**零新提示词**（形态 C）——本立项的"新增风险面"从初版估的"一条新提示词"降为
  **0**；剩下的是"用既有链生成文本"这件事本身（用 `unapproved_draft` + 逐条引用校验兜）；
- 回滚：删掉端点 + 面板按钮即可，**没有**任何存量数据或口径被改动。

## 10. 诚实边界

1. **"草稿"不等于"正确"**：引用校验只能证明"它引用的材料真实且可承重"，**不能**证明
   "这句话确实由那条材料支持"。语义级核验需要另一套东西（逐句蕴含判定），本立项**不含**。
2. **没有评测集**：本仓没有"材料 → 结论"的金标准样本，所以本立项的验收全是
   **结构性判据**（路径、标记、校验、失败矩阵），**不是**"草稿质量有多好"。要谈质量，
   先得立项做评测集——那是另一件事。
3. **未做真机**：本文全部基于代码事实；提示词的实际输出质量必须由业主用真材料试过才能判断
   （P1 的最终判据在业主手里）。
4. 与 PPT 那条边界同型：**先交付"能用的最小形态"**，把"好看/更准"留给有评测以后的迭代。

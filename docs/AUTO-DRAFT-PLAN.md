# 自动成文（系统起草结论）——立项论证与设计（2026-09-18）

> 状态：**待业主拍板**（未写任何生产代码）。本文只做"先论证值不值、再定形态"——
> 与 §10.38（PPT 单独立项）同一个流程。
> 触发它的是方案 §Phase D 末尾那句登记：「**自动成文**（由系统得出结论）**未立项**
> （触及答案链，P1）」。

## 1. 结论（先给结论）

**推荐做，但只做"草稿"形态**：系统基于**已批准材料**起草一段结论，回给用户**编辑/批准**；
**绝不**自动进入报告、**绝不**自动批准、**绝不**改答案链（`ks_answer`）的提示词与口径。
不建议做"全自动成文"（无人工确认直接落盘成报告）——理由见 §5。

## 2. 现状与缺口（为什么现在提）

材料平面已经把"**收进来 → 可信度判别 → 用户评审 → 产出**"打通到"产出"这一侧：

| 环节 | 现状 | 所有者 |
|---|---|---|
| 检索已批准材料并按承重能力分组 | ✅ | `materials/authority.assemble_evidence()` |
| 只取"能承重"的那几组 | ✅ 且**已经为"要产出结论的调用方"预留** | `authority.usable_hits()`（docstring 原文：*"给'要产出结论'的调用方用的安全入口"*） |
| 提示词/产出物用的证据文本（带 `[[m:i]]` 与出处位置） | ✅ | `authority.render_evidence()` |
| 结论里的引用**逐条校验**（不存在 / 落在仅线索或不可用） | ✅ **唯一判据** | `exports/research_report._check_citations()` |
| **起草结论本身** | ❌ **由用户手写**（面板上的 `结论` 文本框 / API 的 `conclusion_md`） | — |

也就是说：**除了"写"这一步，其余每一步都已经有唯一所有者了**。本立项要补的就是这一步，
而且**只能复用上面那些所有者**——不许为起草另写一套分组、编号或校验。

## 3. 两个候选形态（取舍）

### 形态 A：**复用法条链**（把 `ks_answer` 的结论搬过来当草稿）

- 做法：用同一个问题调 `/api/v1/ks/answer`，把它返回的"结论"段塞进报告的 `conclusion_md`。
- ✅ 零新提示词、零新代码路径（答案链早已被审计）。
- ❌ **引用口径对不上**：答案链引的是**法条**（`[[c:i]]`），而报告的校验器只能核**材料**（`[[m:i]]`）
  ⇒ 草稿里的每条引用都会落进"本次无法核验"（`unchecked_law_refs`），报告会如实写"未核验"。
  一份**每条引用都未核验**的结论，价值有限，还会让人误以为"系统已经核过了"。
- ⇒ **不推荐单独用**（但它可以作为形态 B 的**补充**：见 §4.4）。

### 形态 B：**材料链起草**（推荐）

- 做法：`assemble_evidence(project_id, query)` → `usable_hits()` 取可承重组 →
  `render_evidence()` 成提示词 → **一次** LLM 调用 → 得到 `draft_md` →
  立刻用 `_check_citations(draft_md, assembled)` **逐条核** → 连同"未批准草稿"标记一起回给调用方。
- ✅ **引用可核**：`[[m:i]]` 的编号体系与报告完全同一套（`render_evidence` 分配的 `index`），
  校验器也是同一个函数 ⇒ 草稿里"引用了不存在的材料 / 引用了仅线索或不可用的材料"**当场就能发现**。
- ✅ 只看得见**已批准**材料（`search_materials()` 那层的评审硬门），未批准材料**进不了提示词**。
- ✅ 复用答案链的**传输**（`ks_answer._stream_llm` + `_collect_stream`）与测试缝
  （monkeypatch 同一个函数即可，零真实 LLM 消耗）——但**提示词是新的、独立的**。
- ❌ 需要一条**新提示词** ⇒ P1 风险（§5）。这是本立项唯一真正新增的风险面。

## 4. 推荐形态的设计（可照此实现，不必再设计）

### 4.1 接口

```
POST /api/v1/report/research/draft        （引擎）
Body: {project_id, query, limit?(1..50, 默认 8)}
200: {status: "unapproved_draft",
      draft_md,                       # 草稿正文（Markdown，含 [[m:i]]）
      citations: {material_refs, unknown, not_load_bearing, unchecked_law_refs},
      warnings: [...],                # 与报告同款：引用不成立/无法核验/材料不足
      counts: {criteria, usable, corroborated, leads_only, excluded},
      notes: [...]}                   # assemble_evidence 的人话说明（原样带出）
422/404 与 /report/research 完全同款（缺 project_id / 项目不存在）
```

主机侧照惯例加一条**白名单转发** `/ks/report/research/draft`（只认 `project_id`/`query`/`limit`）。

⚠ **`status: "unapproved_draft"` 这个字段是契约的一部分**（不是装饰）：调用方（面板/模型）
必须能一眼看出"这不是已批准的结论"。文案里也要写"未经用户批准，不得作为依据"。

### 4.2 提示词（新增，需在实现时逐条评审）

必须显式写进提示词的四条（与材料平面的规则同源）：

1. **只能**用给定的证据行写结论；**不许**引入证据之外的事实、常识性补充或法条原文；
2. 每个事实性句子**都要**带 `[[m:i]]`，`i` **只能**取给定证据行里的编号；
3. `仅线索`/`不可用`的材料**不在**证据里（若一条主张只有那种材料支持，就**不要写它**）；
4. 证据不足以回答时**如实说不确定/缺什么**，不要编。

⚠ 提示词里**不放** `locator` 的锚点标记（那是给**报告展示**用的，见 `render_evidence` 的
`locator_status` 参数说明）——保持"提示词与展示解耦"这条既有约定。

### 4.3 失败与降级路径（每条都要有测试）

| 情形 | 行为 |
|---|---|
| 项目不存在 / 缺 `project_id` | 与 `/report/research` 同款 404 / 422 |
| `usable_hits()` 为空（没有可承重材料） | **不调 LLM**，直接回 `draft_md: ""` + `warnings: ["没有可承重的材料，未起草——结论不应建立在材料之上"]`（**绝不**靠常识硬写） |
| LLM 未配置 Key / 调用失败 | 500 `llm_unavailable` / `draft_failed`，带可操作信息（照 PPT 缺依赖那条的先例） |
| LLM 输出为空 | 回 200 + 空草稿 + warning（"模型没有产出内容"），**不**当成成功 |
| 草稿里出现 `unknown` / `not_load_bearing` 引用 | 200 + 原样带出草稿 + `warnings` 逐条列出（**不静默删改草稿**——用户要看见模型哪里引错了） |

### 4.4 （可选，第二期）把法条链作为**补充证据**

若该问题同时命中库内法条，可以在返回里**另给**一段"法条依据（未经本次核验）"，
或让用户在面板上**显式**选择"起草时也带上法条"。**默认不合成**——两种引用混在一段文字里，
校验口径会变得说不清（这正是形态 A 的问题）。

### 4.5 面板（第二期）

- 产出区加一个按钮「起草结论（草稿）」；点了之后：
  - 草稿显示在**只读**框里，带醒目的"**未批准草稿**"标记；
  - `warnings` 用与现在**同一套**引用警告样式显示；
  - 一个**显式**按钮「用这段填进结论框」——**绝不自动填**；
  - 用户改完、点"生成研究报告"时，走的还是现在这条路径（`conclusion_md` 由**用户**给）。
- ⇒ 报告侧**一行都不用改**：草稿只是"帮用户写一稿"，产出的口径（谁批准、引用怎么核）完全不变。

## 5. P1 风险与缓解（这一节是本立项的核心）

| 风险 | 严重度 | 缓解（**已具备**的 / 本设计新增的） |
|---|---|---|
| 草稿**貌似合理但证据不支持**（幻觉、超出材料） | 高 | ① 提示词规则 1/4 明确边界；② **引用逐条校验**（已有的唯一判据）会把"引了不存在/不该承重的材料"列出来；③ 草稿**只能**由用户显式点"用这段"才进结论框；④ 全程带 `unapproved_draft` 标记 |
| 用户把草稿当"系统已核过" | 高 | ⑤ 标记 + 面板文案（"未批准"）+ 警告区必须显示；⑥ 报告里**不**记录"草稿来源"以外的任何"已核验"暗示 |
| 提示词与答案链**漂开**（两套口径） | 中 | ⑦ 本设计**不动** `ks_answer` 的提示词与证据口径；起草的提示词是**独立一条**，并在文件头写明"它只服务于起草，不是答案链" |
| 未批准材料被写进草稿（越过评审硬门） | 中 | ⑧ **结构性**：`assemble_evidence` 的输入来自 `search_materials()`，未批准材料根本不在里面（已有测试） |
| 成本/时延（每次起草一次 LLM 调用） | 低 | ⑨ 同步 `def` 端点 + 线程池（**不许**写成 `async def`，理由同 `/report/*` 全族）；`limit` 上限 50；沿用答案链的超时契约 |
| 起草变成"新的事实来源" | 中 | ⑩ 明文：**草稿不是依据**——报告的依据一节仍只由 `assemble_evidence` 渲染，草稿永远进不了那一节 |

## 6. 分期与验收

| 期 | 内容 | 验收判据（每条都要有测试） |
|---|---|---|
| **D-5a**（推荐先做） | 引擎 `/report/research/draft` + 主机白名单转发 | ① 空 `usable_hits` ⇒ **不调 LLM**、回空草稿 + warning（用 monkeypatch 证明 LLM **没被调用**）；② 正常路径：草稿里的 `[[m:i]]` 全部落在可承重组（用假 LLM 返回一段**故意引错一条**的文本 ⇒ `warnings` 必须列出来）；③ `unapproved_draft` 标记与失败路径矩阵（§4.3 每行一条）；④ 端点必须是 `def`（进 `test_declared_sync` 表） |
| **D-5b** | 面板按钮 + 只读草稿 + 「用这段填进结论框」 | ① 面板**不自动**改 `conclusionMd`（断言点击"起草"后结论框内容不变）；② 警告必须显示；③ 构建产物里有"未批准草稿"文案（`smoke-client-entry` 的老套路） |
| **D-5c**（可选） | 法条链补充（§4.4） | 单独立项，先论证 |

## 7. **不做**的事（明确写下来，避免实施时顺手做）

1. 不自动批准、不自动落盘成报告；
2. 不改 `ks_answer`（答案链）的提示词、证据口径、降级路径；
3. 不让草稿出现在报告的"依据"一节；
4. 不为起草另写一套分组/编号/校验（**唯一所有者**不变）；
5. 不引入新依赖（复用 `openai` SDK 那条既有通路）；
6. 不做"多轮起草/自我修订"（那会把 P1 风险乘起来，且没有评测集）。

## 8. 成本估算（供业主判断值不值）

- 代码：引擎端点 ~120 行 + 主机路由 ~40 行 + 面板 ~60 行 + 测试 ~250 行 + 文档；
- 每次起草：**一次** LLM 调用（输入 ≈ 证据文本 + 提示词，输出 ≤ 1200 tokens，沿用答案链的参数）；
- 风险增量：**一条新提示词**（P1），其余全部复用；
- 回滚：删掉端点 + 面板按钮即可，**没有**任何存量数据或口径被改动。

## 9. 需要业主拍板的三件事

1. **做不做**（本立项的整体取舍）；
2. 若做：**默认是否把法条链一并带上**（我推荐**不**，见 §4.4；需要时由用户在面板上显式选）；
3. 若做：**草稿是否允许写进报告**（我推荐允许，但必须由用户**逐次显式**确认——不是开关级别的
   "以后都自动填"）。

## 10. 诚实边界

1. **"草稿"不等于"正确"**：引用校验只能证明"它引用的材料真实且可承重"，**不能**证明
   "这句话确实由那条材料支持"。语义级核验需要另一套东西（逐句蕴含判定），本立项**不含**。
2. **没有评测集**：本仓没有"材料 → 结论"的金标准样本，所以本立项的验收全是
   **结构性判据**（路径、标记、校验、失败矩阵），**不是**"草稿质量有多好"。要谈质量，
   先得立项做评测集——那是另一件事。
3. **未做真机**：本文全部基于代码事实；提示词的实际输出质量必须由业主用真材料试过才能判断
   （P1 的最终判据在业主手里）。
4. 与 PPT 那条边界同型：**先交付"能用的最小形态"**，把"好看/更准"留给有评测以后的迭代。

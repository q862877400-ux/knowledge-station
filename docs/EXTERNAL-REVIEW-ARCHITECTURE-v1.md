# KnowledgeStation 总体架构方案征询（外部评审稿 v1）

**这是什么项目**：一个跑在个人电脑上的「本地资料检索与取证」工具 —— 用户用大白话提问，它在本机资料库里定位到那一段原文，给出带可点击依据的答案。
**现状一句话**：**检索层的"术语式提问"已经好用（前五命中 92.8%），"大白话提问"只有 20%**；同时已有 8,983 篇文档 / 663,634 条条款的真实数据、和 41.5 万条真人问答素材可用。
**我们要什么**：请你给一份**总体架构方案** —— 重点是"下一步该往哪改、为什么、按什么顺序"，而不是单点补丁。

## 节 0 · 名词定义（**先读这一节，后面全部依赖它**）

> 下面每个词在本稿里**只有一个意思**。凡是你需要在本方案里产出的词，都已在首次使用前定义。

| 词 | 定义 |
|---|---|
| **条款** | 一部法规/标准里**编号的最小单元**（如「GB 30871-2014 第 5.1.1 条」）。本项目的检索与引用都以它为粒度 |
| **文档** | 一部法规 / 标准 / 论文 / 制度文件。一份文档含多条条款 |
| **库** | 本机的 sqlite 数据库（当前 8,983 文档 / 663,634 条款 / 2.88 GB） |
| **通道** | 一路独立的召回方式。本项目有 **6 条**（见节 3.3 表） |
| **融合** | 把 6 条通道各自返回的候选**合并成一个排名**。本项目用 RRF（见节 0.1） |
| **gold** | 一道题**正确答案**（本项目的 gold = 该题的正确答案是哪个条款） |
| **考卷 / 尺子** | 一批"题目 + gold"的集合，用来量检索好不好。**考卷 = 尺子**，本稿混用同一意思 |
| **召回** | "正确答案**有没有**出现在候选集里"（不问排第几） |
| **排序** | "正确答案**排第几**"（候选集里已经有了，但可能排在第 800 位） |
| **命中@K** | 正确答案出现在**前 K 名**里的比例。`recall@5` = 前五命中率 |
| **大白话** | 用户用日常说法提问，**不使用**文档里的专业术语。如问"动火作业怎么分级"而不是"动火作业分级" |
| **术语式提问** | 用户直接用文档里的词提问（如"GB 30871 动火分级"） |
| **门禁** | 本仓的一条命令，跑完所有自动检查，**以退出码判定通过与否** |
| **提取树** | 把某个提交的代码单独导出到另一个目录，用来做独立复核，避免与在改的代码互相污染 |
| **口径** | 一个数字"是怎么数出来的" —— 含什么、不含什么。**没有口径的数字不可信** |
| **台账** | 一张**可维护的清单表**（本项目特指"发布渠道清单"，每条记网址、取法、可用状态） |
| **探针** | 一段**只做检测、不改数据**的小程序（如"这个渠道还能不能打开"） |
| **收口** | 把一件事**做完并验收**，不再挂着 |
| **棘轮** | 本项目的一条纪律：**测试通过数只能涨不能跌**（像棘轮只能单向转） |
| **冒烟** | 一套**快速全链路自检**（不深入，只确认"没炸"） |
| **冻结** | 把某个版本**钉住不再改**，保证多人看的是同一份 |

### 0.1 三个必须解释的技术词

| 词 | 一句话解释 |
|---|---|
| **RRF** | 一种**合并多路排名**的算法：不看每路给的分数，只看名次 —— 第 r 名贡献 `权重 /(60 + r + 1)`，各路相加得总分 |
| **向量检索** | 把"文字的意思"变成一串数字（向量），按数字距离找相近的。**它不看字面，只看意思**，所以能处理"换种说法" |
| **FTS5** | sqlite 自带的**全文索引**：按字面（分词后）找。**它只看字面**，换种说法就找不到 |

**⇒ 这就是本项目的核心矛盾**：FTS5 找不到"换种说法"，向量能找到但排不准。

## 节 1 · 摘要（只读这一节也能明白全貌）

**项目**：KnowledgeStation —— 让不专业的人用大白话，对自己机器上的任意资料提问，直接定位到那段可点开的原文。产品定位是**"任何本地资料的检索与取证"**，法规/国标只是数据源之一（虽然目前是最大的那类）。

**形态**：两个进程一起交付，没有独立安装包。**Python 引擎**（`src/core/`，跑检索/入库/核验，对外是本地 HTTP）+ **DSH 插件**（`plugin/`，出侧栏界面、给 AI 挂工具）。

**现状（全部实测，2026-10-11）**：

| 维度 | 数字 |
|---|---|
| 数据 | 8,983 文档 / **663,634 条款** / 2.88 GB / 62 张表 |
| 代码 | 引擎 154 个 py 文件（44,465 行含空行 / **38,982 行不含空行**）；插件 114 个 js/ts 文件（99,723 / **96,567**） |
| 接口 | **176 个 HTTP 端点** |
| 测试 | 173 个测试文件 / **2,928 条用例全过**（门禁 12/12 步通过） |
| 检索通道 | **6 条**（其中 2 条生产恒开、1 条半开、2 条恒关） |

**核心卡点（这是要请你解决的事）**：

| 提问方式 | 前五命中率 |
|---|---|
| **术语式**（用文档里的词） | **92.8%** ✅ 好用 |
| **大白话**（用日常说法） | **20.0%** ❌ 不好用 |

**已经量出来的一条关键事实**：把嵌入模型换成 `Qwen3-Embedding-0.6B`，**召回层（Vector@1000）能从 35.8% 涨到 68.3%（+32.5 个点）**，加一句查询前缀再 +15.8 个点。
**但**：这个涨幅量的是"**候选集里有没有**"，而**用户看到的是"排前 20 名里有没有"（fused@20）** —— 两者之间的转换率在本项目**已被三次量到极低**。
**⇒ 所以"该不该换模型"目前没有依据。这是本稿最重要的一个待决策点（节 6 的 D1）。**

**我们要你交什么**（详见节 8）：一份**总体架构方案**，说明"下一步改哪里、为什么、按什么顺序、每步怎么验收"。**分三批交**（节 7 末尾有分批表），不必一次写完。

## 节 2 · 目标与不做的范围

### 2.1 目标

让**不专业的人用大白话**、对**任意资料类型**提问时，都能定位到**可点开的那段原文**。

**三条总判据**（本项目自己定的，请以此为方案的目标函数）：

| 判据 | 含义 | 当前实测 |
|---|---|---|
| **换词可对** | 同一件事换种说法问，都能找到同一处原文 | ❌ 53% 的大白话与原文**一个字都对不上** |
| **排得上去** | 正确答案要出现在前列，不能只"在库里" | ❌ 有字面重合的子集里只有 **4.4%** 进前五 |
| **换资料类型不塌** | 从法规换到论文/制度文档，机制不推倒重来 | 🟡 英文已解决（0/294 → 96.3%）；中文古籍未解决 |

### 2.2 明确不做（**Anti-Scope**）

> ⚠ **这一节很重要**：如果你给的方案落在这里面，对我们没用。
> 但**如果你认为我们排除错了，请直接反驳**（我们更想要你的反驳，而不是你绕开它）。

| 不做 | 为什么 | 你若认为排除有误 |
|---|---|---|
| **不做"无留痕外发"** | 这是真红线：**每次把内容发到外部服务都必须可审计**（落库可查）。⚠ **注意不是"不许外发"** —— 见下方说明 | 若你认为某处该免留痕，请说明为什么 |
| **不做 Word / PPT 交付物** | 业主已明确否决（只出 Markdown） | 已多次确认，不建议再提 |
| **不做 bbox 高亮框** | 已改成"红色定位箭头" | 同上 |
| **不自己造通用轮子** | 有现成的就读它、抄它；只能从零设计并长期维护的不做 | 若某处必须自研，请说明为什么现成的不能用 |
| **不重建 663,634 条向量**（**默认不做**，但见 D1） | 重建一次成本高（约 1 小时 + 显存），且会让已缓存的哈希失效 | ⚠ **这一条与 D1 直接相关**：换模型**必然要重建向量**。若你认为换模型值得，**请直接说"这条排除错了、理由如下"** —— 我们把它放在这里是**默认倾向**，不是不可翻的定论 |

> ⚠ **关于上面最后一条，我们把话说透**（避免自相矛盾）：
> 「不重建向量」是我们的**成本判断**，而 D1 问的是「**要不要为了收益去付这个成本**」。
> 这两件事**不冲突** —— 我们**没有**排除"重建"这条路，只是**要求你先给账**。
> **若你认为该重建，请直接给出"值不值"的算法，不必绕开。**
| **不做人工标注黄金集** | 业主裁定改用外部 AI 复核（人工标注成本不可接受） | 若你认为某处非人工不可，请说明规模与成本边界 |

**⚠ 关于"外发"这条，必须说清**（很容易被误读成"不许联网"）：

| 项 | 事实 |
|---|---|
| **作答用的 LLM 在哪** | **在云端**（默认 `https://api.deepseek.com`）。每次作答会把**问题 + 检索出的证据片段**发过去 |
| **原始文档会不会外发** | **由用户决定**，系统**不再代为禁止**（2026-09-17 业主裁决：「不能外发的红线不要……我也不知道为啥之前要这样限制自己」） |
| **真正的红线** | **必须留痕** —— 每次外发的完整 payload 落库可审计（`debug_dump` 表 + 外发审计接口） |
| **⇒ 对你的意义** | 你可以**自由建议云端方案**（调 API、云解析等）。**唯一要求是**：该方案要能接进"外发可审计"这个机制。**不要**建议绕过留痕的通道 |

**⇒ 所以"本地优先"指的是**：**检索与数据存储在本机**（不外发语料库），
而**推理可以走云端**。这两件事别混。

## 节 3 · 现状

### 3.1 运行时拓扑（**这一节决定你给的接口设计对不对**）

```text
【当前实际在用 · 形态 B：引擎是被动提供方】

  用户
   │
   ▼
  DSH 宿主（Node，用户手动启动）
   │
   ├─ 插件（plugin/）── 侧栏 React 界面 + 对 AI 暴露 6 个工具
   │       │
   │       └─ 按需"懒拉"引擎：spawn `python -m src.core.main`
   │              随机端口 + 一次性 token（写进 engine.session.json）
   │
   ▼
  Python 引擎（FastAPI，本地 HTTP /api/v1/...）
   │
   ├─ 检索（6 通道 + RRF 融合）
   ├─ 入库（PDF/Office/网页 → 条款）
   ├─ 核验（数值 / 模态 / 法理三层）
   └─ 后台调度器（update/scheduler.py，2 秒轮询，独立线程）
   │
   ├──────────────┐
   ▼              ▼
  sqlite        云端 LLM（默认 api.deepseek.com）
  （2.88 GB，     ⚠ 只发「问题 + 检索出的证据片段」
    62 表）       ⚠ 完整 payload 落库可审计
  ⚠ 写操作走      （「原始文档是否外发」由用户决定，
    "单写者队列"   系统不代为禁止，但必须留痕）
```

**⇒ 拓扑里有两处"出机器"和一处"进机器"，别混**：

| 流向 | 内容 | 是否必须留痕 |
|---|---|---|
| 引擎 → 云端 LLM | **问题 + 证据片段** | ✅ 必须（落 `debug_dump`） |
| 引擎 → 政府网站（可选） | 抓法规原文 | ✅ 必须（外发审计） |
| 云端 → 本机 | 模型下载（可选） | —— |

**必须交代的三件事**（对应评审要求）：

| 项 | 本项目的事实 |
|---|---|
| **AI 跑在哪一侧** | **AI 跑在宿主侧（客户端）**，引擎是**被动提供方** —— 引擎自己不发起 AI 调用，只被 HTTP 调用 |
| **主编排循环谁控制** | **宿主/AI 控制主循环**（它决定问什么、调哪个工具）。引擎内部只有两个自主循环：① 入库的解析 worker；② update 域的调度器（2 秒轮询，**只做定时巡检，不做推理**） |
| **执行环境限制** | ① **引擎单实例**（靠 `engine.session.json` + 探活判定；并发调用会被合并，避免起出"幽灵引擎"）；② **单写者队列**（写操作不得绕过）；③ 引擎**闲置 30 分钟自动关停**；④ 解析 worker 用**子进程**隔离；⑤ 冷启动有 **60 秒**上限 |

⚠ **两条容易踩的**：

1. **引擎会被自动关停**（闲置 30 分钟，默认值，插件配置可覆盖）。
   ⇒ 任何"常驻后台任务"的设计，都要考虑"引擎被关了怎么办"。
2. **"单实例"不是靠锁，是靠会话文件 + 探活** ——
   并发拉起时**后写的会话文件会顶掉先写的**，先起来那个会变成"无人引用的幽灵引擎"。
   ⇒ 现已在同一管理器内**合并并发调用**来防它，但**跨进程不防**。

### 3.3 检索架构（**要改的核心部件**）

**6 条通道**（代码真源 `src/core/domain/models.py` 的 `SEARCH_CHANNELS`）：

| 通道 | 找什么 | 权重 | 生产是否开 |
|---|---|---|---|
| `exact` | 条款号精确匹配 | **2.0** | 仅当提问含条款号 |
| `fts` | FTS5 全文（按字面） | 1.0 | **恒开** |
| `vec` | 向量（按意思） | 1.0 | **恒开** |
| `modality` | 模态词（"必须/应当/不得"） | 0.8 | 仅当提问含模态词 |
| `legal_element` | 法理要素 | 0.8 | **恒关**（生产三个调用点都不传参；该字段全库 **31,249/663,634 = 4.7%** 非空） |
| `behavior_scope` | 行为客体 | 1.2 | **恒关**（该字段全库 0 行非空） |

**融合**：RRF，`分数 = Σ 权重 /(60 + 名次 + 1)`。

**⚠ 三条我们必须如实说明的架构事实**：

1. **通道 A/D/E 的排序键不是相关性** —— 它们的 `ORDER BY` 头两个键是"效力状态"，**等于按入库顺序**。⇒ 不修它，"取前几名"都是任意的。
2. **没有设行数上限是刻意的** —— 实测模态词"应"一次能拉出 **140,555 条**（全库 26.9%）。曾想加 `LIMIT 500`，但**论证被推翻**：加闸的前提是"名次 = 相关性名次"，而它不是。
3. **向量是暴力精确扫描，没有近似索引** —— 663,634 条全扫。当前用 `bge-small-zh-v1.5`（512 维，**CPU/ONNX**）。

## 节 4 · 核心发现（**这些是事实，不是判断**）

> 下面每条都附了"怎么量的"。**如果哪条你算出来不一样，请直接说 —— 那比顺着我们的框架答更有价值。**

### 4.1 大白话检索的真实分布（**这是核心问题**）

用 500 个跨领域术语 × 1,832 条外行说法实测：

| 事实 | 数字 | 怎么量的 |
|---|---|---|
| 大白话与原文**一个字都对不上** | **53.0%**（971/1,832） | 提问与 gold 条文无 ≥2 字公共子串 |
| 有字面重合、但排不进前五 | 47.0% 里只有 **4.4%** 进前五 | 同上，按 gold 名次统计 |
| 按字找 vs 按意思找（前五） | 6.8% vs 5.8% | 两条通道分别单独跑 |
| **两条路合起来** | **11.8%**（前五）/ 24.5%（前二十） | 6 通道融合后 |
| **上限**（直接用术语问） | **68.8% / 87.0%** | 同上 |

**⇒ 关键推论**：53% 的问题**不是排序问题，是"根本对不上"** —— 对这部分，任何排序改进都无效。

### 4.2 换模型的真实收益（**已实测，但缺一格**）

| 实验 | 读数 | 口径 |
|---|---|---|
| 换 `Qwen3-Embedding-0.6B` | `Vector@1000` 0.3583 → **0.6833（+32.50 个点）** | 前 1000 名里有没有 |
| 加查询侧指令前缀 | **+15.84 个点**（CI [+9.43, +22.73]） | 同上 |
| 同模型升维 512→1024 | +1.67 个点（**p=0.73，不显著**） | 放弃 |
| ⚠ **`fused@20`（用户真实看到的）** | **未测** | —— |

**⚠ 缺口**：`Vector@1000` → `fused@20` 的转换率**已被三次量到极低**（有一次是 `Vector@20` 反而从 9.17% 降到 7.50%）。
**⇒ "+32.5 个点"很可能在用户那一层大幅缩水，但缩到多少，没有数据。**

### 4.3 已试过并排除的方向（**别重复提**）

| 试过的 | 判决 | 读数 |
|---|---|---|
| 条款上下文拼进向量 | ❌ 放弃 | +0.83 个点（噪声内） |
| 查询侧术语桥 | ❌ 放弃 | +3.51 个点（低于 6 点阈值） |

## 节 5 · 我们的判断（**下面全部是假设，不是结论**）

> ⚠ **这一节必须被当作假设来读。** 我们给出倾向，同时给出**竞争解释**。

### 假设 1（我们倾向的）：53% 零重合是"表示层"问题，不是"排序层"问题

### 假设 2：换模型（+32.5 个点）是当前最大的可用杠杆，但**证据不足以下决心**

**推理**：在所有试过的方向里，只有它和"查询前缀"给出了显著收益。

### 假设 3：两条独立线的产出"融进来"是低风险高收益的

## 节 6 · 待决策的分歧点（**这是我们拿不准的路线选择**）

### D1 · 换模型这个杠杆，现在用不用？

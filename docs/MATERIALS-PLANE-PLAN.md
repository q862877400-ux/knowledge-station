## 3. 两轴权威模型（核心设计，J2 + J3 的直接推论）

### 3.1 为什么必须是两个轴

J3 举的例子暴露了一个陷阱：**公司制度的"来源可信度"低于国标，但对"我们公司报销怎么走"这个任务，它是准绳。** 如果只用一个分数排序，必然二选一错一个：

- 只按可信度排 → 回答问题时会引用国标却不引用唯一有效的公司制度（答非所问）；
- 只按相关性排 → 会把网络帖子与国标同权（正是你要避免的"随便找个网络文章就当权威信源"）。

⇒ 拆成**正交**两轴：

| 轴 | 含义 | 谁决定 | 作用 |
|---|---|---|---|
| **A 来源可信度** | 这份材料本身可不可信 | 规则定层 + 证据升级 | 决定**引用时怎么标注、能不能承重** |
| **B 任务内效力** | 本次任务以什么为准绳 | **用户声明**（项目级 + 单次覆盖） | 决定**谁说话** |

### 3.2 轴 A：层级定义（可机检，不靠"感觉"）

| 层 | 是什么 | 能否承重 |
|---|---|---|
| **T0** | 法定/官方原文（走现有 flk/govcn 管线） | 可直接作依据 |
| **T1** | 用户自有原始件（财报/公告/合同/公司制度原件） | 对**其自身内容**是初级证据；**跨主体结论仍需外部佐证** |
| **T2** | 权威第三方（监管、交易所、审计机构、标准发布机构、署名研究机构） | 可作依据 |
| **T3** | 二手转述（媒体/自媒体/聚合站） | **只能作线索**；需 **≥2 个独立来源互证**才可作辅证，**单独不得支撑结论** |
| **T4** | 不可回溯（无出处/匿名/内容农场/无原文链接） | **禁止用于结论**；留档并标"不可用" |

**判级证据（机器可查的字段，不是让 LLM 拍脑袋）**：来源域名 / 是否有可直接打开的原文 URL / 发布时间 / 是否原文（而非转述）/ 能否被他源交叉验证 / 与任务的相关性。

**两条硬规则**：
1. **可信度 ≠ 相关性**：来源可信不因此"更相关"；相关也不因此"更可信"。**不因相关而提级。**
2. **每条结论必须追到 (材料, 位置)**；T3/T4 不得单独承重。

**层级可由用户改（J3）**：改层级要记 `tier_source`（system / user）、理由与时间——**留痕，不是为了限制，是为了你三个月后还能看懂当时的判断**。

### 3.3 轴 B：任务效力

- **项目级声明**：`project.authority_policy`（本项目的准则材料 + 说明）；
- **单次覆盖**：一次提问可临时声明"本次以 X 为准"；
- 产出物里**同时显示**两轴：`依据《公司差旅制度》(T1·本项目准则)`、`参考 GB/T xxx (T0·普通)`。

## 4. 两条入库通道（J5）

### 4.1 Track L：法规 / 标准

采集 → 判级 → **评审** → **自动入法规库**（走现有 ingest 管线）→ 材料记录回指 `doc_id`。

- **Non-goal 重写**：`§2.3「非官方渠道下载」`原文在"法规语料"语境下是对的。新政策：**法规仍官方渠道优先**；非官方渠道采到的**必须评审**，且**必须标出实际来源**（`source` 字段区分官方/非官方），**不得与官方来源混同**。
- **前置项（强烈建议先做）**：审计发现 **135 条 `standard_name` 带 `(1)` 后缀**（如 `GB/T 10058-2023` → `电梯技术条件(1)`），而且这 135 条**全部 `total=1`**——带后缀那份**独占了本该干净的记录**。Track L 要"自动入库"，不先修这个就会**放大污染**。

### 4.2 Track M：其它资料

→ 项目的「参考资料」文件夹。**默认 `ephemeral`（仅本次任务）**，用户可提名 `promoted`（长期）。

## 5. 数据模型（材料平面）—— 法条链零改动

**铁律：不碰 `doc_meta` / `clause_revision` / `source_span` / bbox 契约。**
理由：那是取证链的承重墙（§9.3 bbox 契约已踩坑两次），且 `doc_meta.standard_no TEXT NOT NULL UNIQUE` **结构上就装不下财报/新闻**——这正是必须另立平面的根本原因。

拟新增（**待批准，字段名以批准版为准**）：

```
project          project_id · name · created_at · authority_policy(JSON) · note
material         material_id · project_id · origin(user|collected) · kind(legal|other)
                 · title · url · domain · fetched_at · published_at · content_hash
                 · raw_path · mime · source_tier(T0..T4) · tier_source(system|user)
                 · tier_evidence(JSON) · tier_reason · task_role(准则|参考|null)
                 · review_status(pending|approved|rejected) · reviewed_at · review_note
                 · lifecycle(ephemeral|promoted) · doc_id(仅 Track L 入库后回指)
material_chunk   chunk_id · material_id · ord · text · char_start · char_end · page
```

- 存储：`%APPDATA%\KnowledgeStation\materials\<project_id>\`（遵守 §13.0「代码树零运行产物」）
- provenance 字段命名**沿用 `doc_meta` 既有口径**（`source` / `source_url` / `downloaded_at` / `source_status`），避免两套语汇。
- Track L 入库后通过 `material.doc_id` 回指，**不改 `doc_meta`**（回指放在材料侧）。

## 6. 流程与硬门

```
下单 → (采集) → 判级 → 评审闸门 → [已批准材料 + 法规语料] → 分析 → 交付
```

**硬门（J4 的落地，必须不可绕过，不是提示）**：
- `review_status != approved` 的材料**不得进入检索、不得进入分析、不得出现在产出物引用里**；
- 评审闸门**沿用既有形态**：`/api/v1/ingest/preview` 已实现 dry-run + jobs + abort（§9.5 R27 红线），材料评审照此做"待批列表 + 逐条 批准/拒绝 + 可批量"。

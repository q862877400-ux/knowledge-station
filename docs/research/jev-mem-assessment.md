# Jev-Mem 影响评估（2026-09-24）

> **性质**：调研产物。**未改任何产品代码**。
> **触发**：业主给了[一篇公众号整理稿](https://mp.weixin.qq.com/s/uJr6Bb8OrNMDySXs3m7CpQ)问"能不能借鉴"。
> 按仓规**回原始来源核过**（论文全文 + 官方代码仓），不只读二手整理。
> **判据**：业主 2026-09-19 裁定「通用层**纯借鉴**，不造轮子」——有现成的就读它、抄它，只能从零设计并长期维护的就不做。

## 一、一句话结论

**能借鉴，但能借的不是"一套新架构"，而是我们**已经在走的那条路**的延伸**：
把高频、输出有界的判断从大模型手里拿走。我们已用它做合规哨兵；这篇论文把它扩展到**检索路径**上
（路由 / 预算 / 候选打分 / **什么时候停**）。
**它的分数不能借**（LLM 当裁判），**它的多关系图不能借**（记忆单元性质不同，我们的红线未被改变）。

## 二、它是什么（回原始来源）

| 项 | 内容 |
|---|---|
| 论文 | *Jev-Mem: System-One-Controlled Agentic Memory for Efficient AI Agents*，arXiv [2609.23986](https://arxiv.org/abs/2609.23986)，2026-09-21，UT Dallas（Dongming Jiang / Yi Li / Bingzhe Li） |
| 代码 | <https://github.com/libingzheren/Jev-Mem> —— **MIT 许可**，有离线 demo（不需要 Key、不下模型） |
| 基准 | LoCoMo（长期对话记忆），答案模型 GPT-4o-mini |
| 主张分数 | 综合 0.777（最强基线 MAGMA 0.700，+11.0%）；建库 158s（最快竞争者 1044s，6.6×）；查询 0.93s（MAGMA 1.47s，−36.7%） |

**架构**：三个平面 —— ① **System-One 控制面**（Jev：记忆分类、关系判断、查询路由、预算分配、候选打分、**自适应停止**）；
② **共享多关系记忆面**（同一批节点，四种关系视图：语义 / 时间 / 因果 / 实体，外加向量与字面两个索引）；
③ **System-Two 推理面**（只在复杂推理与答案合成时调用）。

**它主张的道理**（论文 §2.2 原话大意）：记忆管理里的这些操作"**是语义的，但不是生成的**"——输出是
标签、概率、分数这类**有界结果**，用自回归大模型逐 token 生成再解析"**没有必要地贵**"，
而且这些判断在关键路径上反复出现，开销会累积。

## 三、我们**已经**在做的（所以"借鉴"的起点不是零）

| Jev-Mem 的做法 | 我们仓里对应物 | 状态 |
|---|---|---|
| System-One 做有界判断，大模型只做推理 | `src/core/llm/jev_guard.py`（合规哨兵）+ `src/core/update/jev_ingest.py`（公告清库） | **已有** |
| 一次批量问多道题（"sharing the same state can be evaluated together in a single batched invocation"） | `jev_client.system_one(state, dict(_QUESTIONS))` —— 4 道题一次发 | **已有** |
| 钉住模型版本，不用会漂的别名 | `JEV_MODEL = "jev-1.13.0"`（官方明示调过阈值就别用 `-latest`） | **已有** |
| 每个 Noul 必须写 `criteria` | `jev_client.noul(instructions, yes=…, no=…)` 强制 | **已有** |
| 不可用时降级、不抛给主链路 | `JevUnavailable` ⇒ 退回词表 / 按规则原样处理 | **已有** |
| 确定性结构直接建边，**不问模型** | 我们有 `clause_number`/`standard_no`/`hierarchy_path`/`page_start` 等确定性结构；但**尚未**用来建边 | **有料未用** |
| 每个循环有硬上限 | **缺**（实测：有两条路不设上限，一句带"应"的话拉进全库 27%） | **缺** |
| 查询路由 / 预算分配 / 自适应停止 | **缺**（6 条路跑 4 条、权重写死；`expand_evidence_chain(max_hops=1)` 写死一跳） | **缺** |

⇒ 论文**新增**给我们的只有最后三行。前六行我们已经在做，且有两处比论文更严（见 §五）。

## 四、可借鉴的四条（每条都注明"为什么对我们可用"）

1. **把"高频、输出有界"的判断从大模型手里拿走——用在检索路径上。**
   我们先前实测过"用大模型改写查询有风险"（只有 20.9% 的查询受益、25.6% 更差）。
   这篇论文给的答案**不是"别改写"，而是"别用生成式改写，要用有界判断"**——这是一个**新的、更可行的选项**，
   而且我们有 Key、有客户端、有中文回归基线。
2. **每个循环都要有硬上限**，而且上限该是**决策次数**而不是时间。论文的默认值：
   `candidate_top_k=10` / `anchor_count=30` / `total_graph_budget=80` / `maximum_nodes=60` /
   `maximum_edges=2400` / **`maximum_jev_calls=16`**；并且"延迟限制是在操作之间检查的，
   所以不是严格的挂钟上限"（论文原话）。**这一条不需要任何新模型，立刻可用**，正好补我们那个洞。
3. **确定性信息就用代码建边，只在不确定时才问模型。** 论文：时间戳顺序直接建时间边、
   共享标识符直接建实体边，"**只在时间顺序隐含时**"才让控制器在
   `before/after/during/contains/overlaps/same_time/unknown` 里选。
   ⇒ 这**恰好是我们的强项**（条款号、标准号、层级路径、页码都是确定性的），而且成本近零。
4. **显式建模"停"的四件事**：证据是否充分 `s_d`、继续找还有没有用 `u_d`、缺什么 `m_d`、有没有未解决的矛盾 `c_d`。
   论文的停止条件是 `s≥θ_suff ∧ m<θ_cont ∧ c<θ_cont`，**或者** `u<θ_cont`（"即使证据还不充分，
   继续找也不值了"）。这给了我们一个**可照抄的判断清单**，而不是自己发明。

**附带一个印证**：论文锚点召回用 **RRF，κ=60** —— 与我们生产口径 `RRF k=60` **完全相同**。
这不是抄，是收敛，说明这条口径是行业默认值。

## 五、**不**该借鉴的四条（含理由）

1. **多关系记忆图本身。** 它的记忆单元是**对话与经历**（叙事），天然富含时间/因果/实体关系；
   我们的单元是**标准条款**。我实测过：`evidence_edge` 13,606 条、**跨文档 0**、密度 **0.026/条**。
   它的图是"写进来时天然带关系"，我们的图要**从零推断**，成本结构完全不同。
   ⇒ 我们自己的红线（**密度 ≥0.3–0.5 才谈多跳**、**不用大模型抽图**）**没有被这篇论文改变**。
2. **它的绝对分数与倍速。** 见 §六。
3. **让模型判断的结果直接落库。** 我们仓里已经学到：官方明示 Jev 的
   "typed output **保证接口、不保证为真**"（`src/core/update/web_ingest.py:104` 引的原话），
   所以**凡是要落库的标记，必须是拿同一条规则能复算出来的事实**。论文把 Jev 判断的关系写进记忆图，
   这个形状与我们的红线冲突。
4. **"Jev 更好所以要它替规则"这个推论。** 我们自己的实测结论是**分工**不是替代：
   规则管"留"、Jev 管"清"，两边各管一头、零重叠（`src/core/update/jev_ingest.py` 的记录：
   规则与 Jev 各 8/8 且**零重叠**）。论文没有改变这个分工。

## 六、必须打的折（诚实说明）

1. **指标是 LLM 当裁判。** 0.777 是 LLM-as-a-Judge。本轮调研已拿到硬数据：
   TREC 2024 人工判定 vs GPT-4o 一致率只有 **56%**；ALCE 说最好的模型"50% 的时候引用支撑不全"。
   ⇒ **"11.0% 相对提升"不能读成"产品更好了"** —— 它只说明在**同一个裁判**下这个架构更讨裁判喜欢。
2. **连作者自己都警告评测协议会虚高。** README 原话：默认 `--best-of-n 3` 使用
   "**reference-aware selection that can bias accuracy**"，所以建议用 `--best-of-n 1`。
   一个会在自己评测里虚高的协议，其绝对分数当然要打折。
3. **规模不明。** LoCoMo 是 10 个长对话。**158 秒建库 / 0.93 秒查询是对话记忆的规模，不是 52 万条条款。**
   论文正文里我没找到记忆规模的数字 ⇒ 倍速**不能套到我们头上**。
4. **它不解决我们最初的痛点。** 业主最初的痛点是**隐性**——"用户说的话里没有合规词，怎么知道要触发"。
   Jev-Mem 解决的是"**给定一个查询，怎么在已有记忆里多跳找到证据**"，
   即"找到之后怎么扩展"，**不是"怎么知道要找"**。后者我们已经用 Jev 做了（词表 1/8、Jev 8/8），
   论文没有超出我们这一步。
5. **二手整理稿不可作为依据。** 业主给的是公众号整理稿（智猩猩AI整理）；本文所有设计细节与
   数字均取自论文全文与官方 README，公众号稿只用来定位原文。

## 七、未能确定

1. **Jev 的调用成本与延迟上界**：论文只给 `maximum_jev_calls=16` 的调用次数上限，没给单次延迟；
   我们本机实测是 **0.47–0.5s/条**（`src/core/config.py:171` 注）⇒ 16 次是**秒级**开销，能否接受要实测。
2. **它那套路由/停止在"条款"这类非叙事语料上是否有增益**：论文没有这类实验。
3. **LoCoMo 上 Jev 与各类基线的公平性**：只读到作者自测，**未找到第三方复现**。
4. **许可适用性**：代码 MIT 可抄（需随附版权声明，与 WeKnora MIT 同规矩）；
   但它 `data/README.md` 里的数据集要各自回原发行方取，许可另算。

# P0.4b 取证报告：通道 A/D/E 的排序键**到底有没有用**

**日期**：2026-10-14
**归属**：总纲 `docs/RETRIEVAL-LONG-RANGE-PLAN.md` §3 的 **P0 主项**（0.4b 行）
**命令**：`var/tmp/p0-4b-evidence.py`（临时库只读）

## 一、总纲留了两个**互相矛盾**的数字，本报告把它量准

P0.4b 那一行同时写着两组数（原话保留、更正在后）：

| 出处 | 说法 |
|---|---|
| 原写 | clause 级 `effective 521,984 / withdrawn 21 / reference 16 / superseded 0 / NULL 0` |
| 2026-09-30 更正 | doc 级 `effective 6,777 / reference 16 / withdrawn 4 / NULL 0`，合计 6,797 |

⇒ 两者**层级不同**（clause vs doc），所以都不算错，但**"名次与相关性无关"这个结论
一直缺一个可复算的分母**。本次量准了。

## 二、实测（生产库只读，2026-10-14）

### 2.1 条款级 `legal_status` 分布（**通道 A/D/E 的候选就是 clause 行**）

| 状态 | 条数 | 占比 |
|---|---|---|
| `effective` | **663,597** | **99.994%** |
| `withdrawn` | 21 | 0.003% |
| `reference` | 16 | 0.002% |
| `superseded` | 0 | 0 |
| `NULL` | 0 | 0 |
| **合计** | **663,634** | 100% |

### 2.2 候选池（排除 withdrawn/superseded 之后）

**663,613 行** —— 这就是通道 A/D/E 一次能拉的候选规模。

### 2.3 `ORDER BY` 三个键**各切多少档**（档数=1 ⇒ 该键没起作用）

| 键 | 档数 | 说明 |
|---|---|---|
| ① `(dm.legal_status IS NULL)` | **1** | 候选里**一个 NULL 都没有** ⇒ 恒为 0 ⇒ **完全没起作用** |
| ② `dm.legal_status` | **2** | 只有 `effective`(663,597) 与 `reference`(16) 两档 |
| ③ `cr.clause_revision_id` | **663,613** | 全序兜底（= ULID = **灌库序**） |

⇒ **键①+键② 合起来只切出 2 档，而候选 663,613 行。**
⇒ **99.9976% 的候选（663,597 / 663,613）落在同一档里**，它们的相对名次
**完全由键③（灌库序）决定**。

## 三、结论（两条，分开说）

### 结论 1：总纲的判断**成立**，且现在有可复算的分母

> 「通道内名次实质上等于灌库顺序，与相关性无关」

**成立**。分母是 **663,613**（不是 522,000，也不是 6,797）——
那两组旧数字各自是别的层级/别的时点的读数。

### 结论 2：那两个键**不是排序键，是产品过滤键**（我拍的板）

总纲留的待定项：「那两键承载"未核验不得承重"的语义 ⇒ 要判它是**排序键**还是**产品过滤键**」。

**我的判定：产品过滤键。** 证据三条：

1. **它要表达的语义是"能不能用"，不是"哪个更相关"** ——
   "未核验不得承重"说的是**准入**（这条能不能当依据），不是**排序**（这条比那条更相关）。
   把它写成 `ORDER BY` 是把准入问题塞进排序位。
2. **它在数据上几乎没有区分度**（键①档数=1、键②档数=2）——
   一个"排序键"如果在 663,613 行里只能分出 2 档，它就不是排序键。
3. **同一份语义在别处已经有正确的落点**：通道的 `WHERE` 子句里
   **已经**在用 `legal_status NOT IN ('withdrawn','superseded')` 做准入
   （见 `hybrid_engine.py` 通道 A/D/E 的 `include_superseded=False` 分支）——
   **那才是准入的位置**。

⇒ **修法方向**：把"未核验沉底"从 `ORDER BY` **移到 `WHERE`**（或明确接受
"NULL 也进候选、但不靠排序区分"），**排序位让给真正与相关性有关的键**。

⚠ **本报告只做判定与取证，不改代码。** 修法要单独一批：
它改的是**产品行为**（哪些条款进候选、进多少），必须配评测读数（`eval/recall-funnel/`）
才能说"改好了"—— 而那正是总纲 P0.4b 后半句说的
「**然后**才谈行数上限」。

## 五、★ 修法取证：**缺的不是排序写法，是排序依据**

总纲要求"把排序改成与相关性有关"。但"有关"**先要有可用的键**。
本批把 `doc_meta` / `clause_revision` 里所有候选字段**逐个量了分档**：

### 5.1 `doc_meta` 候选字段

| 字段 | 档数 | 分布 | 能当排序键？ |
|---|---|---|---|
| `quality_grade` | **1** | A=8983 | ❌ 没区分度 |
| `standard_type` | 2 | recommended 6,130 / mandatory 2,853 | ⚠ 是"强制/推荐"，不是相关性 |
| `doc_type` | 2 | standard 7,173 / 法律法规 1,810 | ⚠ 是"资料类型"，不是相关性 |
| `legal_hierarchy` | 6 | GB/T 6,130 / 法律 1,430 / GB 1,043 … | ⚠ 是"层级"，方向要拍板 |
| `legal_status` | 3 | effective 8,963 / reference 16 / withdrawn 4 | ⚠ **就是现在那两个键**，见 §二 |
| `ccs_code` / `ics` | **1** | 全 NULL | ❌ 空列 |
| `source_status` | **1** | 全 NULL | ❌ 空列 |
| `change_signal` | 5 | NULL 8,933 / issued 24 / draft 16 … | ❌ 99.4% 是 NULL |
| `catalog_hidden` | 2 | 0=8,976 / 1=7 | ❌ 只有 7 篇 |

### 5.2 `clause_revision` 候选字段

| 字段 | 档数 | 分布 | 能当排序键？ |
|---|---|---|---|
| `modality` | 6 | NULL 361,817 / 应 169,624 / 可 27,967 … | ⚠ **它就是通道 D 的过滤键**（拿它再排序是自指） |
| `subject` | 6 | NULL 632,385 / 人民法院 6,011 … | ⚠ **它就是通道 E 的过滤键**（同上） |
| `knowledge_type` | 3 | rule 485,428 / data 121,614 / legal 56,592 | ⚠ 是"知识类型"，不是相关性 |
| **`content_type`** | **3** | normal 646,638 / 附录 9,826 / **前置说明 7,170** | ✅ **见 5.3** |
| `is_mandatory` | 2 | 0=663,504 / 1=130 | ❌ 只有 130 条 |

### 5.3 ★ `content_type` 是**唯一**方向明确的候选（实测内容，不是猜）

三档的**实测内容**：

```
前置说明  [前置1] '中华人民共和国国家标准\n代替 GB 30871—2014\n危险化学品企业…'
          [前置1] 'ICS29.080.10\nK48\n中华人民共和国国家标准\n…'
          [前置1] '前言\n本标准的第1、2、3、4章以及7.2.1…'
附录      [附录 ] '附录\n(规范性\n酒精计温度(t)与20℃时…'
          [附录 ] '附录\nGB/T15092.1—2020 的附录均适用。…'
normal    [1    ] '1 范围\n本文件规定了危险化学品企业动火作业、…'
          [1    ] '1 范围\n本标准规定了高压线路针式瓷绝缘子的结构型式…'
```

⇒ **`前置说明` 是封面 / 前言 / 目次，结构性不是"用户要查的条文"** ——
用户问"探测器装多高"，不可能期望答案是封面上的 ICS 号。

**三条判据都过**：
1. **分档有量**：3 档，最小档 7,170（不是空列）；
2. **语义方向明确**：前置说明沉底**只会**把噪声往后挪，不会把条文挪走；
3. **不误伤**：⚠ **附录不能无条件沉底** —— 实测 `规范性附录` **2,675** 条
   （有约束力）、`资料性附录` **3,358** 条（仅供参考）。
   ⇒ 若将来要沉附录，**必须先按正文里的"(规范性附录)/(资料性附录)"标记分开**
   （正文自带这个标记，实测可判）。

### 5.4 结论：P0.4b 的正确修法是**两件分开的事**

| # | 做什么 | 为什么 |
|---|---|---|
| **A** | 把"未核验沉底"从 `ORDER BY` **移到 `WHERE`**（或明确接受"NULL 也进候选、不靠排序区分"） | §三：它是**准入**语义，塞在排序位是错位 |
| **B** | 排序位让给 `content_type`（**只有"前置说明沉底"这一条方向明确**） | §5.3：其余候选键要么没区分度、要么是过滤键自指 |

⚠ **B 只解决"前置说明"这一档（7,170 / 663,634 = 1.08%）** ——
**它不能把"名次与相关性有关"这件事做成**。剩下 98.9% 的候选**仍然同档**。

⇒ **P0.4b 的真实状态应该改成**：
「**排序依据不足**」—— 不是"排序写法没改"，是**库里没有可用的相关性键**。
要真正修它，得先**造出**一个相关性信号（例如：条款在本文档里的位置、
被引次数、或查询词在该条款里的密度）—— 那是**新能力**，不是改一行 `ORDER BY`。

⚠ **本报告只做判定与取证，不改代码。** 理由：B 改的是**产品行为**
（哪些条款排前面），必须配评测读数（`eval/recall-funnel/`）才能说"改好了"；
而 §5.4 表明**改 B 的收益上限只有 1.08%**，值不值得动要单独判。

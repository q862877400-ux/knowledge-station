## 结论先行（≤15 行）

1. **「还要不要检索」这件事，2025–2026 的实证已经翻过来了，但只翻了一半**：长上下文（LC）在资源充足时平均胜过 RAG（EMNLP 2024 Industry），可**只在浅层针式任务上**；一旦去掉字面重合（NoLiMa）或提高信息密度（Dense Contexts），13 个宣称 128K 的模型里 11 个在 32K 处掉到短上下文基线的一半以下，GPT-4o 从 99.3% 掉到 69.7%【一手，ICML 2025】。**法条是词汇密度最高的文本之一，这条线不能替代检索**【推断】。
2. **多阶段 RAG 管线（RAPTOR/ReadAgent）在同等 token 预算下打不过「直接按原文结构读」**：∞Bench 30K token 时 DOS RAG 93.1% vs 普通 RAG 87.8%，比两个多阶段管线高 2–8 分，而 ReadAgent 平均烧 86K token 还更低【一手，EMNLP 2025】。⇒ **我们「条款一行 + 按结构组织」的方向，是学术上被证明的强基线，不是土办法**。
3. **切分这个方向，2025–2026 有一篇直接打在我们语料上的实证**：德国民法典（约 2,400 条）上 21 种切分策略、525 道题，**按条/按款切 Recall@10 0.47 / 0.46 最高**；语义聚类、Lumber、固定长度全部显著更差；固定 256/64 最低；语义切分索引要多花 38 分钟到 11 小时建【一手，ASAIL 2026】。
4. **「语义切分」被自己的评测否定了一半**：文档检索上它在拼接长文里明显赢（Miracl F1@5 81.89 vs 固定 69.45），在原生短文里输（NQ 41.01 vs 43.79），证据检索与答案生成两边差异都极小 ⇒ **算力成本换不到一致收益**【一手，NAACL 2025 Findings】。
5. **推理密集检索是新的真问题**：BRIGHT 上 BEIR 59.0 的 SFR 掉到 18.3 nDCG@10，BM25 只有 14.5，最好的模型 22.5（论文正文又写 24.3，见 §九）；**把 LLM 写的推理步骤当查询能平均涨 12.2 分，而且 BM25 涨得最多**——即「查询先加工」仍然是最便宜的那一刀，与 D 线结论同向【一手】。
6. **重排不是万能药，而且在法律文本上可能是负收益**：BRIGHT 上加 GPT-4 重排只从 14.3 涨到 17.4；LegalBench-RAG 上 **Cohere 重排器比不加重排更差**；BRIGHT 上的 GAR 复现显示，只有「本身带推理信号」的重排器受益（TFRank-4B 23.0→25.4），非推理重排器会掉（RankLLaMA 12.7→10.6）【一手，三篇】。
7. **法律检索的学术任务和我们不是同一个**：LePaRD 是「判决理由 → 判例段落」，最强模型只到 **59% recall**（限 1 万条最常被引段落）；SG-LegalCite 是「事实+法律原则 → 判例」；STARD/GCSR 才是「口语化提问 → 法条」，已在 F 线写过。**「条款级引用 + 点回原文」依旧零篇**（本轮又核了 24 篇，仍无）。
8. **引用可溯源这一层，最值钱的不是指标而是「怎么造数据」**：LongCite 的 CoF 管线用现成 LLM 两段式（粗定位→细抽取）自动造了 45k 条句级引用样本，训出的 8B 模型 citation F1 **72.0** 超过 GPT-4o 的 **65.6**，且引用长度只有 GPT-4o 的 39%（85 vs 220）【一手】。⇒ 我们缺的「句子—条款」金标可以这样造。
9. **我们没考虑过的范式有五条**（§七）：文档侧扩展（doc2query 系）、重排阶段沿语料图扩候选（GAR）、推理时才做结构化（StructRAG）、可读 DocID 的生成式检索（ACID）、自动构造引用金标（CoF）。**前两条与我们的实测痛点直接对上**。
10. **看完不抄的**：RL 训练检索 agent（Search-R1）、多向量→单向量（MUVERA，现在没底座）、自动 schema 归纳（AutoSchemaKG，标准域有国标）、生成式检索整体（仍要重训）。理由逐条写在 §八。

## 一、检索范式：2024–2026 的新路线

### 1.1 BRIGHT（ICLR 2025，[arXiv 2407.12883](https://arxiv.org/abs/2407.12883)）
- **解决什么**：现有基准都是「关键词/语义能对上」的检索；真实世界里有一类查询必须先推理才知道该找什么（「用同一经济学理论解释的故事」「同一个错误信息对应的语法文档」）。
- **方法一句话**：12 个域、1,384 条真实查询，正例按「是否引用同一结论/定理/报错」判定，判据不是字面相似。
- **数字**（Table 2，平均 nDCG@10）：BM25 **14.5**、BGE 13.7、SFR-Embedding-Mistral **18.3**（同一个模型在 BEIR 检索子集是 59.0）、GritLM 21.0、gte-Qwen 22.5、Google 20.0【一手】。Table 3 重排：BM25 14.3 → GPT-4 重排 top-10 **17.4**、top-100 17.0；Google 19.5 → 22.6【一手】。把 LLM 写的推理步骤当新查询：平均最多 **+12.2 分**，「BM25 涨得最多」，但最好仍低于 30【一手，§4.2 + Figure 3】。
- **能不能用**：**评测口径可借**（进验收层）。我们的「大白话 → 条款」本质就是推理密集检索，BRIGHT 提醒我们：**用 BEIR/C-MTEB 分数选模型会选错**。
- **不能用的理由**：语料是英文 StackExchange/数学/代码，12 个域里没有「法规/标准」；且它是 benchmark 不是方法。

### 1.2 Search-R1（COLM 2025，[arXiv 2503.09516](https://arxiv.org/abs/2503.09516)）
- **解决什么**：让模型自己决定「什么时候搜、搜什么、搜几次」，而不是把检索固定成一次前置步骤。
- **方法一句话**：把搜索引擎当环境，用 GRPO/PPO 做结果监督的 RL，检索回来的 token 不算 loss（retrieved-token loss masking）。
- **数字**（Table 2，7 个 QA 集平均 EM，2018 维基 + E5 检索、top-3 段落）：Qwen2.5-7B-base 上 **Search-R1 0.431 vs 普通 RAG 0.304**；3B 上 **0.325 vs 0.270**；摘要另称相对提升 **24% / 20%**【一手，摘要 + Table 2 两处口径不同】。
- **能不能用**：**方法不抄，交互形态可借**。我们要的是「这条问不出来 → 换个问法再查一次」，这不需要 RL，用一轮改写即可（D 线 GuRE 那条）。
- **不能用的理由**：① 需要可训的 RL 管线（我们单机 Electron + 用户自配 Key，没有训练面）；② 每次查询多轮搜索 + 多次生成，延迟与 token 成本都随轮数线性涨。

### 1.3 GAR 的独立复现（SIGIR 2026，[arXiv 2604.27577](https://arxiv.org/abs/2604.27577)）
- **解决什么**：级联式「先召回 top-k 再重排」有**召回上限**——答案不在 top-k 里，重排再好也救不回来。GAR（Graph-based Adaptive Reranking）不改召回器，而是在重排阶段沿**语料图**往外走，把图上的新文档拉进候选。
- **方法一句话**：以初始 top-b 为入口点，在文档相似图上迭代扩展，每一轮用重排器打分决定往哪走。
- **数字**（Table 2，BRIGHT，BM25 top-100 起、重排预算 c=50/100，平均 nDCG@10）：BM25 **12.6**；Qwen-8B **20.8 → 22.8**（+GAR）；TFRank-4B **23.0 → 25.4**；TFRank-1.7B 19.7 → 21.7【一手】。**反证在同一张表里**：非推理重排器 MonoT5-base 7.6 → 7.6（无变化），listwise 的 RankLLaMA-7B **12.7 → 10.6（变差）**【一手】。
- **能不能用**：**这是本线对我们最对症的一条**（进重排层）。我们实测「候选集是瓶颈：前 50 只有 33%，候选收到 50 时前 20 命中 99%」——GAR 正是对着这个瓶颈换位置下手，且**代价只有几轮重排调用**。
- **不能用的理由**：它要求「文档间相似图」存在。我们**跨文档边 = 0**（任务书 §三），先得把条款间相似边建出来（不必用 LLM，条款正文 embedding 或共用术语即可）。

### 1.4 MUVERA（NeurIPS 2024，[arXiv 2405.19504](https://arxiv.org/abs/2405.19504)）
- **解决什么**：晚交互（ColBERT 类）多向量检索质量高但检索慢，必须专门的 MaxSim 引擎。
- **方法一句话**：把多向量相似度编码成**固定维单向量**（FDE），用现成的 MIPS/ANN 引擎检索，带 ε-近似保证。
- **数字**：达到同等 recall 时**少检索 2–5 倍候选**；相对 PLAID **延迟最多低 5.7×**【一手，摘要 + §1】。
- **能不能用**：**可选零件**，将来换向量底座时一并评估（C 线已列 ANN 候选，MUVERA 是「多向量质量 + 单向量索引」的桥）。
- **不能用的理由**：现在不抄——要先有多向量模型，而我们的向量通道当前是 606 ms 的弱项，先解决底座再谈质量。

### 1.5 StructRAG（[arXiv 2410.08815](https://arxiv.org/abs/2410.08815)）
- **解决什么**：知识密集推理所需信息散落在很多文档里，普通 RAG 检索回来的块噪声大、拼不起来。
- **方法一句话**：**推理时**而不是建库时，判断这个任务适合哪种结构（表 / 图 / 算法 / 目录 / 块五选一，用 DPO 训的路由器），把散落原文重构成该结构再推理。
- **数字**（Loong 基准）：总体 LLM 评分 **60.38**、EM **0.23**；对 RAG 胜率 **62.0%**、对 GraphRAG **53.0%**、对长上下文 **95.75%**；文档越长提升越大（Set1→Set4 对长上下文 +9/+15/+22/+23）；消融：去掉路由器掉到 **45.33**（−15.05）、去掉结构化器 53.92、去掉利用器 55.94【一手，Table 1/Table 3】。
- **能不能用**：**只借形态，不抄实现**。「按问题类型选结构」对我们有限：统计/对比类问题（「哪些国标的试验方法都引用了 GB/T X」）确实需要表式聚合，而我们六通道只能给条款。
- **不能用的理由**：每问一次要 LLM 把所有相关文档重构成结构，成本按问题数×文档数涨；且重构结果是生成文本，**不能直接引用**（只能用来算答案，引用仍要回到原条款）。

### 1.6 SPLADE-v3（[arXiv 2403.06789](https://arxiv.org/abs/2403.06789)）
- **解决什么**：稀疏检索（BM25）有精确词匹配与倒排效率，但不会做语义扩展；稠密检索反过来。
- **方法一句话**：用 BERT 学「词项权重 + 扩展」，产出高稀疏向量，仍走倒排索引。
- **数字**：44 个查询集上的 meta 分析；BEIR 13 集 nDCG@10 里，FiQA-2018 **34.9（SPLADE++）→ 37.4（v3）**、DBPedia-entity 43.6 → 45.0；论文原话是「在整个比较集上 SPLADE-v3 大幅优于 BM25（即使效率更低）」【一手，Table 2 + §3】。
- **能不能用**：**可选**。它保留了我们最看重的东西——**精确词匹配仍在**（条款号、术语、上下标），同时补语义扩展。
- **不能用的理由**：要 GPU 编码全库（千万条），且与「单文件 SQLite/FTS5 便携」冲突；换检索底座已在 C 线结论里定成「两段式、不引外部服务」。

### 1.7 ACID（WikiNLP 2024，[arXiv 2311.08593](https://arxiv.org/abs/2311.08593)）
- **解决什么**：生成式检索（把语料变成模型要背出来的 ID）的 ID 一换成整数序列，就**丢掉了可解释与可回溯**。
- **方法一句话**：DocID 不用聚类整数，用 LLM 生成的**摘要式关键词短语**（或抽取式前 30 token），解码时用前缀树约束只生成库里存在的 ID。
- **数字**（100k 语料）：相对聚类整数 ID 基线，MSMARCO-100k 上 top-10/top-20 recall **+15.6% / +14.4%（相对）**，NQ-100k 上 +9.8% / +9.9%【一手，摘要 + 实验节】。
- **能不能用**：**不抄，但它改了我们对生成式检索的否决理由**。我们（和 F 线）否决生成式检索的理由是「语料烧进参数、变了要重训」；ACID 说明 ID 本身可以是可读文本 ⇒ 若将来走生成式，**可读 DocID 是唯一符合我们引用要求的那条分支**。
- **不能用的理由**：仍要训练生成模型 + 全库重建索引；语料天天变。

### 1.8 文档侧扩展：doc2query 系（2019 起源 + 2026 最新，均为【一手摘要】）
- **解决什么**：查询和文档用词不一致（我们实测 **53.0% 的大白话提问与原文零字面重叠**）。
- **方法一句话**：给**每篇文档**生成「它可能被哪些问题检索到」，把生成的问题拼进被索引的文本——扩展的是文档，不是查询。
- **数字**（只读到摘要）：原始 doc2query（[arXiv 1904.08375](https://arxiv.org/abs/1904.08375)）称「只做检索、不加重排」就接近更贵的神经重排器的效果；2026 年的 QGDPO（[arXiv 2610.04352](https://arxiv.org/abs/2610.04352)，沃尔玛电商）用 DPO + 相关性过滤，称**消掉 50% 无关预测**，过滤再消 14.61%【一手摘要，**未读正文表格**】。
- **能不能用**：**能，这是本线第一条「我们完全没考虑过」的范式**（详见 §七-1）。进**索引构建层**：给每条条款生成「这条能回答什么问题」，拼进 FTS5 的被检索文本。
- **不能用的理由**：生成的问句会带来假匹配（QGDPO 存在的理由就是这个），必须配一道相关性过滤；而且生成文本进索引会轻微污染「被检索文本 = 原文」这条不变量——所以**只能进索引副本，不能进展示与引用用的正文**。

## 二、长文档 / 长上下文 vs 检索

### 2.1 RAG or Long-Context LLMs（EMNLP 2024 Industry，[arXiv 2407.16833](https://arxiv.org/abs/2407.16833)）
- **解决什么**：长上下文模型出来后，「检索还有没有用」需要同条件对比。
- **方法一句话**：同一批数据上，分别用「检索 top-k 喂进去」和「整篇塞进去」跑三个前沿模型，再提出按自反思路由（SELF-ROUTE）：简单的走 RAG，难的走 LC。
- **数字**：**资源充足时 LC 在几乎所有设置上胜 RAG**，但 RAG 成本显著更低；**超过 60% 的查询两种方式给出相同答案** ⇒ 这部分用 RAG 就是纯省钱【一手，摘要 + §1】。
- **能不能用**：**路由思路可借**。我们不可能走 LC（全库 2.2 TiB / 52 万条），但「**同一份候选文档**：简单问题用小窗口检索，复杂问题把相关章节整段塞进去」是可做的。
- **不能用的理由**：它的 LC 是「整篇文档」，我们是「整库」，前提不成立；且它没给成本的具体百分比（我没逐表取）。

### 2.2 DOS RAG（EMNLP 2025，[ACL 2025.emnlp-main.1656](https://aclanthology.org/2025.emnlp-main.1656.pdf)）
- **解决什么**：多阶段管线（摘要、迭代、agent 式遍历）到底值不值。
- **方法一句话**：DOS RAG = **按文档原有结构**检索、按原有顺序把段落喂给模型，不做摘要不做改写。
- **数字**：∞Bench En.MC（229 题 / 58 篇，平均 184K token）30K token 预算时 **DOS RAG 93.1%** vs 普通 RAG **87.8%**，比 ReadAgent 与 RAPTOR 高 **2–8 分**；ReadAgent 平均烧 **86K** token 仍更低【一手，Figure 1 + §4】。
- **能不能用**：**能，而且我们已经在这个位置上**——「条款按条号顺序、带章节标题、原文不改写」就是 DOS RAG 的法律版。它给我们一个**验收基线**：任何复杂度升级（摘要节点、结构化、图）必须在**同等 token 预算**下赢过 DOS RAG 才算赢。
- **不能用的理由**：任务是单文档/少文档问答，不是「百万条款里找一条」。

### 2.3 NoLiMa（ICML 2025，[arXiv 2502.05167](https://arxiv.org/abs/2502.05167)）
- **解决什么**：针式测试（NIAH）能被「问题与针里有相同字面」作弊；真实场景里问题与证据往往没有字面重叠。
- **方法一句话**：构造**问题与针最小字面重合**的针式集，逼模型做隐式联想，测 13 个宣称 ≥128K 的模型。
- **数字**：32K 处 **11 个模型掉到短上下文基线的 50% 以下**；GPT-4o 从 **99.3% → 69.7%**；多数模型**有效长度只有 ≤2K**，GPT-4o 约 8K【一手，Table 3】。
- **能不能用**：**当验收口径可借**。我们的「53% 零字面重叠」正是 NoLiMa 说的那种查询——**这也是为什么不能用长上下文替代检索**。
- **不能用的理由**：任务是人名查找式（haystack 是人造叙事），不是条款检索。

### 2.4 Dense Contexts Are Hard Contexts（[arXiv 2606.06203](https://arxiv.org/abs/2606.06203)，2026 预印本，**未同行评审**）
- **解决什么**：长上下文失效被归因于「长度」和「位置」，忽略了**词汇密度**（单位长度里新信息的速率）。
- **方法一句话**：三个长度相同（≈12K token）、针位置受控、**密度递增**的针式集，测 9B–685B 开源模型。
- **数字**：稀疏上下文里近乎满分的模型，在**高密度**上下文里**掉到 60% 以下**；同基准内只调密度（其余不变）能把性能恢复【一手，摘要 + Figure 1】。
- **能不能用**：**当设计约束**（进评测层）。法条是**极端词汇密集**文本（German 那篇的原话：单个词就承载决定性法律后果）。⇒ 「条款塞进长上下文让模型自己找」在我们语料上是**最坏情况**，不是平均情况。
- **不能用的理由**：预印本、任务人造；只能当趋势证据，不能当定量依据。

## 三、引用与可溯源（2025–2026）

> D 线已写 ALCE 的 recall/precision 与 Sufficient Context。本节只写它们没覆盖的：**句级/原子命题级引用生成、引用数据怎么造、RAG 幻觉语料**。

### 3.1 LongCite / LongBench-Cite（ACL 2025 Findings，[arXiv 2409.02897](https://arxiv.org/abs/2409.02897)）
- **解决什么**：长上下文模型给的答案没有引用，用户没法核；有引用的也往往是「整段」而不是「这句话」。
- **方法一句话**：先建句级引用基准（6 个数据集、中英双语、共 1,000 条），再提 **CoF（粗到细）** 管线：用现成 LLM 先粗定位相关块、再细抽支撑句，批量造 45k 条训练样本，SFT 出 LongCite-8B/9B。
- **数字**（Table 2，平均）：citation F1 **LongCite-8B 72.0 / LongCite-9B 68.2 / GPT-4o 65.6 / Claude-3-sonnet 67.2**；平均引用长度 **85 / 91 / 220 / 132** 句 ⇒ 8B 模型比 GPT-4o 高 6.4 分且引用只有其 39% 长【一手】。Table 3：加引用后答案正确率是原样的 **103%–110%**（不是变差）【一手】。
  - 🔴 **2026-10-25 复核实测后更正（原话保留，不删）**：**LongCite-9B 的平均 citation F1 是 69.2，不是 68.2**——68.2 是它在 **GovReport 子集**上的分。论文正文写「72.0 and 69.2 v.s. 65.8」，且自述提升 6.4 / **3.6**（65.6 + 3.6 = 69.2）可自洽验算。⇒ 8B−GPT4o = **+6.4**、9B−GPT4o = **+3.6**（不是 8B/9B 都高 6.4）。8B = 72.0（85 句）、GPT-4o = 65.6（220 句）、Claude = 67.2（132 句）三项无误。
  - ⚠ **对结论的影响**：无。CoF 管线造出的 8B 模型**仍超过 GPT-4o**（72.0 vs 65.6），「自动造引用金标可行」这个判断不变；变的只是 9B 那一格与差值。
- **能不能用**：**能，两条都进**。① 指标进**引用验收层**（句级 F1 + 引用长度）；② **CoF 管线进数据构造层**——我们缺「句子—条款」金标，这正是自动化造法。
- **不能用的理由**：它的上下文是 4K–35K 字的单篇/少篇文档，引用是「句中编号」，没有「条款号 + 页码 + 坐标」这一层；金标还得落到我们的条款 ID 上。

### 3.2 ALiiCE（NAACL 2025，[arXiv 2406.13375](https://arxiv.org/abs/2406.13375)）
- **解决什么**：句级引用指标会把一句话里的多个原子命题揉成一个，引用「挂在哪半句」评不出来。
- **方法一句话**：用依存树把句子拆成原子命题，在命题级算引用 recall/precision，另加「引用位置变异系数 CVCP」衡量引用是不是全堆在句末。
- **数字**（Table 2，ASQA / ELI5）：GPT-4（5-psg）ASQA **R 76.8 / P 68.2 / F1 72.2**，ELI5 **55.1 / 54.0 / 54.5**；LLaMA-3-8B ELI5 只有 **45.9 / 47.1 / 46.5**【一手】。
- **能不能用**：**能，进引用验收层**。我们的场景更极端：一句话里可能同时说「第 5.2.3 条要求 A」和「第 6.1 条豁免 B」，句级引用会把两条揉在一起算对。
- **不能用的理由**：中文条款的依存句法解析质量未知；且它仍是「英文长答案」任务，没有条款号这一层。

### 3.3 RAGTruth（ACL 2024，[arXiv 2401.00396](https://arxiv.org/abs/2401.00396)）
- **解决什么**：RAG 也会幻觉，但缺**词级**标注的语料来训练/评测检测器。
- **方法一句话**：约 **18,000 条**真实 RAG 回答，人工做 span 级幻觉标注并给强度，覆盖多任务多模型；用它能微调小模型做检测且表现有竞争力【一手，摘要（规模来自摘要，检测器分数我**没逐表取**）】。
- **能不能用**：**可选**。若我们要做「这句话有没有条款支撑」的检测器，这是最接近的公开训练资源。
- **不能用的理由**：英文、开放域；中文条款的「支撑/不支撑」判定要靠我们自己的金标（见 3.1 的 CoF）。

## 四、中文 / 低资源检索

### 4.1 C-Pack / C-MTEB / BGE（SIGIR 2024，[arXiv 2309.07597](https://arxiv.org/abs/2309.07597)）
- **解决什么**：中文没有统一的 embedding 评测，各家自报数字不可比。
- **方法一句话**：一次放出三件东西——训练集 C-MTP、基准 C-MTEB（**6 类任务 / 35 个数据集**）、模型族 BGE。
- **数字**：发布时 BGE 在 C-MTEB 上比此前所有中文 embedding **高 10% 以上**；C-MTEB 的检索子集是 **8 个数据集**（T2Retrieval、DuRetrieval、MMarcoRetrieval、CovidRetrieval、EcomRetrieval、MedicalRetrieval、VideoRetrieval、CmedqaRetrieval）【一手，摘要 + 基准表头】**具体每个检索集的分数我没逐表取**。
- **能不能用**：**可选（选型用）**。这是选中文检索/向量模型时唯一可比的公开榜单；也解释了为什么 F 线的 STARD 上通用中文 BGE（H@20 0.443）能压过法律专用编码器（SAILER 0.236 / Lawformer 0.257）。
- **不能用的理由**：C-MTEB 的检索任务都是通用域短文，**没有条款级、没有编号、没有效力状态**；在它上面排名第一不等于在国标上第一（BRIGHT 已经证明榜单分数会误导）。

### 4.2 中文「字 / 词 / n-gram」之争：**没找到一手实证，明确记为空白**
- 我按 `Chinese word segmentation retrieval character based verses word based` 在 OpenAlex 检索（total 792），返回的是 1994 年的分词算法、2003 年的 SIGHUP 分词评测、2016 年的未登录词抽取——**都是分词任务本身，没有一篇是「分词 vs 字 vs n-gram 对检索效果的影响」**。
- 相关旁证（不是中文实证）：German legal chunking 那篇明写「单个词就承载决定性法律后果（unverzüglich vs sofort）」，所以**字面精确匹配在法域是刚需**；这支持我们「精确条款号 0.1 ms + FTS5 字面通道」的方向，但**不能当作「中文应该按字切」的证据**【推断】。
- **对我们的处置**：不因为这条空白改任何设计。若将来要动 FTS5 的分词（例如换成字级 unigram），必须自建中文条款召回评测再验收（C-MTEB 与 STARD 都不测这个）。

## 五、法律 / 标准域的学术前沿

### 5.1 LePaRD（ACL 2024，[arXiv 2311.09356](https://arxiv.org/abs/2311.09356)）
- **解决什么**：法律段落检索（LPR）——给一段「办案论证上下文」，找出它该引的判例段落。这是律师真实工作里的检索任务。
- **方法一句话**：从 CAP（哈佛判例库，**170 万篇**联邦判决）里抽「引文 + 引用上下文」配对，构成**数百万**条样本；对比检索、分类、生成几类做法。
- **数字**：**分类式检索最好**；但在「最常被引的 1 万条段落」上训练后**最强模型也只到 59% recall**【一手，摘要】；检索工具的市场价被写作「一次检索最高 100 美元」【一手，§1】。
- **能不能用**：**能，进任务定义与训练对构造**。我们已有 **22,992 条条款互引边**，与 LePaRD 的构造方式同构（上下文 → 被引单元），是现成的改写器/重排器训练素材（D 线 GuRE 已提出同一用法）。
- **不能用的理由**：判例 ↔ 判例，查询本身很长（整段论证），不是「大白话 → 条款」；且英文。

### 5.2 LegalBench-RAG（[arXiv 2408.10343](https://arxiv.org/abs/2408.10343)）
- **解决什么**：LegalBench 评的是「生成得像不像律师」，不是「检索找得准不准」。缺一个只评检索步的基准。
- **方法一句话**：从 4 个法律数据集抽 **6,889 条问答对**，语料人工标注到「哪段文字是证据」，只评召回/精度；再横比切分策略与重排器。
- **数字**：语料约 **8,000 万字符**；最有效的组合是 **递归字符切分 + 不加重排**，**Cohere 重排器反而比不加重排更差**；PrivacyQA 上最好配置 Precision@1 仅 **14.38%**、Recall@64 **84.19%**【一手，§4 + Figure 2/3】。
- **能不能用**：**能，两条**。① 「只评检索步」的评测形态直接照抄（我们的红箭头准不准就是这个）；② 它的反证支持我们「重排显式关闭」的现状（`rerank=False`，见 D 线结论第 11 条更正）。
- **不能用的理由**：合同/隐私政策，不是编号条款；且它用的正是 SQLite Vec + text-embedding-3-large，**与我们同族**，可当对照组但不能当上限。

### 5.3 SG-LegalCite（[arXiv 2605.21057](https://arxiv.org/abs/2605.21057)，2026）
- **解决什么**：普通法系引判例不只看事实相似，还要看**援引的是哪条法律原则**；只用事实/上下文检索会捞回「事实像但法理无关」的判例。
- **方法一句话**：把查询从「事实」升级成「事实 + 显式法律原则」，从 8,523 份新加坡最高法院判决里抽 **100,890 条「案件—原则」对**。
- **数字**：8,523 份判决（2000–2025）、100,890 对；11 个基线上**原则增强检索一致更好**【一手，摘要；**具体分数我没逐表取**】。
- **能不能用**：**可选（输入形态）**。它印证我们六通道里「法理要素」这一路：查询侧把「法理要素」显式化，比指望语义相似度补上更可靠。
- **不能用的理由**：判例域，且数据集是 LLM 自动抽取 + 抽样核验构造的，标签质量未见独立复核。

### 5.4 Chunking German Legal Code（ASAIL 2026，[arXiv 2605.19806](https://arxiv.org/abs/2605.19806)）——**本线最重要的一篇**
- **解决什么**：「切分」在法条上到底该怎么切，此前只有传闻没有实证。
- **方法一句话**：以德国民法典（BGB，约 **2,400 条**）为语料，实现并对比 **21 种**切分策略（按条/按款/按句/按命题、固定长度 5 档、contextual chunking、语义聚类、Lumber、RAPTOR），用 525 道带条级金标的德语法律题评测，同时量**召回、查询延迟、建索引时间、索引体积**。
- **数字**（Figure 2，Recall@10，525 题、平均每题约 1.7 条金标条）：**按款 0.47、按条 0.46 最高**；按句/按命题次之；contextual 明显低于结构切分；语义聚类与 RAPTOR 居中游；**Lumber 与固定长度最差，固定 256/64 最低**。统计检验：Friedman p<0.0001，Holm 校正后的配对置换检验显示「各结构单元之间无显著差异，但按条切显著优于其他所有策略」【一手，Figure 2 + §4】。
  - 建索引（Figure 4）：按条 **51 s**、固定 256/64 44 s、contextual 按款 **38 m 8 s**、RAPTOR **3 h 4 m–5 h 51 m**、Lumber **9 h 2 m–11 h 41 m**。
  - 索引体积（Figure 5）：按条 **33.2 MB**、按命题 131.9 MB、RAPTOR 68.5–144.1 MB、重叠固定窗 16/4 最大 **230.9 MB**。
- **能不能用**：**能，这是对我们路线的第三方独立验证**（进解析/切分层）。我们的「条款一行 + 精确条号」在这个实验里就是最强的那个策略，**且是最便宜的之一**。
- **不能用的理由**：它只评到「条级召回」，不评下游生成；单一非专家数据集（德语 BGB）；**它没有处理互引**——而它自己把「reference-aware chunking（把条文依赖的定义并进被索引单元）」列为 future work。**这正是我们的差异化空间**（见 §七-3）。

## 六、知识库构建自动化（切分与 schema）

### 6.1 Is Semantic Chunking Worth the Computational Cost?（NAACL 2025 Findings，[arXiv 2410.13070](https://arxiv.org/abs/2410.13070)）
- **解决什么**：语义切分（按语义相似度找边界）被普遍采用，但收益没人系统测过。
- **方法一句话**：三个代理任务（文档检索、证据检索、答案生成）× 10 个数据集，比固定长度切分 vs 断点式语义切分 vs 聚类式语义切分。
- **数字**：文档检索 F1@5（Table 1）：Miracl\* 固定 **69.45** / 断点 **81.89** / 聚类 67.35；NQ\* **43.79 / 63.93 / 41.01**；Scifact\* 35.27 / 36.27 / 35.70；BioASQ\* 61.86 / 61.87 / 62.49 ⇒ **在拼接长文上语义切分明显赢，在原生短文上输**。证据检索：固定切分在 5 个数据集里 3 个最好，差异极小。答案生成：BERTScore 差异极小（ExpertQA 0.65/0.65/0.65）【一手，Table 1–3 + §4】。
- **能不能用**：**当反证用，结论是「不要为了语义切分付算力」**。它替我们挡住了「要不要上语义切分」这个问题。
- **不能用的理由**：它是英文通用语料；对法条不适用不是因为它错，而是因为**法条有天然边界，不需要猜**（German 那篇已给答案）。

### 6.2 Dense X Retrieval / 命题级粒度（EMNLP 2024，[arXiv 2312.06648](https://arxiv.org/abs/2312.06648)）
- **解决什么**：检索单元该多大——篇、固定段落、句、还是「命题」（原子事实，自带上下文的一两句）。
- **方法一句话**：用 LLM 把维基正文改写成自包含的命题，按命题建索引，与段落/句级对比。
- **数字**（Figure 1）：Recall@5 段落 → 句 → 命题：Contriever **43.0 → 47.3 → 52.7**，GTR **65.2 → 66.7 → 68.0**；下游 EM@500 同向（34.1 → 36.2 → 37.3 / 38.5 → 40.1 → 41.3）【一手】。
- **能不能用**：**可选**。注意收益形状：**弱检索器（Contriever）从细粒度里赚 +9.7，强检索器（GTR）只赚 +2.8** ⇒ 粒度收益与检索器能力互补，我们向量通道弱，理论上更能吃到这个红利。
- **不能用的理由**：命题是 LLM 改写出来的，**改了原文就不能作为引用单元**。对我们只可能做「命题索引 → 命中后映射回原条款」，与我们「条款一行」的存储模型可以共存但要新增一层映射。

### 6.3 AutoSchemaKG（ACL 2026，[arXiv 2505.23628](https://arxiv.org/abs/2505.23628)）
- **解决什么**：建知识图谱要先设计 schema，schema 定死了新数据就装不进去。
- **方法一句话**：让 LLM 抽三元组的同时**归纳 schema**（实体 + 事件 + 概念分层），零人工。
- **数字**：处理 **5,000 万+** 文档，构出 ATLAS 系列图：**9 亿+ 节点 / 59 亿条边**（ATLAS-CC 单库 3,504 万 chunk、2.41 亿实体、6.96 亿事件）；**schema 归纳与人工 schema 的语义对齐度 92%**，零人工介入【一手，摘要 + Table】。
- **能不能用**：**不抄**（见 §八）。
- **不能用的理由**：① 抽取成本按文档数线性涨，千万条款不现实；② 标准域**已经有现成的本体来源**（GB/T 46686.1-2025，见 F 线），不需要自动归纳；③ 抽出来的边是 LLM 断言的，与我们要的「公告级确定性效力边」不是一回事。

### 6.4 Chunking Methods on RAG（[arXiv 2606.00881](https://arxiv.org/abs/2606.00881)，2026，KES/Elsevier）
- **解决什么**：切分新方法越来越多，各自只在自己场景有效，没人横比。
- **方法一句话**：首次系统横向评测一大票切分方法，并量化「切分被当预处理却引入的一堆问题」。
- **数字**：**只读到摘要**，具体方法与分数没取。
- **能不能用**：**待核**。若要做切分横评，它是现成的对照口径来源。
- **不能用的理由**：证据不足，不据此下任何结论。

## 七、对我们：我们没考虑过的 5 条范式（本线最值钱的产出）

> 判据：既不是 D/F 线已评过的东西，也不是「我们已经在做的」，而是**换了一个位置下手**的做法。

**1. 文档侧扩展（doc2query 系）——我们只想过改查询，没想过改文档。**
我们所有的查询侧努力（GuRE 改写、cue list、同义词）都在对付「53% 零字面重叠」。文档侧扩展把同一件事反过来做：**给每条条款生成「它可能被问到的 10~20 个问题」，拼进 FTS5 的被检索文本**。好处是：① 不用改查询链路，六通道里 FTS5 与向量两路直接受益；② 生成的问句不进答案、不进引用，只进索引副本，**不破坏可回溯**；③ 可离线批量做，一次成本、长期收益。风险是假匹配（QGDPO 用 DPO + 过滤消掉 50% 无关预测就是证据），所以必须配一道「生成问句与该条款语义相关性」过滤，且**新生成文本必须落在与正文不同的列**，不能混进展示文本。

**2. 重排阶段沿语料图扩候选（GAR）——我们一直在召回层想办法扩候选，没在重排层想过。**
我们实测的瓶颈是「候选集收到 50 时前 20 命中 99%，全库时前 20 只有 21%」。GAR 的定位正好：召回不动，**重排时沿文档相似图把新文档拉进来**，BRIGHT 上 +2.0~+2.4 nDCG@10。它的前提条件我们**恰好缺**：文档间相似边（我们跨文档边 = 0）。但这条边不需要 LLM 抽——条款正文向量或共用术语就够，成本远低于 HippoRAG 那类 KG。**且论文给了一个必须先验的红线**：只有重排器本身带推理/相关性判断能力时才涨，非推理重排器会变差（RankLLaMA 12.7→10.6）。

**3. 推理时才做结构化（StructRAG）——我们假设结构必须建库时建好。**
我们的六通道与「条款一行」都是**索引期定型**。StructRAG 反过来：查询到了，看这个问题的形状（统计 / 多跳 / 综述 / 单跳），再决定把散落原文重构成表、图、目录还是块。**它避开了「生成摘要污染索引」这个我们否决 RAPTOR/GraphRAG 的理由**（生成的摘要不落库，只在这次问答里用）。可用的最小形态：**只对统计/对比类问题**，在六通道召回之后、生成之前做一次结构化聚合，引用仍指回原条款。代价是每问一次 LLM 重构，且重构结果不可直接引用。

**4. 可读 DocID 的生成式检索（ACID）——我们把生成式检索整体判死了，但否决理由有边界。**
D/F 线的否决理由是「语料烧进模型参数、变了要重训 300k 步」。ACID 指出另一条分支：DocID 不必是聚类整数，可以是**抽取式摘要或前 30 token**，于是「生成的 ID」本身就是可读、可回溯的文本（+15.6% top-10 recall 相对整数 ID 基线）。⇒ **否决结论不变（仍要重训），但否决理由要缩小到「重训成本」而不是「不可回溯」**。这一条的真正价值是：如果哪天语料变成静态（比如历史标准存档），这条路是唯一同时满足「生成式速度 + 可点回原文」的分支。

**5. 引用金标的自动构造（LongCite 的 CoF）——我们一直假设金标只能人工标。**
D 线给的 ALCE 指标用不起来，就是因为没有「句子—条款」金标（当时估的是 200~500 条人工标注）。CoF 用现成 LLM 两段式批量造：先粗定位候选块，再细抽支撑句，造出 45k 条，训出的 8B 模型 citation F1 72.0 超过 GPT-4o 的 65.6。**我们的 22,992 条条款互引边天然就是「上下文 → 被引条款」的对**，可以照 CoF 造「这句话该引哪一条」的金标，人工只做抽样复核。这把「引用验收」从不可做的成本项变成可做的工程项。

**另有一条「学术上明确留白、正好是我们差异化」的方向（不是范式，是空白）**：German 那篇在结论里自己写，**互引解析没有被任何切分策略处理**，建议「把条文依赖的定义并进被索引单元」（reference-aware chunking）。我们的六通道 + 条款互引边正好在做这件事的前半段——**这不是我们落后，是这个领域还没人做**。

## 八、看完不抄（附理由）

| 东西 | 不抄的理由（一手依据） |
|---|---|
| **Search-R1 / RL 训练检索 agent** | 需要可训的 RL 管线与大量搜索 rollout（论文用 GRPO/PPO + 检索环境）；我们是单机 Electron + 用户自配 Key，没有训练面；每次查询多轮搜索，延迟随轮数涨 |
| **MUVERA（多向量→单向量）** | 现在没有多向量底座；我们的向量通道本身是弱项，先解决底座（C 线结论）再谈质量 |
| **StructRAG 整体** | 每问一次要 LLM 重构全部相关文档；重构结果是生成文本、不能引用；只在「统计/对比类」上借形态 |
| **AutoSchemaKG 的自动 schema 归纳** | 5,000 万文档级抽取成本；标准域已有 GB/T 46686.1-2025 当本体来源（F 线）；LLM 断言的边 ≠ 公告级确定性效力边 |
| **生成式检索整体（含 ACID、GCSR）** | 语料天天变 ⇒ 要重训 + 全库重建索引；ACID 只把否决理由缩小到「重训成本」，不改变结论 |
| **语义切分 / Lumber / RAPTOR 级联** | SemChunk：收益不一致；German：结构切分显著更好且快 3~4 个数量级；RAPTOR 建索引 3–6 小时 |
| **固定长度切分** | German：固定 256/64 Recall@10 最低；我们本来就不这么切 |
| **用长上下文替代检索** | NoLiMa：32K 处 11/13 模型掉到基线一半；Dense Contexts：高密度上下文掉到 60% 以下；我们全库 2.2 TiB |
| **Cohere/通用 cross-encoder 重排（无差别上）** | LegalBench-RAG：法律文本上重排比不重排更差；GAR 复现：非推理重排器会掉分；我们本机已实测 `rerank=False` |
| **RM3 / 伪相关反馈** | D 线已判死（UAmsterdam、DS@GT 两处反证），本轮无新反证 |

## 九、对不上的地方（来源互相矛盾，单列不抹平）

1. **BRIGHT 自己的正文与表格不一致**：§4.2 原话「the best model achieving only 24.3 nDCG@10」，但 Table 2 逐模型平均最高是 gte-Qwen **22.5**（SFR 18.3）。可能是 24.3 取自另一配置（如推理步骤查询或集成）。**本文引用一律用 Table 2 的逐模型值**，24.3 只作正文陈述记录。
2. **LegalBench-RAG 的文档数两处不一致**：正文写「714 documents」，Table 2 四个数据集相加是 **72**（18+18+29+7）。我按 Table 2 记 72；716/714 可能是包含其余语料。**未解决**。
3. **「语义切分到底行不行」三处结论方向不同**：SemChunk 说「计算成本换不到一致收益」；German 说「语义聚类居中游、不如结构切」；DenseX 说「越细越好（命题 > 句 > 段）」。**三者语料不同，不能合成一个结论**——能站住的只有「语义切分在拼接长文上赢、在原生有结构文本上输」。
4. **重排是正收益还是负收益，四篇打架**：BRIGHT（+3 分）、DOS RAG（多阶段不如简单）、LegalBench-RAG（法律文本上更差）、GAR 复现（只有推理型重排器受益）。**一致的部分**是「重排器自身能力决定成败」，**不一致的部分**是「通用重排器在专域是否可用」——这与我们实测 `rerank=False` 同向，但不足以推出「永远不加重排」。
5. **LePaRD「分类式检索最好」与 F 线「BM25 是强基线」不是同一任务**：前者是「长论证上下文 → 判例段落」（查询长、候选大），后者是「短提问 → 法条」。别把两条并成「分类优于字面」的通用结论。
6. **NoLiMa 的「有效长度 ≤2K」是针式任务结论**，与 DOS RAG 在 30K token 上拿 93.1% 不冲突：前者测「无字面重合的隐式联想」，后者测「单文档问答」。**引用时必须写清任务类型**，否则会得出「长上下文没用」这种过度结论。
7. **LongCite 正文与表格口径**：正文说「proprietary LLMs 在 LongBench-chat 和 HotpotQA 上 citation F1 只有约 0.5」，Table 2 里 GPT-4o 的 LongBench-Chat F1 是 **79.8**、HotpotQA **53.4**。⇒ 0.5 只对 HotpotQA 成立，正文表述过宽。

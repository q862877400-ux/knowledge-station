## 结论先行（≤15 行）

1. **法律开源四家（ChatLaw / LaWGPT / DISC-LawLLM / 智海-录问）没有一家做「条款级引用可点回原文」**：条文号是**答案里的文本**，不绑定文档/页/坐标。四家里只有 DISC-LawLLM 接了检索，且检索件是外借的 Langchain-Chatchat，法条库只有 **800 多部**法律条例【一手，README】。
2. **把「款级效力关系」做到生产级的不是法律 AI，是英国国家档案馆的 legislation.gov.uk**：一条 effect =（被影响法规 + **被影响条款** + 影响类型 + 施影响法规 + **施影响条款** + 生效日期 + **是否已并入正文** + 人工校正状态），粒度实测到 `s. 121(2)(b)(i)` 与 `Sch. 2 para. 25(a)`【一手，CSV 实抓】。
3. **但代价也是一手的**：2012/13 年度 **128,648 项待处理变更**；议会年产约 15,000 项、内部产能约 10,000 项；承诺「生效后 3 个月内并入正文」；脱欧一次 **10 万+ 修正同日生效**【一手，官方 help/年度报告转述】。⇒ **效力关系是永久运维债，不是一次性建模**。
4. **KAG 的「逻辑形式求解」确实赢多跳事实问答**（HotpotQA/2Wiki/MuSiQue 平均 EM 55.6 / F1 67.0），但**没有任何法律或标准域的证据**；它落地的最大真实规模是支付宝政务 **11,000 篇文档**、492 条样本【一手，论文 §4.1】。
5. **「图谱真被用到」有硬反证**：KAG issue #363（19 条评论）用户实测所有自带 example 的精确匹配（`get_spo`）全空，回答**全走文档检索**；issue 已关闭但最后一条评论（2025-03-19）仍在追问根因，维护方未给统一解释【一手，gh api】。
6. **KAG 代码近乎停摆**：最后一个功能发布 v0.8.0 = 2025-06-28，其后只有零星修复（仓库最后提交 2026-01-28）；组织重心转到 KAG-Thinker（2025-11-14）【一手】。
7. **中文法条检索的公开基准（STARD，1,543 条口语化咨询 / 55,348 条法条）实测**：BM25 H@20 = **0.343**；零-shot 通用中文 BGE **0.443**；**法律领域预训练的 SAILER 0.236、Lawformer 0.257，反而低于 BM25**；在 STARD 上微调的稠密检索 0.507；生成式 GCSR 0.547【一手，arXiv 2607.11109 Table 2】。
8. 这条数据与我们实测「大白话提问 53% 与原文零字面重叠」互相印证：**字面检索在口语化提问上就是弱**（34% H@20），不是我们的实现问题，是这类语料的固有难度【一手 + 本仓实测】。
9. **生成式检索是目前最好的一路，但它把语料烧进模型参数**：语料一变就要重训。我们的语料（现行法规）天天变 ⇒ 这条路在我们这里是自伤【推断】。
10. **「条款级知识图谱」国内学术界已经做过一次**：LegalLPP，4,042 部法 / **269,053 条条文**，但它的边只有 `belongs_to`（182,624）+ 事务链接（4,526 + 2,152 + 1,090），**一条效力/版本关系都没有**；版本更新被当噪音**过滤掉**了【一手，arXiv 2104.02284】。
11. **中国的「标准知识图谱」已有现行国标**：GB/T 46686.1-2025《标准知识图谱 第1部分：实现指南》，2025-12-02 发布、2026-07-01 实施、44 页，归口 SAC/SWG 29。要建标准图谱，本体应当照它，不必自己发明（**正文未读到，未取证**）【一手，官方标准页面】。⚠ **2026-10-25 复核后分档更正**：**编号 / 名称 / 推标性质 / 现行状态 / 发布 2025-12-02 / 实施 2026-07-01** 已在**官方 `openstd.samr.gov.cn`** 核实（比原报告的第三方页更硬）；但「**44 页**」与「**归口 SAC/SWG 29**」**只在第三方站 spc.org.cn**（直取 403、jina 422），官方列表页不含这两个字段 ⇒ **这两个字段未取证，不许当依据**。⚠ **本仓知识站库里没有这份标准**——`ks_resolve_clause("GB/T 46686.1-2025","1")` 返回 404 `clause_not_found`，`ks_answer` 也检索不到它 ⇒ 在入库之前**整条只能当"去查它的线索"**，不得当依据引用。（取用渠道不属调研范围，见 §九 口径。）
12. **国标「被代替/废止」数据源存在但要分清谁说的**：**第三方**标准信息站的标准详情页有「被替代标准」「标引依据：国家标准公告…」字段（例：GB/T 46686.1-2025 页面）；**官方** std.samr.gov.cn / openstd.samr.gov.cn 我实抓的两个页面**都没有出现「被代替」字段**。⇒ **官方有没有可直接用的开放接口 = 未取证**。另有商业查新 API 在卖，返回字段含 `replacedby`（历次版本数组）与 `ObsoleteDate`，来源与准确率**均未取证**【一手（第三方页面）+ 未取证（官方接口、商业接口）】。
13. **表格上可抄的是一件小事**：QAnything 2.0 在跨页长表**拆分时把表头复制到每一段顶部**；超长小节拆分时**在每段前重复同一小节标题**以保归属。这正是我们国标里跨页大表的真痛点【一手，README】。
14. **许可证两个雷**：QAnything 的**默认分支 `qanything-v2` 是 AGPL-3.0**（`master` 分支还是旧的 Apache-2.0，两处 README 徽章互相矛盾）；ChatLaw 也是 AGPL-3.0，LaWGPT 是 GPL-3.0【一手，两分支原文对比】。
15. 总判断见下一节。

## 总判断：「知识图谱 + 逻辑求解」该不该投

**投，但只投薄的那一半：关系边和状态值钱，通用图数据库与通用逻辑形式求解器不值钱。**

### 支持投（有证据）

1. **我们的语料是「强编号 + 强结构 + 强状态」的**。这类语料的信息不在语义相似度里，在**编号**和**状态迁移**里。「这一条现在还有效吗」「被谁改过」「引用的那条还在不在」——用向量永远答不对，用一条边能答对【推断】。
2. **我们现在的图等于没有**：已有 22,992 条证据边，**跨文档 0 条**，有边条款仅 **4.93%**（本仓实测，见 `00-brief.md` §三）。这张图是文档内自环。补边的正确方向不是让 LLM 抽三元组，而是**照 legislation.gov.uk 的 effect 表去填**：两端都精确到条款号，加一个 applied 状态位【一手结构 + 推断】。
3. **本体不用自己设计**：GB/T 46686.1-2025 已经给出标准知识图谱的构建 / 应用 / 更新框架（44 页）——省掉最贵的一步【一手，仅读到范围描述】。
4. **真正有用的「逻辑求解」只是一小块可枚举判定**：取代链传递闭包、被废止后不再召回、被引条款是否仍现行、强制性条文标记的继承。这些是 SQL 递归 CTE / 闭包表的活，不是 LLM 推理的活【推断】。
5. **数据本身是小的、可枚举的**：3 万国标的被代替关系，每条至多几次，总边数是**几万条量级**，且来源是公告（确定性、可审计）。法规修订也一样。**贵的不是数据，是把修订合并进正文**（这一点英国用 128,648 项积压证明了）【一手量级 + 推断】。
6. **GCSR 的 docid 设计反向验证了我们的方向**：它把「法部门 ⊕ 子类 ⊕ **条款功能类型** ⊕ **法律层级** ⊕ **涉及客体** ⊕ 简称 ⊕ 摘要」拼成一个可解析 ID，检索目标就是 ID 本身、再确定性映射回条文。其中「条款功能类型」和「涉及客体」几乎就是我们六通道里的「法理要素」和「行为客体」【一手 + 推断】。

### 反对投（也有证据）

1. **KAG 那条路（LLM 抽知识单元 → 图索引 → 逻辑形式规划/求解）没有法律或标准域证据**；最大落地是政务 11,000 篇文档；社区有硬反证说明图谱没被真正调用（issue #363）【一手】。
2. **KAG 的成本结构对我们是灾难**：KAG 官方 benchmark 自报，在 UltraDomain cs.jsonl（**10 篇文档 / 100 个问题**）上构建 **4,800 秒 / 700.6 万 tokens**，比 LightRAG 贵 41% 时间、58% tokens；摘要任务三项指标（Comprehensiveness 7.57 vs 8.87、Diversity 6.87 vs 8.28、Empowerment 7.54 vs 8.53）**全部输给 LightRAG**；且官方自承「HotpotQA 上 LightRAG、GraphRAG、KAG 的 EM 都是 0」【一手，官方 benchmark 页】。按百万条款线性外推，抽取成本是灾难级【推断，量级未算】。
   - ⚠ **2026-10-25 复核后降档（原话保留，不删）**：复核员**回不到原始页**——KAG 论文（arXiv 2409.13731）HTML 全文搜 `UltraDomain` / `4,800` / `700.6` **全 0 命中**，仓库 README 也没有，而本条当时**没给出"官方 benchmark 页"的 URL**。可独立确认的只有：「UltraDomain cs.jsonl = 10 篇 / 100 问」这一点在仓库 `kag/examples/csqa/README_cn.md` 里有。
   - ⇒ **本条的正确档位是【转述，未回原文】**，不是【一手】。**判断不变**（KAG 在我们这个量级上成本不可行），但**"4,800 秒 / 700.6 万 tokens / 41% / 58% / EM=0"这组数字在拿到原始页之前不许当引用依据**。
3. **英国的代价说明最狠的一条**：这不是模型问题，是**编制问题**——每年进来 15,000 项，能处理 10,000 项，积压 128,648 项。我们只有业主一个人做校对，任何「逐条人工确认效力」的设计在规模上直接死【一手数字 + 推断】。
4. **GraphRAG 系的增量在「全局摘要 / 多跳」，不在「点回那一条」**。我们 90% 的问题是找**那一条**，不是找全景图。独立评测也指向同一处：`Is GraphRAG Needed?`（ACL GEM 2026）发现「检索扩大并不能按比例改善生成质量，面向检索的指标高估了高级检索的收益」【一手，ACL Anthology 摘要】。
5. **字面检索在这个域已经是强基线**（BM25 高于零-shot 法律专用编码器），而这个能力我们已经有了（FTS5 35.6 ms、精确条款号 0.1 ms）。堆图谱改善不了这条通道【一手 + 本仓实测】。

### 落地的具体形态（不是「上一套知识图谱」）

1. **抄表不抄引擎**：按 legislation.gov.uk 的 effect CSV 字段建一张 `clause_effect` 表（放 SQLite，不引图数据库）：`affected_doc / affected_clause / effect_type / affecting_doc / affecting_clause / in_force_date / applied / editor_state`。
2. **数据来源按可靠度排序**：① 官方公告与标准详情页的「被代替」字段（确定性）；② 法规正文里的「依照《X》第 Y 条」（**正则召回候选，不做 LLM 断言**）；③ 才考虑 LLM 抽取。
3. **求解只做闭包查询**：递归 CTE 算取代链、废止继承、引用可达，不引逻辑形式求解器、不引 SPARQL/Cypher。
4. **明确不投**：全文修订版正文合并（英国最大成本项，我们不需要）；KAG / OpenSPG（要 TuGraph 或 Neo4j + ES 或 Milvus，与单机 Electron 冲突，且项目近停摆）。

## 逐个点评

### KAG（蚂蚁 OpenSPG）
- 是什么：基于 OpenSPG 引擎的「逻辑形式引导的混合推理与检索」框架 / 谁维护：蚂蚁集团 + OpenKG / 许可证：**Apache-2.0** / 最后提交：**2026-01-28**（9,123★）；最后功能发布 **v0.8.0 = 2025-06-28**
- **规模**：论文实验用 HotpotQA / 2WikiMultiHopQA / MuSiQue，**各取验证集 1,000 条问题**、语料是 IRCoT 的 Wikipedia 检索语料【一手，论文 §3.1】。真实落地最大是支付宝政务：**11,000 篇文档**，492 条样本，NaiveRAG 精确率 66.5 / 召回 52.6 → KAG 91.6 / 71.8；医疗端是 **180 万实体 / 40 万术语集 / 500 万关系 / 700 条 DSL 规则**，抽样在线 query 召回 60.67% / 精确 81.32%【一手，论文 §4.1/§4.2】。**注意口径：180 万是图谱实体数，不是条款数**，不能当成「支撑百万条款」的证据。
- **表格 / 图 / 公式 / 上下标**：完全未涉及。它的解析走文档分块 + OpenIE 抽取，README 与论文均无表格结构化、公式 OCR 的任何表述【一手，两处均扫过】。
- **中文法规/国标**：**无**。论文只报了政务与医疗两个域；仓库 `kag/open_benchmark/` 下是 2wiki、AffairQA（浙大政务）、csqa 等，**没有法律数据集**【一手，仓库树实测】。
- **引用可回溯**：**这是它唯一值得我们细看的设计**。其「互索引」把 `Chunk` 当成一等实体节点，与知识单元之间建 `supporting_chunks / summary / description` 边，形成「基于图结构的倒排索引」；chunk 的 ID 由 `articleID + paraCode + idInPara` 组成，论文明确写「内容上的相邻对应 ID 上的顺序相邻」【一手，论文 §2.1/§2.2】。这跟我们的「条款一行 + 精确条款号」是同一个思路，且它承认必须回到 chunk 才算完整。
- **对我们**：
  - **抄一句做法**：「图节点必须能反向指回原文块，且原文块 ID 自带层级」。我们已经有，不用抄代码。
  - **逻辑形式求解器不抄**：它依赖 TuGraph/Neo4j + ES/Milvus（论文 §2.2.4 明写 LPG 数据库与向量库），且实测常退化成文档检索（issue #363）。我们要的那点闭包查询用递归 CTE 就够。
  - **代价**：引入 OpenSPG 要一台常驻服务，直接与「单机 Electron 拷走就能用」冲突；这是硬冲突，不是偏好问题。

### KAG-Thinker（蚂蚁，KAG 的后续重心）
- 是什么：「交互式思考与深度推理模型」，给复杂多跳问题提供认知推理范式 / 谁维护：蚂蚁 OpenSPG / 许可证：Apache-2.0 / 最后推送：**2025-11-14**（92★）
- **规模 / 表格 / 中文法规 / 引用**：全部未取证（本轮只核了元数据）。
- **对我们**：**只登记**。它是 KAG 团队活着的部分，但它是**模型**不是工程件，与我们要解决的事（条款库检索与引用）不在一条线上。若将来要追 KAG 的进展，看这个仓库而不是 KAG 主仓。

### QAnything（网易有道）
- 是什么：本地文档问答系统（检索 + 重排 + LLM）/ 谁维护：网易有道 / 许可证：**AGPL-3.0**（默认分支 `qanything-v2`）/ 最后推送：2026-09-23（14,210★）
- **规模**：README 宣称 "massive data question and answer… **no limit on the number of uploaded files**"——**没有任何文档数、条数或吞吐数字，是营销句**【一手】。硬件门槛：**RAM ≥ 20 GB**，依赖 Milvus v2.4.8【一手，README 部署节】。
- **表格 / 图 / 公式 / 上下标**：表格做了真事——2.0 版「分析表格行列布局、**自动识别表头并放到每个拆分片段的顶部**」以解决长表跨页被截断；「正文里夹的表格」能识别成表格而不是段落。图：能识别并保存正文内图片。**公式、上下标：未取证**【一手，README「新旧解析效果对比」节】。
- **中文法规/国标**：无专门处理。但有一条可迁移的规则：**超长小节拆块时，在每一块前重复同一小节标题以标明归属**（README 举的例子标题是 "European Conference: Legal Status of Robots"）【一手】。国标里「一条下面挂 30 页表格」正是这个场景。
- **引用可回溯**：v1.4.0 提到 "file traceability preview"（文件溯源预览），**粒度未取证**（没读前端源码）。
- **对我们**：**代码一行都不抄（AGPL）**。抄两条解析规则（表头复制、小节标题复制），是纯规则，不涉许可。**两阶段检索这件事**：它的理由（只有一阶段 embedding 检索会随数据量增长而退化，加二阶段重排后稳定提升）与我们实测的「候选集是瓶颈、收到 50 条时前 20 命中 99%」是同一件事，**但我们已有 RRF 六通道，不需要它**。

### BISHENG（dataelement）
- 是什么：企业级 LLM 应用平台（工作流 + RAG + Agent + 评测 + 数据管理）/ 谁维护：dataelement（北京数据项素）/ 许可证：**Apache-2.0**（LICENSE 文件是标准 Apache 2.0 全文）/ 最后推送：2026-10-24（12,075★，活跃）
- **规模**：README **无任何文档数或吞吐数字**。最小配置 4 vCPU / 16 GB；推荐 **18 vCPU / 48 GB**，**默认捆绑 ES + Milvus + OnlyOffice**【一手，README 快速开始】。⇒ 这是「一套要你专门养的中台」，不是零件【推断】。
- **表格 / 图 / 公式 / 上下标**：只给了一句「文档解析模型基于 5 年积累的高质量数据训练，含印刷体、手写体、生僻字、**表格识别**、版面分析、**印章**」，配一张 OCR 效果图，**无任何量化指标（准确率/速度）**【一手】。公式、上下标、图表未提。
- **中文法规/国标**：无。【一手】

- 是什么：STARD = 首个中文**法条**检索基准（来自真实公众法律咨询）；GCSR = 把法条检索改成**序列生成**的框架 / 谁维护：清华 THUIR（Yiqun Liu、Min Zhang、Qingyao Ai 等）/ 许可证：**未取证**（论文与数据集许可未核）/ GCSR 论文 2026-07-13 提交（arXiv 2607.11109）

- **中文法规/国标**：**这是最对口的一篇**——它专门处理「口语化提问 ↔ 正式法条语言」的鸿沟，且 docid 明确编码了法律层级（国家法律 / 行政法规 / 司法解释）。

- **核心结果（Table 2，H@3 / H@5 / H@10 / H@20）**【一手】：

  | 类别 | 模型 | H@3 | H@5 | H@10 | H@20 |
  |---|---|---|---|---|---|
  | 稀疏 | QL | 0.305 | 0.318 | 0.330 | 0.339 |
  | 稀疏 | **BM25** | **0.319** | **0.324** | **0.337** | **0.343** |
  | 预训练稠密 | RoBERTa（zh-wwm） | 0.273 | 0.285 | 0.293 | 0.299 |
  | 预训练稠密 | **BGE** | **0.411** | **0.424** | **0.439** | **0.443** |
  | 法律专用 | SAILER | 0.201 | 0.214 | 0.223 | 0.236 |
  | 法律专用 | Lawformer | 0.220 | 0.231 | 0.241 | 0.257 |
  | 微调稠密 | Dense（STARD 微调） | 0.468 | 0.486 | 0.495 | 0.507 |

  - **抄**：docid 的**分层字段序**（法部门 ⊕ 子类 ⊕ 条款功能类型 ⊕ 法律层级 ⊕ 涉及客体 ⊕ 简称 ⊕ 摘要）。其中「条款功能类型」与「涉及客体」几乎就是我们六通道里的「法理要素」和「行为客体」——**独立第三方验证了这两条通道是对的方向**【一手 + 推断】。

  - **代价**：STARD 的许可与获取方式未核，不能直接拿来做我们的验收集；要自建同等口径的评测集，需要「真实口语化提问 + 条级金标」，而后者我们正好没有（有边条款仅 4.93%）。

### 条款级知识图谱的现成做法 I：legislation.gov.uk 的 effect 模型（英国国家档案馆）
- 是什么：英国官方法律数据库的「变更（effects）」数据模型与开放接口 / 谁维护：The National Archives / 许可证：**Open Government Licence v3.0（OGL）**，站点声明另有 EUR-Lex 内容按其条款
- **规模**：站点覆盖 1988 年至今全部初级立法；**2012/13 年度报告记录 128,648 项待处理变更**；议会年产约 15,000 项、内部资源可应用约 10,000 项；**一次脱欧有 10 万+ 修正于 2020-12-31 同日生效**【一手页面陈述 + 该页引用的年度报告，报告本体未读】
- **表格 / 图 / 公式 / 上下标**：不适用。
- **中文法规/国标**：不适用，但**这是我看过的唯一把「条款级效力关系」做成可机读表的公开系统**。
- **引用可回溯**：**到款/项级**。实抓 `changes/affected/ukpga/2010/15/data.csv`（2010 年平等法），字段为：
  `ID, Affected Legislation, Affected Provision(s), Type of Effect, Affected Extent, Affecting Extent, Affecting Legislation, Affecting Provision, RA Date, IF Date, Sav, U, R, Notes, Amendment applied to Database, Welsh Amendment applied to Database, Effect captured by GATE (Y/N), Effect corrected by editor, Effect rejected by editor (false positive), Effect on secondary legislation, Textual or Non Textual Effect (T/NT/CO), Other Information, ...`
  实测样例：`s. 121(2)(b)(i)` ← 由 `2025 c. 023 Sch. 2 para. 25(a)`「words substituted」；`Sch. 19 Pt. 1` ← 由 `2023 c. 055 Sch. 4 para. 197`「words inserted」【一手，2026-10-25 实抓 CSV】
- **对我们**：**这是本线最该抄的东西，抄字段表**。三条直接可用的判断：
  1. **effect 是边，不是属性**：两端各带条款路径，中间带类型（inserted / substituted / words inserted …）。
  2. **必须有 `applied` 状态位**：官方明写「未应用的 effect 会在页面上打横幅提示」——**承认修订文本可能落后于 effect 记录**。我们要照抄这个「知道自己落后」的设计，否则会出现「系统说已废止，但用户点开原文还是旧的」这种最难解释的状态。
  3. **必须有「人校正」字段**：`Effect captured by GATE` / `corrected by editor` / `**rejected by editor (false positive)**`——**自动抽取会产出假阳性，必须留一个可以否掉的位**。这一列是「自动抽效力关系」这件事成熟度的最直接度量，也是我们不该指望全自动的证据。
  4. **代价**：英国是**有编辑编制**做这件事的（承诺生效后 3 个月内并入正文）。我们做的是**窄得多的版本**——只标注状态、不合并正文，所以不需要那个编制；但**这条边界必须写死，一旦越界去做正文合并，就变成 128,648 项积压那种工程**。

### 条款级知识图谱的现成做法 II：LegalLPP / Text-guided Legal Knowledge Graph Reasoning
- 是什么：把「法条预测」形式化成法律知识图谱上的链接预测 / 谁维护：中山大学等（arXiv 2104.02284）/ 许可证：论文称 release dataset + code + 预训练模型，**具体许可未取证**
- **规模**：从广东政务服务网采集 **4,042 部法 / 269,053 条法条**，另有约 140,482 条事务（1,552 个唯一事项）【一手，论文 §2.1】。
- **图谱 schema（论文 Table 2）**【一手】：

  | 关系 | 边数 | 含义 |
  |---|---|---|
  | `belongs_to` | **182,624** | 法条属于某部法 |
  | `base_entry_is` | 4,526 | 法条与事务相关 |
  | `base_law_is` | 2,152 | 法与事务相关 |
  | `right_is` | 1,090 | 事务对应的权利 |

- **中文法规/国标**：**这是国内唯一公开过规模的「条款级法条图谱」**，且它撞上了和我们一样的墙——论文如实写了两类原始问题：① 引用写法不规范（简称「劳动法」=《中华人民共和国劳动法》的简称、缺书名号、带版本后缀如「（2014年修正本）」），**他们靠人工建法条词典来归一**；② **法条会随时间变化，旧条文被删导致事务挂不上法条**，「this problem is mainly due to **outdated laws**」——**他们的处理是「过滤掉挂不上的事务」**【一手，论文 §2.1】。
- **引用可回溯**：节点就是法条，**天然条级**；但没有回到 PDF 页/坐标的机制（数据源是网页）。
- **对我们**：**这张表说明两件事，都会改变我们的判断**：
  1. **「条款级图谱」的边很少**：26.9 万条法条，主边 `belongs_to` 18 万条——**平均每部法只有 45 条边，每条法条平均 0.7 条边**。也就是说**光靠「条文属于哪部法」撑不起一张有用的图**。有用的边必须是效力/互引，而这两类**一条都没有**。
  2. **「版本变化」在这个领域被当噪音处理掉了**：他们把过时法条导致的事务挂不上**直接过滤**。⇒ **学术界到现在没有解决「效力状态」这个问题，是绕过去的**。这是我们判断「值得投」的关键：**它没人做对，所以是差异化，不是重复劳动**；但它也没人做过，所以我们**没有免费的路**。

### 条款级知识图谱的现成做法 III：GB/T 46686.1-2025《标准知识图谱 第1部分：实现指南》
- 是什么：**中国国家标准**，给标准数据预处理 + 标准知识图谱（SKG）的构建、应用、更新提供指导，含 SKG 本体构建示例与行业应用参考实例 / 谁维护：归口 **SAC/SWG 29 全国标准数字化标准化工作组**；起草单位含中国电子技术标准化研究院、中国标准化研究院、同方知网、南京柯基数据等 40 余家 / 许可证：标准文本受版权保护，非开源
- **状态**：2025-12-02 发布、**2026-07-01 实施**、**现行**；44 页 / 69 千字 / ICS 35.020 / CCS L70【一手，openstd.samr.gov.cn 与 std.samr.gov.cn 两个官方页面一致】
- **规模 / 表格 / 图 / 公式 / 上下标 / 引用可回溯**：**全部未取证**——只读到官方页面的「范围」一段，**没有正文**（标准正文要购买）。
- **中文法规/国标**：**它就是讲这个的**。
- **对我们**：**这是本线最重要的一个「别人已经做对了、我们可以直接抄」的入口**。理由：我们要在 3 万国标上建图谱，而中国**已经有一份现行的国标在讲「标准知识图谱该建成什么样、怎么更新」**。按本仓规矩「先查有没有现成的，再决定要不要自己写」，它的价值是**省掉自己发明本体**；前提是拿到正文（⚠ **采购/取用渠道不在调研范围内**——业主 2026-10-25 已说明自己有公开渠道）。**代价**：在拿到正文之前，本报告对它的所有说法都只到「它存在且管这件事」，**不等于我们知道了它的 schema**。⚠ 另：**它是不是有第 2、3 部分（46686.2 …）未查**，见待核清单。

### 条款级「真值库」的最小样本：verified-chinese-law-kb
- 是什么：律师逐条核验 + 具名签署 + 带版本轴的中文法条模块化库 / 谁维护：个人（vickywu97，律师+税务师+专利代理师）/ 许可证：**MIT** / 最后推送：2026-09-16（**1★**）
- **规模**：**8 部法 / 2,327 条**已发布（另有著作权法模块在内部准备）【一手，README】
- **中文法规/国标**：它的字段正是我们要的：每条带 `effective_date` 与 `revision_of`，另有 `knowledge_base/deprecated_laws.json` 专门标「失效/被吸收」的法律名称陷阱；核验留痕在 `verifications.json`（核验人 + 来源 + 日期）【一手，README】。
- **引用可回溯**：条级，回到「官方来源」而非页/坐标。
- **对我们**：**不能当基础设施（8 部法、1 星、个人项目），但它的字段设计值得照抄**：`effective_date` + `revision_of` + 具名核验留痕 + 单独的「名称陷阱」文件。最后这一项对我们特别有用——**法规改名/被吸收（如「民法典」取代九部法）是条款号检索最容易出错的地方**。它自己声称的下游基准 `legal-hallucination-bench` 报「5 个主流模型基础法条引用幻觉率 33.3%–54.2%、增值税域 0%」⇒ **只作【转述】，未复现，不采信为事实**。

## 对不上的地方（来源互相矛盾，单列，不抹平）

1. **QAnything 的许可证，同一个仓库两个答案**。默认分支 `qanything-v2` 的 `LICENSE` 是 **AGPL-3.0**、README 徽章写 `AGPL-3.0`；但 `master` 分支的 `LICENSE` 是 **Apache-2.0**、README 徽章写 `Apache-2.0`。GitHub API 报的 `AGPL-3.0` 是按默认分支算的。⇒ **任何按旧链接/旧分支评估这个项目的人都会得出「Apache-2.0，可抄」的错误结论**。以默认分支为准：**AGPL-3.0**【一手，两分支原文逐字对比】。
2. **KAG 的「显著优于 SOTA」与它自己官方 benchmark 页对不上**。论文摘要说 2wiki 相对提升 19.6%、hotpotQA 33.5% F1；而官方 v0.6 benchmark 页的对比表里，**GraphRAG 与 LightRAG 两行各只有「0 0 0 0」四个数**（KAG 行有 8 个数：三数据集 + 平均的 EM/F1）。⚠ 这可能是抓取时丢格，也可能原页面就没给全——**无论哪种，我都无法从该页取到这两个基线的可比数字**。同一页还自承「用 HotpotQA 构建和测试发现，LightRAG、GraphRAG 和 KAG 的 EM 都是 0」。⇒ **「优于 SOTA」这句话在这份官方页面上拿不到支撑**；能站住的只有「KAG 在多跳事实问答上 EM/F1 = 55.6/67.0」【一手，两处对照 + 抓取完整性存疑】。
3. **KAG 说「克服了传统 RAG 的向量相似度问题」，但实测用户说图谱没被调用**。issue #363 里多名用户报告 `get_spo` 精确检索恒空、回答全走文档检索；有人定位到「chunk 类型混进实体召回」和「同属性实体向量互相覆盖」。**维护方未给统一结论**，issue 被关闭。⇒ 不能断言「KAG 的图谱一定不工作」，但也**不能把「逻辑形式求解」当成已验证的能力**。这条我只主张「未验证」，不主张「假的」【一手，gh api】。
4. **「法律领域预训练编码器」到底有没有用，两处数据相反**。LeCaRDv2（案例检索）零-shot：BM25 R@100 = 0.6262 > 所有神经模型，含 Lawformer 0.2432；STARD（法条检索）GCSR 表：BM25 H@20 = 0.343，**低于**零-shot 通用 BGE 的 0.443，**也高于** SAILER 0.236 / Lawformer 0.257。⇒ 一致的部分是「**BM25 是强基线、法律专用零-shot 编码器不如它**」；不一致的是「通用稠密检索能不能赢 BM25」——**案例检索上不能，法条检索上能（BGE 0.443 vs 0.343）**。可能的解释是任务不同（长文书间相似 vs 短条文匹配），**但我没有证据，标【推断】**。
5. **另一篇（HSP，海事法，IEEE 2026）给的方向相反**：它报 Recall@10 从 **BM25 57.2%** 和 **稠密 61.6%** 提到 73.3%——即**稠密本来就高于 BM25**，且最大贡献来自「查询改写」而不是图。⇒ 与 LeCaRDv2 的「BM25 最高」冲突。差异可能来自语料（自建海事法基准 vs LeCaRDv2），**未能对齐，标未确认**【一手摘要页】。
6. **「知识图谱有用」这件事本身，证据方向不一致**。支持方：GraphRAG 相关独立评测称在实体关系查询上准确率提升 3.4 倍（我**只读到二手汇总**，未核原论文）；反对方：`Is GraphRAG Needed?`（ACL GEM 2026）指出「检索扩大不按比例改善生成质量，检索类指标高估了高级检索的收益」。**两边我都只读到摘要**，**均标【一手摘要 / 结论本身未交叉验证】**。

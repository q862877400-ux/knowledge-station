## 结论先行（≤15 行）

1. **工业界的第一个瓶颈是内存（DRAM），不是分片、不是解析、也不是「检索算法不够快」。** 小红书线上纯内存 HNSW 占到 **0.35 PB DRAM**（搜索 0.8 PB、推荐 0.3 PB、广告 20 TB，知乎/头条转述），用 40 台全闪存替掉约 **35,000 核 + 0.35 PB DRAM**、硬件成本省 >90%【一手·原文：arXiv 2606.13145 摘要，OSDI'26】；Pinterest 1 亿向量基线 HNSW 索引 **121 GB**、量化后 25–50 GB【转述：InfoQ 报道 Pinterest 工程博客】。**分片是所有人的常态，没有一家把它写成瓶颈。**
2. **第二个瓶颈是「过滤」——元数据/租户/权限过滤把 ANN 的账算崩。** 美团外卖 10 亿级向量、ES+FAISS 混合检索，明写 **HNSW 在「高过滤比」下性能折损**（强 LBS 场景）【一手·转载：美团技术团队原文，tech.meituan.com 原链 404】；Airbnb 放弃 HNSW 改 IVF，理由逐字是「大量实时更新 + 高区分度过滤」【一手·原文：arXiv 2601.06873 §7】；Bazaarvoice 从 pgvector 迁走的理由：**上亿向量下后过滤等于把整库搜一遍**（「为什么要搜十亿条，我只需要搜一万条」）【营销，一手·原文：Qdrant case study】。
3. **第三个瓶颈是索引构建时间，它被普遍低估。** 小红书 100 亿向量索引重建「数小时」（GPU 流水线）【一手·原文：arXiv 摘要 + 转述细节】；Pinterest 用 SIMD 线性缩放 SQ 才把查询算力降 10–15%【转述】；Zilliz 自己承认 Elasticsearch「光优化索引就要 20 多小时」【一手·原文：Zilliz 博客（厂商互攻，故可信度高于自夸）】；阿里指出 HNSW 多线程建图「并发 30 以上加速比就到顶」【转述：公众号】。
4. **「引用点回原文」的行业上限是「段落 + 页/URL」，没有人公开做到「条款 + 坐标」。** 最好的一档是 Atlassian Rovo：切 passage 时写入 **page-level metadata（URL + 文档标题）**，做到 **passage 级引用**（每条论断单独挂引用）【一手·原文：Atlassian 工程博客】。Notion 只到「链接到 Notion 文档」【一手·原文：Data Council 演讲逐字稿】。法律科技到「具体文档/条款摘录」【营销/转述】，Octus 存到了 **word-level bbox 的每页 JSON**，但不用于引用 UI【一手·原文】。⇒ **我们的「页 + 红色定位箭头」在公开实践里属于最细的一档；再往下一档（条款↔坐标）没人公开做过。**
5. **表格的生产做法只有一句话被两家独立说出：整份管道的地板在解析，不在检索。** 「没有 reranker 能捞回一个根本没被抽出来的数字，没有 embedding 能表示一张被 OCR 撕碎的表格」【一手·原文：Octus 工程博客】；微软金融文档 RAG 的做法是：Azure Document Intelligence 按页出结构 → 表格/图/文本各走专用处理 → **靠文档元数据（公司/财年/期数）过滤，而不是靠相似度**（几十份极相似的 10-K，纯向量必错期）【转述：ZenML 对微软分享的记录】。
6. **「单机不引外部服务能撑多大」有硬证据：单机 10⁷ 量级没问题，10⁹ 起必须集群。** SPANN 论文：内存只放质心、倒排落 SSD，**用 10% 内存拿到 ~1 ms 的 90% recall@1**，且「已部署进 Microsoft Bing 支撑数千亿规模」【一手·原文：arXiv 2111.08566 摘要】；但 Bing 的数千亿本身是集群，论文的「单机」是实验设定——**不能读成「单机能撑千亿」**。
7. **我们的量级（1000 万条款）正好落在「单机可撑」的边界内，前提是内存/磁盘混合 + 量化 + 过滤先行**——这三条正好是 Pinterest/小红书/SPANN/美团四家各自独立走到的地方，与 C 线的两段式结论同向。【推断，有上述四家一手数字支撑】
8. **ANN 不是免费的：它同时是性能旋钮和正确性风险，生产上是被场景逼着换算法，不是被 benchmark 逼着换。** Airbnb 明确写「我们起初对 HNSW 很兴奋，最终发现它不适合我们的流量模式」【一手·原文】。这与 C 线「ANN 在我们这里是正确性故障」相互印证，且给出了**换算法的判据**（更新率、过滤选择性、top-k 大小、SLA）。
9. **写放大是 RAG 知识库特有的成本项，普遍被忽略。** Notion：**100 亿 chunk，每月要写 150 亿条 embedding**（因为一页一个月内会改多次），峰值 **10 万条 embedding/分钟**，查询只有 **100 QPS** 峰值【一手·原文：Data Council 演讲】。⇒ 读写比是 1:1500 万，**知识库是写系统，不是读系统**。
10. **厂商 case study 只能取「失败模式」，不能取「性能数字」**：Elastic/Qdrant/Pinecone/Zilliz 的页面上没有一个数字带硬件、数据集、recall 目标三件套；且同一家厂商会公开攻击别家的 benchmark（Zilliz 骂「脱离生产环境的 benchmark 谁信谁输」）【一手·原文】。
11. **中文大厂的数字几乎全部是企业自述、无第三方复现**（阿里 950 万条 30 ms、百度 VectorDB「高于开源 7 倍」、字节 200 亿单库）。可用的部分：**它们选了磁盘/量化而不是加内存**，这条路线选择比数字可信。
12. **法律科技的公开技术面极薄**：Harvey 公开的是「agentic search + 60+ 法域/400+ 数据源」这类**流程**信息，检索实现（索引粒度、向量/混合、切分）一字未公开（E 线同结论）【一手·原文】；CoCounsel 公开的检索方式反而是 **keyword + boolean + terms-and-connectors + Parallel Search**，不是向量优先【转述】。

## 结论先行·补：四条必答问题的一句话答案

| 问题 | 一句话答案 | 最强证据 |
|---|---|---|
| 规模化检索的真实瓶颈 | 内存 → 过滤 → 索引构建 → 解析 | 小红书 0.35 PB DRAM→40 台闪存；美团 HNSW 高过滤比折损；Pinterest 121 GB 索引 |
| 谁做到「引用点回原文页/坐标」 | 无人公开到坐标；最细到「段落+页/URL」 | Atlassian passage 级 + page metadata；Octus 有 bbox 但不用于引用 |
| 表格/公式怎么落库 | 「解析定天花板」；表格当独立元素并保留结构，配元数据过滤 | Octus「tables as first-class」；微软 Azure DI 分元素处理 + 元数据过滤 |
| 单机 vs 集群 | 10⁷ 单机可撑（SSD+量化）；10⁹ 必须集群 | SPANN 10% 内存 / 1 ms；Notion 10B chunk / 15B 写入每月 |

## 逐个点评

### Pinterest（Manas 分布式搜索平台）
- 是什么：自研分布式检索平台，embedding retrieval 是核心能力；**80+ 集群**，服务首页信息流/搜索/相关 Pin/广告/通知【一手·原文：Pinterest 工程博客段落（经搜索工具抓回）；完整原文另见同文 InfoQ 报道】。
- **规模（数字）**：语料「正迈向数百亿 embedding」（tens of billions）；量化基准跑在 **1 亿 embedding 的 GraphSage 数据集**上【转述：InfoQ 2026-09-15 报道 Pinterest 工程博客（我未读到 Pinterest 原文页面）】。
- **量化实测（同一份报道，口径=索引大小/Recall@100/QPS，无硬件说明）**：HNSW 基线 **121 GB / 93.72% / 302.5 QPS**；HNSW+PQ **32 GB / 77.25% / 276.4**；HNSW+SQ **50 GB / 92.92% / 305.2**；IVF 基线 **97 GB / 91.69% / 1659.8**；IVF+PQ **6.8 GB / 76.00% / 1747.9**；IVF+SQ **25 GB / 95.71% / 1588.8**【转述】。
- **SSD 服务**：SPANN+PQ 相对 DiskANN **3× QPS、1/3 延迟、召回只掉 5%**；5 亿 embedding 的推荐场景里 SPANN 比纯内存 HNSW **省 40% CPU**；线上量化落地后服务成本降 **20–30%**【转述】。
- **表格/公式/中文法规/引用**：不适用（推荐/搜索语料，不是文档库；无表格结构、无条款、无引用回溯）。
- **对我们**：**抄它的判据，不抄它的栈**。可借：①「索引大小 ÷ 召回」的**权衡表写法**（我们评估 int8/二值时应照这个格式给数字）；②**SSD 承载 + 小质心驻内存**的方向，与 sqlite-vec partition key 同构；③「量化先在 1 亿样本上离线扫，再线上 A/B」的流程。不抄：多集群、SPANN 实现、ColBERT 多向量（我们存储量级不允许）。代价：无（只借判据）。

### GitHub（Blackbird 代码搜索 + Elastic 语义搜索）
- **Blackbird**：自研 Rust 检索引擎，公开口径是 **4,500 万仓库 / 115 TB 语料 / 25 TB 索引**，被用于替代 Elasticsearch 的代码搜索；技术点：trigram 分词、delta 压缩、动态分片分配、几何 XOR 过滤器、索引与查询分离【**转述**：GitHub 官方博客本轮**抓取失败**（多路径 404/机器人验证），上述数字来自一张第三方汇总表与 HN 评论；**属未取证，不得当一手数字用**】。
- **GitHub × Elastic（语义搜索）**：**3.95 亿代码仓库、数十亿文档**；用 Elasticsearch 做 issue 类内容的语义搜索；采用 **BBQ（Better Binary Quantization）压缩 32×** + oversampling + rescoring 保召回；搜索平台团队「约 5–6 个工程师」维护【**营销材料**，一手·原文：elastic.co GitHub 客户案例】。
- **对我们**：①「一个 5–6 人团队维护亿级用户搜索」这句说明**运维复杂度可以靠托管件买掉**——但我们买不了（便携约束），所以这条对我们反而是反例；②BBQ 32× 与我们 int8（4×）/二值（32×）是同一族，可作内存预算的旁证；③Blackbird 的 **trigram 分词**与 C 线建议的 FTS5 trigram 同路，等我们有容量再核原文。

### Notion（AI 搜索 + turbopuffer）
- 是什么：Notion 内部 RAG（Notion AI 搜索），向量存 turbopuffer（对象存储原生检索引擎）；讲者是 Notion 数据平台工程师 + turbopuffer 联创【一手·原文：Data Council 2025 演讲逐字稿，Turbopuffer 官网发布】。
- **规模（这是本线最硬的一组读写数字）**：**数百万 workspace → 100 亿+ 文本 chunk**；**每月写入 150 亿条 embedding**（因为一页一月内多次编辑）；**峰值 10 万条 embedding/分钟**；**查询峰值只有 ~100 QPS**【一手·原文】。
- **延迟/成本**：Notion 侧「所有查询峰值 **50–70 ms**」；迁到 turbopuffer 后「一年省下**数百万美元**」；turbopuffer 侧：warm p50 **8 ms** / p99 **35 ms**，cold p50 **343 ms** / p99 **554 ms**（768 维、1M 文档、~36 GB 规模的自测口径）【一手·原文（演讲）；benchmark 是 turbopuffer 自测】。
- **架构**：namespace = S3 前缀（**生产 5,000 万个 namespace**）；写入 = 先写 WAL 再合并索引；查询与索引节点池分离、可弹性扩到「数十万节点」再缩回【一手·原文】。成本口径：S3 **$0.02/GB** vs 传统三副本 SSD 方案约 **$0.40–0.60/GB**【一手·原文】。
- **引用**：Notion 的引用是「链接到 Notion 文档」，**不到块/坐标**【一手·原文】。
- **对我们**：①**写放大**这条必须吸收：我们的条款库将来若支持「文档改一版就重嵌」，量级也是亿级写入/月，要提前设计「只嵌变更条款」；②**「冷查询 300–800 ms」是可接受的产品代价**（对方明确接受），对照我们 606 ms 的向量通道——说明「慢查询 + 精确召回」在别的产品里是可用形态；③它证明**对象存储/单机盘上的检索引擎可以撑 10B chunk**，方向与「不引外部服务」不矛盾（turbopuffer 是云服务，但架构思想是「索引落廉价存储 + 缓存热数据」）。

### Uber（Search Platform：ES → Sia → OpenSearch）
- 是什么：Uber 搜索平台演进史（2025-06-20 博客，作者是搜索平台总监/首席工程师）【一手·原文】。
- **规模**：Uber Eats **全球 100 万+ 餐厅**，单次会话常见 **1,000+ 菜品/餐厅**候选；早期「每 6 个月要把集群容量和机器数翻一倍」【一手·原文】。
- **踩过的坑（对我们最有用的一段）**：Uber Eats 的数据是 **store（父）→ item（子）** 的层级；Lucene **没有满足其规模要求的父子 join**：index-time join（BlockJoin）一改父/子就要整块重索引；query-time join 两趟查询、过度取数、延迟高。他们的解法是**把子文档物理地按父分组连续存储、父按 UUID 分区、组内按静态 rank 排序**，再写自定义 join 算子；代价是「持续写入下维持有序布局很难」，于是做了**读写分离**：ingester 从 Kafka 读、commit 时强制 merge 成单 segment 上传对象存储，searcher 只读【一手·原文】。
- **对我们**：**这是「文档→条款」层级在工业界最接近的一次公开解剖**。我们现在的「条款一行、父文档 id 外键」等价于 query-time join，而 Uber 明确说这条路「over-fetch + 高延迟」；他们最终选了**物理共置（条款按文档连续、按文档内序排列）**。⇒ 若我们将来 1000 万条款要做「文档内上下文」类查询，物理共置 + 只读快照的读写分离，是可直接借的形状。代价：写入路径要重构（我们目前单写者队列，改造成本中等）。
- 另：Uber 因为「自己实现 Lucene 的向量检索、每个新算子都要双份实现」而放弃自研，转 OpenSearch——**自研检索底座的长期维护成本，是被一家万人公司公开认输过的**。【一手·原文】

### 小红书（HELMSMAN，OSDI'26）—— 中文大厂最硬的一手
- 是什么：面向全闪存的聚类式 ANNS 系统，已在小红书搜索/推荐/广告/内容审核/RAG **稳定运行数月**【一手·原文：arXiv 2606.13145 摘要（OSDI'26 接收）；部署细节另见头条/知乎转述】。
- **规模（摘要级，可信）**：线上**40 台全闪存**承载了此前需要**约 35,000 核 + 0.35 PB DRAM** 的 ANNS 负载；**省 90%+ 硬件成本**；**十亿级索引（重）建在数小时内**完成【一手·原文】。
- **规模（转述级，仅供参考，⚠ 与摘要矛盾，见「对不上的地方」第 10 条）**：单索引**数百亿**高维向量、**百万级 QPS**、**5–10 ms** SLA；DRAM 占用 搜索 **0.8 PB** / 推荐 **0.3 PB** / 广告 **20 TB**；内存实际只用掉理论吞吐的 **32–43%**；DRAM **$8/GB** vs PCIe5 SSD **$0.2/GB**（1/40）【转述：知乎/头条两篇报道，数字互相对得上，但均非官方，且与论文摘要的 0.35 PB 总量冲突】。
- **为什么不用图索引**：图搜索在 SSD 上是**串行依赖 IO**（下一步访问哪个邻居取决于上一步读出的结果），带宽打不满、长尾被单次 SSD 延迟放大；高 top-k 下吞吐只剩纯内存 HNSW 的 **1/10–1/25**（DiskANN/Starling/PipeANN 都如此）⇒ 他们的结论是「**适合高带宽 SSD 的是聚类式，不是图式**」【转述】。
- **对我们**：①**这是 C 线「ANN 是正确性故障」之外的另一个独立结论**：即便放弃正确性、接受 ANN，**图式在磁盘上也是错的介质匹配**；聚类式（质心驻内存 + 倒排落盘）才是。与我们「分区 + 片内精确算」天然同构；②**「40 台服务器 vs 35,000 核」**是唯一一个把「内存成本」量化到机器数的生产数字，可用于向业主解释「为什么不能靠加内存解决千万级」；③注意：**40 台仍然是集群**，不能拿来证明「单机能撑」。

### 阿里巴巴 / 淘天（Hologres 的 HGraph 索引）
- 是什么：淘天客户运营团队用 Hologres 做「向量 + 全文」一体化检索（智能客服、规则比对、舆情），**知识条数口径「数十万到上百万条」**【一手·原文：阿里云开发者社区 2026-02-28】。
- **数字（本线少见的「同数据量不同索引」对照）**：**950 万条 × 128 维**下，旧引擎 Proxima 平均 RT **4 秒**，自研 HGraph **约 30 ms**；40 万条时两者差不多（40 ms vs 30 ms）；叠 OLAP 过滤/排序后整体「数百毫秒」【一手·原文】。注意：**128 维**，不是我们的 512/1024 维。
- **对我们**：①给了一个**「千万级、低维、纯向量召回 30 ms」**的量级锚点——反过来说明我们 606 ms @52 万（512 维、无 ANN、含 IO）慢在**实现方式**而不是硬件；②「一张表里向量 + 全文 + 标量过滤 + JOIN」是他们选型的第一理由，与我们「单文件里 FTS5 + 向量 + SQL 过滤」同构，**说明这条路在工业界有人走**（只是他们用数仓，我们用 SQLite）。

### 阿里（HNSW 分布式构建）
- 是什么：智能引擎事业部讲「分治构图」解决 HNSW 建图慢（淘宝天猫、拍立淘、闲鱼召回都在用图索引）【**转述**：微信公众号文章，未署官方发布号】。
- **关键数字/结论**：HNSW 多线程建图「**并发 10 以内接近线性加速，到 30 之后加速比基本到顶**」；分布式方案 = 拆数据集 → 各自构图 → 合并边 → 细化；「只为建索引慢就扩列不划算」【转述】。
- **对我们**：**这是我们「换嵌入模型要重算千万条款」时最直接的成本预警**：并发换不来线性加速，构建时间是硬成本，必须走「增量/分治 + 只重建受影响分片」。

### 字节跳动（VikingDB + 火山引擎 DiskANN）
- **VikingDB（官方文档）**：语料「**万亿级向量**」（豆包/抖音同源技术）；服务字节生态 **50+ 业务线**；**单索引最大 100 GB**；条件过滤能力「**比开源 ES 高 10 倍**」【营销材料，一手·原文：BytePlus 文档】。
- **火山引擎云搜索 DiskANN（技术团队文章）**：给出内存估算式「**向量数 × 4 × (维度 + 12)**」并算账：DEEP10M（96 维、1000 万）≈ **4 GB**；MS-MARCO（1024 维、**1.38 亿**）≈ **534 GB** ⇒ 需要 **12 台 × 64 GB** 节点；按此式 **10 亿级需约 100 个节点、100 亿级约 1,000 个节点**；用 DiskANN 后「1000 万级只需 **70 MB** 内存」；已在「**200 亿单一向量库**」落地，客户「几十台机器撑百亿级」【一手·转载：字节跳动技术团队原文，原始发布页经长亭社区转载】。
- **对我们**：**这条公式可以直接拿来核我们的量级**：1000 万 × 512 维 × 4 × (512+12) ≈ **10.5 GB**（f32，与 C 线表 2 的 19.1 GiB 差在口径：这条式含图结构开销、C 线只算原始向量）。两条独立算法给出同一量级 ⇒ **512 维下 64 GB 单机在内存上够用**，与 C 线结论一致；真正的墙是「全表算距离」的算力，不是内存。

### 美团（外卖 GPU 向量检索）
- 是什么：到家搜索团队的 GPU 向量+标量混合检索系统（2024-04-11）【一手·转载：美团技术团队原文，tech.meituan.com 原链本轮 404，读的是 it168 全文转载】。
- **规模**：基于「Elasticsearch + FAISS」实现「**10 亿级+** 高维向量集的标量+向量混合检索」；索引算法演进 HNSW → IVF → IVF-PQ → IVF-PQ+Refine【一手·转载】。
- **踩过的坑（验收级线索）**：①**HNSW 「在高过滤比下性能会有折损」**，到家场景是强 LBS 过滤（配送范围），这一条直接暴露；②IVF 要「全量加载进内存」，内存成为瓶颈；③IVF-PQ 内存降了但召回掉，所以要 +Refine【一手·转载；本轮只读到文章前半，GPU 侧的加速比/延迟数字**未取证**】。
- **对我们**：**「元数据过滤 + ANN」的组合在生产上会退化**，这是 C 线 pgvector/Qdrant 结论的工业界复现，且是中文场景（配送范围 ≈ 我们的「标准语料范围/文档类型」过滤）。建议：我们的向量通道**先把过滤做完再算距离**，不采用「先 ANN 再过滤」。

### 腾讯（微信 ZeroSearch，内存检索引擎）
- 是什么：腾讯 WXG 自研、面向微信生态的**纯内存检索**引擎（替代磁盘式 ES/Lucene 路线）【**转述**：CSDN 读书笔记，非官方发布】。
- **做法**：倒排/正排/元数据全常驻内存，瓶颈从 IO 变成 CPU；**计算分级 L0（离线质量分）→ L1（轻量打分，全量）→ L2（精排，只打 Top）**；任务模型把「求交 / L1 / L2 / 清理」流水线化，避免求交饿死打分；线程池从三池改成按 CPU 饱和调度的策略【转述】。
- **对我们**：**「L0/L1/L2 分级打分」是我们可以直接借的顺序**：与 C 线「先收窄候选，再精确算距离，再重排」完全同构；他们额外给的是「**求交会饿死打分**」这个实现级教训——我们若把六通道做成并行流水线，要注意通道间负载不均。**无数字（未取证）**。

### 百度（VectorDB）
- **规模宣称**：单表**百亿级向量**、**十万级分片**、可扩到上千节点；「各场景性能高于开源产品 **7 倍**」；全文检索性能「高于 ES」【营销材料，一手·原文：百度千帆开发者社区】。
- **可信部分**：参加了中国信通院「可信数据库」**首批向量数据库性能测试**（标准《向量数据库性能测试方法》，覆盖稠密/多向量/标量向量融合三类场景，指标含构建时间/QPS/平均/P99 时延/CPU/内存），测试数据集含 Cohere 1M、OpenAI 5M、LAION 100M；宣传口径是「百万和亿级稠密向量检索性能表现优异」——**没有公布任何具体数值**。【一手·原文：百度公告 + 微信公众号】
- **客户侧（唯一带数字）**：「某大型国有银行」知识检索效率提升 **80%**、日均调用 **数十万次**；「某大型证券」投研/合规问答【营销材料】。
- **对我们**：**「有标准、有测试、没数字」是这类公告的通病**——我们要引「百亿级」时必须同时写「未公布测试数据」。国内首个向量库性能标准的**指标清单**（构建时间/P99/CPU/内存）值得我们照抄成自己的验收表。

### Wikimedia（CirrusSearch，只登记）
- 用 Elasticsearch 替代旧搜索：旧搜索按日批量更新，Cirrus「约每 30 秒」更新一次；支持 `insource:` / `hastemplate:`，并索引 PDF/DjVu 文本【转述：2014 Wikimania slides 摘录，材料已过期，无集群规模/延迟数字】。**对我们**：可作 FTS 刷新周期的历史参照，不作依据。

## 厂商案例（营销材料，单列，只取失败模式不取性能数字）

> 判定标准：页面上的数字**没有硬件、没有数据集、没有 recall 目标** → 一律当广告。下列五家的**客户踩坑描述**有内部一致性（多家客户独立提到同一类问题），这部分可用。

### Elastic（客户：Anyone.com / GitHub）
- **Anyone.com**：**2.1 亿条记录放在单个 Elasticsearch Serverless 索引**上；迁移前 Postgres「超过数千万条就无法集群」；全国范围 count 查询从 **6.5 秒**降到 **中位 5 ms / P95 33 ms**；迁移工期 **1.5 周**；约 **95%** 查询走 ES；全栈 **3 行 Terraform**【营销材料，一手·原文：elastic.co 客户页 + success story PDF】。
- **GitHub**：见上文（3.95 亿仓库 / 数十亿文档 / BBQ 32×）【营销材料】。
- **对我们**：**「2.1 亿条单索引 + P95 33 ms」是「单索引能装多大」的一个可用锚点**（虽为营销，但迁移前后对比与工程量自洽）。**失败模式**：Postgres 在「数千万」量级就是天花板——这条与 C 线 pgvector 结论一致，值得记。

### Qdrant（客户：Bazaarvoice）
- **数字**：现有 **27 亿条评论向量**；迁移搬了 **4–5 TB**；目标 **<100 ms** 延迟、**~98%** 召回；存储降 **~100×**；分区数比 Postgres 少 **~100×**【营销材料，一手·原文：qdrant.tech/blog/case-study-bazaarvoice】。
- **失败模式（可用）**：pgvector 阶段「每加一个客户/产品都要手工建分区；跨产品查询要在**数千个分区**间迭代，延迟飙升；存储和 RAM 涨到**数 TB 级**」；「上亿向量下，后过滤等于搜整库——为什么要搜十亿条，我只需要搜一万条」【营销材料，一手·原文】。
- **对我们**：**「分区键先行」是唯一能同时解决内存与过滤的东西**——对应我们 sqlite-vec 的 partition key，与 C 线建议一致。

### Pinecone（客户：Delphi + 自身基础设施）
- **Delphi**：**>1 亿向量**（跨数千客户）、**P95 100 ms**、检索只占端到端响应时间 **<30%**；每个 creator 一个 namespace 做隔离；从开源向量库迁来的三个坑：**HNSW 索引无界增长到不可预测**、**数据量涨后 ANN 变慢**、**分区数硬上限**【营销材料，一手·原文：pinecone.io/customers/delphi】。
- **Pinecone 自身（Google Cloud 案例）**：存储「**数千亿向量**」、服务「**每秒数百万查询**」【营销材料，一手·原文：cloud.google.com/customers/pinecone】。
- **对我们**：**「分区数硬上限」这条我们目前没有**（SQLite 无此约束），是我们的相对优势；「HNSW 索引无界增长」是我们评估任何 ANN 方案时要先问的。

### Milvus / Zilliz
- **RaBitQ（Milvus 2.6 起）**：1 bit/维二值量化，**QPS 提升 3×** 且精度可比；实现要点：每向量 2 个浮点辅助量、AVX512 `VPOPCNTDQ` 加速 popcount【一手·原文：blog.milvus.io】。
- **Zilliz Cloud**：支持「**1000 亿向量**、**sub-20 ms**」；RaBitQ + 分级存储使基础设施成本降 **70%**；迁移到 Arm（Graviton3）后**索引构建快 50%**【营销材料（联合署名 Arm 博客），一手·原文】。
- **Zilliz 的自曝（反证价值最高）**：「大部分 benchmark 对生产毫无助力」；「传统 benchmark 假设数据已导入、索引已建，但生产是**数据持续流入**，不可能为重建索引停机几小时」；「Elasticsearch 宣传毫秒查询，但**光优化索引就要 20 多小时**」【一手·原文：zilliz.com.cn 博客——厂商攻击对手，故其承认的自家短板更可信】。
- **对我们**：**二值量化（32×）是我们 3000 万条款时的最后一张内存牌**（C 线已算：1000 万×512 维二值 ≈ 0.6 GB），Milvus 的生产实现证明它可用；但注意它的代价——**辅助量每向量 2 个 float**，我们若用要一并算进预算。

### Vespa（客户：PlayStation 类电商案例）
- 一手页面只给「六个 ML 模型上线、迁移后消除数据孤岛」这类定性描述，**没有数字**【一手·原文：vespa.ai webinar 页】。第三方评测文章称「数十亿文档 sub-100 ms p99」，但那是评论站，**未取证**。
- **对我们**：不取。Vespa 作为底座已在 C 线评价。

## 对我们（结论的落地形状）

**A. 能直接借的（做法级，不引依赖）**
1. **分级处理 + 批处理**：Slack 的「实时走槽位限流、摘要夜里批处理」→ 我们所有「全库 embedding / 全库标签 / 全库摘要」类任务一律离线批处理，不进在线路径。
2. **passage 级引用 + 页级元数据**：Atlassian 的形状（chunk 携带 URL + 标题）→ 我们每条条款行已带 doc_id + page + bbox，只需在生成层把「引用挂在论断上」而不是「挂在回答末尾」，这是**产品可见的差异点**。
3. **L0/L1/L2 打分分级**（腾讯 ZeroSearch）+ **先过滤再算距离**（微软金融 RAG、美团、Bazaarvoice 三家独立）→ 写死为检索顺序，不做「ANN 后过滤」。
4. **按文档物理共置子记录**（Uber Eats store→item）→ 我们条款表的聚簇顺序应是 (doc_id, 条款序)，而不是 rowid 插入序；这对「文档内上下文」「同文档条款连读」有直接收益。
5. **索引构建要能增量、要能分治**（阿里 HNSW：并发 30 就饱和；小红书：GPU 流水线数小时/十亿）→ 换嵌入模型时不做全量重算，按分片滚动重建。
6. **解析的「天花板论」**（Octus）→ 我们所有检索质量问题的上限由 MinerU 的表格/公式抽取决定，优化检索前先量化解析残缺率（B 线已有口径）。
7. **验收表照抄信通院指标清单**：索引构建时间 / QPS / 平均 / **P99** / CPU / 内存——我们现在只有平均耗时，缺 P99 与内存。

**B. 证明「我们的单机路线有天花板」的证据**
- Notion：**100 亿 chunk、每月 150 亿写入**，单机文件系统与单进程 SQLite 无解（写放大 + 备份粒度）。
- Atlassian：**200 亿文档 / 2,000 数据节点**；GitHub：**数十亿文档**；这两家的形态不是「一个 .db 能装下」。
- 小红书：**0.35 PB DRAM**——即使全部量化到二值，10⁹ 量级仍是 PB 级存储。
- ⇒ 天花板在 **10⁸ 条款以上**，不在我们现在的 10⁷。**10⁷ 不需要集群**（SPANN 单机 10% 内存 ~1 ms 的 90% recall 是直接证据）。

**C. 证明「不引外部服务也能撑住」的证据**
- SPANN（单机 + SSD，10% 内存，~1 ms，Bing 采用）；
- turbopuffer 的架构思想（索引落对象存储 / 廉价介质，热数据留缓存，warm p99 35 ms）；
- 小红书证明了「聚类式 + 廉价介质」在 10¹⁰ 量级的生产可行性（代价是 40 台机器）；
- 阿里 Hologres 证明「向量 + 全文 + 标量过滤在同一引擎内」是成立的（我们用一个 SQLite 文件模拟这个组合）。
- **没有一家**证明「单机能撑 10⁹」，包括 SPANN（论文的 10 亿是实验配置，Bing 的数千亿是集群）。

**D. 明确不抄的**
- 不抄 Uber 的自研检索底座路线（他们自己认输，转 OpenSearch）；
- 不抄任何「ANN 后过滤」；
- 不抄厂商案例里的性能数字当基准（无硬件/数据集/recall 三件套）；
- 不抄 ColBERT / 迟交互（Pinterest 的 multi-embedding 是数亿→数百亿向量场景，我们存储不够；C 线已否）。

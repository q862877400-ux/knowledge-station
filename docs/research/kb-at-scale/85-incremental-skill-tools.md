## 一、把「星数」换成「下载量」：**两个结论被加强，一个结论要改口径**

### 实测数字（2026-10-25 抓，`pypistats.org/api/packages/<pkg>/recent`，单位=次）

| 包 | 最近一日 | 最近一周 | 最近一月 | 前十条线当时怎么说 |
|---|---:|---:|---:|---|
| **docling** | 95,525 | 889,881 | **2,909,751** | B 线：「Docling 当第二解析器（MIT 最干净）」 |
| **sqlite-vec** | 174,854 | 1,718,837 | **5,539,485** | C 线：「pre-v1、5 个多月无提交，维护风险须记」 |
| **fastembed** | 177,338 | 1,632,342 | **5,233,605** | 我们正在用的嵌入运行时 |
| **unstructured** | 49,139 | 629,440 | **2,462,836** | B 线：「厂商自曝 OSS 表格只有四成对」 |
| **marker-pdf** | 3,178 | 21,802 | **116,251** | B 线：「不抄」 |
| **mineru** | 3,246 | 26,705 | **109,382** | B 线：「主干升级到它」 |
| **magic-pdf** | 260 | 1,880 | **14,341** | B 线：「已停在 1.3.12，旧包名」 |

**口径必须写清**：PyPI 下载量含 CI、镜像、容器重建，**不等于用户数**；但它能反映「有多少自动化流水线在依赖它」，这恰恰比星数更接近"生产采用度"。

### 由此产生的三件事

**1. ✅ 加强：`magic-pdf` 确实已死，换包判断成立。**
`magic-pdf` 月下载 **14,341**，是 `mineru` **109,382** 的 1/7.6，且上游停更在 1.3.12。⇒ B 线「我们锁的是旧包名的旧代号」这条**从"文档过时"升级为"依赖已经没人用了"**。

**2. ⚠ 要改口径：Docling 的生态采用度是 MinerU 的 26 倍。**
docling 月下载 **290 万**，mineru **10.9 万**——**26.6 倍差**。B 线当时说"Docling 当第二解析器"是从**能力/许可证**角度定的（MIT 最干净、能力与 MinerU 重叠但弱一些），**没看采用度**。
- **不改变主结论**（MinerU 在合并单元格/上下标/LaTeX 上仍是唯一做全的，B 线的核心依据没动摇）；
- **但加强"第二解析器选 Docling"这一半**：生态大 = 坑被别人踩得多 = 遇到问题有地方查，这正好补 MinerU 文档薄、issue 区冷清（A/E 线已记）的短板；
- **也提一个反面**：docling 的 290 万下载里有大量是"顺手装的"—不能当作"能力被验证"。

**3. 🔴 新发现，C 线要补一条：sqlite-vec 月下载 554 万，但它 46 天没有一次提交**
`gh api` 实测 `asg017/sqlite-vec` 最近 100 次提交：**最新 2026-05-18，最旧（第 100 次）2026-02-13**——即 **100 次提交全部挤在 2 月中到 5 月中这 3 个月内，之后至今 5 个多月零提交**。
- C 线原判断「pre-v1 且 5 个月无提交 ⇒ 必须锁版本并留存 vendored 源码」**成立，而且现在有了新的一层含义**：
- **它同时是"高采用 + 零维护"**：月下载 554 万说明大量生产系统依赖它，而作者 5 个月没动 ⇒ **一旦它出问题（SQLite 升级、平台兼容、CVEs），没有上游可等**。
- ⇒ 对我们的实操含义（不是建议，是事实）：**vendored 源码 + 锁 SQLite 版本**这两件事的优先级，比 C 线原来写的更高；且**不要把"换掉 sqlite-vec"当作随时可做的备选**——554 万月下载量意味着替代品也未必更稳，替换成本要用真数据算。

**对照组（证明"活跃度"能分开）**：同一时间窗内，MinerU 最近 100 次提交覆盖 **2026-09-20 → 2026-10-11（21 天）**，docling 覆盖 **2026-10-14 → 2026-10-23（9 天）**。⇒ **这两个是活跃项目，sqlite-vec 不是**。这个对比口径（"100 次提交跨多少天"）比"最后提交日期"更能区分"慢速维护"和"停摆"。

## 二、`gh search code`：找到一份别人做的解析工具横向对比（但样本太小）

按 skill 的说法（"能搜到别人 README 里的横向对比表和实现细节"），搜 `MinerU Docling` 命中：

- **`LemonTeaViTA/Baize`**（Apache-2.0，0 star，最后推送 2026-06-17）：一个中文企业级 RAG 知识库，仓里有 `rag-eval/scripts/parse_compare.py --tools mineru docling`，即**作者自己在做 MinerU vs Docling 的解析对比脚本**。
- 另有 `jtravs/paperextract`：把 `mineru / docling / marker` 做成可切换后端（`backend = choice(data["backend"], "mineru docling marker")`）。

**价值判断（不许夸大）**：
- **正面**：证明"同时接多家解析器 + 可切换后端"是别人的**实际做法**，不是我们臆想；也证明"解析器对比"是社区真在做的事。
- **负面**：Baize 是 **0 star** 的个人仓，它的对比脚本**没有公布结论数据**；paperextract 只做后端抽象不产结论。⇒ **这两条不能当"已有权威对比"用**，只能当"别人也在做同一件事"的旁证。
- **对 B 线的意义**：我们若要"交叉校验"（B 线建议的 Docling 第二解析器），形状就是 `parse_compare.py` 这种——**同一批文件跑两个后端，比单元格数/表格结构/上下标保留**。这三个指标 B 线已经定好了，不用改。

## 三、OpenAlex 引用链：按被引排序会被综述淹没，证明 skill 那条是对的

按 skill 说的"先找被引最高 3 篇"，我用 `mcp__openalex__search_works`（query=`document parsing benchmark PDF table structure extraction`，2024 起，按被引排序）取前 6：

| 论文 | 被引 | 跟"文档解析"有关系吗 |
|---|---:|---|
| A Survey on RAG Meeting LLMs（KDD 2024） | 824 | 泛 RAG 综述，不涉及表格结构 |
| Harnessing the Power of LLMs in Practice | 643 | 通用 LLM 综述 |
| **Enriching Location Representation…** | 499 | **完全无关**（地理语义），且它的 abstract 还是错的（内容是 CPS 故障检测） |
| Large language models (LLMs): survey… | 391 | 通用综述 |
| Large Language Models: A Survey | 324 | 通用综述 |
| Gemini 1.5 | 302 | 长上下文 |

**结论（这条本身就是发现）**：**在这个 Query 下，"按被引排序"返回的六篇里没有一篇是文档解析**。这正是 skill 为什么要强调"顺引用链走比关键词搜索准"——**高被引综述会吃掉所有排序位**。
- 顺带记一条数据质量事实：OpenAlex 里 **W4401306886 的标题与 abstract 不匹配**（标题是地理语义，abstract 是 CPS 故障检测）⇒ **OpenAlex 的 abstract 字段不能无条件当原文引用**，这和本仓"字段描述 ≠ 运行时语义"是同一类坑。
- **对本轮的意义**：G 线的"OmniDocBench / olmOCR-Bench"是**榜单**不是论文，走 OpenAlex 找不到；**文档解析领域的权威脉络要靠榜单 + 官方 README，不靠被引排序**。这条我记下来，不硬凑引用链。

## 四、Wayback：两页都能取到快照，但**它证明不了"持续维护"**

`http://archive.org/wayback/available` 对 `github.com/asg017/sqlite-vec` 与 `github.com/opendatalab/MinerU` 都返回 200（最近快照 2025-12-29 / 2025-12-25）。
- **诚实说**：GitHub 的 README 页面快照**看不出提交节奏**（页面内容几个月不变很正常）。⇒ **判断维护状态用 `gh api commits` 比 Wayback 准**（上面第一节就是这么做的）。
- Wayback 真正有用的场景是"**某个页面 404 了，想知道它以前写了什么**"——本轮没遇到这种需求，**所以这条工具我用了但没产生结论，如实记**。

## 五、这一轮对前十条线的影响（只列有变化的）

| 线 | 原结论 | 现在 | 性质 |
|---|---|---|---|
| B 「magic-pdf 是旧包名」 | 文档过时 | **依赖已基本没人用**（月下载 1.4 万 vs mineru 10.9 万） | **加强** |
| B 「Docling 当第二解析器」 | 从许可证/能力定 | **再加一条：生态采用度是 MinerU 的 26.6 倍**（290 万 vs 10.9 万月下载） | **加强，但注明下载量≠能力验证** |
| C 「sqlite-vec pre-v1 无提交，锁版本」 | 维护风险 | **补一层：它的月下载 554 万 = 高采用 + 零维护**，一旦出问题没有上游可等；vendored 优先级更高 | **加强** |
| 方法论 | 「看星数」 | **改口径：星数不判真伪，下载量 + 提交窗口一起看**；`100 次提交跨多少天` 比"最后提交日"更能区分慢速维护与停摆 | **新增判据** |
| 方法论 | 「按被引排序找权威」 | **不行**：本次实证六篇高被引无一篇相关；必须顺引用链或看榜单 | **skill 那条被本轮实证** |

**明确没做到的**：
1. Baize 的 `parse_compare.py` **没跑过**，它的对比结论也不存在——只能说"别人也在比"，不能说"别人比出了什么"。
2. Wayback 只做了可用性验证，**没产生任何事实结论**。
3. OpenAlex 引用链**没有真正串起来**（时间用在验证"被引排序不可用"上）；"顺链找权威"这件事对文档解析域**本来就弱**——该领域的权威是榜单不是引用关系。
4. 下载量是**第三方统计**，含 CI 与镜像，**不能当用户数**，我在上文每处都写了这个限制。

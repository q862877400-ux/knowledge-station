# E 线 · 商用产品（检索底座 / 法律专业 / 国内法规标准 / 国内云）

> 抓取日期：2026-10-25（下列 URL 当日可达）。标注【转述】的是二手（评测文、公众号、招聘页），未读到一手技术文档。
> 规模口径按业主 2026-10-25 更正：目标语料是「中国现行的所有法律法规、地方标准、规章制度」，国标 3 万多条 × 每条约几百条 ≈ 几百万条款。我们仓里 6,797 篇 / 522,021 条是**测试子集**，不是目标规模。

## 结论先行（≤15 行）

1. **没有一家把"几百万条款 + 条款级引用 + 效力状态"做全。** 大厂的做法是"一个库一份索引 + 配额挡规模"，不是"一个索引装全国法规"。档位：借鉴（配额页就是天花板证据）。
2. **最该抄的一条：工标库的"条文级废止"形态** —— 被替代的条文在原标准里划线、点开看废止出处、再点"查看替代标准"。这正好补我们"跨文档证据边 0 条"的空档，且不需要重建语料。档位：借鉴（最高优先）。
3. **关键判断：法宝的条款/款级锚点是人工编辑建库。** 官方公告原文写"由资深编辑细致严谨整理"，建国以来千余篇法律逐条编注。**推论：纯自动切库拿不到同等质量；我们只能把人工压到"效力关系"这一薄层，条款切分必须自动。** 档位：借鉴（这是判断，不是事实）。
4. **多版本并存，国内两家都是"并存对照"而不是"覆盖"**：法宝四种版本形态（官方/编注/对照/法宝整理版）+ 变迁史时间轴；工标库"标准资源对比"。我们仓里连一份旧版都留不住。档位：借鉴。
5. **效力状态标签的正确形态：标签挂在"引用"上，并写明标签不能代替读原文。** Protégé 原话是"信号只是起点，不能替代你自己去读判决"。我们只标了库里条款的状态，没标"这次引用时该条是什么状态"。档位：借鉴。
6. **表格/公式：只有 Google 明写"抽取文本块与表格"**；其余全停在"解析文档、切片"。**没有一家公开承诺公式转写与上下标。** 档位：未取证（对我们反而是空档）。
7. **所有规模数字都是配额，不是实测。** Bedrock 10 TB/库、Vertex 单次导入 10 万文件、Pinecone 单请求 1,000 条 / 2 MB、Azure 单页 1,000 条结果 —— 这些是"允许多大"，不是"跑过多大"。档位：一手。
8. **AWS Kendra 2026-07-30 起不再对新客户开放**，官方迁移文档指 Bedrock Managed KB，但连接器 32 → 7。连 AWS 自己都收掉了"通用检索引擎"这条路。档位：借鉴（不抄）。
9. 秘塔的**招聘 JD** 自己写了"大规模近似语义向量搜索 + 基于知识的结构化信息抽取"；用户实测说引用能顺着核对，但深追问会编出很像真的标题。档位：转述。
10. 得理法搜托依托中科院深圳先进技术研究院联合实验室的法律大模型 —— 国内唯一取到"研发主体"的品牌，检索实现未取证。档位：转述。
11. 威科先行 / CoCounsel / Spellbook **本轮一条技术路径都没取到**（只有功能页、合规页）。档位：待核。
12. 不必抄的：Pinecone（向量库本体）、Glean（连接器生态）、Spellbook（合规话术）。档位：不适用。

## 逐个点评

### Azure AI Search（Microsoft）
- 是什么：托管检索服务；Microsoft 维护；闭源商业。另有一层产品形态值得记：Azure 官方写明它同时是 **Foundry IQ**（给智能体用的、带权限的知识层）的底座。
- **规模**：宣称侧无数字；**硬证据在配额页**。两套计费形态：专用（Basic / Standard S1–S3 含 S3 HD / Storage Optimized L1–L2 / Free，按 Search Unit 计）与无服务器预览（Serverless Developer，按索引配额 + CU/小时）。**配额失败与容量失败是两个控制器**，要按报错的操作去定位；接近存储/向量上限时拿 `storageSize` 与分区存储比。⚠ **2026-10-25 复核后就地更正（原话保留）**：原文「引擎过载护栏最多 1,000 个实例」是**误读**——官方原文是 Lucene 对**通配符/正则**查询的限制："It caps the number of **patterns, variations, or matches** to **1,000 instances**. This limit is in place to **avoid engine overload**." ⇒ 1,000 指**通配符/正则的命中/变体数**，不是"引擎实例数"。
- **单次上限**：关键词检索与向量检索的文本属性，检索词最大 **32,766 字节**（32 KB − 2）；前缀/正则 1,000 字符；一页结果最多 **1,000 篇**；建议 ≤100 条；默认 50 条。服务 2 个管理密钥 + 50 个查询密钥。
- **表格/图/公式/上下标**：检索层不管；文档只说哪些字段 `searchable`（被评分）、哪些 `retrievable`（被返回）。**未取证**。
- **中文法规/国标**：无任何专门处理。分词器是通用的。
- **引用可回溯**：检索层不产引用，只返回文档与分数；引用靠上层拼。
- **混合检索的内核（可直接对我们）**：只要并行执行 ≥2 条查询就上 **RRF**，分数 `1/(rank+k)`，**k ≈ 60**，各路求和后重排。并列给了查询条数算法：全文 + 1 个向量 = 2 条；再加 2 个向量字段 = 3 条；2 条向量查询跨 5 个字段 = 11 条。`maxTextRecallSize` 默认 **1,000**，全文侧硬停在 1,000 条命中。
- **对我们**：抄三样 —— ① RRF 的 k≈60 与我们一致，说明我们没选错（这是反证式确认）；② "全文侧硬停 1,000 条"这个数给了我们候选集该收到多大的外部参照；③ 配额失败 / 容量失败分开报错这个做法。不抄：字段级 searchable/retrievable 那套抽象，对我们单文件 SQLite 是负担。

### Google Vertex AI Search / Gemini Enterprise
- 是什么：Google Cloud 的托管检索 + 智能体平台；闭源商业。
- **规模**：结构化数据必须是 JSON Lines/NDJSON，单文件 < 2 GB、单行 < 1 MB，**单次导入请求最多 1,000 个文件**；另一个语种镜像写"一次最多导入 **100,000 个文件**"（两个不同层级的上限，见「对不上的地方」）。文档 < 200 MB（HTML/TXT/JSON/XHTML/XML 与 PPTX/DOCX/XLSX/XLSM 各自 200 MB 档）。
- **表格/图/公式/上下标**：**唯一一家在文档里明说能抽取"文本块与表格"的**。公式、上下标：未取证。
- **中文法规/国标**：无专门处理。
- **引用可回溯**：文档侧说明回答可带来源，但"回到第几页"颗粒度未取证。
- **另一条产品形态**：建数据存储时必须启用"文档到切片"的切分，RAG 才生效 —— 与我们"先切后索"同构。
- **对我们**：抄"表格作为独立可检索元素"这个明确立场（我们已做跨页表格转 Markdown，比它更细，但对外表述可借它的说法）；不抄其托管形态。注：该页只能通过语种镜像读到，属一手但非 canonical，引用时须说明。

### AWS Bedrock Knowledge Bases（含 Managed Knowledge Bases）
- 是什么：AWS 的托管 RAG 底座，对接 Bedrock 模型；闭源商业。
- **规模（配额页，硬证据）**：每个知识库**默认 1 个并发摄取任务**、**5 个数据源**、**总存储 10 TB**（可调）；每个摄取任务 **25 个文件**；每账号 **100 个知识库**；BDA 解析器与"用基础模型当解析器"各 **1,000 个文件**上限；托管版知识库：并发摄取 **50**、数据源 **200**、`Retrieve` 每库 **600 RPM**、`GetDocumentContent` 每库 **5 RPS**；每个 Agent 只能关联 **2 个知识库**。
- **表格/图/公式/上下标**：未取证。解析器只到"文件级上限 1,000 个"。
- **中文法规/国标**：无。
- **引用可回溯**：`RetrieveAndGenerate` 返回 citation 数组，带来源元数据（URL 等）。这是"引用随回答一起返回"的标准形态。
- **对我们**：抄"引用作为返回结构的字段，不是渲染时拼的"这条（我们 `evidence_url` 已是这个路子）；"每个 Agent 只关联 2 个库"说明大厂也怕一次喂太多库，印证我们"候选集收到 50 才把前 20 命中率从 21% 拉到 99%"的做法。

### AWS Kendra（单独列，因为它在退场）
- 是什么：AWS 的老一代企业检索；**官方公告：2026-07-30 起不再对新客户开放**。⚠ **2026-10-25 复核后就地更正**：抓取日（2026-10-25）该日期**已生效**——官方原文用现在时 "the service **is no longer open** to new customers"，并写明维护模式自 **2026-06-30** 起。原文写的"未来时、尚未执行"作废。
- **迁移文档给出的对比（一手，信息量最大）**：Bedrock Managed KB **内建 RAG 并返回指向源文档的引用**，而 Kendra 原生没有；Kendra 能做**同义词表**、**按索引词表自动拼写纠错**、**`SubmitFeedback` 点击反馈**、**摄取期前后 Lambda 钩子**；连接器 **Kendra 32 个 vs BMKB 7 个**。
- **对我们**：这份对比表等于 AWS 自己给出的"通用检索引擎该有什么"清单。我们只有其中一项（精确条款号）。但**它列的几项我们大多不需要**：同义词表我们靠"法理要素"通道覆盖，点击反馈我们没有用户量支撑。结论：不抄这条路，只抄"把引用写进返回结构"。

### Elastic（含 Elasticsearch Relevance Engine）
- 是什么：开源检索库 + 商业发行版；Elastic License 2.0 / AGPL-3.0 / SSPL 三选；仓库活跃。
- **规模**：底层 Lucene 单分片文档数上限是硬约束（本轮**未取到一手页**，见待核清单）。
- **表格/图/公式**：不涉及，纯检索层。
- **引用可回溯**：不产引用。
- **可直接对我们**：`rrf` retriever 官方文档写明用 RRF 公式合并 ≥2 个子检索，`rank_constant` **默认 60**，且解释"值越大，低排名结果影响越大"。**这与 Azure 的 k≈60 相互独立地对上了** —— 我们六通道用 RRF 是对的。
- **对我们**：抄 `rank_constant=60` 这一个数（已一致，确认用）；不抄 ES 本身（我们 sqlite-vec + FTS5 够用，换成 ES 是纯增依赖）。

### Cohere（Embed / Rerank）
- 是什么：向量与重排 API；闭源商业服务。
- **规模（一手，API 参考页）**：一次 Rerank 请求里「文档数 × `max_chunks_per_doc`」必须 **< 10,000**；**推荐单请求 ≤ 1,000 篇文档**；超长文档自动截到 `max_tokens_per_doc`，**默认 4,096**，最小 1。⚠ **2026-10-25 复核后出处更正**：这组数字来自 **v1 参考页**（`docs.cohere.com/v1/reference/rerank`）；v2 页已无 10,000 与 `max_chunks_per_doc` 约束，只剩"推荐 ≤ 1,000"与 `max_tokens_per_doc=4096`。数字本身已逐字核实。
- **表格/图/公式**：不涉及。
- **引用可回溯**：不产引用，只回相关性分数与索引。
- **对我们**：这三条数直接决定"重排能不能放在条款粒度上"。我们 522,021 条条款全量重排不可能（远超 10,000），但**候选集 50 → 重排 50** 完全在推荐区间内。结论：重排只作用在候选集上，这条不用再论证。

### Pinecone
- 是什么：托管向量库；闭源商业服务。
- **规模（一手，操作上限页）**：带向量的记录 **1,000 条 / 单请求 ≤ 2 MB**；带文本的记录（integrated embedding）**96 条**（因为托管嵌入模型批大小上限 96）；单文档 2 MB；可过滤元数据 **40 KB/条**；记录 ID 512 字符；稠密向量维度上限 **20,000**；稀疏向量非零值 2,048；`full_text_search` 字符串字段 ≤100 个、每字段 100 KB / 10,000 token。
- **表格/图/公式**：不涉及。
- **引用可回溯**：不产引用。元数据能存页码/条款号，但"回原文"靠上层。
- **对我们**：这三条证明"向量库本身不是壁垒"—— 它把页码、条款号塞进 40 KB 元数据就交差了，剩下的全在应用层。**我们的 `evidence_url` + PDF 页码 + 红箭头，正是它不做的那段。** 结论：不抄（自建 sqlite-vec 已够），但用它的上限反证"我们 606 ms 线性扫不是产品缺陷，是选型代价"。

### Glean
- 是什么：企业内搜索 + 助手；闭源商业。
- **技术路径（官方文档页）**：连接器把数据抓进**租户隔离**的索引，检索时用"你的权限"过滤；Grounding 走 RAG 工作流（检索 + 必要时实时取源）；点击结果**通常跳回源系统**，源系统可能再校验一次权限。
- **规模**：宣称侧无数字，未取证。
- **表格/图/公式**：未取证。
- **引用可回溯**：引用回源系统（文档/工单），不到页。
- **对我们**：抄两条产品形态 —— ① **权限过滤在检索层**（我们企业自有材料评审门是同构的：只有 approved 材料进提示词）；② **"点击后回源系统再校验一次"**。不抄：连接器生态（那是他们的护城河，也是我们的成本陷阱）。

### Harvey
- 是什么：律所向 AI 平台；闭源商业。
- **技术路径（官方 release notes，2026-08-26 起）**：Vault 检索改为 **agentic** —— 把整个 Vault 挂给查询，它自己浏览目录、按文件名与内容搜、看元数据、收窄到相关文件，再读相关段落，生成带"回到具体文件"的引用。
- **规模（官方明写的限制，最有用）**：**单次查询最多挂 2 个 Vault**；**Vault 超过 10,000 个文件时仍必须手动选文件**，整库挂载不支持；"正在往更大规模做"。
- **表格/图/公式**：无专门承诺。**但有一句关键原话**：它读的是上传处理时抽取出来的文本，"对多数文档与原文件一致，然而**版式很重的 PDF 或 OCR 有问题的扫描件，读起来可能与原件不同**"。
- **中文法规/国标**：无。
- **引用可回溯**：引用到**具体文件与页**（官方原话"cites the specific files and pages it used"），且是只读、访问留审计轨迹。
- **对我们**：这句话是我们版面分析路线最好的外部支撑 —— **商用天花板产品公开承认"版式重的 PDF 抽文本会走样"**，而我们做的是版面分析 + 跨页表格 + 页面几何。抄：agentic 逐步收窄（我们六通道里"法理要素"通道可承担）；不抄：Vault 挂载这种把规模挡在 10,000 文件门外的做法。

### 北大法宝（pkulaw）
- 是什么：中国最早的法律数据库；北京北大英华；闭源商业。
- **规模**：宣称侧无数字。库结构是"法律法规库 + 司法案例 + 专题模块"。

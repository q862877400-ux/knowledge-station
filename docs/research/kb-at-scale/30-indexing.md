# C 线：索引与检索底座（规模修正版）

> 抓取日期：2026-10-25（所有 URL 当日可达）
> 本线只回答一件事：条款数从 52 万涨到 1000 万～3000 万时，KS 现有「单文件 SQLite + FTS5 + sqlite-vec」哪一环先塌、换成什么、付什么代价。
> 规模口径：3 万+ 条国标 × 每条数百条款 ⇒ 百万～千万级条款，取 **1000 万** 为设计点、**3000 万** 为上限；向量维度取 768/1024 两档（bge-m3、bge-large-zh 均为 1024）。
> 本线全部数字都标了口径。凡标【推断】的是我按实测斜率或公式算出来的，不是谁测的。
>
> ⚠ **2026-10-25 第二轮就地更正（旧文保留，不删）**：上面「取 768/1024 两档」是**假设换模型**的口径；**本仓现在实际是 512 维**（`src/core/retrieval/embedder.py:EMBEDDING_DIM = 512`，模型 `bge-small-zh-v1.5`；`src/core/storage/schema.sql:131` `embedding FLOAT[512]`）。⇒ 表 2 的内存数字对**现状**偏高约 2 倍：**512 维下 1000 万 × f32 = 19.1 GiB（不是 38.1）、int8 = 4.8 GiB、二值 = 0.6 GiB**；3000 万 f32 = 57.2 GiB、int8 = 14.3 GiB。**结论不变**（向量通道仍是先塌的那一环，因为它取决于「全表算距离」而非维度），但**"64 GB 放不下"只对 1024 维成立**；按 512 维现状，内存不是主要矛盾，**候选集收窄才是**。

## 结论先行

1. **先塌的是向量通道，不是全文检索，也不是条款号检索。** 实测 52.2 万条款 606.0 ms，sqlite-vec 无 ANN 索引（纯暴力扫描，见下）⇒ 按同一斜率外推 1000 万条款 **11.6 s/次查询**、3000 万 **34.8 s**。这不是"慢了"，是交互式检索的终点。【实测斜率 + 推断外推】
2. **条款号精确查找完全不受影响。** 0.1 ms 走 B 树，O(log n)，1000 万行只多两三次比较，仍是 0.1–0.2 ms；这一条在 3000 万条款上依然成立，是全系统唯一"加数据不变慢"的路。【实测 + 推断】
3. **近似检索（HNSW/IVF/PQ）在我们这儿不是性能旋钮，是正确性故障。** 它的定义就是"可能漏掉真邻居"；我们要求"每条结论必须能指回条款原文"，漏一条就是错答。所以本轮结论是 **不引入 ANN 作为唯一向量路径**，代价写在第 6 行。【推断，有 pgvector 官方文档佐证：加近似索引后"同样的查询会返回不同结果"】
4. **可行的替代是两段式：先用条款号/关键词把候选压到 10²–10⁴，再在候选集上算精确距离。** 我们的实测支撑：**候选压到 50 时 top-20 命中 99.0%**；候选 2000 条 × 1024 维 = 7.8 MB，重排是毫秒级；候选 5 万条也只有 195 MB。【实测 + 推断】
5. **两段式的洞在关键词那一段，不在向量那一段。** 实测 1832 个自然语言问题里 **53.0% 与原文零字面重叠**，FTS5 一个候选都给不出；另有 5.3% 才落入 top-5。所以两段式必须配一条"零候选时"的兜底，兜底不能是全库暴力扫描（第 1 行已否）。【实测】
6. **内存/磁盘：单台 64 GB 机器能跑，但只有量化后才宽裕。** 1000 万 × 1024 维：float32 **38.1 GB**、int8 **9.6 GB**、二值 **1.19 GB**；HNSW 图另加 `4×m` 字节/向量（m=16 ⇒ 0.60 GB）。3000 万 × 1024 维 float32 是 **114.4 GB**，64 GB 机器直接放不下。【推断，公式对得上华为云官方文档的 `num_vectors*4*m` 口径】
7. **单文件体积：1000 万条款约 42 GiB，3000 万约 126 GiB。** 由实测 2,246.0 MiB / 522,021 条款 = 4,512 字节/条款线性外推。【实测 + 推断】
8. **「拷走就能用」必须放弃一半：放弃"一个 .db 文件"，保留"一台机器 + 无外部服务 + 拷目录即走"。** 42–126 GiB 单文件仍是可拷的，但每次备份/移植是几十 GB 级拷贝，且向量扫描要求整份进页缓存。最小替代见"对我们"一节。【推断】
9. **要不要上外部检索服务（ES/Milvus/Vespa）？就我们这四问，答案是不上。** 它们在 1000 万级给的 p95 是几十毫秒（厂商自测），但换来的是常驻进程 + JVM/容器 + 内存翻倍（replica=1 即 ×2）+ 许可证风险；而我们的正确性需求（不漏条款）它们同样只能用 ANN 满足，一样漏。买不到我们要的东西。【一手文档 + 转述基准】
10. **可借鉴的只有一件事：分片 + 分区键 + 候选集重排的工程形状**，从 sqlite-vec 的 partition key 与 Qdrant 的 query planner 抄结构，不抄依赖。【一手文档】

### 四问的数字汇总（口径写死在表里）

**表 1：三条通道随条款数怎么变**（52.2 万列的数是实测；1000 万/3000 万是按 19.16×/57.47× 外推）

| 通道 | 52.2 万（实测） | 1000 万 | 3000 万 | 是否随行数增长 | 口径 |
|---|---|---|---|---|---|
| 条款号 / 标准号精确匹配 | 0.1 ms | 0.1–0.2 ms | 0.1–0.2 ms | **否**，B 树 O(log n) | 实测斜率 + 推断 |
| FTS5 全文 | 35.6 ms | **≤682 ms** | ≤2.0 s | 亚线性～线性，看词频 | 实测 + 线性上界（**上界不是测量**） |
| sqlite-vec 向量 | 606.0 ms | **11.6 s** | 34.8 s | **是，严格线性**（无 ANN 索引，全表算距离） | 实测斜率外推 |
| 全库文件体积 | 2,246.0 MiB | 42 GiB | 126 GiB | 是，4,512 字节/条款 | 实测 + 外推 |

**表 2：1000 万 / 3000 万条款的向量内存（GB）**——直接回答"64 GB 单机够不够"

| 维度 | 1000 万 f32 | 1000 万 int8 | 1000 万 二值 | 3000 万 f32 | 3000 万 int8 | 3000 万 二值 |
|---|---|---|---|---|---|---|
| 768 | 28.6 | 7.2 | 0.89 | 85.8 | 21.6 | 2.68 |
| 1024 | **38.1** | **9.6** | 1.19 | **114.4** | 28.7 | 3.58 |
| 1536 | 57.2 | 14.3 | 1.79 | 171.7 | 43.0 | 5.36 |

HNSW 图另加 `4×m` 字节/向量（官方公式，m=16 ⇒ 1000 万 0.60 GB、3000 万 1.79 GB）。**结论**：64 GB 机器在 1000 万 × 1024 维上，f32 勉强（38.1 GB 向量 + 页缓存 + 全文索引），int8 宽裕；3000 万只有 int8（28.7 GB）能放，f32（114.4 GB）**不可行**。【推断；公式对得上华为云 ES 兼容文档 `num_vectors×4×m`】

**表 3：两段式的第二段多久**（候选集上算精确距离，1024 维 f32；按 20 GB/s 内存带宽估）

| 候选数 | 内存 | 估算耗时 | 这一档怎么来 |
|---|---|---|---|
| 50 | 0.2 MB | <1 ms | 我们的实测档：top-20 命中 **99.0%** |
| 2,000 | 7.8 MB | ~0.4 ms | 一个宽一点的 FTS5 `OR` 查询的常见量级 |
| 50,000 | 195 MB | ~10 ms | 零候选兜底时的分片内暴力扫描 |

⇒ 把 11.6 s 换成"几十 ms"的，不是换库，是**换查询顺序**。真正的成本在第一段：FTS5 在 1000 万条款上按线性上界是 682 ms，须靠 trigram 分词与"只在命中的分区里扫"压下来。

## 逐个点评

> 说明：以下 12 项都是**检索底座**，本身不解析文档。§四 模板里的「表格 / 图 / 公式 / 上下标」对它们全部**不适用**——那些由 20-parsing 线决定，检索底座只负责"按给定切片建索引并召回"。我逐项写"不适用"而不假装有点评，避免把解析线的账算到索引头上。

### Elasticsearch
- 是什么 / 谁维护 / 许可证 / 最后提交：Elastic 官方，Java/Lucene。许可证**三选一**：`AGPL-3.0 only` / `SSPL v1` / `Elastic License 2.0`（`x-pack` 仅 ELv2）。最后提交 2026-10-25，78,370 星。【一手：读 `LICENSE.txt` 原文 669 字符】
- **规模**：官方只在"能放下"的层面给口径，不给 p95。ES 自己的内存公式我找到的是华为云 CSS（ES 兼容）文档：`mem_size = (dim × dim_size + neighbors × 4) × num + delta`；**图部分 = 4×m 字节/向量**（`neighbors` 默认 64）。文档里**唯一的示例**是 **SIFT10M（128 维 f32、1000 万条、neighbors=64、1 副本）⇒ 单副本约 7.7 GB、双副本 15.4 GB、含 80% 熔断余量 19.3 GB，官方建议 1 台 64 GB 或 2 台 32 GB**。【一手：华为云文档，2026-10-25 复核】
- ⚠ **2026-10-25 复核后就地更正（原话保留，不删）**：原文写「它的示例正好是 1000 万向量 / 1024 维 / int8 / m=16 / replicas=1 ⇒ 20.34 GB」——**官方文档没有这个示例**（全文无 1024 维、无 int8、无 m=16、无 20.34 GB）。那个 20.34 GB 是**按上面的公式自算的**，属【推断】，不能当一手示例引。本线其余结论不依赖它（表 2 本来就是自算）。
- **表格/图/公式/上下标**：不适用（底座）。
- **中文法规/国标**：有官方 `smartcn`、`analysis-ik`（第三方 medcl）；条款号 `5.2.3` 这类点号数字需要自定义 `pattern` 分词器，否则被当单词。**我没有实测它的条款号召回**，只能标待核。【推断】
- **引用可回溯**：能存 offset/payload，但高亮框属 §六 已否决项，不做。
- **对我们**：不抄。AGPL/SSPL 双许可对一个可能对外分发的桌面端是硬风险；JVM 常驻 + 内存 ×2 违反便携约束；且它的向量路径仍是 ANN（HNSW），不解决第 3 行的正确性问题。**唯一可抄的是 `on_disk_rescore` 的思路**（把向量留盘上、重排时再读），这正是两段式的工程化说法。【一手文档片段：`bbq_disk` / `on_disk_rescore`】

### OpenSearch
- 是什么 / 谁维护 / 许可证 / 最后提交：AWS 主导的 ES 7.10 分支，Apache-2.0（最干净的一个）。13,904 星，最后提交 2026-10-24。【一手 GitHub API】
- **规模**：官方 benchmark 全是 AWS 自家托管服务口径，无独立复现。混合检索走 `hybrid query` + search pipeline + RRF 归一化，形状与我们的六路 RRF 同构。【一手文档描述】
- **中文法规/国标**：自带 `smartcn` 分析器；IK 需装第三方插件。
- **对我们**：不抄。理由同 ES，且它的优势（AWS 托管、免运维）对我们不成立——我们不分云端。
- **可抄**：search pipeline 里做 RRF 归一化的位置划分（先各自打分再统一融合），比我们现在"六路各自排序后按名次融合"更可解释。【推断】

### Vespa
- 是什么 / 谁维护 / 许可证 / 最后提交：Yahoo 起源的商用开源检索引擎，Apache-2.0。7,144 星，最后提交 2026-10-25（最活跃之一）。【一手 GitHub API】
- **规模**：Vespa 官方博客有自家亿级文档的延迟文章，但**均为厂商自测**，未找到独立复现；我本轮没读到其 p95 数字，标待核。
- **中文法规/国标**：中文支持需自带 linguistics 配置，无开箱即用中文分析器；条款号匹配靠 `match: exact` 字段，思路与我们的精确通道一致。
- **对我们**：不抄（依赖重）。**可抄它的"filter-first"查询计划**：先用结构化条件（效力状态、文档类型）缩小，再算相关度——这正是我们两段式的顺序，Vespa 把它做成了默认规划器行为。【一手文档描述】

### Milvus
- 是什么 / 谁维护 / 许可证 / 最后提交：Zilliz 主导，Apache-2.0。46,470 星，最后提交 2026-10-23。【一手 GitHub API】
- **规模**：官方基准是自家数据集 + 自家硬件 + recall@k，属**厂商自测**；2.5 起支持 BM25 全文检索，可做"全文 + 向量"同库。运维需要 etcd + MinIO + 多层组件（standalone 除外）。
- **中文法规/国标**：中文分词不在其职责内，需外部先切好；条款号精确匹配要自建标量索引。
- **对我们**：不抄。为一个单机桌面产品引入 etcd/对象存储级依赖，等于把"拷走就能用"整个送掉（违反 AGENTS.md 便携硬约束）。它的分布式能力我们用不上。
- **注意**：Milvus standalone 可单进程跑，但仍是容器/JVM 级部署，不是"一个文件"。

### Qdrant
- 是什么 / 谁维护 / 许可证 / 最后提交：Rust 写的向量库，Apache-2.0。35,232 星，最后提交 2026-10-23。【一手 GitHub API】
- **规模**：官方文档把"过滤后召回塌陷"讲得最清楚，也是本轮最有用的一手材料：查询规划器按过滤选择性估计在**四条路径**里选（可过滤 HNSW、开 ACORN 的 HNSW、payload 索引、全表扫描）；官方举例：一个命中 1% 点的 `AND` 过滤，500 次查询里 **471 次走 payload 索引、29 次走图**。【一手：Qdrant 官方博客《Pre-Filtering vs Post-Filtering (and Why Qdrant Does Neither)》，2026-08-07——⚠ **2026-10-25 复核对出处更正**：这组数据不在 `documentation/search/search/` 的 Query Planning 节（那节只有 6 条原则性策略）；正文与数字已逐字核实】
- **表格/图/公式/上下标**：不适用。
- **中文法规/国标**：无内置中文分词，BM25 需外部切词。
- **引用可回溯**：payload 可存任意溯源字段，支持按 id 取回。
- **对我们**：不抄（外部服务）。**抄它的规划器思想**：先估"过滤后还剩多少"，剩得少就直接走倒排/标量索引，剩得多才走图——我们的两段式正需要这个决策点，且可以直接用 SQLite 的 `EXPLAIN QUERY PLAN` 当"估算器"。

### Weaviate
- 是什么 / 谁维护 / 许可证 / 最后提交：德国 SeMI，**BSD-3-Clause（但 `wl/` 目录是企业版专有，混合许可）**。16,908 星，最后提交 2026-10-24。【一手：读 LICENSE + GitHub API】
- **规模**：混合检索（`hybrid`）是它的招牌，BM25 + 向量 + `alpha` 权重融合；中文有 `gse` 分词模块。
- **中文法规/国标**：`gse` 是 Go 版 jieba 系分词，对"GB 50016-2014"这种标准号仍需自定义规则。
- **对我们**：不抄。混合许可是隐性法务债（企业版目录不能碰）；`alpha` 权重可解释性不如 RRF。
- **可抄**：把"融合权重"限制成单一显式参数（`alpha`），比六路各自调参更好维护——我们现在六路权重是隐式的名次平均。【推断】

### pgvector
- 是什么 / 谁维护 / 许可证 / 最后提交：PostgreSQL 扩展，**PostgreSQL Licence**。23,470 星，最后提交 2026-10-24。【一手：读 README】
- **规模**：README 两句话是本轮的关键证据：默认**精确**最近邻"提供完美召回"；加近似索引"用部分召回换速度"，且"**加索引后同样的查询会返回不同结果**"。过滤塌陷写得更明白："近似索引下过滤发生在索引扫描**之后**；若条件命中 10% 的行，HNSW 默认 `hnsw.ef_search=40` 时平均只有 **4 行**匹配"。0.8.0 起有迭代索引扫描（受 `hnsw.max_scan_tuples` / `ivfflat.max_probes` 约束）。IVFFlat 的 lists 取 `rows/1000`（≤100 万行）、`sqrt(rows)`（>100 万行）。维度上限：`vector` 2000 / `halfvec` 4000 / `bit` 64000。建索引会提示 `hnsw graph no longer fits into maintenance_work_mem after 100000 tuples`。【一手 README 原文，行号见 jsonl 的 evidence_url】
- **表格/图/公式/上下标**：不适用。
- **中文法规/国标**：无（Postgres 全文检索对中文需 `zhparser`/`pg_jieba`，我未验证）。
- **对我们**：不抄（要一个常驻 Postgres 进程，便携性直接归零）。**但它是本轮最有价值的反面教材**：官方亲口承认"过滤后只剩 4 行"，正是第 1 行"向量通道先塌"的另一条路径。
- 借它的数字做量纲校验：它自己建 100 万行的 HNSW 就要警告内存，我们是 1000 万～3000 万。

### LanceDB
- 是什么 / 谁维护 / 许可证 / 最后提交：Lance 列式格式上的嵌入式向量库，Apache-2.0。11,764 星，最后提交 2026-10-25。【一手：读 README + GitHub API】
- **规模**：README 原文"Search billions of vectors in milliseconds with state-of-the-art indexing"——**只有宣称，无数据集/维度/recall/硬件口径**，属典型厂商话术。【一手 README 原文，行 42】
- **对我们**：**这一项值得单独评估**，因为它是唯一"嵌入式 + 列式 + 自带 ANN（IVF-PQ）+ 版本化"的形态，能保住"无外部服务"。代价：引入 Rust 依赖与 `lance` 文件格式，多一套数据文件（不再是单 .db），且它的 IVF-PQ 同样是近似（第 3 行问题原样存在）。【推断】

- **对我们**：不抄。它解决的是"人类搜索框"，不是"条款号精确定位"。

### Tantivy / Quickwit
- 是什么 / 谁维护 / 许可证 / 最后提交：Tantivy 是 Rust 的 Lucene 等价物（MIT，16,322 星，2026-10-23）；Quickwit 建在 Tantivy 上做分布式日志搜索（Apache-2.0，11,738 星，2026-10-24）。【一手 GitHub API；Quickwit 的 LICENSE 我未逐字读，只信 API 的 spdx】
- **规模**：Quickwit 的宣称是"PB 级日志、秒级搜索"——口径是日志而非条款，不可直接搬；Tantivy 自身是库不是服务，规模取决于调用方。
- **表格/图/公式/上下标**：不适用。
- **中文法规/国标**：Tantivy 有 `jieba` tokenizer（`tantivy-jieba` 第三方 crate），我未验证其对条款号的行为。
- **对我们**：**Tantivy 是本轮第二值得动心的东西**：纯 Rust 库、无外部服务、mmap 索引、可嵌进进程——正好补 FTS5 在 1000 万级排序/短语上的可能短板（第 1 行把 FTS5 排第二位塌）。代价：多一个 Rust 依赖 + 索引目录（不再单文件），且它只解决全文、不解决向量。**标为可选，待实测**。

### SQLite FTS5 / sqlite-vec
- 是什么 / 谁维护 / 许可证 / 最后提交：FTS5 是 SQLite 内置全文索引；sqlite-vec 是 Alex Garcia 的向量扩展，**Apache-2.0**，8,212 星，最后提交 **2026-05-18（13 个仓库里最陈旧，5 个多月未动，维护风险须记）**。【一手：读 README + GitHub API】
- **规模**：README 通篇**没有任何 ANN 索引**：示例就是 `where sample_embedding match '...' order by distance limit 2`，即全表算距离取 top-k；自我描述只有"极小、足够快"（"extremely small, 'fast enough'"），**未给任何性能口径**；纯 C、无依赖、"SQLite 能跑的地方就能跑"（WASM、树莓派）。README 顶部明写 `pre-v1, expect breaking changes`。【一手 README 原文】
- **关键能力（规模方案要用到）**：`vec0` 虚表支持 float / int8 / 二值向量、元数据列、辅助列、**分区键（partition key）**。分区键正好是实现"按领域/文档类型先分片，再在片内暴力算"的原生手段。【一手 README】
- **表格/图/公式/上下标**：不适用。
- **中文法规/国标**：FTS5 有 `unicode61` / `trigram` 分词器；**trigram 对 `5.2.3`、`GB 50016-2014` 这类串可直接子串命中**，是本轮发现的低成本改进点（无需 jieba）。【推断，待实测】
- **引用可回溯**：一行一 clause，`rowid` 即回指，天然可点回原文——这是我们现有优势，不能为换库丢掉。
- **对我们**：**继续用，不换。** 它的问题是"没有 ANN"，而我们的结论恰恰是"不需要 ANN，需要候选集"。要付的代价是：我们自己得把两段式的第一段（条款号/关键词收窄）做扎实，并在零候选时给出兜底。sqlite-vec 的 partition key + int8 是我们的内存解药（1000 万 × 1024 维 int8 = 9.6 GB）。风险：pre-v1 且 5 个月无提交 ⇒ 必须锁版本并留存 vendored 源码。
  - ⚠ **2026-10-25 增量补充（下载量口径，详见 `90-synthesis.md` §十一.1）**：sqlite-vec 的 PyPI 月下载 **5,539,485**（全清单最高，比 fastembed 的 523 万还高），而 `gh api` 实测它最近 100 次提交**全部挤在 2026-02-13 → 2026-05-18 这 3 个月内，之后 5 个多月零提交**。⇒ 它是**「高采用 + 零维护」**：大量生产系统依赖它，一旦出问题（SQLite 升级/平台兼容）**没有上游可等**。⇒ 「vendored 源码 + 锁 SQLite 版本」的优先级比原文写的**更高**；同时**不要把"换掉它"当随时可做的备选**——554 万月下载量说明替代品未必更稳，替换成本要用真数据算。
  - 判活性用**「最近 100 次提交跨多少天」**比"最后提交日"准：同窗对照 MinerU **21 天**、docling **9 天**、sqlite-vec **94 天且停在 5 月**。

### 迟交互（ColBERT / ColBERTv2 / PLAID / ColPali / ColQwen2）
- 是什么 / 谁维护 / 许可证 / 最后提交：`colbert-ir/colbertv2.0` 权重 **MIT**（143.6 万下载）；`vidore/colpali-v1.3` **MIT**；`vidore/colqwen2-v1.0` **Apache-2.0**。仓库元数据我只取到权重卡，斯坦福 ColBERT/PLAID 源码仓的 stars/提交本轮未取到，标待核。【一手：HF API 模型卡】
- **规模**：迟交互的本质是"每 token 一个向量"，存储是单向量的 **1–2 个数量级**；官方论文口径是压缩后仍数十倍于单向量。在 1000 万条款上这是不可行的（单向量已 38.1 GB，×20 即 762 GB）。【推断，基于迟交互定义】
- **表格/图/公式/上下标**：不适用（但 ColPali 的输入是页面图像，会把"表格/公式"变成像素——这属于 20-parsing 线的题目，本线不抢）。
- **对我们**：**不抄，明确不适用**。理由只有一条：存储量级与我们 1000 万条款 × 单机 64 GB 直接冲突。**但 ColPali/ColQwen2 的用途要记一笔**：如果将来要做"扫描件国标页面的版面检索"，它是唯一现成路径（MIT/Apache 许可友好），属 20-parsing 线决策。

### 重排器（bge-reranker / jina-reranker / Cohere Rerank / cross-encoder）
- 是什么 / 谁维护 / 许可证 / 最后提交：`BAAI/bge-reranker-v2-m3` **Apache-2.0**（1,472.7 万下载，最主流）；`jinaai/jina-reranker-v2-base-multilingual` **CC-BY-NC-4.0（非商用！须单列）**；`colbert-ir/colbertv2.0` MIT；Cohere Rerank 是**商用 API，无开源权重**。【一手：HF API + 许可字段】
- **规模**：cross-encoder 的成本是"每个候选一次前向"，因此**它只能吃两段式筛过的候选**——2000 候选 × 1024 token 在 CPU 上是分钟级，在 GPU 上是秒级；这正是它必须放在第二段的硬理由。【推断】
- **中文法规/国标**：bge-reranker-v2-m3 是多语模型，中文可用；对条款号这类字面串它不擅长（本来该由第一段解决）。
- **对我们**：**可作第二段的最后一步，但排在向量距离重排之后**（向量先砍到 50，再上 cross-encoder）。**不要碰 jina 的 v2**（CC-BY-NC-4.0，商业产品不可用）；要 jina 就用 `jina-reranker-v1-turbo-en`（英文，本轮未取许可）或直接用 bge。Cohere Rerank 需联网 + 付费 + 数据出境，与"数据全在本机"冲突，不选。

### 嵌入式 ANN 候选（2026-10-25 第二轮补查——上轮漏了"能保住无外部服务"的一类）

> 为什么补：C 线的结论是「不引入外部检索服务 + 不把 ANN 当唯一路径」，但**如果 sqlite-vec 哪天撑不住，有没有仍能塞进 Electron 单机进程的替代**？上轮把这一格漏了。元数据全部 `gh api` 2026-10-25 抓，能力只到 README 级。

- **FAISS**（facebookresearch，MIT，41,204★，2026-10-25，C++）：Flat / IVF / HNSW / PQ 全都有，是学术界事实标准。**Windows 上游 wheel 是否可用未取证**（本机没装、没试），引入即多一套 C++ 运行库与索引文件。
- **USearch**（unum-cloud，Apache-2.0，4,352★，2026-10-25，C++ 单头文件 + Python 绑定 <1 MB）：README 明写支持 **Windows/Linux/macOS/iOS/Android/WASM**，向量类型含 **f32/f16/i8/二值**，可自定义距离。README 自带 benchmark 表（例：1 亿条 96 维 f32 建索引 2.6 h、1536 维 f32 5.0 h）——**厂商自测，无第三方复现**。【一手 README】
- **hnswlib**（nmslib，Apache-2.0，5,357★，2026-09-15）：HNSW 的参考实现，header-only C++；Windows 上要自己编 Python 绑定，**未取证**。
- **Chroma**（chroma-core，Apache-2.0，29,572★，2026-10-23，已用 Rust 重写）：嵌入式模式可进程内跑，但产品定位是"AI 应用数据库"，带元数据与集合抽象；**规模口径未取证**，从定位看不是为千万级条款设计的。
- **对我们**：这四者都能保住「一台机器、无外部进程」，但**一个都改变不了本线的正确性判断**（ANN 的定义就是可能漏掉真邻居）。它们唯一的合法位置是**零候选兜底时的候选生成器**——生成出来的候选仍必须回到精确距离重算。若哪天必须换掉 sqlite-vec（它 pre-v1、5 个多月没提交），按现有证据**首选 USearch**（Windows 明确、i8/二值、绑定小），FAISS 次之（生态最大但 Windows 打包未取证）。代价与第 5 点同：多一个本地二进制 + 一套索引文件，"单 `.db`"再退一步——**所以只要 sqlite-vec 还够用，就不换**。

## 对不上的地方（来源互相矛盾处，单列，不抹平）

1. **pgvectorscale 471 QPS vs Qdrant 41 QPS（50M 向量 / 768 维 / 99% 召回）——这是厂商自测，且对手方没被公平调参。** 数字本身：PG+pgvectorscale p50 31.07 / p95 60.42 / p99 74.60 ms、索引建 11.1 h；Qdrant 1.13.4 p50 30.75 / p95 36.73 / p99 38.71 ms、建 3.3 h；硬件 r6id.4xlarge（16 vCPU / 128 GB）。**Benchmark 作者自己承认**："我们没能给 Qdrant 的 HNSW 找到合适参数……在这份大数据集上把 ANN-Benchmark 用过的可能性都试一遍时间上做不到，我们迭代了几周。" ⇒ 一边是自家工程师调、一边是现学的人调。【转述：二手分析引作者原话，我未读 Timescale 原文】
2. **同一份 benchmark 被大量二手文章当成"pgvector 很快"，而它测的是别的东西。** 获胜配置用的是 **pgvectorscale 的 StreamingDiskANN + 二值量化**，不是 pgvector 的 HNSW；版本是 pgvector 0.6.1（现已 0.8.3）、2025 年 4 月跑的。二手文章把一年前的运行写成"2026 基准"。⇒ 任何"pgvector 千万级没问题"的说法，先问它测的是不是 pgvector。【转述，二手分析明确指出】
3. **"能装下"被当成"p95 够用"。** 华为云文档给的是内存**容量**公式（1000 万 × 1024 维 int8 × m=16 × replica=1 ⇒ 20.34 GB），不等于延迟；各家的官方 "benchmark" 又多为 recall@10 + QPS，**p95/p99 与内存 GB 通常不同时给**。本轮我能拿到的、同时给 50M 级 p95 与内存的，只有上面那家自测（且被质疑调参）。⇒ 结论：**1000 万条款级"混合检索 p95 几十毫秒"这个说法，我没有找到可信的独立复现**，只能标待核。【推断 + 缺口说明】
4. **ann-benchmarks 本身被质疑过。** 检索到一篇 YDB 工程博客《Are published ANN-Benchmarks DBMS results trustworthy?》，主张已发表的 ann-benchmarks 数据库结果不可尽信；**该文正文我抓取失败（HTTP 404），只读到标题与摘要式描述，未读到其论证细节**，因此不作为本线结论依据，只登记为"独立基准亦被质疑"。【转述，正文未读到——明确标注】
5. **"sqlite-vec 适合生产"两边说法不一。** 官方 README 只说"pre-v1、可能有破坏性变更、足够快"，无任何规模数据；社区说法从"够用"到"百万级就慢"都有，我未取到有口径的第三方实测。我们自己的 606 ms @52 万条款是**唯一有口径的数字**，故本线一律以它为基。【一手 README + 实测】

## 对我们（结论的落地形状）

不改"单文件 + 无外部服务 + 拷目录即走"这条线，只改一层：**把"每次查询都全库算向量距离"换成"先收窄候选再算距离"**。

1. **第一段（收窄）**：条款号/标准号精确通道（0.1 ms，不动）+ FTS5 trigram（补 `5.2.3`、`GB 50016-2014` 的字面命中）。目标：把候选从 10⁷ 压到 10²–10³。
2. **第二段（重排）**：在候选集上算**精确**向量距离（2000 条 × 1024 维 = 7.8 MB，毫秒级）+ 可选 bge-reranker-v2-m3（Apache-2.0）砍到 50。
3. **零候选兜底**（针对 53.0% 零字面重叠的问题）：按 `vec0` 的 **partition key** 分片（领域/文档类型），在片内暴力扫描——分片到 50 万条款时单片 580 ms（按 606 ms×52 万外推），可接受；**不再做全库扫描**。
4. **内存**：现状 **512 维**（bge-small-zh-v1.5）下 1000 万条款 f32 = **19.1 GiB**、int8 = **4.8 GiB** ⇒ 64 GB 单机够用；只有在换 1024 维模型时才必须 int8。**但另有一条与本线无关、却会放大记忆负担的既存缺陷**：`clause_repo` 取 `content_text[:512]` 再嵌入、模型窗口也是 512 token ⇒ 实测 **2.06%（13,666/663,634）条款只有头部进向量**、尾巴独有词 117,654 个（`docs/RETRIEVAL-LONG-RANGE-PLAN.md` 0.10-量化）。换更大窗口的嵌入模型会同时放大维度与存储，**两件事要一起算账**。
5. **必须放弃的**：单 `.db` 文件。改成"一个目录 + N 个分片 .db + 一份 manifest"。备份=拷目录，仍是一台机器、无外部进程。**这是本轮唯一被规模逼退的约束。**

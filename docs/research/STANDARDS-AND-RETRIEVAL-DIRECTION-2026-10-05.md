# 外部标准与检索方向调研（2026-10-05）

> 本轮两件：**OKF/ARD 标准动向** + **ripgrep 那篇文章的适用边界**。
> ⚠ 本文是**外部参考材料**，不是待办。**结论先行，未核的一行一条。**

---

## 一、结论（三句）

1. **OKF 你的产品用不上；ARD 才可能真成标准，而跟它只需几行 JSON。**
2. **ripgrep 那篇讲的是"代码"，跟我们领域相反——它是防止走错路的对照，不是该抄的答案。**
3. **三条外部证据（编码智能体源码研究 / TREC 2025 / 我们自己的实测）指向同一件事：词面对得上时文本搜索赢；对不上时谁都不行。**

## 二、OKF 与 ARD：两个东西，一个可能成标准，一个不一定

### 2.1 先纠正三处（那份转述报告说的与实测不符）

| 转述说 | 实测 |
|---|---|
| 只有 OKF 一个 | **是一对**：**ARD 2026-06-17** 发、**OKF 2026-08-11** 建 |
| "**零生产采用证据**" | ❌ **错**。Google Cloud **官方博客专文**、接进 **Knowledge Catalog**（真产品）、**PyPI `okflib` + npm `js-okf`**、厂商原生支持 |
| OKF 叫 "Open Knowledge **Framework**"、管"网站结构" | ❌ 中文营销号说错。是 **Format**，管**知识包（bundle）**，**不是网站结构** |

### 2.2 ARD 的关键事实（我读了 Google 官方开发者博客原文）

- 全名 **Agentic Resource Discovery**，**2026-06-17** 由 Google 两位工程师（Senior Staff + Distinguished）在官方开发者博客发布
- **「Developed with partners across the industry」**（有伙伴墙）
- 🔴 原文：**「built upon the AI Catalog data model from the AI Catalog Working Group under the Linux Foundation」**
  ⇒ **挂在 Linux Foundation 下**——这是"真要成标准"的经典做法
- **Google Cloud 产品支持**：`Agent Registry`（Gemini Enterprise Agent Platform）
- **它明说自己会"让路"**：「ARD **让开**——把可验证的信任元数据交出去，让 agent 用**它自己的原生协议**建立直连」
  ⇒ **ARD 不是 MCP 的对手，是 MCP 上面的一层**
- 机制：在你**自己的域名**下放一个 `ai-catalog.json`；目录里可以列 **MCP servers / A2A agents / OpenAPI tools**

### 2.3 分层的胜算（那份报告把它们混成一层了）

| 层 | 标准 | 谁在推 | 胜算 |
|---|---|---|---|
| **调用层**（怎么调） | **MCP** | Anthropic 主导，**已是事实标准**（Google 自己的博客都在教「把 REST API 变成 MCP 工具」） | **已定** |
| **发现层**（哪儿有这能力） | **ARD** | **Linux Foundation + Google Cloud 产品 + 伙伴墙** | **较高** |
| **格式层**（知识长什么样） | **OKF** | Google 一个仓库，**1 个贡献者、6 次提交、v0.2、40 天没推送** | **最不确定** |

### 2.4 对我们的动作（三个口子，只有一个要写代码）

| 层 | 我们现在 | 该做什么 | 代价 |
|---|---|---|---|
| MCP | **已是 HTTP API** | 不用做——包一层 MCP 即可 | 低，随时 |
| ARD | 无 | **留个口子**：将来在域名下放 `ai-catalog.json` 声明"我能查法规原文" | **几行 JSON** |
| OKF | 知识在 SQLite | **不跟产品，只准备一个导出器** | **一个脚本** |

**⇒ 怕它成标准，正确的应对是"保证自己随时能吐出来"，不是现在改存储去适配。**
**而 KS 现在没绑死（知识在数据库、对外是 HTTP），这就是最好的位置。**

## 三、ripgrep 那篇：适用边界在文章自己写的最后一句里

**文章**：《传统 grep 已死，Claude Code、Codex 都用 ripgrep 了》（公众号"业余草"）

**它说的事实**（⚠ **下列三条我都没独立核过**，是文章说的）：
- Claude Code 核心工程师 Boris Cherny：**"agentic search is really just glob and grep, and it outperformed RAG"**
- 源码级证据：Claude Code 的 `GrepTool` import ripgrep；Codex CLI 内置 `rg` 二进制；Gemini CLI 捆绑
- **2026 年对 11 个编码智能体的源码研究**：**"没有一个"靠向量检索理解代码库**

**🔴 但它自己划了圈**：
> 「在**代码这个结构化、关键词密度极高**的领域，暴力扫一遍往往比精心建索引更便宜、更准、更可控」

**⇒ 代码能用 ripgrep，是因为代码里有标识符**（`isRetryEnabled`）——**用户问的和库里写的字面高度重合**。
**⇒ 我们的领域相反：53% 的大白话和条文一个字都对不上。**

### 3.1 三条对我们成立的

**① 印证了护城河的方向（最值钱）**
文章那个理由——**「输出格式天生为 Agent 设计：自带文件名、行号、上下文，还是合法 JSON；agent 拿到 `file:line` 后定点读取，不用把几十个文件塞进上下文」**——
**正是 KS 在做的，而且我们更细**：ripgrep 给 `文件:行号`，**我们给 `标准号 + 条款号 + 页 + 坐标`**。
⇒ **"给 agent 可定点读取的结构化定位"是这些顶级工具的核心设计**，而我们的"条款级"比它更语义化。

**② 支持把向量"降级"，不支持"砍掉"**
我们自己的实测：**向量路贡献≈0，却每次付 0.6 秒**（`NEXT-DEV-PLAN` §四 登记 1）。
⚠ **但不能砍**——同处记着：**它恰好是 P1/P2 唯一在用的语义路**。
⇒ **两边合起来正好是 P4 路由规则**：
* **本篇文章** → 词面重合高时，**文本搜索优先**
* **UvA（TREC 2025）** → 词面重合弱时 **稠密重排 +10.6%**，重合强时**反而变差**

**③ 一张自检清单（它列的五条胜利理由，我们各占几条）**

| ripgrep 赢在哪 | 我们 |
|---|---|
| 确定性、可复现、可解释 | ✅ **占**——`sqlite-vec` 是暴力扫，**确定性**（不是近似索引） |
| 低延迟 | ⚠ **不占**——向量路 0.6 秒 |
| 零依赖、开箱即用 | ⚠ **半占**——本地，但要起 Python 服务 |
| **结构化输出给 agent 定点读** | ✅ **强占**——比它更细 |
| 噪音过滤（.gitignore 默认跳过） | ⚠ **未核** |

### 3.2 一条反证

**"没有一个靠向量"只覆盖 11 个编码智能体，不能推广**：
- **TREC 2025 冠军方案（0.6824）就用了微调的稠密检索器**
- 同一篇文章也承认 Claude Code 后来加了 LSP 支持，**"精度层"仍是必要补充**

⇒ **准确读法**：编码 agent 不用向量，是**代码领域不需要**；不是向量本身没用。

## 四、三条独立证据合起来（这是本轮最该记住的）

| 证据 | 领域 | 结论 |
|---|---|---|
| **11 个编码智能体源码研究**（经上述文章转述） | 代码，**词面高度重合** | **文本搜索赢** |
| **TREC 2025 ToT 官方基线** | 描述性回忆，**词面常不重合** | 纯向量 **0.0514** vs BM25 **0.1700**，**两个都差**；冠军 **0.6824** |
| **我们自己的实测** | 法规大白话 | 按字 **6.8%** / 按意思 **5.8%**——**无差别** |

⇒ 🔴 **共同结论：**
**在"词面对得上"的领域，简单文本搜索赢；在"词面对不上"的领域，谁都不行——那才需要更重的手段（改问题、训练、外部知识）。**
**而我们的 53%，正落在第二类。**

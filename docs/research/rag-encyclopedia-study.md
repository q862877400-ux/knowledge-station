### 评价指标：哪些能**纯机械复算**（我们只收这种）

| 指标 | 能不能纯机械 | 备注 |
|---|---|---|
| `IDBasedContextPrecision` / `IDBasedContextRecall` | ✅ **纯集合运算** | **我们的 `(标准号, 条款号)` 就是天然 id** ⇒ 零新数据、零模型。**性价比最高** |
| 机械版 `ContextPrecision@K` | ✅ **纯算术**（`v_k` 取自金标） | 比我们现在的布尔 `exact_hit@1` **多一个"相关项有没有排前面"的排序信号** |
| `StringPresence` | ✅ 机械 | 检查答案里有没有写出标准号/条款号——"结论必须带引用"里**唯一能纯机械守住的一半** |
| `ExactMatch` / `BLEU` / `ROUGE` / `CHRF` / `Levenshtein`… | ✅ 机械 | RAGAS 官方给了示例值可做对齐测试（Levenshtein `0.8918918918918919`、BLEU `0.7071067811865478`、ROUGE-L f `0.8571428571428571`、CHRF `0.8048`） |
| **Faithfulness（忠实度）** | ❌ 要模型拆 claim + 逐条判定 | 官方另给 HHEM 小 T5 分类器替代第二步；**它在中文法规上零证据**，未验证前**别进门禁** |
| **AnswerRelevancy** | ❌ 要模型反推问题 + 嵌入 | **且不需要标准答案**；官方自己注明**分数不保证在 0~1** |
| ContextRecall / ContextPrecision 默认版 | ❌ 要模型 | 但有 NonLLM / IDBased 机械变体可替 |

## 三、我们**已经比资料更进一步**的地方（别被"早就有答案"抹掉）

> 🔴 **先说一条自我更正**：我先前在这份笔记的草稿里，把"候选集规模效应"写成"教程空白、我们独有"。
> **文献核实后改口**：那条**不是我们发现的新东西**——2021 年就有一篇专论标题几乎逐字对应
> （见 §四前）。真正的空白只存在于**这份教程**里，不存在于学界。原文留痕。
> 同理，发现 1、3 也都是**已知现象**。⇒ **我们没有任何一条是"别人没发现"的**，
> 但也**没有任何一条被文献否定**。

1. **重排的适用边界（分档量化）**：教程把 Cross-Encoder 当"**普遍**更准的精排"、不分档不提失效条件。
   我们实测：**它在"说法与原文零词面重合"那档无效且略负（挪上去 12 / 挪下去 18）**，
   只在"说法里直接含术语名"那档有效（条款前 20 命中 20.4% → 26.0%）。
   ⚠ 现象本身**已知且有名字**（经典叫 `vocabulary problem` / `term mismatch`；
   重排模型侧叫 `lexical bias`）。**半新的是我们这一刀**：把"恰好零重合"单独切出来、
   给量化对照——这一档的论文**没找到**。
2. **候选集规模效应**：教程**完全空白**——它没有任何规模-效果数据，而且
   **所有演示都建在 3~6 条数据上**（第 11 章自述"6 个 Entity"、第 12 章告警显示索引只有 3 条），
   **结构上不可能观察到规模效应**。我们的实测（候选 500 → 42,181，前五命中 47.3% → 8.6%）
   它**覆盖不到、也不反驳**。
   🔴 **但学界早有一条专论**：Reimers & Gurevych, ACL 2021
   [*The Curse of Dense Low-Dimensional Information Retrieval for Large Index Sizes*](https://aclanthology.org/2021.acl-short.77/)
   ⇒ **我们该引用它，不该声称是发现。**而且它的**对称结论正好给我们背书**：
   **索引越大，稀疏（BM25）表征反而越稳** ⇒ 我们"保留 BM25 一路 + RRF 融合"是**对的**，
   而且这解释了为什么我们的混合路线有效。
3. **分档评估**：教程全程用**单一平均值**谈效果；我们的关键发现**正是靠分档才看得见**
   （零重合 vs 有重合、术语名重合 vs 定义正文重合）。⇒ 这是方法论上的优势，
   也提醒我们自己：**口径混了就看不出真相**（本会话已经在"非 A 标签"上栽过一次）。
4. **#1 那条修法的覆盖面是量出来的**：**19,693 个空标题里 19,649 个（99.8%）都有同编号的子条款**，
   只有 44 个没有 ⇒ **不用重切、不用重导**就能覆盖几乎全部。
   （口径：正文 <12 字、`hierarchy_path` 为空、编号形如 `4` / `4.1` / `5 技术要求`。）

### 🔴 顺带挖出一个**真缺陷**：长条款的尾巴没进向量（已登记计划 P0.10）

学第 2 章时看到一条硬原则「块 ≤ 嵌入窗口」。核到 `bge-small-zh-v1.5` 窗口是 **512 token**
（HF config 原文核过），而 `clause_vec` 是**一条条款一行、一个向量**（`schema.sql:119-123`）。
实测（取库里最长的 8 条，4,001 字）：**全文的向量 vs 只取前 800 字的向量，余弦恰好 1.0000**
（N≥800 全部 1.0000）⇒ **超出部分被截掉，尾巴根本没进向量**。
规模（字符口径）：>512 字 **10,892 条（2.087%）**、>768 字 **5,021 条（0.962%）**。
⚠ **只有向量那一路漏尾巴**：`clause_fts` 索引的是**全文**，所以按字找仍能找到尾巴上的词。
⚠ `1 汉字≈1 token` 是**推断**，严格口径要用分词器数。
⇒ **这条是"学资料学出来的"**：不是教程有这个缺陷，是**拿它的硬原则去量我们自己的库**才发现。

## 五、**与业主红线的冲突点**（照抄论文就会破线）

1. **CRAG 在置信度低时会"自动去网上搜"**。
   业主台账写死：**缺标准不得自动下载、必须人批、无旁路**（NOT-DOING #20）。
   ⇒ **结构可借，"自动上网"那一支必须改成"问人"。**
2. **HyDE / 一切"自由生成再检索"的做法，与第一条铁律冲突**。
   业主铁律：**禁止用模型预训练知识直接给合规结论**。
   而 HyDE 的机制**就是**把模型记忆里的东西写出来、再拿它去检索 ⇒
   **等于把禁止的东西从后门塞回检索路径，而结果看起来还"有出处"**。
   更硬的一条外部证据：《Hypothetical Documents or Knowledge Leakage? Rethinking LLM-based
   Query Expansion》（**ACL 2025 Findings**，[arXiv 2504.14175](https://arxiv.org/abs/2504.14175)）
   **挑战**了"模型能生成有用的假设文档"这个假设，指出那些提升**集中出现在"生成的文档里含有
   金标准那句话"的样本上** ⇒ 成绩**可能被评测集灌水**（模型本来就知道答案）。
   ⇒ **HyDE 这条路：不走。**我们有"实测 25.6% 更差" + 一篇 ACL 论文两条依据。

### 我们**走对了**（有文献背书）

保留 BM25 稀疏一路 + RRF 融合；不在全库做语义选择而用**有界候选集**；rerank **默认关**；
提问侧"词干 + 前缀"。特别是发现 2 那篇的对称结论——**索引越大稀疏表征反而越稳**——
等于给我们"混合检索"这条路背书。

### 🔴 三个**现成的工具我们没用**（按性价比，全部来自 FTS5 官方文档）

| # | 工具 | 为什么值得试 |
|---|---|---|
| 1 | **前缀索引 `prefix='2 3 4'`** | 官方说前缀查询可以**不额外扫一遍索引**。我们的前缀方案现在 p90 **20.5×** / 最大 **3144×** 放大，这条**可能直接把它压下来**（**建议，未实测**） |
| 2 | **`insttoken`** | FTS5 内建，我们完全没用 |
| 3 | **索引侧 `tokenize='porter ascii'`** | 从根上消除词形不匹配。⚠ 但我们实测过 `porter` 会**改坏标识符**（原词存活率 61.6%）⇒ 这条与"通用资料"的要求冲突，**不如前面两条** |

### doc2query：一条真实存在、但我们**不能莽撞上**的路

- **它确实存在**（[arXiv 1904.08375](https://arxiv.org/abs/1904.08375)，2019）：**入库侧**给每篇文档
  生成"用户可能怎么问"的假查询，把"用户词"和"文档词"对上。
  与我们"提问侧术语桥"**互补**：一个管"用户词→库词"，一个管"库词→用户词"。
- ⚠ **动手前必读**：[Doc2Query--](https://arxiv.org/abs/2301.03266)（*When Less is More*）
  ——假查询会**幻觉、反噬效果并膨胀索引**；**过滤后**才 +16%、查询耗时 −23%、索引 −33%。
- ⚠ 且假查询要**单独建索引再融合**（[Doc2Query++](https://arxiv.org/abs/2510.09557)），
  别拼进正文——否则正文被污染，引用就指不准了。
- ⚠ 一条**与我们红线相关的**：生成式假查询同样有"**知识泄漏**"风险（见 §五第 2 条），
  上它之前必须先用**不含答案**的语料验，不能拿"模型本来就知道"的题去测。

### 一条**便宜的现成诊断信号**（可以立刻用）

文献建议"只在诊断出 mismatch 时才做查询扩展"（selective expansion，
[Zhao & Callan SIGIR 2012](https://dl.acm.org/doi/10.1145/2348283.2348354)，⚠ 403 仅核到标题）。
⇒ **我们手上已经有这个诊断信号**：本会话实测的"**与定义条款零实词重合**"本身就是现成的
mismatch 判据 —— 那 1,078 条零重合样本，正好就是"该触发扩展"的那一档。

### 🔴 文献下载的一条硬教训：**HTTP 200 ≠ 抓到的是那一篇**（2026-09-25 实测）

让子代理按"推断出来的" ACL 链接去抓 4 篇论文：**4 个 URL 全部 HTTP 200**，
但**页面内容是另外的论文**（域名对、状态码对、看起来一切正常）。
⇒ 落地成判据：

> **抓到一页 ≠ 抓到那一篇。** 状态码、域名、"看起来像"**都不构成证据**；
> 只有**页面上的身份字段（标题／作者／年份／DOI）与目标逐字对上**才算抓对。

**它和我们产品的关系比它看起来更近**：我们对外承诺的"引用能点回原文"，
同一类错误就是——**能点开 ≠ 点开的是那一条**。所以引用锚点必须落在
**可机械核验的标识**上（标准号 + 条款号、文档哈希 + 字符区间），
而不是落在"一个 URL"或"一段看起来相似的文字"上。
本仓已有一次同型取证（`docs/CHANNEL-COVERAGE-PLAN.md` 的 **G14「HTTP 200 ≠ 有数据」**）——
那条讲的是"**200 但没有数据**"，这条讲的是"**200 但有数据、只是不是我要的那一份**"，
两种都要防。

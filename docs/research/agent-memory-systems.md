## §0 一句话结论

**业主问的"做一个介于 RAG 知识库与记忆之间的东西，把 agent 的记忆扩展到百万/千万条"——
这次调研给出的答案分三句：**

1. **方向成立，而且我们比这批项目更有资格做**：我们已经有它们都没有的三样东西——
   **逐字原文**、**效力由发布机关决定**（不是"谁记得更晚谁赢"）、**评审三态硬门**。
2. **但"百万/千万条"目前是无人验证过的地带**：全领域的记忆评测量程只到 **≤1.5M token**、
   **最大条目数 21,793 条**；公开的"百万级"要么是 **token 长度**，要么是**纯向量索引**，
   **没有一个是"记忆系统管百万条记忆"**。所以**没有现成配方可抄**——这一条必须我们自己量。
3. **而且"把检索层堆到百万条"这条路是堵的**：我们自己的实测（§6）是**随条数线性**（522k 行 636.6 ms），
   我们用的向量索引官方自述就是**只能暴力扫**（官方基准只到 100k）。
   ⇒ 能到百万/千万的**不是原文层，而是它上面的"窄表"派生层**（§2.2 末尾）。

**给业主的决策简报：**

- **现在已经有的**（不用新建）：原文逐字可点回、效力状态可查、材料评审三态、范围提问、
  办事台三条流水线、以及一套真机跑得通的门禁。
- **缺的只有一样**：**没有一层"派生记忆"**——谁问过、哪条原文答的、结成了什么结论、后来有没有被推翻。
  今天这些**全部没有落盘**（问过的记录 1000 行就被挤掉，§6.1）。
- **"百万/千万"能不能做到的判断**：**原文层可以不动**（它已经不是记忆，是资料库）；
  派生层是窄表（一条一行），**到百万/千万条是存储与索引工程问题，不是模型问题**。
  但**能不能"记住得准"到这个量级，目前没有任何人验证过**——包括我们。
- **建议的第一步（不是动手建，是先定规矩）**：写一份**属于自己的"记忆策略"**——
  存什么、多粗、留多久、凭什么证据、谁能改、冲突怎么显示。
  理由：我们**已经因为这个出过一次事**——"保留多久"曾在两处各自决定，结果记录被误删
  （§1.4 引 hindsight 的删除约束，正是同族教训）。
  **没有这份策略，任何规模的记忆层都会重犯同一个错。**
- **不建议做的**：不要为了"百万"去自建向量索引、不要照抄哪家的常量（RRF 的 k 各家不同，§5.3）、
  不要把知识库改造成记忆系统（那会丢掉可追溯性）。
- **要抄的只有两处**（其余一律不造轮子）：① 图边的时间失效（旧依据不删、只失效）；
  ② 删除必须指名目标、否则整批作废的强约束。

## §1 我们自己在用的那一套（Hindsight）—— **拆解式**结论

**方法**：读本机实物（源码 / 数据库只读 / 服务只读接口），不看二手介绍。全程只读（PG 强制只读事务、HTTP 只发 GET）。

### 1.1 它是什么

| 项 | 事实 |
|---|---|
| 开源？ | ✅ **开源**，而且本机**既有运行态也有完整源码**（不是"只有服务"） |
| 许可证 | **MIT**。wheel 内 LICENSE 全文 1075 B（`Copyright (c) 2025 Vectorize AI, Inc.`，`License-Expression: MIT`），**与上游 GitHub 的 LICENSE SHA256 逐字节相同** |
| ⚠ 许可证陷阱 | **两处写着 "Apache 2.0"，与发布物矛盾**：包元数据的说明正文末尾、以及**正在运行的服务的 `/openapi.json`**。⇒ **别引用那两处** |
| 形态 | PyPI 包 `hindsight-api` **0.10.0**（326 个 `.py` / 11.81 MB）+ **内嵌 Postgres 18.1 + pgvector 0.8.5**（数据目录约 **4.7 GB**） |
| DSH 侧 | 插件 `@vectorize-io/hindsight-coding-agents` **0.6.1**，**只发布打包产物、无 TS 源码**（对它只能 grep 产物） |

### 1.2 技术路径（三句话）

* **写**：宿主钩子（停止/空闲）→ 按文件 sha256 去重 → 切块 3000 字 → **云端模型抽事实**（world / experience 两类）→ **本地小模型**（384 维）→ **建图**（时间边 ≤20/条；语义边取近邻 top-50 且阈值 0.7；因果**只**写 caused_by）+ 抽实体。
* **读**：**3 种事实类型 × 4 路**（语义 HNSW / 关键词 BM25 / 图扩展 / 时间窗）**一次调用跑完** → **RRF 融合** → **本地重排模型**。
* **"知识页"不是归并产物**：它是另一类对象（心智模型）的**目录投影**，每页一份模型摘要 + 每小时错开刷新；**全库只有 15 页**。

### 1.3 数据模型要点

Postgres 18.1，**25 张表、0 张分区表**。核心：

* 事实本体表：文本 + **384 维向量** + 事实类型 + **4 个时间列** + **来源血缘**；
* 图边表：枚举里有 7 种边，**实测只写 3 种**（semantic / temporal / caused_by）；
* 实体表 + 实体共现表；原文与切块表（按内容哈希去重）；
* 知识页 → 外键 → 心智模型；观察历史（版本）；
* **作废归档表**（把作废的事实挪走、**丢掉向量**，回滚时重算）；
* **全量请求留痕表**（每次抽取的完整提示都存）。

**向量索引形态**：**30 个按（库，事实类型）切的 partial HNSW 索引**（10 库 × 3 类型）+ 1 个给心智模型。

### 1.4 到百万/千万条会先坏在哪（**证据分层**）

| # | 结论 | 证据层级 | 内容 |
|---|---|---|---|
| A | **先坏在"库的数量"，不是单库数据量** | **源码明写** | 索引建在共享表上会**扇出**：源码原文说"一个库的索引会被摊到**其它每个库**的查询上；**每库三个索引、几千个库就耗尽锁表**"（上游 issue #3485）；另一处补充：撞上它的部署**连"删除一个库"都跑不了**。⚠ 本机是 10 库 = 30 索引 ⇒ **离墙还有约两个数量级** |
| B | **图边表是单体最大对象** | **实测 + 推断** | 实测 5.91M 行 / **2,684 MB**（堆 693 + **索引 1,991**），其中单个唯一索引 **827 MB**；约 454 字节/边、**实测约 45.3 边/事实** ⇒ **推断**：100 万事实 ≈ **21 GB**、1000 万 ≈ **210 GB**。**是线性不是二次**（边数有硬上限：时间边 ≤20/事实、语义边 top_k=50） |
| C | **"几百万行"已经爆过一次** | **源码记录了真实事故** | 原文：在"multi-million-row"的库上，两条语句**都无法在超时前跑完，任务每一次都失败、永远失败**（issue #3222）；修法是改成**队列驱动**。⇒ **推断**：同类没改成队列的库级语句就是下一个 |
| D | **召回会先于延迟退化，而且不报错** | **源码取舍 + 推断** | HNSW 的 `max_scan_tuples` 被**故意**从 pgvector 默认的 20000 降到 **4000** ⇒ **推断**：过滤很苛刻的查询会"**召回变浅但静默**" |
| E | 本机 100% 的事实"归并时间"为空 | **实测，但须区分解读** | zcode 库 114,951 条事实、归并标记全空。⚠ **这不是性能积压、是配置**：一个开关关着，让归并的门槛从不提交。副作用（实测+定义）：那条"未归并"的偏索引**覆盖全库、永不剪枝** |

**E 行已用官方接口复核（2026-09-26 收工前，只发 GET）**：`GET /v1/default/banks/{id}/stats` 直接给出口径数字——
我们那个库 **`total_nodes` 114,970**（经验 28,628 + 世界 86,342）、`total_links` **5,337,849**、
`total_documents` **3,529**、**`pending_consolidation` = 114,970（= 全部，一条都没归并过）**、
**`total_observations` = 0**、`last_consolidated_at: null`。
⇒ **"11 万多条事实"这条数字成立，而且就在我们这个库里**（§1.7 里我原先登记的"归属库待查"可以撤销）。
⇒ 而**对照那两个老库**（`dsh-user` 201 条 / `dsh-knowledge` 95 条）都**有** observations、
`last_consolidated_at` 也是**非空**的 ⇒ **归并能力本身是好的，是我们这个库没开**。

### 1.5 两个**口径陷阱**（引用时务必避开）

1. `/stats` 里的"实体边数"（zcode 报 **132,845**）**不是图边表的行数** —— 该类型实测 **0 行**；
   它的公式是 `Σ min(n-1, 10)`，即"**图视图会画出来的**实体边数**估算**"。**别当真实边数引用**。
2. 数据量全是**单次实测**，且 Postgres 自己的行数估算**严重过期**（它说图边表 19,090 行，实际 **5.91M**）
   ⇒ 本笔记一律用 `count(*)` 的数。

### 1.6 🔴 **关于"更正"这件事，我要更正我自己**（2026-09-26）

**我先前对业主说过**："这个记忆库没有删除动作；它唯一被认可的纠错机制是**写入一条 `Correction: <主题>` 记录，
让新事实盖过旧事实**（工具本身就是这么设计的）。"

**拆解调研证明这句话有一半是假的**：

* **`Correction:` 在 326 个源文件里出现 `0` 次**（`grep` 全源码）⇒ 它**不是引擎机制**；
  真实身份是**宿主插件 hook 提示词里的一条命名约定**（报告已逐字引用原文）。
* 实际借力的是**通用设施**：新事实 + 时间排序 + **显式作废**（有一张作废归档表）。
* ⚠ 而**"归并取代"这条路在本机压根没开**（`enable_observations=false` ⇒ 归并门槛从不提交；
  旁证：`async_operations` 里归并只有 58 条、全部完成于 2026-09-10 那次迁移）。
  ⇒ **"新事实自动盖过旧事实"在本机并没有在跑**；能"盖过"的是**时间排序**（新的排在前面），
  以及**显式作废**。

**这条为什么值得单独写**：我当时是**照着工具描述**下结论的（"工具本身就是这么设计的"），

### 2.2 技术原理谱系：常见类型只有「六个流派」

业主问"常见热门类型有哪些、技术原理是什么、特点优劣是什么"。按**存的是什么**分类，这批项目落在六个流派里，
每个流派的原理、优势、代价都是同构的：

| 流派 | 存什么 | 代表 | 原理 | 优势 | 代价（**这是关键**） |
|---|---|---|---|---|---|
| **① 逐字原文派** | 用户的**原话**，一个字不改 | MemPalace | 全文逐字入库（Wing→Room→Drawer）；另建**压缩索引层**供模型扫；读出＝余弦+BM25 凸组合重排 | 设计目标就是 **100% 召回**；无抽取损失；可审计（能指回原话） | 体量随对话**线性膨胀**；索引层要靠压缩换速度；**不做泛化**（不会"总结出你的偏好"） |
| **② 抽取事实派** | LLM 抽出的**原子事实/偏好** | mem0、Memori、memobase | 写入时 LLM 抽事实（mem0 四步：查重→抽→去重嵌入→实体抽取），再用 LLM 判 `ADD/UPDATE/DELETE/NONE` | 紧凑、跨会话、精度高 | **抽取损失不可逆**（抽掉的原文就没了，没有回退源）；写路径要调 LLM（成本/延迟）；冲突靠 LLM 判断，**没有权威** |
| **③ 时间图派** | 实体/关系**边**，带生效与失效时间 | graphiti、cognee、zep | 边带 `valid_at`/`invalid_at`/`expired_at`；发现矛盾时**旧边标失效但不删**，时间查询走 valid-at-time 子图 | 能回答"**三月份**那会儿是哪个"；多跳；证据链可追 | 建图成本高；**实体消解错了会一路错下去**；边数膨胀（§1.4 B：hindsight 实测 **45.3 条边/事实**） |
| **④ 分层/虚拟内存派** | 主上下文 + 可换入换出的外部存储 | Letta（前 MemGPT） | 借鉴操作系统分页：主上下文固定、外部无界，模型自己调记忆工具触发"缺页换入" | **模型自己决定什么重要**；结构显式（记忆块可读可写可限长） | **每次记忆操作都在关键路径上** ⇒ 尾延迟；块会膨胀；后台改写主智能体不知道 ⇒ **静默漂移** |
| **⑤ 单文件/嵌入式派** | 一个自包含文件 | memvid | 一个 `.mv2` 文件内放头 + WAL + 向量/全文/时间/图多条轨道，读时多路候选 RRF 融合 | 零服务、可携带、可加密 | 单写者；**引擎本身不必抄**（我们已经有库） |
| **⑥ 常驻答案派** | 事实 → 观察 → **常驻答案**三层 | hindsight（§1） | 事实层之上再生成"观察"（带证据与计数）与"知识页"，页面过期就重算 | 常用问题不必每次重推；带了证据与新鲜度 | 多一层就有多一层的**过期与不一致**（§1 的 `consolidated_at` 全空就是这个坑） |

**穿透六个流派的五条选择轴**（任何系统都必须各选一个值，选完就决定了它的性格）：
**① 写在哪**（热路径当场写 / 会话后后台写）· **② 粒度**（逐字 / 事实 / 边 / 页）·
**③ 读怎么融合**（几路信号 + 怎么重排）· **④ 冲突谁说了算**（时间新的赢 / **权威方赢**）·
**⑤ 遗忘怎么做**（物理删 / 标失效 / 降级显示 / 按频次降温）。

**最本质的取舍是一句话：保真 ↔ 泛化。** 逐字派保真但不泛化；抽取派泛化但**丢掉的原文永久丢失**。
所有"记忆系统"的优劣，基本都是这一条的不同摆法。

**这一条直接回答了业主的"中间形态"该怎么定位**（我们的判断，不是文献结论）：
我们的知识库**本身就是①逐字原文派**（条款原文逐字入库、可点回原文），而且比它们多一件它们都没有的东西——
**效力由发布机关决定**（现行/废止/即将实施），不是"谁记得更晚谁赢"。
所以"介于 RAG 与记忆之间的东西"不该是把知识库改造成记忆，而是**在①之上补一层②的索引 + ⑥的常驻答案**：
把"谁问过、哪条条款答的、结成了什么结论、有没有被推翻"沉淀成**派生层**——
**原文层不动**（保真、可审计），派生层可重算、可失效。
这样既能到百万/千万条（派生层是窄表），又不会因为抽取损失而丢掉可追溯性。

### 2.3 这批系统**共同不解决**的三件事（对我们最关键）

1. **条款级引用**：它们能给出"某条记忆"，但给不出"标准号 + 条款号 + 可点的原文位置"。全部 14 个项目里，
   只有 `letta-code` 的 `docs/examples/mods/memory-citations.ts` 给出同族形态
   （引用快照 + 只许引用快照内的路径 + 没观察到读取就不许编引用）——**这正是我们已经在做的**。
2. **效力的权威来源**：它们建模的是"记忆的新旧"（谁记得更晚谁赢）；我们建模的是"法规的现行/废止/即将实施"
   （由**发布机关**决定，不由时间决定）。**这是根本差异**，不能靠抄它们的冲突解决来替代。
3. **评审硬门**：没有任何一个项目有"未经批准的材料不得进结论"这种关卡——它们是"能记住就记住"。
   我们的**评审三态（待评审/已批准/已否决）是产品级判据**，不属于记忆系统的能力范围。

### 3.1 学术侧的类型学是**另一种切法**（按机制，不是按存什么）

§2.2 那六个流派切的是"**存的是什么**"；学术侧通常按"**机制怎么实现**"切，得到六类，可与 §2.2 对齐：

- **遗忘**：是**一等公民**不是异常路径（MS 第 13 课原文把 forgetting 列进记忆管理定义）；
  **合规级做法是"不改写、只作废"**——mem0g 冲突时旧边标 invalid **但不删除**，时间查询走 `valid-at-time` 子图；
  显式更正必须应用**显式**调 `update`/`delete`（自动抽取只做追加）；按使用频次**降温到冷存储**。
- **分层是共同底座**：MemGPT（主上下文/外部上下文，类比 RAM/Disk，缺页=记忆工具调用）、
  Letta（Core/Recall/Archival，表里带 **"Written by"** 列）、MS（六类）、LangMem（语义/情景/程序）
  ——名字不同，**结构同构**。
- **四条共同工程纪律**：① 只存值得复用的，不存逐字 transcript；② 读取必须带 **scope 过滤**
  （user/agent/run），否则用户之间、agent 之间的记忆会串味；③ 延迟要管（小模型先判"值不值得存取"，或合并放后台）；
  ④ 要能评估（LoCoMo / LongMemEval / BEAM）。
- **sleep-time compute 的具体形态**（ai-engineering 第 08 课，原文已读）：跑**第二个智能体在后台、离线于关键路径**，
  它处理转录与代码上下文、把 `learned_context` 写进共享记忆块、并合并/作废归档记录。
  三个推论：**无延迟代价**、**允许用更贵更慢的模型**、**天然有巩固时间窗**。
  该课同时列出三种失败形态：**块膨胀**（写入撞上限，需在写入前挂摘要器）、
  **静默漂移**（后台改写了记忆块而主智能体不知道 ⇒ 要**版本化并展示差异**）、
  **投毒合并**（后台智能体把攻击者可触达的内容并入核心 ⇒ 需二次审核）。

### 5.1 ⭐ 最重要的负结论：**没有人真跑过"百万条记忆条目"的端到端记忆系统**

必须先分清**三种"百万级"**，混起来就会得出错误结论：

| 被真测过的"百万级" | 到什么量级 | 在测什么 | 是不是在测"记忆系统管百万条记忆" |
|---|---|---|---|
| **(a) token 量** | BEAM 四档 **128K/500K/1M/10M** token（10M 档每段均 **10,435 条用户消息 / 7,757 轮**）；LongMemEval-V2 到 **25M/115M** token | 合成对话的**上下文长度** | ❌ 不是。单位是 token，10M token 里可能只装几万条原子记忆 |
| **(b) 纯向量检索索引** | HNSW **10M 向量**；FAISS/DiskANN **1B 向量**；VectorDBBench 用例 1M/10M/100M | 索引本身的**速度与召回** | ❌ 不是。没有写入、冲突、遗忘、溯源 |
| **(c) 记忆系统的评测规模** | 见下表 —— **最大条目数是 21,793 条** | 记忆的**读/写质量** | ✅ 是，但**量程差"百万条"一个半数量级** |

**记忆系统真实评测过的规模（全部回一手核过）**：LOCOMO 每段对话平均 **9,209.2 token**（50 段 / 7,512 题）；
MemGPT 开创性评测只有 **5 个会话**；MemoryBank **10 天 / 15 个虚拟用户**；
LongMemEval_S 约 **115k token**（≈40 会话）；MemoryAgentBench **103k–1.44M token/题**；
**2026 年最严肃的"规模"研究（`2605.07313`）阶梯顶端只有 400 个追加无关会话（s4 = 401.2 会话 / 1.03M token/query）**，
论文自己定义 `s* > 400 means no breakdown is observed through s4` —— **量程到 400 就封顶了**。
条目数最大的公开数字是 **MemTest 的 21,793 条**（独立 OSS 项目，**非论文、无同行评审**）。

⇒ **对业主那句"扩展到百万/千万条"的直接含义：现有文献不构成任何外推授权。**
所有"记忆有用/无用"的结论都只在 ≤1.5M token、≤2×10³ 条问题的量程内成立；
跨出这个量程会发生什么，**只有间接证据，没有受控实验**。

## §6 **我们自己的曲线**（本机真库实测，2026-09-26）

业主问的是"我们的记忆能不能到百万/千万" ⇒ **第一手答案要从我们自己的曲线上看**，不在别人的博客里。

**真库规模**：文档 **6,797** / 条款 **522,021** / 向量行 **522,021**；数据集约 **2.2 GB**。
查询示例「防火间距不足时应该怎么处理」，每项取 **7 次中位数**（`var/tmp/probe-recall-latency.py`）。
**下表是机器静下来后的复测值**（2026-09-26，四路调研代理全部收工后）——与忙时那次相差不多，
说明量级可靠（忙时那次是 636.6 ms，见下方诚实边界）：

| 通道 | 耗时 | 随数据量怎么变 | 形态 |
|---|---|---|---|
| 查询嵌入（512 维） | **1.3 ms** | 固定 | — |
| **向量 KNN（k=20）** | **606.0 ms** | **线性 ∝ 条数** | **逐条比对，无 ANN 索引** |
| 全文 / 倒排（k=20） | **35.6 ms** | 基本不涨 | 倒排索引 |
| 精确条款号 | **0.1 ms** | 不涨 | 有索引 |

**外推**（**只对向量那一路成立**，因为它是逐行扫；按 **1.1609 ms/千行**）：

| 条数 | 向量那一路约 |
|---|---|
| 100 万 | **1.16 秒/次查询** |
| 1000 万 | **11.61 秒/次查询** |

**佐证"是逐行扫、不是索引"**：k 从 20 改成 500，耗时只从 606 ms 到 982.6 ms（**小一个量级的变化都没有**），
若是 ANN 索引，k 会显著影响耗时。⚠ 但 **k=1 反而 751.9 ms > k=20 的 606.0 ms**，
且**忙时那次也是同样的倒挂**（879 ms vs 637 ms）⇒ 这**不是负载噪声**（静下来仍复现），
是这条查询路径上一个**未解释的形态差异**（可能 k=1 走了不同的执行计划），**登记为待查，不影响"线性"这个结论**。

### 6.1 两个发现叠在一起（本节最重要）

1. **它是唯一的规模墙**：三条路里只有向量那一路随条数线性涨；
2. **而固化的消融结论说：问答场景里它贡献≈0** —— 精确条款号是绝对主力（关掉掉 **38 个百分点**）、
   全文值 **1.1 个百分点**，**向量/模态/法理要素/行为客体四路在问答场景贡献≈0**（保留是为审查场景与将来）。
   出处：`docs/ENCYCLOPEDIA.md` §3.3（2026-08-23 实测，结论已固化）+ `docs/VISION-TREE.md` §8。

⇒ **我们每次提问都在为一个"实测贡献≈0"的通道付约 0.6 秒**（默认六路通道含向量，
除非调用方显式收窄：`SEARCH_CHANNELS` 含 `vec`；问答路径透传调用方给的通道集）。
而这**正是**"记忆要上百万/千万条"会先撞上的那面墙。

**而且这条墙的性质已经被别人的官方件证实**（§5.3 第 1 条）：`sqlite-vec` 官方自述就是
**brute-force only**、官方 benchmark 只做到 **100k** 向量。
⇒ **我们的 606 ms 不是配置没调好，是这条技术路线的天花板。**

⚠ **诚实边界**：
* 忙时那次（636.6 ms）是**同时跑着 5 个调研代理**时量的；已按承诺**在机器静下来后复测**（606.0 ms），
  两者相差 <5% ⇒ **量级结论站得住**；
* "贡献≈0"的含义是"**把它去掉，问答指标不动**"，**不是**"它永远没用"；
* 🔴 **2026-09-27 补一条更要紧的：这条消融只证了"无贡献"，没证"无害"。**
  外部三条独立反证（源 `var/tmp/study/problems/F-chunking.md` §推翻既有做法）：
  ① **Bekko（arXiv 2607.25180, 2026-07）实测 BM25 打败全部 12 个稠密模型**于长文档基准
  （NanoLongEmbed 0.822 / NanoMLDR 0.740），并引 bge-m3 论文自报"dense long-document retrieval
  remains an open problem"；② **ECHR 法律域实测按相似度排比随机排还差**
  （arXiv 2606.03728 原文："ranking by similarity performs **worse than random selection**
  at surfacing gold citation paragraphs"）—— **这一条正落在我们的语料类型上**；
  ③ 强塞静态通道在留出折上**显著变差**（arXiv 2608.02112）。
  ⇒ **"去掉它指标不动"与"它会拖后腿"是两件事，我们只做过前者。**
  在 ECHR 那条出来之前，**不能**把"默认关掉向量通道"当成已证无害的动作；
* 默认关掉它属**行为改动**（要复核），且这属**业主决定**。

### 6.2 与 §1.4 对照：两套系统的墙**不是同一面**

* **我们的墙**：单库（单表）**条数** ⇒ 一条路逐行扫。
* **Hindsight 的墙**：**库的数量** ⇒ 每库 3 个向量索引在共享表上扇出，几千个库耗尽锁表（1.4-A）。

⇒ 这给了一个**方向性的启发**：规模化的第一手段可能不是"把一张表做大"，而是**分区/隔离**。
但**两边都还没到墙**（我们 52 万条、它 10 个库），所以这**只是方向，不是结论**。

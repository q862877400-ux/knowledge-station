# 命名与分类规范（正式件）

> **这是仓库的正式命名规范**（001-project-consolidation T001 的产出）。
> **设计依据与决策过程**（含 v1 为什么作废、v1 原文留痕）在
> [`specs/001-project-consolidation/contracts/naming-convention.md`](../specs/001-project-consolidation/contracts/naming-convention.md)——
> 那里是**设计契约与取舍记录**，本文件是**规则本身**。两处分工刻意如此：
> 规则要短、要能一眼执行；取舍理由要留痕、不该混进规则里。
> **本文件是规则的唯一归属层**；别处提到命名规则一律链到这里，不再复述。

**生效日**：2026-10-05（v2 定案）｜**执行记录**：[rename-map.md](../specs/001-project-consolidation/rename-map.md)

---

## 一、第一原则：代码跟随语言，文档跟随本仓约定

| 类别 | 规则 |
|---|---|
| **Python 代码** | `snake_case.py`（PEP8） |
| **JS/TS 代码** | 跟随**同目录既有**写法（本仓混用，不再强推一种） |
| **文档** | 沿用本仓"标准文档全大写、其余按目录"的既有约定 |
| **目录** | 全小写 kebab-case |

**反例**：`src/core/api/routes_channels.py` 的**下划线是对的**——它是代码，不是文档。
按"文档全小写"去改它，会断掉每一个 `import`。

---

## 二、文档文件名：用连字符 `-`，不用下划线 `_`

**反例**：`docs/LAW_SOURCE_PLAN.md` ⇒ 应为 `docs/LAW-SOURCE-PLAN.md`。
（这条**只管文档**；代码里的下划线不适用，见 §一。）

---

## 三、文档大小写

- **标准文档**（被 `AGENTS.md` 或 `README` 点名的）**保留全大写**——全大写本身就是
  "这是常驻引用、不是随手笔记"的信号。**不许**为了整齐改成小写。
- **其余文档**保留现有大小写；新增文件按所在目录既有写法。
- `README.md` / `INDEX.md` / `CONTRACT.md` / `AGENTS.md` / `LICENSE` 用全大写（通用约定）。

**反例**：把 `docs/NOT-DOING.md` 改成 `not-doing.md` ⇒ `AGENTS.md` 里的引用当场断掉，
而 `AGENTS.md` 是每轮必读的注入文件，改它的成本远大于收益。

---

## 四、分类靠目录，不靠文件名前缀

**不许**用 `plan-` / `research-` / `ledger-` 这类前缀当分类器。

**理由**：用前缀分类会把分类**写死在名字里**——一个文档从"计划"变成"历史"就得改名，
而改名要修全仓引用。用目录分类则只需移动文件。

**反例**：`plan-kb-folder.md` ⇒ 应为 `docs/KB-FOLDER-PLAN.md` 放进 `docs/`，
归档时移动成 `docs/archive/old-plans/`，名字一个字不用改。

---

## 五、日期后缀只给"会被取代的真源"

格式 `-YYYY-MM-DD`。

| 带日期 | 不带日期 |
|---|---|
| 计划、方案、阶段台账、状态快照 | 研究笔记、组件契约、map、索引、规范 |

**反例**：给 `docs/wiki/components/retrieval.md` 加日期 ⇒ 它每改一次就"该换日期"，
而它并没有"被下一版取代"的语义。

---

## 六、写日期前必须核系统时钟

> 2026-10-05 实测：两份新文档的日期全写成上文带过来的 `2026-09-30`，而当天是 `10-05`。
> **从上文继承日期而不核时钟，必错。**

---

## 七、目录职责（一个东西只归一处）

| 目录 | 装什么 | 不装什么 |
|---|---|---|
| `docs/` | **当前真源** | 历史、过程记录 |
| `docs/wiki/` | **接手文档**：大 map、项目现状、组件契约 | 实现细节 |
| `docs/archive/` | **历史**：被取代的计划、过期基线、调研过程、已收口复核 | 任何仍然算数的东西 |
| `docs/research/` | **外部研究**的结论 | 本仓自己的计划与台账 |
| `specs/` | **Spec Kit 工作区** | 产品文档 |
| `var/` | **本地产物**（不进版本控制） | 任何需要交接的东西 |

**边界口诀**：**"交接时新人需要看它吗？"** 需要 ⇒ 不是 `var/`；不需要 ⇒ 不该在 `docs/`。

---

## 八、"历史"与"真源"的判据

一个文档进 `docs/archive/`，当且仅当满足其一：

1. 有更新的同类文档取代了它；
2. 它记录的是**过程**，结论已落进别的文档；
3. 它对应的工作**已收口**；
4. 它的数字/结论与当前基线冲突且无人维护。

**拿不准 ⇒ 进归档，不删。**（`var/` 下不受版本控制，**只移动、不删除**。）

---

## 九、改名执行契约

1. **先出对应表**（每行：现名 / 新名 / 理由 / 受影响引用数）。
2. **脚本机械执行**（`git mv`），**不许**手敲路径。
3. **同步改正三类引用**：文档间链接 / 代码里引用的文档路径 / 门禁脚本断言。
4. **跑独立的全仓断链检查**（`python scripts/docs/check-links.py`）验证残留为 **0**；
   **不许**只凭"门禁绿了"断言——门禁扫不到全部文档。
5. **最后跑门禁**，测试基线**不许**下降。
6. **撞车停下来报告**，**不许**静默加后缀。

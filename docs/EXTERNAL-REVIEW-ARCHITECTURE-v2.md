# KnowledgeStation 总体架构方案征询（外部评审稿 v2）

**这是什么项目**：一个跑在个人电脑上的「本地资料检索与取证」工具 —— 用户用大白话提问，它在本机资料库里定位到那一段原文，给出带可点击依据的答案。
**现状一句话**：**"换一种说法就找不着"是这个项目最大的问题** —— 在**法条库**上，日常说法提问的前五命中只有 **11.8%**；在**另一套完全不同的语料**（中文技术笔记）上同一个病照样犯（术语式 92.8% → 大白话 20.0%）。**⚠ 这两组数来自两个不同的检索平面、口径也不同，不能混用**（详见节 4.1）。同时已有 8,983 篇文档 / 663,634 条条款的真实数据、和 41.5 万条真人问答素材可用。
**我们要什么**：请你给一份**总体架构方案** —— 重点是"下一步该往哪改、为什么、按什么顺序"，而不是单点补丁。

## 节 0 · 名词定义（**先读这一节，后面全部依赖它**）

> 下面每个词在本稿里**只有一个意思**。凡是你需要在本方案里产出的词，都已在首次使用前定义。

| 词 | 定义 |
|---|---|
| **条款** | 一部法规/标准里**编号的最小单元**（如「GB 30871-2014 第 5.1.1 条」）。本项目的检索与引用都以它为粒度 |
| **文档** | 一部法规 / 标准 / 论文 / 制度文件。一份文档含多条条款 |
| **库** | 本机的 sqlite 数据库（当前 8,983 文档 / 663,634 条款 / 2.88 GB） |
| **通道** | 一路独立的召回方式。本项目有 **6 条**（见节 3.3 表） |
| **融合** | 把 6 条通道各自返回的候选**合并成一个排名**。本项目用 RRF（见节 0.1） |
| **gold** | 一道题**正确答案**（本项目的 gold = 该题的正确答案是哪个条款） |
| **考卷 / 尺子** | 一批"题目 + gold"的集合，用来量检索好不好。**考卷 = 尺子**，本稿混用同一意思 |
| **召回** | "正确答案**有没有**出现在候选集里"（不问排第几） |
| **排序** | "正确答案**排第几**"（候选集里已经有了，但可能排在第 800 位） |
| **命中@K** | 正确答案出现在**前 K 名**里的比例。`recall@5` = 前五命中率 |
| **大白话** | 用户用日常说法提问，**不使用**文档里的专业术语。如问"动火作业怎么分级"而不是"动火作业分级" |
| **术语式提问** | 用户直接用文档里的词提问（如"GB 30871 动火分级"） |
| **门禁** | 本仓的一条命令，跑完所有自动检查，**以退出码判定通过与否** |
| **提取树** | 把某个提交的代码单独导出到另一个目录，用来做独立复核，避免与在改的代码互相污染 |
| **口径** | 一个数字"是怎么数出来的" —— 含什么、不含什么。**没有口径的数字不可信** |
| **台账** | 一张**可维护的清单表**（本项目特指"发布渠道清单"，每条记网址、取法、可用状态） |
| **探针** | 一段**只做检测、不改数据**的小程序（如"这个渠道还能不能打开"） |
| **收口** | 把一件事**做完并验收**，不再挂着 |
| **棘轮** | 本项目的一条纪律：**测试通过数只能涨不能跌**（像棘轮只能单向转） |
| **冒烟** | 一套**快速全链路自检**（不深入，只确认"没炸"） |
| **冻结** | 把某个版本**钉住不再改**，保证多人看的是同一份 |
| **判据** | 一条**可以判真假**的验收条件（本文档节 8.4 给了写法模板）。⚠ 本稿**不用"红线"这个词**指它 |
| **红线** | **不可逾越的约束**（本稿只在节 2.2 与节 9.1 用这个词）。⚠ 与"判据"**不是一回事** |
| **表示层** | 指"把用户的话变成库里能找到的词"这一层（与"排序层"相对）。⚠ **不是**界面展示层 |
| **排序层** | 指"候选集里已经有了，怎么把正确答案排到前面"这一层 |
| **`Vector@1000` / `fused@20` / `fused@8`** | 三个**测量口径**：`Vector@1000` = 「在向量通道前 1000 名里吗」；`fused@20` = 「六通道融合后前 20 名里吗」；⚠ **`fused@8` = 生产实际返回给用户的那一格**（引擎 `EVIDENCE_CAP = 8`、`top_k` 缺省 8）。**最该看的是 `fused@8`** |
| **个点** | "个百分点"。如 35.8% → 68.3% 是 **+32.5 个点** |
| **召回层** | 指"候选集里有没有"这一层（与"用户看到的前 20 名"相对） |
| **重排器** | 拿到候选后再用模型重新打分的组件（本项目**生产未启用**） |
| **术语桥** | 把用户的口语词换成库内术语的一张对照表（本项目**试过，判决放弃**） |
| **DSH** | 本项目挂靠的宿主程序（DeepSeek Harness）—— 它跑插件、给侧栏界面、驱动 AI 主循环 |
| **侧栏** | 宿主界面右侧那一栏，本项目的所有界面都在那里 |
| **业主** | **本项目的出资与决策人**（一个人）。⚠ 不是"房产业主" |
| **平面** | 两套互相独立的资料集合：**法条平面**（法规标准，663,634 条款）与**材料平面**（用户自己上传的资料，7,872 切片）。两者的数字**不可混引** |

### 0.1 三个必须解释的技术词

| 词 | 一句话解释 |
|---|---|
| **RRF** | 一种**合并多路排名**的算法：不看每路给的分数，只看名次 —— 第 r 名贡献 `权重 /(60 + r + 1)`，各路相加得总分 |
| **向量检索** | 把"文字的意思"变成一串数字（向量），按数字距离找相近的。**它不看字面，只看意思**，所以能处理"换种说法" |
| **FTS5** | sqlite 自带的**全文索引**：按字面（分词后）找。**它只看字面**，换种说法就找不到 |

**⇒ 这就是本项目的核心矛盾**：FTS5 找不到"换种说法"，向量能找到但排不准。

## 节 1 · 摘要（只读这一节也能明白全貌）

**项目**：KnowledgeStation —— 让不专业的人用大白话，对自己机器上的任意资料提问，直接定位到那段可点开的原文。产品定位是**"任何本地资料的检索与取证"**，法规/国标只是数据源之一（虽然目前是最大的那类）。

**形态**：两个进程一起交付，没有独立安装包。**Python 引擎**（`src/core/`，跑检索/入库/核验，对外是本地 HTTP）+ **DSH 插件**（`plugin/`，出侧栏界面、给 AI 挂工具）。

**现状（全部实测，2026-10-11）**：

| 维度 | 数字 |
|---|---|
| 数据 | 8,983 文档 / **663,634 条款** / 2.88 GB / 62 张表 |
| 代码 | 引擎 154 个 py 文件（44,465 行含空行 / **38,982 行不含空行**）；插件 114 个 js/ts 文件（99,723 / **96,567**） |
| 接口 | **176 个 HTTP 端点** |
| 测试 | 173 个测试文件 / **2,928 条用例全过**（门禁 12/12 步通过） |
| 检索通道 | **6 条**（`fts`/`vec` 恒开、`modality` 半开、`exact` 按提问触发、`legal_element`/`behavior_scope` 恒关） |

**核心卡点（这是要请你解决的事）**：

| 提问方式 | 前五命中率 | 属于哪个平面 |
|---|---|---|
| **术语式**（用文档里的词） | **68.8%**（上限） | **法条库**（500 术语 × 1,832 说法） |
| **大白话**（用日常说法） | **11.8%** ❌ | **法条库**（同上） |
| 术语式（小样本） | **92.8%** ✅ | **材料平面**（69 例，**纯按字找**） |
| 大白话（小样本） | **20.0%** ❌ | **材料平面**（20 例，同上） |

⚠ **这两组数不能混引**（见节 4.1 的口径说明）：它们是**两个不同的检索平面**、
**不同的样本量**（1,832 vs 69/20）、**不同的通道数**（6 通道 vs 只有按字找）。
**"下一步该改哪个平面"本身就是一个待你判断的问题（Q4）。**

**已经量出来的一条关键事实**：把嵌入模型换成 `Qwen3-Embedding-0.6B`，**召回层（Vector@1000）能从 35.8% 涨到 68.3%（+32.5 个点）**，加一句查询前缀再 +15.8 个点。
**但**：这个涨幅量的是「**候选集里有没有**」，而**用户看到的是 `fused@8`**（引擎证据上限 **8 条**；`fused@20` 只是中间口径）—— 两者之间的转换率在本项目**已被三次量到极低**。
**⇒ 所以"该不该换模型"目前没有依据。这是本稿最重要的一个待决策点（节 6 的 D1）。**

**我们要你交什么**（详见节 8）：一份**总体架构方案**，说明"下一步改哪里、为什么、按什么顺序、每步怎么验收"。**分三批交**（节 7 末尾有分批表），不必一次写完。

## 节 2 · 目标与不做的范围

### 2.1 目标

让**不专业的人用大白话**、对**任意资料类型**提问时，都能定位到**可点开的那段原文**。

**三条总判据**（本项目自己定的，请以此为方案的目标函数）：

| 判据 | 含义 | 当前实测 |
|---|---|---|
| **换词可对** | 同一件事换种说法问，都能找到同一处原文 | ❌ 53% 的大白话与原文**一个字都对不上** |
| **排得上去** | 正确答案要出现在前列，不能只"在库里" | ❌ 有字面重合的子集里只有 **4.4%** 进前五 |
| **换资料类型不塌** | 从法规换到论文/制度文档，机制不推倒重来 | 🟡 **英文：能对上已解决（0/294 → 96.3%），但排进前 5 只有 16.7%** ⇒ 与主线的病同型；中文古籍未解决 |

### 2.1b 成功线与止损线（**这一节是上一版漏掉的，请重点看**）

**⚠ 关于"重建 663,634 条向量"——它不在上面这张表里**（它**不是**红线，是**默认倾向**）：

**⚠ 关于"外发"这条，必须说清**（很容易被误读成"不许联网"）：

| 项 | 事实 |
|---|---|
| **作答用的 LLM 在哪** | **在云端**（默认 `https://api.deepseek.com`）。每次作答会把**问题 + 检索出的证据片段**发过去 |
| **原始文档会不会外发** | **由用户决定**，系统**不再代为禁止**（2026-09-17 业主裁决：「不能外发的红线不要……我也不知道为啥之前要这样限制自己」） |
| **真正的红线** | **必须留痕** —— 每次外发的完整 payload 落库可审计（`debug_dump` 表 + 外发审计接口） |
| **⇒ 对你的意义** | 你可以**自由建议云端方案**（调 API、云解析等）。**唯一要求是**：该方案要能接进"外发可审计"这个机制。**不要**建议绕过留痕的通道 |

**⇒ 所以"本地优先"指的是**：**检索与数据存储在本机**（不外发语料库），
而**推理可以走云端**。这两件事别混。

> ⚠ **本稿不把"断网怎么办"列为约束** —— 请按**联网可用**的前提给方案。
> 你**不需要**设计离线降级路径，也**不必**在方案里考虑网络中断。

**必须交代的三件事**（对应评审要求）：

| 项 | 本项目的事实 |
|---|---|
| **AI 跑在哪一侧** | **两侧都有**（这条最容易搞错，请看清）：<br>① **宿主侧** —— DSH 的 AI 通过 **6 个工具**调引擎；<br>② **引擎侧** —— 引擎**自己带云端 LLM 客户端**：`POST /api/v1/ks/answer` 会**由引擎直接**向 `api.deepseek.com` 发起一次流式调用（`src/core/llm/ks_answer.py`），并把完整 payload 落 `debug_dump`。<br>⇒ **引擎不是纯被动提供方**，它有出站调用。 |
| **主编排循环谁控制** | **宿主/AI 控制主循环**（它决定问什么、调哪个工具）。引擎内部**没有**"2 秒轮询的 update 调度器"——那个调度器的 `start()` **全仓无人调用（死代码）**，引擎启动时明确不走它。引擎启动时真正常驻的只有 **2 个**：单写者队列消费者、**法规目录刷新（3600 秒心跳、天级刷新）**。⚠ 公告扫描与入库预览 worker 是**按需起的 daemon 线程**（结束即退），深度通道心跳在**解析子进程**里 —— **都不是引擎常驻**。 |
| **执行环境限制** | ① **引擎单实例**（靠 `engine.session.json` + 探活判定；并发调用会被合并，避免起出"幽灵引擎"）；② 写操作走 `write_transaction()`（`BEGIN IMMEDIATE` 短事务）——⚠ `write_queue` 表**只接 `ingest_doc` 一种操作**，其余写路径是直写（**引擎 `src/` 下 82 处 `INSERT`**；不含 `tools/` 下的采集脚本）；③ 引擎**闲置 30 分钟自动关停**；④ 解析 worker 用**子进程**隔离；⑤ 冷启动有 **60 秒**上限 |

⚠ **三条容易踩的**：

1. **引擎会被自动关停**（闲置 30 分钟，默认值，插件配置可覆盖）。
   ⇒ 任何"常驻后台任务"的设计，都要考虑"引擎被关了怎么办"。
2. **"单实例"不是靠锁，是靠会话文件 + 探活** ——
   并发拉起时**后写的会话文件会顶掉先写的**，先起来那个会变成"无人引用的幽灵引擎"。
   ⇒ 现已在同一管理器内**合并并发调用**来防它，但**跨进程不防**。
3. **`write_queue` ≠ "所有写操作"** —— 表和消费者都在，但**只注册了 `ingest_doc` 一种操作**；
   其余写路径直接 `INSERT`。⇒ **别按"所有写都排队"设计并发模型**。

### 3.3 检索架构（**要改的核心部件**）

**6 条通道**（代码真源 `src/core/domain/models.py` 的 `SEARCH_CHANNELS`）：

> **代号约定**（后文说"通道 A/D/E"时指这张表的代号）：
> **A**=`exact` · **B**=`fts` · **C**=`vec` · **D**=`modality` · **E**=`legal_element` · **F**=`behavior_scope`

| 代号 | 通道 | 找什么 | 权重 | 生产是否开 |
|---|---|---|---|---|
| **A** | `exact` | 条款号精确匹配 | **2.0** | 仅当提问含条款号 |
| **B** | `fts` | FTS5 全文（按字面） | 1.0 | **恒开** |
| **C** | `vec` | 向量（按意思） | 1.0 | **恒开** |
| **D** | `modality` | 模态词（"必须/应当/不得"） | 0.8 | 仅当提问含模态词 |
| **E** | `legal_element` | 法理要素 | 0.8 | **恒关**（生产调用点不传参；该字段全库 **31,249/663,634 = 4.7%** 非空） |
| **F** | `behavior_scope` | 行为客体 | 1.2 | **恒关**（该字段全库 0 行非空） |

**融合**：RRF，`分数 = Σ 权重 /(60 + 名次 + 1)`。

**⚠ 三条我们必须如实说明的架构事实**：

1. **通道 A/D/E 的排序键不是相关性** —— 它们的 `ORDER BY` 头两个键是"效力状态"，**等于按入库顺序**。⇒ 不修它，"取前几名"都是任意的。
2. **没有设行数上限是「不能加」而不是「不该加」** —— 通道 A/D/E 的通道内名次不是相关性名次，加 `LIMIT` 会任意丢候选；**代价是内存问题未解决**（已登记为独立缺陷）。实测模态词"应"一次能拉出 **169,624 条**（占现库 663,634 的 **25.6%**）。曾想加 `LIMIT 500`，但**论证被推翻**：加闸的前提是"名次 = 相关性名次"，而它不是。
3. **向量是暴力精确扫描，没有近似索引** —— 663,634 条全扫。当前用 `bge-small-zh-v1.5`（512 维，**CPU/ONNX**）。

## 节 5 · 我们的判断（**下面全部是假设，不是结论**）

> ⚠ **这一节必须被当作假设来读。** 我们给出倾向，同时给出**竞争解释**。
> **若你认为根因在别处，请直接说。** 那比顺着我们的框架答更有价值。

### 假设 1（我们倾向的）：53% 零重合是"表示层"问题，不是"排序层"问题

**推理**：提问与原文一个字都对不上 ⇒ 排序再怎么调，也没有共同信号可用。

**竞争解释**：
- **1a**：这 53% 里**很多本来就不该能答**（问题超出库的范围）⇒ 那正确做法是**识别并拒答**，不是硬找。
- **1b**：不是"对不上"，而是**分词粒度**问题（如中文古籍 30.2% 的 token 被切成单字）⇒ 那该修分词，不是改表示。
- **1c**：是**评测集本身失真** —— 那 1,832 条是 AI 生成的"外行说法"，**真人未必这么问**。⚠ **这一条我们刚刚获得了反驳它的证据**（41.5 万条真人问答），但**还没用上**。

### 假设 2：换模型（+32.5 个点）是当前最大的可用杠杆，但**证据不足以下决心**

**推理**：在所有试过的方向里，只有它和"查询前缀"给出了显著收益。

**竞争解释**：
- **2a**：`Vector@1000` 的收益**到不了用户那一层**（转换率极低已被三次量到）⇒ 那这个杠杆是**假的**。
- **2b**：即使到得了，**代价**（重建 663,634 条向量 + 需要 GPU）可能不值。
- **2c**：**排序层**才是真瓶颈（4.4% 进前五）⇒ 换模型救不了。

### 假设 3：两条独立线的产出"融进来"是低风险高收益的

**推理**：真人问答能直接补上"真实提问分布"这个缺口；渠道台账能补上"官方来源覆盖"。

**竞争解释**：
- **3a**：这批数据**偏科**（税务一家占 11.9%、广东一片）⇒ 直接当尺子会**把系统往那几个领域调优**。
- **3b**：**领域不匹配** —— 政务问答问的是"户口怎么落""营业执照怎么办"，而本项目的库是**法规标准**。两者交集可能比想象的小。
- **3c**：融入的**工程量**可能超过收益（要建数据管道、要清洗、要分层）。

## 节 6 · 待决策的分歧点（**这是我们拿不准的路线选择**）

> ⚠ **本节只给"分歧的背景与两边的理由"，问题本身在节 7。**
> **同一件事不要在节 6 和节 7 各答一遍** —— 请只在节 7 作答。
> 每节末尾的「→ 提问在 Qn」就是它的编号。

### D1 · 换模型这个杠杆，现在用不用？

- **支持用**：唯一量出显著收益的方向（+32.5 / +15.8 个点）；模型已缓存在本机；显卡可用。
- **反对用**：收益量在 `Vector@1000`，**用户看到的是 `fused@8`**（生产基线 **5.83%**；`fused@20` 是 8.33%），转换率极低。
- **我们缺的那格数据**：**换模型之后**的 `fused@20`。
- **→ 提问在 Q2。**

### D2 · 排序层（P0.4b）该不该先修？

- **事实**：通道 A/D/E 的排序键**等于入库顺序**，与相关性无关。实测 `legal_status` 分布为
  effective 8,963 / reference 16 / withdrawn 4（**99.8% 是 effective**）⇒ **"效力"这个维度在数据上几乎没有分辨力**。
- **但**：`(dm.legal_status IS NULL)` 这一键表达的是"**未核验沉底**"这一**排序偏好**。⚠ 源码注释明确写着：**"能不能承重"的判据在 `authority`/`evidence` 那一侧，不在排序里**（原话：「也不与"未核验不得承重"冲突——那是"谁排前面"，这是"能不能承重"」）。

### 8.4 验收判据要写成四段式

> 术语说明：本稿把"能判真假的验收条件"叫**判据**。**不叫"红线"**（那个词容易理解成告警阈值）。

```text
① 判据        一句话，可判真假
② 检查方式    怎么测：读什么、跑什么、比什么
③ 通过条件    具体的数或布尔条件
④ 反向验证    怎么证明「把修复去掉，它会失败」
```

**第 ④ 段是关键**：没有它，一条检查可能永远通过，成为废检查。

### 🔴 乙、P0.4b：先修通道 A/D/E 的排序键 —— **P0 的主项，一直没动**

**为什么重要**：总纲写得很直白——**"不修它，任何截断都是任意的"**。

现状（**我今天只读复核过**）：`ORDER BY (dm.legal_status IS NULL), dm.legal_status, cr.clause_revision_id`
出现在 `hybrid_engine.py` 的 **三处**（第 279 / 345 / 369 行），而 `legal_status` 挂在 **`doc_meta`** 上、**不在条款行**。

⚠ **总纲里那组数需要更正**（总纲写的是"effective 521,984 / superseded 0 / NULL 0"）：
今天实测 **`doc_meta.legal_status` 是 effective 6,777 / reference 16 / withdrawn 4，合计 6,797，NULL 为 0**。

⇒ **更正后的判断**：前两个键**不是恒为常数**（有 20 篇非 effective、且 NULL 与非 NULL 确实分得开），
所以它们**确实在做排序**；但它是**按"效力状态"排、不是按"相关性"排** ⇒
**名次与相关性无关**这个结论仍然成立，**但成立的原因与总纲写的不同**。⇒ 修它的方向要重新定：
**不是"让两个键分出档"（它们已经分了），而是"这两个键该不该占前两位"**。

⚠ 这一点**必须先查清再动手**：第 255–266 行的注释显示，这两个键是**故意**加的（"未核验不得承重"的反向），
第 259 行还说明**采集件（NULL）会被静默排除在精确命中之外** ⇒ **它们承载着一条产品判据，不只是排序**。
**动它 = 改产品语义，不只是改排序** ⇒ 属必验类别，且需要你确认"效力状态该不该优先于相关性"。

**连带**：0.4 那次"给两条不设上限的路加硬上限"就是**因为这个才撤掉的**（复核实测 6/6 挤出正确条款、384 篇文档的条款被砍光）。⇒ **0.4 和 0.4b 是一件事的两半**，0.4b 不修，0.4 永远做不了。

**验收**：排序键在真库上**真的分出档**；修完之后 0.4 的硬上限才有意义。
**属必验类别**（改检索契约）。

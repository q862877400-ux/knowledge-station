# 运行时：引擎怎么起、端口令牌在哪、数据放哪

> **这份是手写的**（其他 8 份由 JSON 生成）。原因是运行时行为**不能从静态代码推出来**。
> 每条都标了「已验证 / 未验证」，别把未验证的当结论。

---

## 一、引擎怎么起

| 项 | 内容 | 验证状态 |
|---|---|---|
| 入口 | `python -m src.core.main`（工作目录 = 仓根） | 代码里可搜到 |
| 端口 | **随机**。绑 `127.0.0.1:0`，由系统分配 | 已在门禁日志里见过不同的随机端口（45777 / 8230 / 9547） |
| 令牌 | 启动时随机生成 | 见下 |
| 如何把端口/令牌告诉调用方 | ① stdout 打两行 `KNOWLEDGE_STATION_PORT=<n>` / `KNOWLEDGE_STATION_TOKEN=<t>`；② 同时写文件 `<数据目录>/engine.session.json` | 代码 + 门禁日志都印证 |

### `engine.session.json` 里有什么

```
port       端口
token      令牌（**明文**）
pid        进程号
started_at 启动时间
```

> ⚠ **令牌是明文存的。** 这不是"缺陷"的判断，只是一个事实：
> 任何能读这个文件的东西，都能调引擎的全部接口（除了健康检查）。

---

## 二、哪些接口不用令牌

| 接口 | 是否需要令牌 |
|---|---|
| `GET /api/v1/health` | **不需要**（用于探活） |
| `OPTIONS *` | **不需要**（跨域预检） |
| 其余全部 | **需要** `Authorization: Bearer <令牌>` |

## 三、健康检查返回什么（门禁在验的）

门禁里那一步实测过三态：

| 字段 | 取值 |
|---|---|
| `status` | `healthy` / 其他 |
| `vector_engine` | 实测见过 `unknown` |
| `dbStatus` / `parserWorker` / `uptimeSeconds` | 都在响应里 |

并且门禁实测：**12 条重活在飞时 `/health` 仍是毫秒级**（p95 ≈ 0.05–0.10 秒）。
这是"健康检查不能把重活拖进来"的判据。

## 四、数据放哪（这是最要紧的一节）

| 位置 | 内容 | 体积（实测） |
|---|---|---|
| `var/data/` | **生产库 + 证据原件**（PDF/图/条款） | **74 GB / 358,400 个文件** |
| `var/models/` | 本地模型文件 | 7.0 GB / 79 个文件 |
| `var/tmp/` | 临时产物 | 1.6 GB / 14,111 个文件 |
| `tests/fixtures/seed/knowledge-seed.db` | **随仓的种子库**（生产库真子集） | 13.3 MB / 82 部标准 / 4,809 条条款 |
| `%APPDATA%\KnowledgeStation` | 旧版数据目录 | **本机已不存在**（已迁到 `var/data`） |

> **`var/` 全部被 `.gitignore` 排除** ⇒ 不在 `git ls-files` 里。
> 下一棒要知道：**仓里能提交的只有代码和种子库；真实数据在 `var/data/`，不进版本控制。**

### 数据目录怎么决定（优先级）

引擎支持用环境变量 `KS_DATA_DIR` 指定数据目录（门禁用它把测试隔离到临时目录）。
模型目录用 `KS_MODELS_DIR`。**这两个变量在门禁里都会显式指定**，所以门禁跑的是隔离数据，
不会碰 `var/data/`。

## 五、便携约束（业主亲定的硬规矩）

| 规矩 | 现状 |
|---|---|
| 代码里**不许写死绝对路径** | ⚠ **实测有 13 处写死旧工作区 `D:/AI/work space/zcode`**，其中 2 处是运行期真的去读它 |
| 插件要从自身位置往上找仓根 | `plugin/src/engine.js` 有 `findEngineRoot`，认 `src/core/main.py` 这个标记 |
| 虚拟环境的底座要能自愈 | `healVenvHome()` —— 因为 `pyvenv.cfg` 的 `home` 是绝对路径，venv 又不带标准库，整包换盘符就直接不可用 |

那 13 处的明细在 `10-observed.md`，**本检查不判断该不该修**。

---

## 六、插件侧怎么跟引擎说话

| 项 | 内容 |
|---|---|
| 插件怎么找引擎 | 读 `engine.session.json`；找不到时可能自己拉一个 |
| 工具数 | 6 个模型工具（`ks_ping` / `ks_collect` / `ks_answer` / `ks_effect_report` / `ks_materials` / `ks_resolve_clause`） |
| 宿主侧路由 | 前端通过插件注册的 `/ks/*` 路由调引擎，**不是直连**（跨源那条 127.0.0.1 是例外） |
| 复用规则 | 门禁实测：`engine.session` 存在且活着就复用（`reused: true`），**绝不 spawn 第二个 python** |

## 七、还没验证的（明确列出来，别当结论）

| 项 | 为什么没验证 |
|---|---|
| 真起引擎并调每个接口 | 需要真模型/真数据库，本轮只做只读检查 |
| `ks_answer` 端到端能不能用 | 上一轮实测每次 `Connection error`；**本轮没有复测**（要先配模型密钥） |
| 前端在浏览器里的实际渲染 | 需要真浏览器；门禁里有三套要真浏览器的冒烟，本检查没跑 |
| 生产库 `var/data` 里那 8,983 部文档的实况 | 74 GB，只做了统计，没逐部核 |

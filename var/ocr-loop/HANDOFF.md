### 5.7 🐛 修掉一个会造成"全库误评估"的假命中（本轮最关键）

`artifact_index.resolve` 第一步是 `root / doc.get("doc_id")`；**doc_id 为空时
`root / ""` 就等于 `parse_out` 根目录**，而 `root.is_dir()` 恒为真 → 一切文档
都被"解析"到整个 parse_out 根、读到**全体产物**。新语料未入库（doc_id 为空），
正好踩中：`doctor` 一度报"新语料 auto=231"，全是假的。

修法：① 空 doc_id **不直取**；② 新增 `_usable_dir()` 防护（挡 `parse_out` 根、
`.stash` 留档区、非 parse_out 直接子目录）；③ 新增**落位消毒名**解析
（`_land_key`，与 `vlm_ocr.land_dir` 同口径）——新语料产物住在
`parse_out/<消毒std_no>/`，索引的 `norm_stem` 与之不同形，不单独试一次就永远
定位不到自己的产物。

**教训**：`Path / ""` 是恒等于父目录的陷阱；"解析成功"必须校验**解析到什么**，
不能只看 `is_dir()`。

## 十、本会话修掉的三个"静默致死"缺陷（都会让推进归零）

这三个都属于**"没人看着就会悄悄停"**的类型，是本会话最有价值的产出：

### 10.1 一个超限文件杀掉整批（云异常未捕获）

**症状**：批次 2 跑到 116/500 进程消失，日志无异常（异常在工作线程里）。

**根因**：`mineru_cloud._poll_result` 对云侧"解析失败"是
`raise MineruCloudError`，而 `run_cloud` 没 catch —— 异常从工作线程**穿过
ThreadPool**，整个批量进程当场死亡。实测触发：`GB/T 16751.1-2023` **241 页**
超过云硬限（`number of pages exceeds limit (200 pages)`）。

**修法**（两层）：
1. `run_cloud` 捕获 `MineruCloudError` → 记为 `fatal` 并**转本地 VLM**
   （页数超限是**能力边界**不是临时故障，换 key 无用）；
2. `vlm_ocr.main` 加 `_safe_stage()` **批次级安全网**——单部文档抛任何异常
   都不许杀掉整批，异常写进记录供取证。

**验证**：修复后前台实测该 241 页文档 → `↳ 云能力边界：… → 本地 VLM`，
本地 VLM 正常起（241 页分 4 窗），批次继续。

### 10.1b 本地 VLM 兜底"钉住整个 chunk"（并发度被一个慢文档吞掉）

**症状**：修好 10.1 后批次推进仍极慢——卡在第一个 chunk 20+ 分钟。

**根因**：本地 VLM 是 **in-process 串行**（GPU 独占），而原实现把它**嵌在
chunk 循环里**：一个 241 页文档把整个 chunk 钉住，**并发 4 的另外 3 个 worker
全在等它**。逐批跑 35,243 部时这是主要瓶颈。

**修法**：改为**两阶段**——云阶段保持并发、只做云；需本地兜底的文档
**收集到队列**，云阶段全部结束后**串行**跑本地 VLM。
（fatal 失败不入 state，故中途崩溃会在下次续跑时重试，语义安全。）

**验证**：实测日志
```
↳ 云能力边界：… → 排队等本地 VLM      ← 不再阻塞
    ✓ cloud ok 5.8s / 6.7s / 5.7s     ← 其余 3 部照常并发完成
[5/387] [6/387] [7/387] [8/387]       ← 批次立刻推进
```

### 10.1c 本地 VLM 输出名含非法字符直接失败

**症状**：241 页文档转本地后 `OSError: [Errno 22] Invalid argument`（1 秒内）。

**根因**：国标源文件名常含**全角斜杠** `／`（U+FF0F，如 `GB／T 16751.1-2023 …`）
——Windows 禁止该字符作文件名，MinerU 用它建输出文件时被拒。

**修法**：`run_local_vlm` 用 `_land_key()` 消毒后的名字作 MinerU 输出名
（只影响输出名，不碰源文件读取）；`land_dir` 的消毒逻辑抽成 `_land_key()`
单一所有者（与 `artifact_index._land_key` 同口径）。

**验证**：消毒 4/4 通过（含 `<>:"/\|?*` 全字符集）；实测该文档已越过原失败点、
进入正常推理（241 页分 4 窗）。

### 10.2 watchdog 因未加引号的空格路径静默拉不起来

**症状**：`[watchdog] 警告：pid= 启动即退出`（pid 为空），且 err 无任何输出。

**根因**：`Start-Process -ArgumentList` 里传的是**含空格的相对路径**
（`var/ocr-loop/vlm_ocr.py`），PowerShell 不做引号处理 → 一个路径被**拆成多个
参数**传给 python，进程启动即失败。

**修法**：改用**绝对路径并显式加引号**（`"\`"$scriptAbs\`""`），`$log/$err`
也走 `Join-Path $root` 拼绝对路径。**从 3 秒等改到 5 秒**并回写 err 尾部。

**验证**：修复后 `[watchdog] 已拉起 pid=32776`，批次正常续跑。

### 10.3 driver 把"进程消失"当"批跑完"，对截断数据取基线

**症状**：批次 2 崩在 116/500，driver 立刻记「批次 #2 已结束」并开始取基线。

**根因**：完成判据只有"无 vlm_ocr 进程"——**崩溃时进程也会消失**，于是对
**不完整的数据**取基线并推进，评测口径直接失真。

**修法**：`_wait_batch()` 用双判据——进程消失 **且** 进度达标
（`progress = state 里 status∈{ok,textlayer} 且属于本批的键数 ≥ 清单 n`）；
未达标则**重新拉起续跑**（state 保证断点续跑），连续中断超 5 次才停待人工；
**绝不带着不完整数据推进**。

### 10.4–10.7 第四轮（2026-09-15）：跨批推进链上的四个"静默致死"

这四个都出现在**批次 2→3 切换的第一分钟**，共同点是**日志看上去一切正常**。
它们比前面的更危险：前面几个会让"一批"白跑，这四个会让**整个 35,243 部目标冻住**。

#### 10.4 ❗driver 路径拼错 → 每一批都会"交人工"停下（推进链断掉）

**症状**：`_wait_batch` 走到 `_batch_progress` 后立刻 `no-total`，driver 停止推进。
日志只有"批次 #N 无进度信息（0/500）→ 交人工"，**看上去像"还没跑完"**。

**根因**：`EV / cfg["list"]` —— `cfg["list"]` 里**已经带了 `evolve/` 前缀**
（`batch_config.set` 写入 `evolve/work_batch2.json`），与 `EV = HERE/"evolve"`
再拼就变成 `…/evolve/evolve/work_batch2.json`（不存在）。异常被 `except` 吞掉
→ 退化成 `0/0`，**不报错**。

**修法**：`_list_path(cfg)` 单一所有者——按"相对 ocr-loop 根"解析
（`HERE / cfg["list"]`），兼容旧写法（`ROOT/"var"/"ocr-loop"/cfg["list"]`），
都不存在则返回 `None` → `_batch_progress` 返回 `total = -1`
→ `_wait_batch` 报**"清单路径解析失败"**并停，**绝不静默退化成 0 部**。

**验证**：真路径 499+1/500 判定"已完成"；坏路径（不存在的清单）返回 `(0,0,-1)`。

#### 10.5 ❗`Start-Process -ArgumentList` 不加引号 → 静默跑空批（每天白烧额度）

**症状**：批次 3 被拉起后 `目标 0 部（待处理 0）`，**1 秒内退出码 0**。
driver 每 20 秒重拉一次，42 秒内连拉 3 次。

**根因**：`-ArgumentList` 传的是**数组**，PowerShell 用空格重新拼接且**不加引号**
→ `--corpus-list D:\AI\work space\zcode\...` 被拆成多个参数 → 清单路径不完整
→ `targets_from_corpus_list` 对每条路径 `p.exists()` 全 False → **0 部**。
（**与 10.2 是同一个坑**：watchdog 当年踩过并修了，driver 这份是另写的、没照做。）

**修法（两层）**：① 清单与脚本路径都加引号（`'"{corpus}"'`）；
② **启动前预检** `_preflight(lp)`：复用 `vlm_ocr.targets_from_corpus_list`
（**单一所有者**，与真正跑批同口径）先算一遍，`可解析目标数 != 清单条数` 就
**拒绝启动并同时报出两个数字**——让"清单空"和"参数传递坏了"可区分。

**验证**：加引号后 `目标 1 部（待处理 1）` 并开始处理；预检真清单 500/500 通过、
坏清单 `(0, 2)` 拒绝。

#### 10.6 ❗driver 对刚启动的批次立刻查进度 → 判"未跑完"→ 重拉（双实例并发）

**症状**：批次 3 刚健康开跑（`[8/500] … 云VLM…`）就被重拉，日志写
"重新拉起续跑（第 1 次）"——**两个进程并发跑同一批**。

**根因**：`_batch_progress` 只统计**已到达终点**的文档，而首批文档从提交到落
state 需要十几秒~数分钟。driver 拉起后**立刻**查 → 0+0/500 → 判"未跑完" → 重拉。

**修法**：`START_GRACE_S = 150` 秒**启动宽限期**——宽限内即使进度是 0 也不重拉。
判据用**时间**而不是进度，因为进度天然滞后，用进度判"启动失败"必然误判。

**验证**：日志出现"启动宽限中（剩 Ns，不因 0 进度重拉）"，不再出现重复拉起。

#### 10.6.1 ❗`start_batch` 的**管道继承死锁**——driver 会整进程崩掉（2026-09-15 实测）

**症状**：批次 4 推进到 272/500 时 **driver 消失**（`driver=0`）、job 报 `exit code 1`，
堆栈落在 `batch_advance.py` 的
`subprocess.run(cmd, capture_output=True, text=True, timeout=120, env=e)` →
`TimeoutExpired`。**推进链断**（批次本身还在跑，但没人换批）。

**根因**：`start_batch` 用 `Start-Process … -PassThru | Select-Object -ExpandProperty Id`
把 pid 打到 **stdout**，再由 `subprocess.run(capture_output=True)` 读回。
但 `Start-Process` 启动的**子进程继承了那个 stdout 写端**（虽然它自己的 stdout
被 `-RedirectStandardOutput` 指到日志文件，**继承来的句柄仍在**）→ 管道**永不关闭**
→ `communicate()` 一直等到超时 → driver 抛异常崩溃。

**两次修正（第一次不够，以实测为准）**：
1. 只把 pid 改走**临时文件**（`Out-File`）→ 实测仍 **62.9 秒**（管道照样被继承）；
2. **彻底不建管道**：`subprocess.run(..., stdout=DEVNULL, stderr=DEVNULL,
   stdin=DEVNULL, timeout=90)` → 实测 **0.4 秒**。

**验证**：修复后 `start_batch` 返回 True、耗时 **0.4s**；driver 连续运行、
宽限期日志正常（"启动宽限中（剩 129s…）"）。

**推广（Windows 上启动常驻子进程的通用坑）**：**别用管道回读子进程信息**。
`Start-Process` 的子进程会继承父进程的标准句柄，任何 `capture_output=True`
都可能挂到超时。要传信息就让包装器**写文件**，并把父进程的三个标准流全设为
`DEVNULL`。同文件里 watchdog 侧无此问题（它把 pid 写 `watchdog.log`，不用管道）。

### 10.7 ❗两个 vlm_ocr 并发 → 状态台账互相覆盖 → 双方都卡在 8/500**症状**：批次 3 卡在 `[8/500]`，**日志 3 分钟无更新**、state 记录 0、CPU 30 秒
只涨 0.7 秒。杀掉后**单独跑同一批立即恢复**（4 部 ok）——证明是并发自伤。

**根因**：`commit_rec` 是 `state[key] = rec; save_json(STATE, state)`
——**整体读改写、无跨进程锁**。后写者用**自己启动时的旧快照**覆盖已落盘记录：
前者完成记录被抹掉（重启后重复提交、重复烧云额度）。上面的 10.6 正是双实例来源。

**修法（两道）**：
① driver 侧 `START_GRACE_S`（10.6）从源头消除重复拉起；
② `vlm_ocr` 侧 `_guard_single_instance()` **单实例闸门**：锁文件
   `vlm_ocr.lock` 用 `os.open(O_CREAT|O_EXCL)` **原子创建**做互斥；已有锁且
   **pid 活着** → 打印原因后**正常退出**（退出码 0，driver 才会走等待逻辑）；
   pid 已死 → **接管**（被杀/崩溃留下的陈旧锁必须能接管，否则闸门永久堵死）。
   **不用心跳过期判活**——本地 VLM 单部可达 52 分钟（实测 241 页 `wall_s=3129`），
   任何心跳阈值都会误杀正在正常工作的长文档（watchdog 那次踩的就是这个坑）。

**踩坑记录（本轮最隐蔽的一个）**：`_pid_alive` 里写了 `subprocess.run(...)`，
而 `vlm_ocr.py` **没有 import subprocess** → 每次调用都 `NameError` →
被 `except: return True`（"查不动就当活着"的保守兜底）**静默吞掉** →
函数**永远返回"活着"** → 陈旧锁永不接管 → 闸门永久堵死。
**用 `sys.settrace` 逐步跟踪才看到**（静态读代码、复刻逻辑、看字节码都显示应该返回 False）。
教训：**"保守兜底"的 except 会掩盖真实故障**——兜底分支必须在日志里留痕，
否则"保守"就变成"永远错"。

**验证**：`test_single_instance.py` 8 项行为断言全绿（含"陈旧锁必须接管"
"让位者不得清锁"两个反向对照）。

### 10.11 巨型文档策略：**先复用现成产物，再谈跳过**（用户两次指令的合成）

用户第一条指令（2026-09-15）：
> 「像这种巨型文档过于长的，不利于我们快速迭代、快速寻找问题、快速进化的这个
> 路径的文档可以直接跳过，寻找正常尺寸的去进行识别和参与循环就好了」

用户第二条指令（同日，**修正了第一条的边界**）：
> 「本地已经 OCR 好了的、本地有文件的，那你就直接用吧，就算他是巨型文件，
> 但是都已经是现成可以拿来用的了，那为什么不用呢？只有说未来遇到了要再次 OCR
> 的时候就把它跳过」

**合成为一条规则**（`vlm_ocr` 里的处理顺序，不可颠倒）：

| 情形 | 处理 | 依据 |
|---|---|---|
| 页数 ≤ **200**（`OVERSIZE_PAGES`） | 正常走云 → 云失败才本地 | 云硬限即 200 页 |
| 页数 > 200 **且盘上已有可用产物** | **直接复用**（`channel=reuse`，`status=ok`，零 OCR） | 用户第二条：现成的就用，别浪费 |
| 页数 > 200 **且无产物**（=需要重新 OCR） | **跳过**并记台账 `vlm_oversize_skipped.json` | 用户第一条：跳过后循环才快 |

**为什么 200**：这正是云服务页数**硬限**（实测 241 页报
`number of pages exceeds limit (200 pages)`）；超限只能走本地，而本地实测极慢——
346 页 8114s（135 分钟）、369 页 4617s（77 分钟）、408 页逾 1 小时；
且本地 VLM **串行 GPU 独占**，一部巨文档就把整批推进钉住数小时。

**实测效果**：批次 3 的 5 部（228–408 页）**盘上没有产物**（旧运行中途被杀，
从未成功落地）→ 按第二列跳过，批次 3 随即收满（495 完成 + 5 跳过 = 500），
**当轮自动取批次 4**；批次 4 开局即跳过 2 部（714 页、206 页）→ 立刻进入正常尺寸文档。
而批次 3 另两部巨型文档（346 页、369 页）**本地已跑成且有产物** → 被正常评估
（它们出现在基线里），**没有被丢弃**——这正是第二条指令要保护的情形。

**台账与补跑**：跳过项累计在 `vlm_oversize_skipped.json`（含页数、路径、原因），
**不丢账**；将来若要补跑，按该清单单独跑即可（本地会花数小时/部）。
`driver` 把 `skipped-oversize` 算作"已到终点"（否则批次永不完成）。

### 10.7.1 ❗driver 与 watchdog 互相抢着拉 → 进程增殖到 5 个（2026-09-15 实测）

**症状**：批次 4 卡在 40/500 十多分钟；`vlm_ocr` 进程数**增殖到 5 个**、
`driver` 出现多份；`watchdog.log` 连续写"已拉起 pid=…"。

**两个叠加的根因**：

1. **driver 心跳只在写日志时更新** → 主循环一旦被卡住，心跳就变旧。
   实测 driver 被卡 **37 分钟**（见下），心跳超 `STALE_MIN` → watchdog 判定
   "driver 卡死"→ **另拉起一份 vlm_ocr**；而 driver 也在拉 → 两者抢。
2. **driver 被卡的原因**：它在用 `pwsh -Command Get-CimInstance …` 查进程，
   实测 **371 ms/次**，高负载（本地 VLM 吃 2–3 核）时更慢甚至挂住。
   而 `_procs()` / `_batch_proc_cpu()` 每轮巡检都要调 → 主循环阻塞。
   **附带发现**：`psutil.process_iter(["pid","name","cmdline"])` 也慢——**2 秒/次**
   （逐进程读 cmdline 在 Windows 上很贵）；正确写法是先按 name 便宜筛选、
   **只对少数 python 进程**读 cmdline → **7 ms**，比 pwsh 快 50 倍。

**修法（三处）**：
- `batch_advance._vlm_ocr_procs()` 改用 psutil（7–18 ms），pwsh 仅作兜底；
- **心跳独立成守护线程**（`_start_heartbeat()`，每 30 秒无条件刷新）——
  与主循环是否阻塞无关；
- `watchdog.ps1` 仲裁判据从"心跳新鲜"改为**"driver 进程存活"**
  （`Get-Process -Id` 快且准）：driver 活着就一律退让，**慢 ≠ 死**。

**验证**：修复后进程清点稳定为 `driver 1 对 + vlm_ocr 1 对`；批次 4 从
卡死的 40 → 56 部继续推进；`_liveness_sig()` 耗时从 2 秒级降到 **11 ms**。

### 10.8 停滞自愈：进程活着 ≠ 在干活

`_procs()` 只要看到进程就 `while` 死等**永不超时**——10.7 那种卡死会白等到
天荒地老（本目标跨天运行）。故 `_wait_batch` 加**停滞检测**：
存活签名 `(已完成, 已失败, 待本地, 总数, 日志mtime, **进程累计CPU**)`，
阈值 `_stall_min()` 不变 → 判卡死 → **杀掉该批进程后重拉**（state 保证断点续跑）。

#### ❗CPU 项是**必需**的，不是锦上添花（2026-09-15 实测）

**缺陷**：签名里只有"进度 + 日志 mtime"时，**本地 VLM 跑巨型文档会被误杀**。
本地 VLM 是**长时间单篇推理**——408 页文档实测需 **68–90 分钟**，其间
**既不写日志也不写 state，只有 CPU 在涨**。于是任何固定阈值都会短于它：
实测 408 页文档跑到**第 10 分钟**时 driver 已在报"停滞 10/30 分钟"，
继续下去就会**杀掉→重提同一部→又等同样久 → 无限循环**。

**修法**：签名纳入**当前批全部 `vlm_ocr` 进程的累计 CPU 秒数**
（`_batch_proc_cpu()`，经 `Get-Process -Id <pid> | $_.CPU`）。
CPU 在涨 = 在真干活 → 签名变化 → 停滞计时自动重置。
实测修复后：同一次 408 页推理期间，driver 只输出
"仍在跑（进度 493+0（待本地 7）/500）…"，**不再出现停滞计数**。

**推广**：判"进程是否卡死"时，**"在消耗 CPU"比"有没有输出"更可靠**——
长任务天然长时间无输出。

### 10.8.1 单实例闸门必须**等待**，不能立刻退出

**缺陷**：闸门（10.7）原本抢不到锁就**立刻退出**。而 driver 看到进程退出就重拉
（每 20 秒一次，**最多 5 次**）→ 5 次机会在 100 秒内耗尽 → driver 报
"反复中断 → 待人工"，**整条推进链静默停住**——而真正在跑的那个实例完全正常
（实测场景：本地 VLM 正在跑 408 页文档，需 68–90 分钟）。

**修法**：闸门在锁被占用时**轮询等待锁释放**（`LOCK_WAIT_S`，默认 900 秒；
`--lock-wait <秒>` 可覆盖，测试用 0 以快速判定）。这样 driver 的每次重启
都变成一次"等着接手"的机会，而不是耗尽重试次数。

### 10.8.2 阈值为什么是 30 分钟（`_stall_min()`）

每次重启都**丢弃 in-flight 的整个 chunk**（`as_completed` 的结果只在本进程内，
未落 state 的 8 部要重做）——实测批次 3 因 12 分钟阈值被重启两次、
**两次都白丢一整块**。故 `_stall_min()` 取 `max(30, 云预算+缓冲)`，
且**必须大于云预算**，否则会"杀掉正卡在云轮询的进程→重提同一部→又卡在同一处"
的**无限循环**。有了 CPU 判活后，阈值只需覆盖"云等待 + 短时无 CPU 的间隙"。

### 10.9 `pending-local`：把"还没做"与"做完了但失败"分开

**缺陷证据**（2026-09-15 实测，会造成**内容永久缺口**）：云解析失败的条目
**当场就落盘为 `failed`**，而本地 VLM 兜底在**批次末尾串行**跑才更新它。
若进程在本地阶段前被杀（停滞自愈就会 kill；崩溃、断电同理），这些文档变成
**终态失败**：下次启动 `status=="ok"` 的跳过判据不会重做它们
（`failed` 既不等于 `ok` 也不被当待做），而 driver 的 `done+failed>=total`
还会把这批判成"已完成"→ **内容缺口 + 假完成**。

**修法**：云失败时落盘 `pending-local`（"还在等本地兜底"），本地跑完才写
`ok`/`failed`；待做判据改为 `status not in ("ok","textlayer")` 即重做；
driver 的完成判据加上 `not pending_local`。
三个位置口径必须一致，否则缺口会从另一个口子回来。

**验证**：全语料扫描出 5 条旧口径的 `cloud-failed` 记录并改回 `pending-local`，
下一轮即被重做。

| **部分文档永久 pending** | 同一份文档重提仍卡；**改成 ASCII 文件名也一样卡**（排除文件名编码）；换 key 也一样 |
| 20 部探针 | **15 部云成功 / 5 部云失败** → 5 部进本地兜底队列 |
| 单批吞吐（并行 8） | 峰值 **~1000 部/小时**（云健康时）；云降级时掉到 ~25 部/小时 |
| 本地 VLM | **~200 秒固定启动开销**（2 页 211.8s）+ ~4.6 页/分；241 页 3129s |
| 云额度 | 5000 文件/日；实测一批 500 部用量 <500，**额度不是瓶颈** |

#### 10.10.1 ❗"三个 key 都拥塞"= **服务侧间歇降级**，不是 key/文档/额度问题

**问题**：云侧出现大批"解析失败（轮询超时）"时，怎么判是"某个 key 被限"、
"某份文档解析不了"、还是"服务整体降级"？判错会浪费时间换 key 或换文档。

**实测判据（三种对照做完才能下结论）**：

1. **同一份新文档 × 三个 key** → `project/loop2/loop3` **全部 154s 超时**
   → 与 key 无关。（若只有某个 key 超时，才是 key 被限/额度问题。）
2. **同一份文档稍后重测** → **5.8 秒成功**（连"终态失败"的 8 页/1.5MB 文档也一样）
   → 与文档无关，是**时间窗口**问题。
3. **额度与用量**：今日 1248/5000、各 key 用量正常（project 1373 / loop2 64 /
   loop1 3 / loop3 1）→ **排除额度与配额**。

**结论**：云侧会**间歇性降级**——降级窗口内任务被**正常接受并返回任务号**，
但**永不完成**（轮询超时，`status == "pending"` 直到超时）；窗口过后同一文档
几秒即成功。窗口长度实测约 15–40 分钟，一天内多次出现。

**这对策略的含义（重要）**：
- **换 key 无用**（三 key 同降级）；**换文档无用**（同一文档事后就成）；
- **加长超时收益有限**：600s×2 在降级窗口里一样超时（窗口 >20 分钟时），
  而在健康时段 5.7s 就够——超时值的实际作用是**健康时段留给慢文档的余量**；
- **真正的解法是"晚点重试"**：把失败文档记为 `pending-local`（见 10.9），
  下一轮/下一个批次再提交。实测它们**几乎都会在下一次尝试时成功**。
  故 `_requeue_cloud_failures()` 在批次收尾把云失败转回待做，是**核心恢复机制**，
  不是权宜之计。
  ⚠ **这条机制在 2026-09-15 22:1x 之前是"半截"的**：转回待做**有人写、没人读**
  （`pending-local` 只存在于它所属批次的清单里，而 driver 收批后立刻换一批
  全新零重叠的文档 → 这类记录永远不会被再消费）。修复见 **10.12**。

**排期含义**：剩 27,000 余部 ≈ **8–20 天**（取决于云健康时段的占比）。
判断当前处在哪种状态，跑：
```
& .\.venv\Scripts\python.exe -X utf8 var\ocr-loop\cloud_health.py            # 探针（一次）
& .\.venv\Scripts\python.exe -X utf8 var\ocr-loop\cloud_health.py --report    # 历史趋势
```
探针固定用小 PDF，让耗时只反映服务状态；三 key 全失败即判定为服务降级。

### 10.12 ❗状态台账的"未到终点"记录**无人消费** → 静默内容缺口 + 假完成（2026-09-15 22:1x 修）

**这是"state 持久化"的第二个真缺陷**（10.7 是键被覆盖、5.1 是别名死键，两者是
**写入侧**；这条是**消费侧**）——写入侧修好了，读侧从来没有过。

**症状**：批次能"完成"、日志能说"已完成 496/500"，但其中的若干部**再也不会被做**。

**现场证据（两处，都可在台账里复查）**：
1. `GB／T 34001-2016 中国修船质量标准`（152 页）与
   `GB／T 46085-2025 系留式观光气球通用技术条件`（27 页）在 19:46 / 20:13 被
   `_requeue_cloud_failures()` 重分类为 `pending-local`；
2. 批次 4 于 20:19 被宣布"已完成 496/500"（其中 2 部刚被重分类）、driver 立刻
   推进批次 5；
3. 批次 5 的清单里**没有**这两部 → `vlm_ocr` 只会被以**当前批清单**拉起
   （`--corpus-list evolve/work_batch5.json`）→ 这两部此后**无人再碰**，
   而当时的会话把它报告成"**已转 pending-local 的失败项会在下一轮自动重试**"。
   实测 22:1x 干跑：全库残留 **50 部**（这 2 部 + 批次 5 当轮的 48 部云失败）。

**根因（两处，都在 `batch_advance.py`）**：
- **顺序反了**：`_wait_batch` 先用 `done+failed+skipped >= total and not pending_local`
  判"到齐"→ **紧接着才**把 `failed` 重分类成 `pending-local`。决策与落盘互相矛盾：
  批次被宣布完成的同时，它的缺口刚被正式标记为"未到终点"。
- **没有消费者**：`pending-local` / `failed` 只存在于**它所属批次的清单**里，
  而 driver 收批后走 `next_batch`（**全新、零重叠**，见 `next_batch.prior_batch_paths`）
  → 上一批的残留不进任何清单。10.10 说的"核心恢复机制"因此**只写了没人读**。

**修法（规范所有者层 = `batch_advance.py`；它拥有"跨批推进"与"state→批次清单"边界）**：
1. **重分类提到收批判据之前**，并**重读一遍** state —— 决策与落盘一致；
2. 收批判据改为 **"每部文档都到过一次终点"**
   （`完成+失败+待人工+巨型跳过+待重做 >= 总数`）：`待重做`不再**拦死**推进
   （否则一部云侧永久卡死的文档会把整条链钉住），但它**必须**被带走；
3. 新增 **`_carry_over()`**：构建下一批清单时把**全局**残留并入
   （`paths = 全新 + 残留`，清单里新增 `carried_over` 字段），
   并在日志里点名——**这是"晚点重试"机制唯一的消费者**；
4. **显式终点 `needs-human`**：本地 VLM 失败（识别层能力边界）、记录无源 PDF、
   或**携带重跑满 `MAX_CARRY=3` 次**仍未成功 → 转 `needs-human`（append-only 台账
   `evolve/carry_over.jsonl` 记每次携带），**永远带着数字出现在日志里**，
   既不静默丢、也不无限重试；
5. **口径诚实化**：收批日志不再写"已完成 N/N"，改印
   `收批：完成 X · 残留 N 部（带进下一批重跑）· 巨型跳过 Z · 待人工 V / 共 T`；
   `仍在跑` 行同样改成分桶数字（旧写法 `285+48（待本地 0）/500` 会把 48 部失败
   读成"进度"）；基线路加印**未进分母的部数**（`scout` 的 `skipped_pipeline`），
   防止"评估 496 部 · 命中 0"被读成"500 部零缺陷"。

**验证**：
- **审计报告 `AUDIT-100PCT-CLAIM.md`**（业主质询"几百部百分百完美入库"的核对结论：

  含上述那 2 部搁浅文档（修复上线后它们会随下一批清单重跑）；
- 生效方式：**driver 必须重启**（`vlm_ocr` 不用动）——watchdog **不负责**拉起

**教训（可迁移）**：写状态的一方修好≠状态可用。**每一个"未到终点"的状态值都必须

### 10.14 云并发度实测校准：`--parallel 8 → 24`（吞吐 ×1.94，2026-09-16）

**背景**：`--parallel 8` 长期未测。实测中位文档 29s → 单 worker 理论 ~2 部/分钟，
8 并发应 ~16 部/分钟，而批 6 实际只有 8–12 部/分钟 → **客户端并发可能不足**。

**探针**（`var/ocr-loop/probe_concurrency.py`，新工具）：取本批尚未做过的文档，
每档 20 部、整档一次并发发起、三 key 轮转分配：

| 并发 | 吞吐 | 时延中位 | 每 key | 失败 |
|---|---|---|---|---|
| 8 | 15.8 部/分钟 | 26.3s | 均衡 | 0 |
| **24** | **30.6 部/分钟** | **29.3s** | 均衡 | 0 |

**吞吐 ×1.94 而时延几乎不变 = 云侧不排队**（若云是瓶颈，时延会随并发线性上升）。
故**我们一直是客户端并发不足，不是服务端瓶颈**。取 `PARALLEL = 24`
（每 key 约 8 并发，探针只跑 20 部、尚未触及上限，故留余量）。

⚠ **样本量教训（第一版结论自相矛盾）**：首轮每档只取 8 部，得"并发 16 比并发 8
更慢"——而任务数（8）尚未触及并发上限、两者**本应完全等价**。方差压倒并发信号。
**每档至少 20 部，看时延中位而不是总墙钟。**

**生效方式**：`PARALLEL` 是 `start_batch` 的常量，而 `start_batch` 每批新起一个
`vlm_ocr` → **改常量即可，批 7 自动生效，无需重启任何进程**（批 6 不受影响）。
`_stall_min()` 只由 `CLOUD_TIMEOUT_S × CLOUD_ATTEMPTS` 推导（=30 分钟），
**与并发度无关**；并发变大后批进程 CPU 增长更快，停滞误判只会更少。

### 10.15 表格护栏的两个死判据 + 两个新口径量（2026-09-16，独立审计提出后自查）

**一、`table-<kind>` 名下两条护栏**曾经**全不可达**（该类实际是 0 条可达判据）：

| 护栏 | 声称防的事 | 不可达原因 |
|---|---|---|
| `no-rows` | 表格整体丢失 | `evolve.py` 的 `if thtml:` 在 `content_markdown` 为空时**整段跳过** `table_defects()` → 恰在"整体丢失"时失效 |
| `image-missing` | 符号图丢失 | `table_defects` 只在传入 `image_exists` 时才检查图片，而调用点**没传** → 恒不触发 |

**修法**：
- `image-missing`：接上真口径。实测（`probe_table_img.py`，15 部/96 张表）
  `<img src>` 是**裸 sha256.jpg 文件名**，文件在 `<产物>/mineru/<标题>/auto/images/`
  → 按 basename 在产物树里递归找（带缓存，避免逐单元格 walk）。
- `no-rows` 够不着的那条路 → 我曾新增 `table-body-missing`，**已删除，见第二节**。

**二、`table-body-missing` 的两个版本都被实测推翻（保留证据，别再犯）**：
- **第一版**按"条款页范围内有表、而该条款 `content_markdown` 为空"判 → 实测
  `GB 30871-2022` **报 30 处**、`GB/T 1000-2016` 报 1 处，**全部误报**。
  反证：GB 30871-2022 `table_len=7119`、`preproc=7114`、`missing=3 字符`
  ——**表格文本完整进了判据**，只是被**绑到别的条款**上。按页范围判实测的是
  **绑定差异**，不是缺失，属无判别信号。
- **第二版**改文档级 `table_len < max(200, 0.2×preproc)` → 独立审计全量重跑
  **215 部命中（8.5%）**；我实地复核抽样 20 部：**全部 `preproc == para`、少读 0.0%**
  ——表格一个字都没丢。根因：`0.2×preproc` 对小于 200 字符的表**恒成立**
  （`para==pre` 时 `max(200, 0.2pre)=200 > para`），固定下限在作怪。
  反向核对：真少读 >5% 的文档（`GB／T 20892-2020` 少读 14.3%）**一部都没命中**。
- **代价**：它 31 部假命中直接触发"达线类→停止推进"，把推进链停在第 6 批收批处
  （批 6 基线 32 命中里它占 31 部 = 96.9%）。**判据错误可以直接停掉整条产线**。

**结论**：零真阳性 = 无判别信号 → **按项目纪律删除**（同 `col-count-mismatch` /
`empty-cell-run`），不做"第三次改改看"。**恢复条件**：出现"文档级表格确实整份丢失"
的实测样本，且判据必须**相对**（如 `para < 0.5×preproc` 且 `preproc ≥ 2000`），
不能用固定下限。现状：**"整份丢失"这一档目前没有类级护栏**，是已知缺口，
不再用假护栏糊上（`no-rows` 仍在，只是够不到"html 为空"那条路）。

**三、两个新口径量（都只是量，不是缺陷类）**：

### 10.16 ❗云阶段消费器**无超时** + 记录缺 `key` 崩 worker（2026-09-16 批次 7 实测）

> ⚠ **本节第一版把根因写成"线程卡在连接层"，那是误判**。真实根因见"根因二"：
> **429 提交限流**。保留误判过程，是因为它演示了一个危险的推理陷阱（见文末教训）。

**症状**：批次 7 于 `00:44:14` 启动（`--parallel 24`）。`00:45:20` 后：
- **状态文件 16 分钟零字节增长**（`ok 32 / failed 27` 一动不动），日志几乎不动；
- 但进程 **CPU 仍在烧**（60 秒内 +11.86s ≈ 20% 一个核）、27 线程；
- **只有 3 条 established 连接**（24 个 worker 若都在轮询 HTTP 应有 ~24 条）；
- 驱动按"CPU 是否增长"判活（§10.8 的设计），故**认为"慢≠死"、一直退让不救**。

**根因一（结构缺陷，已修）**：`vlm_ocr.py` 用
`((_fut2doc[fu], fu.result()) for fu in as_completed(_fut2doc))` 消费全部 future。
`fu.result()` **没有超时**，而 `mineru_cloud_submit_and_wait` 的 240s `deadline`
**只在轮询循环里检查**——线程若卡在 connect/连接复用/重连路径（httpx `timeout=120`）
之外，该 future 可以永不返回。一个 future 永不返回 → `as_completed` 交不出它 →
主线程永久阻塞 → **剩余文档连提交都不会发生**（实测只处理 62/500 即停摆）。

**根因二（真实天花板，本轮最关键发现）**：**云侧按提交端点限流**——
`POST https://mineru.net/api/v4/file-urls/batch` → **429 Too Many Requests**。
批次 7 的 `vlm_batch7.err` 里 **429 出现 303 次**；那些 `wall_s` 仅 0.1–2.1s 的
"即时失败"**全是 429**。即：**`--parallel 24` 顶穿了提交速率上限**，
所谓"降级窗口"里很大一部分其实是**我们自己打出来的 429**。

**根因三（我自己的修复引入的新缺陷，最危险）**：为根因一加的兜底记录只写了
`status/channel/msg`，**缺 `key`** → `commit_rec` 的键护栏抛
`RuntimeError: ! 状态键非法=None（std_no=None）`，从 `main()` 穿出
→ **整个 worker 死亡**（`vlm_batch7.err` 末尾即此 traceback）。
扫描后发现**同类缺陷共 3 处**，其中 2 处是**预先存在**的：
`_safe_stage` 的"云阶段异常"分支、`cloud_disabled()` 分支——
它们一直缺 `key`，只是 429 成为常态异常后才把这条路径踩响。
**教训：给"异常/兜底路径"补记录时，必须让它与正常路径产出同形记录**，
否则兜底本身变成新的致死点。

**修法**（三处配套，缺一不可）：
1. `as_completed(fmap, timeout=…)` + `except TimeoutError`：超时即把尚未返回的项
   产出为**可重做失败**（`status=failed` + `channel=cloud`），然后继续收尾；
   超时值 = 云端预算 ×1.6（=384s）——健康文档实测最大 215s，故不误杀。
2. `ex.shutdown(wait=not _timed_out[0])`：**超时后必须不等**，否则 `wait=True`
   把"带超时的消费"重新变成永久阻塞。⚠ `_timed_out` 必须在**分支外**定义一次
   ——在 `_iter_done` 里再定义一次会让闭包写内层对象、外面读外层，标志永远 False。
3. `_abandoned` 键集合 + **所有兜底记录补 `key`**（`_fallback_rec` 统一构造）。
   迟到返回的结果**只记日志、不落盘**，否则会把已判 `failed` 改回 `ok`，
   而 driver 已按 failed 计入残留 → 同一部重复处理、口径串味。
4. **并发回到 8**（见 §10.17）。

**回归仪器**：`var/ocr-loop/test_cloud_stage_timeout.py`（12 项）——含
**反向对照**（无卡死时不许误报超时）、迟到结果不许覆盖、
以及**扫描护栏**（遍历 `vlm_ocr.py` 全部记录构造，断言"直接落盘的必须有 `key`"，
这一条能直接抓住根因三那类缺陷）。另有只读自检 `probe_rec_keys.py`。

**可迁移教训**：
- 凡"主线程等 worker 结果"的地方，**`result()` 都必须带超时**；
  `as_completed` 只保证"完成即交付"，**不保证"总有完成"**。
- **"进程有 CPU 消耗"不能证明"批在推进"**——本缺陷里 CPU 一直在烧、状态却是冻的。
- ⚠ **"时延不涨"不能推出"可以提高并发"**：429 限流与低时延可以同时成立
  （被限流失败的请求耗时极短）。判断是否触限要**看错误码**，不是看时延。
- ⚠ **我连续两次误判同一现场**（先"240s 超时簇"、再"线程卡在连接层"），
  两次都是因为**只看了消息文本、没看 HTTP 状态码**。
  `msg` 里的"轮询 240s"是**配置值**不是实际耗时（已改为"配置超时 Ns"），
  而 429 只出现在 `.err` 日志里。**定位限流类问题，先 grep 状态码。**

### 10.18 ❗`MineruCloudError` 宽判 → 限流被当"云能力边界" → 白烧数小时 GPU（2026-09-16，代价最大）

**缺陷**：`run_cloud` 的 `except MineruCloudError` 把**所有**该类异常都返回
`fatal=True`（注释写的是"能力边界类（页数超限/格式不支持）"），于是立即转本地 VLM。
但 `MineruCloudError` 同时承载两类语义完全不同的错误：

| 类别 | 真实文本样例 | 云侧再做一次能成吗 |
|---|---|---|
| **能力边界** | `number of pages exceeds limit (200 pages)`、格式不支持 | ✗ 不能 → 转本地**对** |
| **瞬时/限流** | `429 Too Many Requests`、`retry limit reached`、超时、5xx | ✓ **能** → 必须**重投云** |

**代价（实测）**：429 风暴期间 **135 部**被误判 `fatal=True` → 全部路由进本地 VLM。
本地 VLM 比云**慢约 20 倍**且**串行独占 GPU**（~200s 固定启动 + ~4.6 页/分钟）
→ **数小时 GPU 时间**被烧在"重投云几秒就能成"的文档上。
更糟的是：这与本项目**自己写下的告警正好相反**——`vlm_ocr.py` 的 `pending-local`
注释里明确写着"其余（云**拥塞**导致的超时）：**必须重试云**……早先的实现把它当
'待本地'，于是云恢复后这些文档仍被送去慢 20 倍的本地 GPU"。**实现与设计相悖。**

**为什么之前没暴露**：429 是"我自己打出来的"——`PARALLEL 8→24`（§10.17）触发了提交限流，
才让这条一直存在的错误路径变成常态路径。**所以这是"提并发"这个错误决定连带炸出的真缺陷**。

**修法**：
1. 新增窄判据 `_is_capability_boundary(err_text)`：**能力边界白名单**命中才算 fatal，
   且**先排除**瞬时特征（`429` / `too many requests` / `retry limit` / `timeout` /
   `502|503|504` / `connection` / `temporarily`）。白名单优于黑名单——
   未知错误默认走**重投**（误判成可重投只多花一次云调用；误判成 fatal 白烧数分钟 GPU）。
2. 瞬时类走"换 key 重试 → 全失败则落 `failed`（**不设 fatal**）"
   → 由 `_requeue_cloud_failures` / `_carry_over` 带进下一批**重投云**。
3. **存量状态修复**：`repair_fatal_misclass.py`（预演/`--apply` 两态、带反向核对）
   把 `fatal=True` 且 `channel=cloud` 且 `status∈(failed, pending-local)` 且 **≤200 页**
   的 135 条改回 `fatal=False / status=failed`；**真巨型 8 条（228–408 页）保持原状**。

**回归仪器**：`test_cloud_stage_timeout.py` 第 5 组（7 条判据用例，含 429/5xx/连接类
反向对照与页数超限/格式不支持正面对照）。

**可迁移教训**：
- **一个异常类型承载两种语义时，catch 之后必须再分类**，不能整体当作其中一种。
  此处"能力边界"与"临时故障"混在 `MineruCloudError` 里，宽判的代价是**数小时 GPU**。
- **"降级兜底"路径要算成本**：转本地看似"稳"，实则是慢 20 倍——兜底策略本身要
  按"重投便宜还是兜底便宜"来选，而不是"有兜底就先用兜底"。
- 提并发前先问"**我们自己会不会打出限流**"；并发问题的第一现场往往不是"云慢"，
  而是"我们太快"。

**⚠ 为什么这件事最严重**：driver 的"剩余候选"**永远不含它们** →

① 在**整语料**上按 `norm_stem` 分组（不是过 block 之后才分组）；

### 10.28 `dot-leader` 判据与所有者层**口径错位**：达线闸门误报 → **整链停摆 1h50m**（2026-09-16）

用 `KS_CORPUS_LIST` 指向该批清单——**注意 `verify_batch.py` 默认看的是

| 文档 | 命中原文 | 判定 |
|---|---|---|
| GB 2099.5-2008 | `……（正在考虑中）` | 括号内是**中文** → 正文省略号，正常标点 |
| GB／T 14315-2008 | `……（省略）` | 同上 |
| GB／T 39398-2020 | `……（\nD TGD, ᵢ = …` | 括号内是公式，非编号 |

**根因（同类错位第三次）**：检测器分支①是 `…{2,}\s*[（(]`——**只要省略号后面
跟个括号就报**，括号里是什么完全不管。而**所有者层**
`src/core/text_utils._RE_FORMULA_LEADER` **明确要求括号内是编号**
（`[A-Za-z]?\.?\s?\d{1,3}…`），注释写死了理由：
「**只放宽空格，不放宽字符类**——避免把正文括号内容误当编号」。
→ **检测器报缺陷、所有者层（按设计）不清洗**，同一处文本永远报缺陷。

`text_utils` 注释里自己记着：同类错位**已修过两处**（`…{3,}`、`\.{6,}`），
**本条括号分支是当时漏掉的第三处**。

**修法**：分支①加"括号内须有数字"（可带前导字母/点/空格），与所有者同口径：

```python
# 旧：…{2,}\s*[（(]           ← 只要括号就报
# 新：…{2,}\s*[（(]\s*[A-Za-z]?\.?\s?\d{1,3}
```

**收窄 ≠ 把判据改瞎**（三重复核）：
1. 真缺陷 **6 种形态仍全部捕获**，含附录字母号 `……( B.6`、`……(C. 3`；
2. 新增 `test_dot_leader_judge.py` 钉 **双向同源口径契约**：
   *分支①命中 ⇒ 所有者层必须真的会清洗它*，反之亦然——**这条契约测试是防未来
   再漂移的关键**（本次漂移正是因为它不存在）；
3. 用**同一算法**重跑批次 13 侦察：`dot-leader` **整类消失**、总命中 **7 → 4**、
   达线解除；门禁 pytest `1140 passed, 3 skipped` + mypy 122 文件干净。

**可迁移教训**：**判据必须与其所有者层同源口径**。凡"检测器报缺陷"而
"所有者层按设计不动"的组合，都是在生产**永久误报**——要么对齐判据，
要么对齐所有者，二者必居其一。

### 10.26 `needs-human` 原是**永不携带的终点**：临时失败被判终态的**第四处**（2026-09-16）

**先纠正 §10.25 的结论**：§10.25 说"修这个缺陷必须动两处（常量 + 携带计数），
处置完即好"。**这是错的**。实测：`repair_needs_human.py --apply` **跑了两次**
（台账 `04:07:25`、`04:11:49` 两条 `state_repair`，各自自报 `repaired=37`），
两次都在 30 分钟内被**原样推翻**——04:14:47 复查 state，`needs-human` 仍是 37，
且这些记录的 `ts` 仍是 `03:21/03:53`（批 10 收尾时刻，**根本没被改动过**）。

**真正的根因（新的一类，值得单独记住）**：`vlm_ocr.commit_rec` 是**整体读改写**——
`state[key] = rec; save_json(STATE, state)`（见 `vlm_ocr.py:714` 注释）。
worker 启动时把整个 state 读进**内存**，之后每次提交都用**内存里那份 dict 整份覆盖文件**。
于是在 worker 活着的时候，**外部脚本对盘上 `vlm_ocr_state.json` 的任何修改都是无效的**：
它只活到 worker 下一次提交为止（秒级）。

> **教训（可迁移）**：修复必须做在**持有该状态的进程里**。对一个被活跃进程
> 整体读改写的文件做外部修补，等于写进一个**会被覆盖的缓存**——而且它会
> **自报成功**，让人以为修好了。这与 §10.20 的"用展示层文本做判定"是同一类毛病：
> **改了不归自己所有的东西**。

**第四处缺陷本身**：`needs-human` 在 `_carry_over` 里被写死为"永不携带"的终点
（白名单只认 `pending-local` / `failed`）。后果：**每一次云降级窗口都会生产一批
永久内容缺口**，而且 `MAX_CARRY` 3→8 只保护**将来**的记录，**救不了已经被钉死的存量**——
所以只调常量是**结构性不够**的，必须有**复归**路径。

**实测证据**（生产 state 逐条判定）：
- 37 部 `needs-human` **全部**落在"可重试"（`channel=cloud` 且 pdf 在盘上），**无一例外**；
- 页数 7–79，**远低于 200 页硬限** → 没有一部是云能力边界；
- `_carry_over(dry_run=True)`：修复前 `retired=37`、这 37 部此后再无任何代码路径消费；
  修复后 `readmitted=37 · carried=113 · retired=0`。

**修法（所有者层 = `_carry_over`，它正是持有 state 的那个进程）**：

| 机制 | 值 | 作用 |
|---|---|---|
| `_terminal_human_reason()` | 判据只用**记录自身客观事实** | 真终态仅两类：`channel∈{local-vlm,local}`（识别层能力边界）、无 `pdf` 或文件不在盘上。**不解析 `msg`**（它是展示层，会被层层前缀拼接，见 §10.20） |
| `READMIT_HARD_CAP` | 24 | 复归后的携带上限 |
| `READMIT_QUOTA` | 40 / 批 | 防一口气灌进上千部把本批全新文档挤掉 |
| `readmitted` 标记 | `True` | 复归记录**改用硬上限**而非 `MAX_CARRY`，否则会在 8 附近**来回抖**（携带→撞 8→判回→复归→…） |
| `human_reason` 字段 | 退役原因 | 结构化留痕，日后不必解析 `msg` |

（复归件的实际成功率要等批次 12 跑到末尾量：`_carry_over` 把它们**追加在清单尾部**，
故它们在批内**最后**被处理。）

**⚠ 运维事实（接手必读）：watchdog **不会**替你重启 driver。**
`watchdog.ps1` 只做一件事：driver 进程真死了就**接管拉起一个 `vlm_ocr`**，
它**不懂跨批推进**（源码注释自己写明了）。所以杀掉 driver ≠ 自动换新代码，
必须手动重启，否则推进链停在批次边界：

```powershell

taskkill /T /F /PID <trampoline_pid>      # /T 连子进程一起杀
& .\.venv\Scripts\python.exe -X utf8 var\ocr-loop\batch_advance.py --size 500 --max-batches 20
```

**改完 `batch_advance.py` 必须重启 driver 才生效**（内存副本，§10.25 已记）；
`vlm_ocr.py` 的改动则必须重启 **worker**。
两处都靠**进程启动时间 > 文件 mtime** 来证明"这次确实加载了新代码"。

### 10.24 ⚠ 诊断计数器 `vlm_key_usage.json` **不是权威口径**（我据此误判过一次）

**现象**：该文件报 `project 2109 / loop2 304 / loop3 6`，据此我判断
"轮转起始 key 被竞态吃掉、key 用量严重失衡"，并据此写了一轮归因。

**真相**：权威口径是**记录自身的 `cloud_key` 字段**（`vlm_ocr_state.json`）——
批 10 实测 `loop2: 138 · project: 136 · loop3: 3`，**project 与 loop2 几乎完全均衡**
⇒ **轮转一直是有效的**，我上一轮的归因是错的，已撤回。

**为什么会错**：`add_key_use()` 是**无锁 read-modify-write**
（`load_json` → `+1` → `save_json`），而批量侧有 24 线程 + 可能并存的多个 driver
同时调用 → **互相覆盖丢失**。该文件只适合"大致看有没有 key 被完全闲置"。

**处置**：`add_key_use` 的 docstring 已写明"非权威、要精确查 state 的 `cloud_key`"，
把这个坑钉在函数上（防止下一个接手者重踩）。

**教训（本会话第 5 次因"仪器"而非"事实"出错）**：
**一个数字看起来合理，不等于它是权威来源。** 我手里一直有记录级的
`cloud_key` 字段（每条记录都带），却先去信了一个全局计数器。
**先问"这个数字是从哪来的、有没有竞争写入"，再拿它做推理。**

### 10.23 ✅ **已结案：不是缺陷**——"worker 静默消失"实为**正常退出 + driver 接力**

> ⚠ **本节原判为"未解缺陷（worker 静默消失）"，2026-09-16 03:0x 由取证仪表证伪**。
> 错误结论留在文档里比不写更危险，故保留原文并在此更正。

**原判依据（现已证伪）**：`.log`/`.err` 都在同一条超时消息处结束、state 停止更新、
进程对消失、driver 隔几分钟才重拉。

**证伪证据（`worker_diagnostics.log`，本轮新增的取证仪表读到）**：
```
[02:55:01] pid=37040 START
[02:55:01] pid=37040 faulthandler 已启用…
[03:03:39] pid=37040 ATEXIT（正常退出 / SystemExit）
```
该 worker 跑了 **8.6 分钟**后**正常退出**，且 `vlm_batch8.log` 的启动行显示它
**规划了 316 部**（`目标 596 部（走云 316，… 已完成 279）`）——它**干完了自己那一波**。

**真实机理（正常设计行为）**：
1. `vlm_ocr` 每轮从清单里取"尚未到终点"的文档，处理完就退出（正常收尾，走 atexit）；
2. driver 看到"未跑完"→ 按设计 `start_batch` 重拉续跑（批 8 实测第 1/2/3 次）；
3. state 断点续跑，零丢失。

**我为何误判**：把"**driver 的 5 分钟重拉间隔**"读成了"worker 异常消失"。
`_sleep_until_dead`（§10.21）已把这段间隔从最坏 5 分钟压到"进程一没就重拉"，
所以这个观感问题现在也一并消失了。

**未解项清零**：原列的三条验证方法（RSS 峰值、系统事件日志、faulthandler）
不再需要——**取证仪表已给出"正常退出"的直接证据**。

**留下的一般教训**：**"日志戛然而止 + 进程消失"不等于"异常死亡"**——
正常退出同样会戛然而止。判据应当是**退出路径**（atexit 有无留痕），
而不是"日志看起来断了"。这个错我犯了一次，仪表装上后 30 分钟内就被纠正。

### 10.22 `parallel=24` 的收益边界：**只在健康窗口兑现**（2026-09-16 批 8 实测）

**收益（已测到）**：批 8 启动后 7.5 分钟内，真云 OCR **72 部 → 9.6 部/分钟**
（单部中位 21.2s）；批 7 在 `parallel=8` 下同期约 **1.4 部/分钟** → **×7**。

**边界（同样重要）**：该收益**只在云健康窗口内兑现**。批 8 在 `02:28–02:34` 健康期
跑出 72 部，`02:34` 起云侧转入降级（`.err` 连发 `云解析轮询超时`）→
state 停止更新、真云 OCR 归零。**此时 24 个槽位只是被钉在 240s 超时上**，
提高并发不再有任何增益。

→ **结论**：并发度决定"健康窗口内的产能上限"，**不能**改变"降级窗口的产能下限"。
两者是独立的两根轴（另一根是 §10.10 的窗口宽度/频次）。
排期估算必须同时看这两根轴，不能只看并发。

**启动瞬时的 429 突发（新观察，非缺陷）**：批 8 于 `02:27:28` 启动、24 并发齐射
→ `02:28` 一分钟内出现 **87 条秒败（`wall_s` 中位 0.2s）**，`batch8.err` 里
429 计 93 次；**此后不再出现**（`batch8.err` 计数停在 93）。
即：**429 是启动突发，约 1 分钟自愈**，失败项全部落 `failed` → 跨批重投。
先前那次 303 次 429 的"风暴"另有叠加因素：**我重启 driver 时旧 worker 未退出，
多份 worker 长期并存**（§10.20）。故回退判据先查"是否多 worker 并存"是对的。

**验证到的一致状态**：批 8 里 `fatal=True` **0 条**（全库仍 9 条，全是真巨型
228–408 页）——§10.18/10.18b 的误判修复在全新批次上确认有效，**未再出现
"限流/文件占用被当云能力边界 → 白烧本地 GPU"**。

### 10.21 driver 的固定 300s 睡眠 → **可中断睡眠**（worker 一死立刻重拉）

**缺陷**（2026-09-16 实测观察）：`_wait_batch` 用固定 `time.sleep(300)` 等下一轮判活。
**worker 若在这 5 分钟里死掉，driver 要睡满才回到 `while _procs()`** → 最坏空窗
**5 分钟**；而这类死法在整轮里**反复发生**（我自己重启 worker 时、429 风暴里的多次崩溃、
批 7 期间至少 8 次重拉）。空窗期间**没有任何文档在被处理**，是纯产能损失。

**修法**：新增 `_sleep_until_dead(total_s, step=20)`——按 20 秒步进轮询进程存在性，
**批进程一消失就立刻返回**，让外层 `while _procs()` 立即判假、走重拉分支。
只轮询 `_procs()`（pid+name 过滤，毫秒级），**不改动任何判据**：
stall 阈值、启动宽限期、重拉次数上限全部不变。

**未做（记录在案）**：`CLOUD_TIMEOUT_S = 240` 对"永远不会返回的任务"偏长
（每部白占 4 分钟槽位）。但降它需实测"健康文档的最长耗时"——§10.10 记过
实测最大 215s，故 240 不该动；真要降须先有一份更新的耗时分布。

### 10.20 并发定案 **24**：429 的真因不是并发（我的第三次归因才对）

**结论**：`PARALLEL = 24`。**429 在真实批次下为 0**（`vlm_batch7.err` 新文件仅 3,656 字节，
vs 429 风暴时的 75,926 字节；新记录里 23 条失败**全是 240s 超时**、无一条 429）。

**我在此常量上错了两次，留证以免第四次**：

| 次序 | 我的归因 | 对错 |
|---|---|---|
| 第一次 | 探针说"8→24 吞吐 ×1.94、时延不涨" → 提并发 | 方向对，但**没识别 429** |
| 第二次 | 撞 429 → 判定"并发已到天花板" → 回退 8 | ❌ **错**：把"我们打出的 429"读成"服务端不允许" |
| 第三次 | 单账号限流探针 → 429 与并发上限无关 | ✅ **对** |

**决定性测量**（`probe_key_limits.py`，**全档只用同一个 key** 以排除多 key 混用）：

| 账号 | 并发 8 | 并发 24 | 持续 40 部（两波） | 429 |
|---|---|---|---|---|
| `loop3` | 18.5 部/分 | **77.8 部/分** | **88.1 部/分** | **0** |
| `project` | 44.8 部/分 | **78.6 部/分** | — | **0** |

→ **单账号在 24 并发下毫无压力**。429 的真实成因是
**`use_key()` 写全局 settings 被多线程互相覆盖**（`run_cloud` 重试循环里反复 `use_key`）
→ **同一账号被并发猛打、其余账号闲置**；叠加当时**多个重复 worker 并存**
（我重启 driver 时旧 worker 未及时退出），把量进一步压到一个账号上。

**为什么该提并发**（批 7 实录，这是真实的产能损失）：
12 分钟里**只有 17 部走真云 OCR**（另 109 部是复用产物、`wall_s=0`）
→ 真云速率约 **1.4 部/分钟**；而同 key 探针 8 并发就有 18.5–44.8 部/分。
差距来自 ① 并发放大 ② 失败文档撞满 240s 超时**占住槽位**
（8 个失败 × 240s ≈ 32 分钟·槽 ÷ 12 分钟 ≈ **2.7 个槽被长期占住**）。

**回退判据**（写进 `batch_advance.py` 常量注释）：若 24 并发下再现 429，
**先查是否有多个 worker 并存**（`CommandLine -match 'vlm_ocr'` 应只有 2 个进程：
启动器 + worker），再考虑降并发——**不要**直接归因并发。

**⚠ 遗留（尚未修，已记）**：`use_key()` 改全局、`run_cloud` 重试时反复 `use_key`
——多线程下 key 会被混用（`state` 里"key=project 占绝大多数"即其证据）。
单账号在 24 并发下既然毫无压力，**这个混用目前只影响"哪个账号被用得多"、
不影响成功与否**；但它是"多账号分池"这件事的唯一障碍，若要真按账号分池需先修它。

### 10.19 `_INDEX_HEAD` 前缀白名单：`中文索引`/`英文索引` 曾不被认作索引起始（2026-09-16 修）

**缺陷**（审计 H8 的 `toc-ingested-as-clauses` 命中追查而来）：`_INDEX_HEAD` 原为
`^\s*索\s*引\s*$`——**只认整块恰为「索引」**。而实测标准文末常写
`中文索引` / `英文索引` / `汉语拼音索引` → **索引态从不置位** → 索引条目被当正文吞入。

**现场证据**（用 pipeline 自己的 `load_middle_items()` 取切分器真正消费的 items）：
```
GB/T 13964-2008 照相机械术语   items 1529 条
  #7     目次                    ← 目录态正常
  #1464  '中文索引'              ← 旧判据不置位
  #1468  '白平衡 …… 2.78'        ← 索引条目（页码是**小数**，非 1–3 位整数）
  #1489  '英文索引'              ← 其后的整段英文索引被当正文
```

**修法**：前缀取**白名单** `(?:中文|英文|术语|汉语拼音|拼音|拉丁文|西文)?`
——⚠ **不能用 `[\u4e00-\u9fff]{1,4}`**：后者会把 `见索引` 也收进来
（正则自测**当场抓到**这个误报）。索引标题的前缀是有限枚举。

**误报核对（改的是入库路径，必须核）**：60 部语料扫描 → `_INDEX_HEAD` 命中 **4 条，
全是真索引标题、零正文误报**：
`GB/T 14733.5-1993` 的 `中文索引`/`英文索引`、`GB/T 15962-2018` 的 `索引`/`汉语拼音索引`
（后者旧判据同样不认 → 本次修复在语料上确有新增收益）。
见 `var/ocr-loop/probe_index_verify.py`。

**回归仪器**：`tests/test_toc_ingest.py` 新增两项（`test_index_head_accepts_prefixed_titles`
含 7 条正向 + 7 条反向对照；`test_prefixed_index_section_not_absorbed` 缺陷现场重放）。
门禁 `1134 passed`（+2）。

**⚠ 方法论教训（本轮踩坑，价值高于修复本身）**：
我为查这个缺陷**手写了两版内容提取探针**（`probe_index_head` 报 0 块、
`probe_index_title` 报 10 块——**互相矛盾**）。原因是各自手写了一套
`para_blocks → sub.blocks → lines → spans` 遍历，**结构与真实产物形态不符**。
改用 pipeline 自己的 `load_middle_items()` 后一次就得到权威答案。
**教训：读产物必须用生产代码自己的加载器，手写提取就是错仪器**——
它会让你在"数据里到底有什么"这个最基础的问题上得到错误答案，
而后续所有推理都建立在它之上。

### 10.18b 同类缺陷第三次：`_safe_stage` 把所有异常一律标 `fatal` → 又一次送本地 GPU

**同一根因的第二、第三次表现**（§10.18 是第一次）。`_safe_stage` 的
`except Exception` 分支返回 `fatal=True`，含义是"云再也不可能成功 → 转本地 VLM"。
但兜住的异常里绝大多数是**临时**的：

| 实测记录 | 条数 | 真实性质 |
|---|---|---|
| `PermissionError: [WinError 32] 另一个程序正在使用此文件` | 16 | **临时文件占用**（两台 worker 重启时争同一目录） |
| `PermissionError: [Errno 13] Permission denied` | 14 | 同上 |
| `PermissionError: [WinError 5] 拒绝访问` | 3 | 同上 |

**代价**：33 部被标 fatal → 排进本地 VLM（**慢约 20 倍、串行独占 GPU**）
→ 白烧数十分钟到数小时。而它们**重试即可**。

**修法**：异常分支按**类型**分可重试 / 不可重试——
`PermissionError / OSError / TimeoutError / ConnectionError` 一律
`fatal=False` + `status=failed` → 由 `_requeue_cloud_failures` / `_carry_over`
带进下一批重做；只有明确的不可重试异常才标 fatal。
**存量修复**：`repair_permission_fatal.py`（预演 / `--apply` 两态）修回 33 条。

**修复后实测（01:30–01:36，134 条新记录）**：
`fatal = 0`（此前动辄 34–135）、失败**全部走 `channel=cloud`**（不再有本地队列积压）、
成功率 **127/134 = 95%**。

**三次同类缺陷的共同教训**：**`fatal=True` 的语义是"终态、不可重试、转慢通道"，
它是一个昂贵断言**——每次误判的代价是数分钟到数小时 GPU。故凡要设 `fatal`，
必须**按错误类型白名单窄判**，默认值应当是"可重试"。

### 10.17 云并发度定案：**回到 8**（24/16 都被实测否决）

§10.14 记了探针结论（健康时段 8→24 吞吐 ×1.94、时延不涨），我据此把并发提到 24——
**方向是错的**。真实批次立刻暴露：**云侧按提交端点限流（429）**。

**探针为什么测不出来**：它用**小文档**（3–40 页）、跑在**健康时段**、只测 20 部，
提交速率远低于限流阈值。**探针只能回答"云侧是否排队"，不能回答"我们的提交速率
是否已触限"**——后者才是本项目真正的天花板。

**定案 `PARALLEL = 8`**（批次 1–6 长期验证的值）。提并发只会把预算烧在 429 上，
并把失败文档堆成"每部最长 240s 超时"的 worker 占用；**降级窗口内吞吐由
"窗口宽度 ÷ 超时"决定，与并发度无关**。

**尚未实测的提速方向**（不要当已验证）：① 多账号 key 分流（各账号独立限流）；
② 主动降速（限流类失败后指数退避），而不是提高并发。



**一、`table-<kind>` 名下两条护栏**曾经**全不可达**（`table-<kind>` 实际 0 条可达判据）：

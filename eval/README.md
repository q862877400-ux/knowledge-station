## 二、两批考卷的口径差异（**交接 §五 第 5 条，这里说清**）

**它们不是同一把尺子，通过率不可比、样本不可混算。**

| 项 | 正向（`bunny-benchmark/`） | 反向（`reverse-benchmark/`） |
|---|---|---|
| **怎么造的** | 先有一批外行说法（来自 `lay-phrasing/`），再**按类型规则去配**一条条文 | 先从库里挑出"能读出问法"的条文，**让模型看着条文写问法** |
| **gold 怎么来** | 规则配的（说法里的数值/判定词 ⇒ 配要求条款，否则配定义条款） | **就是那条条文本身**（配对天然正确） |
| **样本量** | 送审 150 ⇒ **可用 24** | 配对 310 ⇒ **可用 171** |
| **判定方式** | 自包含文档送审，**独立调 3 次**取多数 | 同样 3 次盲判取多数（**不告诉它这是反推来的**） |
| **最大缺陷** | 🔴 **判定会摇摆**：同一对输入 4 次调用得出**相反**结论 ⇒ 它的 README 自己把 24 条标为**"只能算待复验"** | 🔴 **循环论证**：问法是看着条文写的 ⇒ gold 天然偏向"能读出问法的条文"，**召回率会虚高** |
| **天花板** | 语料侧约 **100 条**（"说法↔术语"的关联是生成时贴的标签，不保证说法在问那个术语） | 未测；但 171 条只落在 **79 条独立条款 / 72 篇文档**上 |
| **能用它算什么** | 断"造题这条路通不通"（正/反向造题法的相对通过率） | **相对比较**：同一套设置下 A 与 B 谁好、每条丢在哪一步 |
| **不能用来算什么** | ❌ 不能当"系统召回率"（样本 24 且未复验） | ❌ 不能宣布"系统召回率是 X%"（循环论证使其偏乐观） |

**⇒ 混用规则（三条硬线）**：

1. **不许把两批的通过率放在同一张表里比** —— 造法不同、样本量差 7 倍、判定稳定度不同。
   历史记录里那张"五条造题路对比表"（`reverse-benchmark/README.md` §二）之所以能比，
   是因为它用的是**同一套 bunny 三路判定口径**，且**只比造题方法、不比系统**。
2. **不许用正向那 24 条去量系统** —— 它自己的归属文档写着"只能算待复验"。
3. **用反向那 171 条时必须连带引用"循环论证"那条限制** —— 见
   `recall-funnel/REPORT.md` §八 第 1 条；`contracts/benchmark.schema.md` 也写明
   **本批 gold 不是人工确认的**（违反该契约的 `confirmed_by` 必须是人，FR-004/SC-003 未满足）。

### ⚠ "正向"有两个不同的数，别当成一批

| 说法 | 实际指的是 | 资产在仓库里吗 |
|---|---|---|
| **正向 24 条** | `bunny-benchmark/usable-24.jsonl`（150 送审 → 多数判 PASS 的 24 条） | ✅ 在 |
| **正向 106 条** | `reverse-benchmark/README.md` 对比表里的「正向·旧配法（术语标签）+ 旧语料，13.4%，**106 条」** | ❌ **不在** —— 那句自己写着"语料已用完" |

**⇒ 交接文档 `docs/HANDOVER-2026-10-06.md` §五 第 5 条写的是"正向 106 条 vs 反向 171 条"，
指代不清**：106 那批**只是对比表里的一个历史计数，资产没留下**，
仓库里能实际拿来跑的正向资产只有那 **24 条**（且它自标"待复验"）。
**下一轮要量系统，只能用反向那 171 条。**

## 三、`golden/` 与 `baseline.json`：**另一件事，别混进来**

- `golden/` 的 **96 条**（实测）分型：`modality` 43 / `exact` 24 / `semantic` 20 /
  `legal_element` 3 / `modality_adversarial` 3 / `compliance` 3。
  它是**防倒退的尺子**（改代码后不许掉下来），**不是难度尺子**
  —— 这点写在 `specs/002-recall-funnel/spec.md` 的 Assumptions 里，本周期**不改它的用途**。
- `run_benchmark.py` 的用法：

  ```powershell
  & .venv\Scripts\python.exe eval\run_benchmark.py --db eval\golden\knowledge-snapshot.db
  ```
  默认对**快照库**跑（可复现、不依赖本机 `%APPDATA%`）；不传 `--db` 则对真库跑。
- **`golden/` 的命中判据是 (标准号, 条款号) 对**，不是只比条款号
  （2026-09-24 改的；理由与留痕在那份 docstring 里）。
- `baseline.json` **已写入**（实测 263 字节，2026-09-23）：
  `exact_hit@1 = 0.8889`、`recall@5 = 0.9778`、`recall@10 = 0.9889`、
  `modality_intercept_rate = 1`、`n_search = 90`、`n_adversarial = 3`（金标 `count = 96`）。
  ⚠ **它不含 `code_revision` 字段**（`contracts/baseline.schema.md` 要求有）⇒
  **无法判断这几个数是哪一版代码跑出来的**。用它当基线之前，先确认 `golden.json`
  在该时间点之后有没有改过；要重写就用 `--write-baseline`（且先在干净的工作区跑）。
  ⚠ **更正留痕**：本文初版写的是「`baseline.json` 当前是 0 KB 的空文件」——**那是错的**，
  错因是 `Get-ChildItem` 把 263 字节按 KB 取整显示成 `0`，我没回原始来源核。**已按实测改正。**

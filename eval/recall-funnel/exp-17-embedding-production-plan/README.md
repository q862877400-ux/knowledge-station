### ★ 一个**很容易踩**的坑（本方案最重要的发现）

**不能把前缀无脑加在 `embedder.embed_query` 里。** `src/core/storage/clause_repo.py:426`
（`_reindex_clause_indexes`，补丁重算向量）用的是

```python
emb = embedder.embed_query(f"{title or ''}\n{content_text[:512]}")   # ← 这是【条文侧】文本！
```

也就是说 **`embed_query` 被两处调用**：查询侧（`hybrid_engine.py:310`）和**条文侧**（`clause_repo.py:426`）。
把前缀加在 `embed_query` 内部 ⇒ **补丁重算会把查询指令前缀加到条文向量上**，
于是"被改过的条款"和"没改过的条款"用了**两套文本口径** —— 行数、维度、KNN 全正常，
**没有任何读数能看出来**。⇒ 前缀必须做在**调用点**（或给 `embed_query` 加显式参数，默认不加）。

## 三、成本账（★ 与"关掉向量路省 ~0.6 s"逐项对账）

| 项 | 现役 `bge-small`（CPU） | 目标 `Qwen3-0.6B`（GPU fp16） | 差 |
|---|---|---|---|
| 查询侧嵌入（warm p50） | **1.38 ms** | **32.02 ms**（p90 34.74） | **+30.6 ms/问** |
| 冷启动（首次加载） | — | **5,154.3 ms** | 首次多 ~5 s |
| 峰值显存 | 0 | **1,164 MiB** | RTX 4080 SUPER 16,376 MiB ⇒ 富余 |
| 向量路扫描（663,634 行，`clause_vec`） | 1,074.7 ms | **1,074.7 ms（不变）** | 0 —— 维度仍是 512，KNN 是同一张同形表 |
| 无显卡时的替代 | — | CPU fp32 **72.88 ms**〔抽样 30 条〕 | 可用，慢 2.3× |

**对账（这是本任务书点名要算清的那笔）**：

1. **两笔账不是同一笔**。「关掉向量路」省的是**扫描**（`NEXT-DEV-PLAN` §四记 **606.0 ms @52 万行**；
   E4b 在 **663,634 行**实测 **1,074.7 ms**）；「换模型」多花的是**嵌入**（**+30.6 ms**）。
   ⇒ 换模型的代价比"省下的 0.6 s" **小 20–35 倍**，**不能用一方的收益抵另一方的代价**。
2. **但两者强相关**：关掉向量路 = **丢掉 E4 量到的全部收益**，而 P1/P2 到目前为止**所有**提升都靠向量路
   （`exp-13/14/15` 的每条臂都在向量路上量）。⇒ 只要向量路还留着，就该把它换成好的模型；
   真要关，那是**另一个**决策（属行为改动，且要先把 P1/P2 的结论收口）。
3. **相对占比**：32.02 ms 嵌入 ÷ 1,074.7 ms 向量路扫描 = **2.98%**（E4b 原话）。
   ⚠ 这只是**向量路内部**的占比，**不是端到端延迟占比**（本仓没有端到端读数，不声称）。
4. **冷启动 5 s 是一个真问题**：建议上线时**启动即预热**（本方案**未验证**预热的有效性，只登记建议）。

## 四、可续跑重建（本轮实际做出来的东西）

### 4.1 设计（`rebuild-shadow.py`）

- **只读真库**（`file:...?mode=ro`）；**没有**任何写源库的路径（判据 `test_module_has_no_write_path_to_source`）。
- 影子表写在**独立库文件**里（不复制 3.1 GB 整库）；表名 `clause_vec_qwen`，DDL 与生产 `clause_vec`
  **同形**：`vec0(clause_revision_id TEXT PRIMARY KEY, embedding FLOAT[512])`。
- **断点续跑 = `rowid` 游标 + 库内 checkpoint 表**，且 **checkpoint 与数据同一次 `conn.commit()`**
  ⇒ 强杀只会整批回滚，游标不会超前后错位。
- **口径守卫**（`model_id` / `out_dim` / `text_formula_sha` / `limit`）：任一不一致**当场报错**。
- **文本公式**：`f"{title or ''}\n{content_text[:512]}"`（与 `clause_repo` 两处逐字一致）。
- **取数过滤**：`WHERE trim(coalesce(content_text,'')) <> '' ORDER BY rowid`（与 E4 同口径）。
- **向量存储格式**：实测 sqlite-vec 把 `json.dumps(list)` 与 `array('f').tobytes()`
  **存成完全相同的 2048 字节 float32**（逐字节相等，`var/tmp/exp-17/probe.py`）
  ⇒ 用快的 blob 路径，与生产 `_serialize_vec`（json）**逐字节等价**，不引入新变量。

### 4.2 五项验证读数（`verify-resume.py` → `result.json`，**全过**）

| # | 验什么 | 读数 | 判定 |
|---|---|---|---|
| T1 | 一次跑完 vs 中断续跑 | 300 行 **0 处不同**；`one_shot_digest == resumed_digest`（`d1c1c06b…`） | ✅ |
| T2 | **真强杀**（`Popen.terminate()`，不是干净退出）后续跑 | 强杀时已落盘 **2,080** 行；续跑到 20,000 行后 **0 处不同** | ✅ |
| T3 | 幂等（对已完成的库原样重跑） | `rows_written = 0`，全表哈希不变 | ✅ |
| T4 | **真模型口径 vs E4 冻结向量** | 复刻 E4 分批（每批 16）⇒ **64/64 逐字节相同**（`cos_min = 1.0`、`maxdiff = 0`） | ✅ |
| T5 | 真库一行没动 | mtime / size / `clause_vec` 663,634 / `clause_revision` 663,634 **前后全同** | ✅ |

**T4 的副读数（★ 一条要记住的坑）**：把同一批 64 条**一次**喂进去（换一种分批）⇒
只有 **16/64** 逐字节相同，`maxdiff = 8.4e-4`、`cos_min = 0.999995`。
根因 = **fp16 的批不变性**：cuBLAS 对不同 batch/序列长度会挑不同 kernel，累加顺序不同。
⇒ **拿"逐字节相同"当嵌入口径判据时，必须复刻对方的分批**；否则会把 1e-4 的浮点差异
误读成"口径抄错了"（本轮第一版就是这么误报的，已就地更正）。

## 五、切换与回滚（**推荐方案 A**）

### 方案 A：影子表 + 表名切换（推荐）

1. **建表 + 重建**（生产照旧，零停机）：跑 `rebuild-shadow.py` 把影子库填满；
   把它作为 `clause_vec_qwen` 挂进真库（或直接把影子库文件里的表并入主库）。
2. **校验**：行数 = 663,591；KNN 可查；抽样 64 条与 E4 冻结向量逐字节相同（本轮 T4 已做，切前再在同库上做一遍）。
3. **写入侧**：`vec_batch` **算一次嵌入、写两张表**（`clause_vec` + `clause_vec_qwen`）
   ⇒ 保留**一键回滚**能力。代价 = 多一份存储（663,591 × 2,048 B ≈ **1.27 GiB / 1.36 GB**）+ 写入略慢。
   ⚠ **不要**写成"写两次 = 嵌入两次"（那是白烧一倍 GPU）。
4. **查询侧**：前缀做在 `hybrid_engine.py:310` 调用点（**不是** `embed_query` 内部，见 §一 的坑）。
5. **回滚**：把 `VEC_TABLE` 常量改回 `clause_vec` + 重启。旧表**一行没动**。

### 方案 B：原地替换（**不推荐**）

`INSERT OR REPLACE INTO clause_vec` 覆盖。风险：覆盖到一半失败 ⇒ 表里一半新模型一半旧模型，
**没有任何读数能看出来**（正是本脚本 `ckpt_guard` 要防的那类坏法），且**没有回滚**。

- **两条首轮逃逸的教训**（值得通用化）：
  1. **"分开提交"只在"两次提交之间被强杀"时才出错** ⇒ 运行期测不出来，只能**静态钉住代码结构**。

     必须比**集合本身**（`set(ids) == 期望的非空 id 集合`）。

## 一、为什么做这个（不是新方向，是补上一刀的缺口）

`exp-13` 的 §五 诚实边界第一条自己写着：

> **只测向量路，不测 `fused@20`** —— 生产实际给用户的 20 条要走完整六路融合，**本批未跑**。

并且它因此**只肯**把 `D1` 判成"**向量路**净负"，不肯说"对产品净负"（第 12 轮复核 P1 `G-1` 正是
在这一点上打回了措辞）。本批就是把这个缺口补上：**同一批四条臂，改的是送进融合管线的查询串。**

## 二、口径（跑前写死，见同目录 [`stop-loss.json`](stop-loss.json)）

- **考卷** = `eval/recall-funnel/benchmark-v2.jsonl` 的 **headline 120 条**（与 `exp-8`/`exp-13` 同口径）。
- **模型** = 生产 `bge-small-zh-v1.5`（fastembed，CPU/ONNX），走 `src.core.retrieval.embedder.embed_query`。
- **融合** = **生产函数** `hybrid_engine.search_with_details(query, top_k=1000, rerank=False,
  boost_bookmarks=False, expand_chain=False)`（与 `funnel.py` 逐字同一条调用；**不重写第二套融合**）。
- **唯一变量** = 送进融合管线的查询串。索引 / 条文 / 向量表 / 生产代码**一个字不动**
  —— 改写只在实验脚本里 **monkeypatch** 两个钩子（`embedder.embed_query`、`hybrid_engine._fts_query`）。
- **臂 → 查询串映射（必须按通道分别施加，否则不是"生产会怎么用"）**：

| 臂 | 向量通道 | FTS 通道 | 精确/模态通道 |
|---|---|---|---|
| `A0_raw` | 原样 | 原样 | 原样 |
| `B1_bge_instruction` | `为这个句子生成表示以用于检索相关文章：` + 提问 | **原样** | 原样 |
| `C1_domain_prefix` | `检索相关法规与标准条文：` + 提问（**自造**） | **原样** | 原样 |
| `D1_prf_expand` | 扩展串 | **扩展串** | 原样 |

  ⚠ `B1/C1` 是**指令前缀**，喂 FTS 无意义（`exp-13` 已按此处理）；`D1` 的扩展词是**内容词**，
  两个通道都该用。`D1` 的扩展串**直接复用 `exp-13` 已冻结的 `per-query.jsonl` 的 `d1_query`**（不重算）。
- **主终点** = `fused@20`（**用户实际看到的前 20 条**）；副终点 = `fused@100` / `fused@1000` /
  `fused` 中位名次 / `by_subset(fused@20)`。
- **阈值（预注册，与 `exp-13` 同）**：**推广** = Δ ≥ **+8.18pt** 且 McNemar 双侧 p < 0.05；
  **观察** = 0 < Δ < +8.18pt；**放弃** = Δ ≤ 0。

## 四、判决（按预注册阈值机械算）

**⇒ 三条改写全部【不改】。** 逐条：

| 臂 | 落档 | 理由 |
|---|---|---|
| `B1_bge_instruction` | **观察**（+0.84pt） | 方向为正（1 进 0 出、中位名次 9→7），但**只有 1 条、p=1.0** ⇒ 与 `exp-13` 的 +4.17pt（向量路）一样**不够格** |
| `C1_domain_prefix` | **放弃**（Δ ≤ 0） | **−3.33pt、0 进 4 出** ⇒ 与 `exp-13`（向量路 −6.67pt）**同向且更差**，"自造领域前缀"在**用户可见层也**是负的 |
| `D1_prf_expand` | **放弃**（Δ ≤ 0） | **−0.83pt** ⇒ **在融合层也是负的**；这**补上了 `exp-13` 不敢下的那个断言**（当时只敢说"向量路净负"） |

**⇒ 三条可带走的结论**：

1. **`exp-13` 的主判决在"用户实际看到的前 20"上被独立确认** —— 不是向量路的假象。
   `D1`（PRF）那条尤其重要：`exp-13` 里它是唯一"@1000 涨、前 20 跌"的臂，
   本批在**完整融合**下复现了"前 20 跌"（−0.83pt、1 进 2 出）⇒ **它的坏处在产品层真实存在**。
2. **查询侧便宜改写这条路（在现役生产模型上）到本批为止可以收口了**：
   三条里最好的 `B1` 只有 +0.84pt（融合层）/ +4.17pt（向量路），都够不上门槛
   ⇒ **P2 想拿收益不能再指望"改查询串"**（在 `bge-small-zh-v1.5` 上）。
3. **本批真正的收获是一条结构事实而不是一个 Δ**：**用户的可见范围通常 ≈ 40 条**
   （115/120 题；**少数 5/120 题因触发模态通道达 1000** —— 见 §三 注 1 的 P1 更正）。
   ⇒ 它把 P2 的靶子从"排序"再往前推了一步：**先解决"池子太小"（候选深度/限量），
   再谈"池内排序"** —— 这与 `exp-6`（单纯放大上限没用）、`exp-8`（深度有大收益）**三者合起来**
   指向同一件事：**限量的方式**（怎么把深读候选**筛进** 40 条池子），而不是"再多加一路"或"再改一次查询"。

  聚合加 `--aggregate` 重算。⚠ 本批产物**不含时间戳字段** ⇒ 可做裸文件哈希比对。
- **★ 断点续跑是必需的（不是可选）**：单次融合调用里 **sqlite-vec 的 KNN 占 ~0.96 s**
  （暴力扫 663,634 行）⇒ 120 条 × 4 臂 ≈ **8 分钟**，**超过工具的后台任务 timeout 上限（600 s）**
  ⇒ 必须能续跑（本批实测 471 s 跑完，是被中断过一次后接续完成的）。

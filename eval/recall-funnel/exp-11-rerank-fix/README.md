## 一、这份实验回答什么

`docs/RETRIEVAL-LONG-RANGE-PLAN.md` **P0·0.7** 登记的是「`reranker.py::rerank` 只返回分数、不返回顺序」。
本轮**先探针实测**，发现它比登记写的**严重**：

* 唯一的调用方 `hybrid_engine._rerank_results` 把 `scores[i]` 当「**第 i 条候选**的分」用，
* 而 `rerank()` 返回的是**已按分数降序排过**的列表 ⇒ 调用方那句
  `sorted(range(n), key=lambda i: scores[i], reverse=True)` 作用在**降序输入**上，
  退化成 **恒等置换**。

⇒ **rerank 阶段从不改变顺序**（这一层是死的）；且 `debug["rerank_score"]` 把分数**贴到错的条款**上。

探针：`var/tmp/probe-rerank-order.py`（真实模型，不入库）——`rerank()` 返回 `[9.7385, -0.9695, -4.0088]`（降序），
`_rerank_results` 输出顺序 == 输入顺序。**本实验量的是"修好之后到底有没有收益"**，供「要不要把重排接进生产」拍板。

## 二、口径（照 `summarize.py`，不另立一套）

| 项 | 定义 |
|---|---|
| **主结果 120** | `bucket == "keep"` 且 `flags ∩ {gold_multi_def, gold_dup_text} == ∅` |
| **全量 171** | 全部（本批 `answer_out_of_corpus` 全 False） |

| **B 臂** | 把同一批 RRF 前 **24** 条交给**生产的** `he._rerank_results(q, res24, top_k=K)` 再取前 K 条 |

**为什么每问只做 1 次检索**：`perform_hybrid_search` 的真实做法就是「RRF 排序 → 取 `cap=rerank_n(24)` →

「`rerank=True, top_k=K` 的结果」，而 B 臂走的仍是**生产函数本身**（不是重写一份）。
本实验已用「修复前 B==A 171/171」把这条等价关系钉死。

## 四、判决（对照预注册 `stop_loss`）

| 档 | 门槛 | 本批实测 | 命中 |
|---|---|---|---|
| **可接生产** | Δ ≥ +5 条（≥ +4.2pt）**且** p < 0.05 | +2 条 / p=0.5 | ❌ |
| **观察** | Δ ≥ +3 条但 p ≥ 0.05，**或** 0 < Δ < +5 条 | **+2 条、p=0.5** | ✅ |
| 放弃 | Δ ≤ 0 | | ❌ |

⇒ **主终点落在「观察」档**，**不满足接生产门槛**。全量 171·K8 的 +5 条虽然够数，但 **p=0.0625 ≥ 0.05**，同样不够。

**两项决定**（已按业主授权"自己拍板并写明理由"执行）：

1. **0.7 必须修** —— 修之前这一层是死的（`n_reordered=0`），且 `debug["rerank_score"]` 把分数贴错条款。
   修复是"把这一层变成活的"的**必要前置**，与"接不接生产"是两件事。
2. **重排不接生产** —— 按上面判据，收益（+1.67pt、p=0.5）不足以覆盖 **1.1 s/问** 的代价，
   且远低于可接生产门槛。落地方式：把两处**隐式** `rerank=True` 的调用点
   （`src/core/api/server.py` 主问答路径、`src/core/vision/local_vision.py`）**显式写成 `rerank=False`**。
   这与修复前的**实际行为逐位等价**（空转 == 关闭）⇒ **不构成新的行为改动**，不需走必验流程。

## 五、连带发现（已登记，本批**未**修）

`hybrid_engine._protect_exception_clauses`（"例外条款保护"）**在真实调用形态下恒不生效**：
`_rerank_results` 传进来的 `kept` 长度**已经等于 `top_k`**，于是 append 的例外条款紧接着被
最后那句 `return kept[:top_k]` **原样切掉**。
实测 `var/tmp/probe-exception-protect.py`：`kept` 长度 == `top_k` ⇒ 例外**不保留**。

* 既有用例 `tests/test_reranker.py::test_rerank_exception_clause_kept` 用的是「`kept` 一开始就短于 `top_k`」
  的形态 —— **真实路径上不会出现** ⇒ 那条判据测的是个不存在的场景。
* **为什么本批不修**：修它 = 改一个**安全相关护栏**（例外条款 = P1 精度），属**行为改动**；
  而在本轮决定下（`rerank=False` 接生产）`_protect_exception_clauses` **根本不可达**
  （只在 `rerank=True` 时被调用）⇒ 不修**不产生新风险**。
* **但它是"接重排进生产"的前置条件**：一旦将来开启重排，例外条款会被重排挤掉 ⇒
  **必须先修它再谈接生产**。已写进 `_protect_exception_clauses` 的 docstring 与总纲 P0·0.7 段。

## 一、三项（来自本仓纪律，逐项有出处）

### ① 冻结批次：先打 tag，再**数出**提交条数写进任务书

- 动作：`git tag verify-freeze-<批次名>`，然后
  `git rev-list --count <base>..<frozen>` 把条数**写进复核任务书正文**。
- 为什么：不数就会"凭印象写 3 条"，而复核者按你给的条数核对区间——**它无从发现你数错了**。
- 出处：`AGENTS.md` §复核；`docs/CODE-REVIEW-CHECKLIST.md`。
- ⚠ 冻结区间里**不许夹带别人的提交**（`tools/gov-qa/**` 每 3 小时往 master 直接提交，会污染计数）。

### ② 派复核前，机械确认「没人在写这棵树」

- 动作：`git status --short` 看有无本批之外的改动；必要时看关键文件的 mtime。
- 为什么：**实测踩过两次**。最近一次（E1）：复核进行中我又往被复核目录提交 ⇒ 冻结事实失效。
- 出处：`AGENTS.md` §复核（2026-09-21 实测那条）。

### ③ 只跑被触碰面的最小证据 + 快照

- 动作：`pwsh -File scripts/run-gates.ps1 -Quick`（**一条命令、以退出码为准**），
  然后 `& .\scripts\snapshot-project.ps1 -Label <短名>`，收工 `git rev-parse <tag>^{commit}` 核。
- 为什么：全量留给 `-Full`；"我记得跑过哪几条"是本仓已修掉的老毛病。
- 出处：`AGENTS.md` §门禁 / §搬运与记录。

### ④（本仓补充）台账**边跑边写 + 断点续跑**

- 动作：任何"每条 >0.9 s × 几百条"或"总时长 >10 分钟"的实验，台账逐条 `append + fsync`，
  或像 `exp-17/rebuild-shadow.py` 那样"游标 + 同库 checkpoint（与数据同一次 commit）"。
- 为什么：本环境**一轮跑不完**长实验（进程无法跨轮存活）。
- 出处：`docs/CHANNEL-COVERAGE-PLAN.md`；`exp-17` README §四。

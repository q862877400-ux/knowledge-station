# E9 结论：**候选列当"筛子"没有可用收益** —— P2 诊断·第 1 刀

> **性质**：P2（排序）诊断，**只读、不改任何生产代码、不写库**。
> 脚本 `measure.py`（口径在 docstring 里**跑前写死**）｜原始读数 `result.json`。
> 库 = `%APPDATA%\KnowledgeStation\database\knowledge.db`（`mode=ro`，3.106 GB）。

## 一、结论先行

**没有任何一列能当筛子把正确条文提上来。连"样本内 oracle 上界"都不够一个量级。**

| 最好单列 `content_len_bucket` | 60.8% | **1.645×** | 2,628 |
| 最好两列 `content_len_bucket × effective_year` | 32.9% | **3.044×** | 1,420 |
| 其余 13 列里 8 列 | ≥91% | **≤1.10×** | ≈4,300（等于没动）|
| **随机基线**（随便扔 5% 的库）| 95% | 1.053× | 4,104 |

**而"有用"的门槛**（中位名次 4,322 要进到用户能看见的地方）：

| 目标 | 需要提速 |

| 进 `Top1000`（候选深度上限） | **4.32×** |

⇒ **最好两列 oracle（3.04×）连最低门槛（4.32×）都没到；单列最好（1.645×）只有它的 38%。**

## 三、三条读法

1. **"看起来有富集"的列，一落到"要保住 95% 金标"就没了。**
   `legal_hierarchy='部门规章'` 富集 **15.4×** 很漂亮 —— 但它**全库只有 674 行、只含 1 个金标条款**
   ⇒ 它能贡献的金标覆盖率上限是 **1/64 = 1.6%**，对"保住 95%"毫无帮助。
   `is_suspicious=1` 富集 1.35×、`type_confidence=0.5` 富集 1.35× 同理：
   它们本身就占全库 **44%**（291,905 行）—— 扔掉它们 = 扔掉 44% 的库，**却只保住 41% 的金标**，不划算。
   ⇒ **富集倍数 ≠ 可用信号；判据必须是"覆盖/筛选"的帕累托，不是单点富集。**
   ⚠ **顺带查清一件事（本批新实测）**：`is_suspicious=1` 与 `type_confidence=0.5` 在**全库上逐行同步**
   （`GROUP BY is_suspicious, type_confidence` 只有 6 组，`(1, 0.5)` = 291,905 行，`is_suspicious=1` 下**没有别的** `type_confidence` 值）
   ⇒ **这两列不是两个独立信号，是同一个信号**（`is_suspicious` 是 `type_confidence` 的派生标志）。
   所以上表里它们读数相同不是巧合；**别把它们当两票**。

2. **有真分辨力的三列，恰好都是"不能当产品筛子"的列。**
   排前面的 `content_len_bucket`（条款长度）/ `effective_year`（生效年份）/ `clause_number_shape`（条款号段数）
   —— 这三列**一个都不能拿去筛用户的问题**：不能说"只检索 40–99 字的条款"、"只检索 2003 年生效的"。
   即使强行用，**最好两列也只有 3.04×**，离最低门槛 4.32× 还差一截。

3. **数量级不对，不是"再调调"能补的。**
   目标是 **216×（Top20）/ 43×（Top100）**；现有手段是 **1.6×（单列）/ 3.0×（两列）**。
   差的是**一到两个数量级** ⇒ 这不是"排序权重调参"能解决的事，**P2 的瓶颈不在这 14 列上**。

---

## 四、判定（P2 诊断·第 1 刀 收口）

**决定：这 14 列都不改。不为它们改排序、不为它们改融合权重、不为它们加过滤。**

理由：
1. **连样本内 oracle 上界都够不到最低门槛**（3.04× < 4.32×）—— 而 oracle 是**拿答案拟合出来的**，
   真实可用方案只会更差。**"连作弊都不够"是最强的一种否定。**
2. 唯一"有分辨力"的几列是**类型/时效属性**，把它们当筛子用 = **发明一条产品语义**
   （"只搜短条款"），违反宪法原则 VI「只做缝合不做发明」。
3. 与既有拍板一致：`NEXT-DEV-PLAN §二乙`（2026-10-09）已定"**拿到相关性信号之前不改排序**"，
   本实验把这个"没有信号"的判断**从'有没有可用列'推进到'这些列当筛子也没有收益'**。

## 五、诚实边界（必须一起读）

| 项 | 说明 |
|---|---|
| **`r95` 是样本内 oracle 上界** | 取值排序是拿**同一份 64 个金标**拟合的 ⇒ 不是能上线的方案。**正因为是上界，"不够"才具有决定性。** |
| **本实验量的是"硬筛子"** | 软先验（按列加权打分）理论上更平滑，但它能用的信息**完全来自同一列** —— 一列在"保住 95% 金标"上只解释到 60.8% 的库，软先验不可能好一个量级。⚠ 要真量软先验必须改融合权重，而那已被拍板冻结（`NEXT-DEV-PLAN §二乙`）。 |
| **金标只有 64 个条款** | 120 条提问落在 64 个不同条款上。已同时报"按提问加权"的副口径；两口径在 13/14 列上一致，`legal_hierarchy` 从 0.734 变 0.911（**加权后更差**）⇒ **不影响结论方向**。 |
| **64 个金标 = 抽样，不是全部** | 这是 headline 考卷的 64 个金标条款，**不是"所有正确条文"**。 |
| **已排除文档身份列** | `standard_no` / `doc_id` / `standard_name` **不测** —— 那是泄漏（知道答案在哪篇才筛得动）。 |
| **未做** | ❌ 未测"3 列以上联合"（2 列已 3.04×，加列只会更接近 oracle，且会放大过拟合）；❌ 未测软先验；❌ 未测"与 FTS 交叉"的**池内**区分度（那属另一条线，已被 exp-6/exp-7 量过：放大上限 +1.67pt、融合算子 +0.83pt）。 |
| **跑在只读活库上** | 库会继续长大（本批 663,634 行）；重跑数字会变，**结论方向不受影响**（差的是数量级）。 |

## 六、这条结论**改了**什么

| 之前 | 现在 |
|---|---|
| 「P2 第 0 刀：库里**没有现成的相关性列**」 | **加强为**：「这 14 个属性列**当筛子也没有收益**（最好 oracle 3.04× vs 最低门槛 4.32×）」 |
| 「P2 的诊断清单：通道权重 → RRF 常数 → BM25 参数 → 片段长度 → 同号条款次序」 | 其中"**片段长度**"这一项现在有数了：长度**有**分辨力（2.05× 富集）但**不可用**（不能当筛子）；"**同号条款次序**"与 `clause_number_shape` 相关（1.45× 富集，同样不可用） |
| 下一步该往哪走 | **不在"给 A/D/E 找排序键"这条线上** —— 那条线的库里没有信号。真正的大头仍是 `exp-8` 量出的**候选深度 +21.7pt**，而它已被 `exp-6` 证明"单纯放大上限没用" ⇒ **需要的是"把排得远的捞到前面"的手段（查询改写 / 语料内统计关系）**，不是列先验。 |

### ★ 留言板「广度 + 深度」两段打法（2026-10-07 定型）

1. **广度**：`people-liuyan-df` 不带 fid 跑时间流，多批慢跑（每窗约 30 条、冷却 ≥1h）
   ⇒ 采集过程中**每条记录自然带出 `extra.fid`**（该版块号）；
2. **深度**：`recon/build-fid-map.py` 把已采数据聚成「省市 → fid」表，
   `people-liuyan-fid` 按表逐个版块采满（**轮转 + 配额均分**，见下）⇒ 想深挖哪个省就深挖哪个省。
3. ★★ **按省直达（2026-10-07 重大发现）**：留言板**省级版块按行政区划顺序两两连续编号**——
   `省委书记 fid = 539 + 2×序号`、`省长/市长/主席 fid = 书记 + 1`：
   ```
   北京 539/540  天津 541/542  河北 543/544  山西 545/546  内蒙古 547/548
   辽宁 549/550  吉林 551/552  黑龙江 553/554  上海 555/556  江苏 557/558
   浙江 559/560  安徽 561/562  福建 563/564  江西 565/566  山东 567/568
   河南 569/570 …（至新疆 599/600）
   ```
   **实扫确认 16 省**（`recon/liuyan-province-fid-scan.json`），其余按规律推算并标
   `confirmed=false`（`recon/liuyan-province-fids.json`，**推算项用前需实扫**）。
   ⇒ 新适配器 **`people-liuyan-prov`**：按该表**逐省采**（每省 2 版块、每版块独立游标、

   ⚠ **各省存量差异很大（2026-10-07 实测，轮转 12 轮后）**：东部/中部省可达 12+ 条，
   **西部省份（黔 4 / 滇 4 / 新 5 / 藏 6 / 甘 7 / 青海 7）明显偏少**——不是没轮到，

### ⚠ people-liuyan 的四个未决问题（2026-10-07 实测记录）

1. **403 限流（阈值很敏感）**：请求过密返回 **403 + 2.3KB HTML 拦截页**。
   **实测预算（2026-10-07 五轮对照，含延时批）**：每个冷却窗约 **40-50 次调用**
   （列表+详情合计），窗后冷却 **≥1 小时**（25/70 分钟两档都试过：70 分钟后
   能过 40 次然后再次 403）⇒ **每小时约能收 30-35 条**。
   df 行数据**不带答复正文**（只有 `lastAnswerTime`）⇒ 每条 1 次详情省不掉。
   **运行配方（最终版）**：`PAUSE ≥ 2.5s`、**单批 ≤35 条**、批间歇 ≥1 小时；
   **上量靠过夜多批**（如脚本循环：采 35 条 → 睡 1 小时 → 重复），
   别在交互式会话里硬刷。403 就停，按 id 去重天然续采。
   ★ **必须带游标续采**（2026-10-07 加）：时间流按时间**倒序**，若每轮从流头跑，
   去重会把新数据全挡掉（实测一轮只新增 1 条）。df 适配器现把 `lastItem` 持久化到
   `data/.people-liuyan-df.cursor`，每翻一页即写回 ⇒ **每轮配额都花在新数据上**。
   排查提示：日志出现「从游标续采：…」即生效；`lastItem` 数值**递减**属正常（倒序流）。
   ⚠ 性价比对照：广东 hdjlpt 模式 20 分钟采了 1.18 万条（无 403）——
   **省线优先于 df 走量**，df 见缝插针。
2. **翻页深度存疑**：bw 流正式采集扫到 54 条后光标耗尽（`lastItem` 空 / `hasData` 异常值）。
   可能是"单次查询流就这么多"，也可能是**轻度限流把第 3 页打成了空页**——当时分不清
   （`recon/liuyan-sitewide-cursor.txt` 只有 403 复现，无干净对照）。
   **别把 30 条当平台总量**——平台留言总量以百万计。
3. **部委按 fid 采不到答复**：各部委版块页多是"提交入口"（生态环境部 fid=5062 全部 22 条
   皆待回复）⇒ **采全站流（不带 fid）、按行内 `forumName` / `extra.pForumNames` 归属**。
4. **✅ 已解决（2026-10-07）：答复字段 = `dataType==4`；`dataType==9` 是网友跟帖**
   **判定证据**（`recon/df-datatype-diagnose.out.txt`，两个流实测 contentList）：
   ```
   [0] dataType=1  留言本体
   [1] dataType=9  网友跟帖  （13~95 字，口语：「应予以取消。取消后用于其他用途」）
   [2] dataType=4  官方答复  （138~236 字，公文：「您好！……已收悉……经与……核实……」）
   ```
   **已修**：`_liuyan_common.harvest_liuyan` 改收 `dataType==4`；
   `dataType==9` 存 `extra.netizen_comments` 并标 `extra.answer_kind`，**两类不混用**。
   **修复效果实证**：重采部委流 37 条 → **A 类考卷 11 条**（修前那 30 条网友跟帖全是 C 类，
   因为跟帖不点名依据、只有官方答复才点）；可定位率 30/37。
   错数据留证：`recon/bw-suspect-30records.jsonl`（30 条）、`recon/df-suspect-5records.jsonl`（5 条）。
   ⚠ 教训：**字段语义必须逐流验证，不能因为"接口同构"就照搬**；错数据是我自己审计发现的
   （发现时已在语料里躺了 4 轮），并由此引出对**全源**的 answer 字段审计（见 §一·补）。
   💡 **副产品**：网友跟帖是**真人语言语料**（真实群众的建议/反问/诉苦），已按
   `extra.netizen_comments` + `answer_kind` 单独标注，供「真人问题/口语表达」用途，
   **绝不混进官方答复字段**。

#### ★ 吉林扩厅局的**正解：扫 `groupId`**（2026-10-08）

第二批用「**猜域名**」探吉林其余厅局 ⇒ 大量 `ConnectError`、多数站首页没有 IGI 指纹。
**换的做法**：吉林 IGI 是 `haiyun.jl.gov.cn/IGI` + `(siteId=117, appId=96)` **全省固定**，
**只有 `groupId` 区分厅局** ⇒ 直接**扫 groupId 一个整数维度**，**不依赖任何厅局域名**。

扫描器 `recon/jl-groupid-roster.py`（列表接口回 `datas.pageInfo.totalResults`
⇒ **一个 groupId 一次请求**就能拿到该厅信件总数，不必翻页）。

**结果（`recon/jl-groupid-roster.txt`）：`groupId` 158~195 + 255，共 38 个厅局 / 3,497 封信。**

## 三、★ 怎么找 `channelid`（这是 WAS5 路线唯一的难点）

生态环境部的接口是 `/was5/web/search`，**难点不是接口，是那个 `channelid`**。方法：

1. 打开该站的**互动/问答栏目页**（如 `https://www.mee.gov.cn/hdjl/`）；
2. **把页面整个抓下来，找 `channelid` 这个词** —— 它通常**内联在页面的 `<script>` 里**，
   和一段叫 `interactionParams` / `leaveWordParams` 的参数对象放在一起：
   ```js
   var leaveWordParams = { channelid: 223015, keyword: '', orderby: '-DOCRELTIME',
                           perpage: 10, page: 1 }
   ```
3. 也可以先搜 **`ajax`** 这个词 —— 列表是哪个函数拉的、参数叫什么，都在同一段里。
   （生态环境部那段里就是 `.ajaxCjwtList` / `.ajaxCjwtPage`。）

**一条命令挖出这段**（把 URL 换成目标站）：
```powershell
.venv\Scripts\python.exe -c "import re,httpx;t=httpx.get('https://目标站/互动栏目/').text;b=re.findall(r'<script[^>]*>(.*?)</script>',t,re.S|re.I);[print(x[:800]) for x in b if 'channelid' in x or 'ajax' in x.lower()]"
```

⚠ **不带 `channelid` 调用时，连本站也返回 711 字节空页** ⇒
**不许**据"返回空页"判定某个站没有 WAS5（我犯过这个错，见 README 坑 3）。

## 四、两种问答站 —— **只有一种能当考卷**

| 型 | 特征 | 能不能当考卷 |
|---|---|---|
| **列表型** | 一条条"问题 + 官方答复"的列表，可翻页/分页 | ✅ **能**（答复里常点名依据文件）|
| **聊天机器人型** | 页面是**对话气泡**（Vue/React 单页），有 `robot.js` 之类；问答由模型现生成 | ❌ **不能** —— 没有固定的"官方答复"可依，**没有 gold** |

**怎么分辨**：抓下来看有没有 `v-for` + `fd-user-msg` / `fd-sys-msg` 这类气泡模板，
或者有没有 `robot.js`。市监的 `gjjly` 就是这一型。

## 五、省市站该从哪下手（**给接手的人的建议顺序**）

1. **先照搬同一套中间件**：在省/市的**生态环境厅**、**应急管理厅**站上试
   `GET https://<域名>/was5/web/search`。**省级站与部级站常是同一家做的。**
2. **按栏目名找入口**，常见叫法：`互动交流` / `公众参与` / `常见问题` / `留言选登` /
   `咨询投诉` / `在线咨询` / `政策咨询` / `回应关切`。
3. **找 `channelid`**：按上面第三节的办法。
4. **找不到接口就走真浏览器**（业主已授权）：`browser_*` 工具打开页面，
   看网络请求里那条 XHR 的 URL 与参数 —— 那是**最快**的找接口办法。
5. **拿下一个就先跑一遍 `measure-locate-rate.py`**，看这个站的**在库率**。
   **在库率低的站，爬再多也进不了考卷**（只会进补料清单）。

### 9. ★★★ 本轮最高价值发现：`harvest.py::_load_done` 用 `splitlines()` ⇒ **一个 U+2029 就把整站永久读崩**

**症状**：`hi-zcwd` 跑到第 5 块时 `rc=1`，报
`json.decoder.JSONDecodeError: Unterminated string starting at: line 1 column 584 (char 583)`，
**栈顶在 `harvest.py:56 _load_done`** —— 也就是说**一条数据都还没采，光是读已落盘文件就崩**。
诡异的是：用 `for line in open(...)` 逐行校验，**坏行 0**。

**根因**（已复现、已定量）：

```python
# 旧：harvest.py:52
for line in path.read_text(encoding="utf-8").splitlines():
```
`str.splitlines()` 的换行定义**不止 `\n`** —— 它把 **U+2028 (LINE SEPARATOR)、
U+2029 (PARAGRAPH SEPARATOR)、U+0085 (NEL)** 也算换行；
而 `json.dumps(..., ensure_ascii=False)` **不转义** 这三个字符。
⇒ 答复正文里只要出现 **1 个** U+2028/U+2029/U+0085，那一行就被**从中间切开**，
`json.loads` 抛 `Unterminated string` ⇒ **`_load_done` 崩 ⇒ 整站 rc=1 ⇒ 之后再也采不进一条**。

**实测证据**（`hi-zcwd` 文件里 U+2029 恰好出现 **1** 次）：
`split("\n")` 得 2205 行（正确），`splitlines()` 得 2206 行（多切一刀），
切点第 2069 行末尾 = `…及饮`，报错 `line 1 column 584` **与 traceback 完全一致**。

**★ 全库扫描：已坏 6 个文件（不是只有我这一个）**

| 文件 | 危险字符 | 后果 |
|---|---|---|
| `hi-zcwd`（海南政策问答）| U+2029 ×1 | 已坏 |
| **`zj-hangzhou`**（杭州民呼我为）| **U+2028 ×8** | **已坏（另一个对话的线）** |
| **`zj-huzhou`**（湖州）| U+2029 ×1 | **已坏** |
| **`zj-lishui`**（丽水）| U+2028 ×3 | **已坏** |
| **`zj-mhww`**（浙江省统一平台）| **U+2028 ×9** | **已坏** |
| **`zj-ningbo`**（宁波）| U+2028 ×5 | **已坏** |

⇒ 这解释了为什么**浙江民呼我为系 5 个站的 mtime 停在 4~7 小时前**（248/329/413/391/608 分钟）：
不是没人跑，是**跑了就崩、一条进不来**。⚠ 该系是**另一个对话**的线，我未动它的数据文件。

**修法**（`harvest.py`，共享文件，**只改 `_load_done` 一个函数**）：
`splitlines()` → `split("\n")`，并把 `json.loads` 包 `try/except` **跳过坏行**
（坏行不该让整站停摆）。修后实测：**6 个文件全部正常读入**
（hi-zcwd 2205 / zj-hangzhou 3000 / zj-huzhou 2080 / zj-lishui 350 / zj-mhww 1000 / zj-ningbo 3000）。

⚠ **影响另一个对话**：此改动会让它那 5 个浙江站**从「跑就崩」恢复为「能续采」**；
同时 `_load_done` 对坏行由「抛异常」改为「跳过」——若将来真出现坏行，
行为是**静默跳过**而非报错，需知悉。

### 4. ★ 新能力：`igi-chunked.py --resume-margin N`（跨轮页续跑）

**为什么必须做**：本轮实测，**每轮重跑都会把已落盘的页重列一遍**——
`shenyang-123` 白翻 40 页（146 s）、`nmg-66` 白翻 160 页（233 s）、`gz-70` 白翻 160 页（346 s），

（重列**不是**为了抓新增：本轮所有重列窗口都是 0 新增，说明列表在本轮时间尺度内是稳定的。）

**做法**：按 `(key, siteId)` 记「已翻完的最大页号」到 `recon/.igi-page-progress.json`
（临时文件 + `os.replace`，避免被杀时留半截 JSON）；下轮从 `已翻页 + 1 - N` 续，
**窗口按 `--page-chunk` 对齐**。只在窗口**真翻完**（`harvest_igi` 正常返回）才记进度，
异常/失败不记 —— 免得下次跳过没翻的页。

**实测证据**（受控两遍，`nanjing_igi --only 13 --max-pages 3 --page-chunk 1 --resume-margin 1`）：

```
pass1: [nanjing-igi-13] 第 1 页：1 条 … 第 2 页 … 第 3 页
       进度文件 = {"nanjing-igi-13": 3}
pass2: [1/1] siteId=13 跨轮续跑：上轮已翻到第 3 页 ⇒ 从第 3 页起（重叠 1 页）
       只请求了第 3 页
```

**默认关闭（`0` = 旧行为）** ⇒ 另一个对话的 `recon/igi-resume.sh` **一行不改、行为不变**。

**⚠ 已知代价（必须知道再用）**：若上游把新信件**插在列表头部**，页号整体下移，
续跑会**漏掉它们**（只有整站重列才抓得到）⇒ **要「新信不漏」就不传本参数**。
本轮的取舍是：这是**历史回填**项目，先把存量拉满；将来需要「新信不漏」时整站重列一轮即可。

**为什么必须做**：同一实例 ⇒ 接了就**把同一批信件记两遍**（`(source,id)` 不同 ⇒ 下游去重挡不住）。

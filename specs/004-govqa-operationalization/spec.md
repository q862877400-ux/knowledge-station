# Feature Specification: 政务问答采集系统的可运维化

**Feature Branch**: `004-govqa-operationalization`

**Created**: 2026-10-10

**Status**: Draft

**Input**: User description: "彻底实现这个全面的可运维，然后可使用，然后深度和广度全部都做到最好，做到不能更好为止"

---

## 背景：为什么需要这个特性

系统当前已积累 **359,823 条**政务问答数据、**331 个采集适配器**、覆盖 **32 个省级行政区**。
但用户指出两个关键问题：

1. **「通道打通是为了以后它有更新的时候，我一个轮询就可以获取到最新的」** ——
   这条**核心目的从未被验证过**。331 个适配器目前只能「跑一次拿全量」，
   没有任何一条链路被证明可以「只取增量」。
2. **「存量我是要拿来做数据分析」** —— 但数据深度极不均衡
   （云南 84 条 vs 重庆 11,269 条，差 134 倍），且 14 个省 <3,000 条，
   拿去做「全国分析」时这些省的结论没有统计意义。

**换句话说：系统现在是一台「能一次性扒全量的机器」，还不是「可长期运营的数据服务」。**

---

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 增量轮询：一条命令拿到最新数据 (Priority: P1)

用户希望「每隔一段时间跑一次，只把新增的问答拿下来」，而不是每次重扒全量。
现在必须做到：**系统能记住每个通道上次采到哪里，下次只取更新的部分。**

**Why this priority**: 这是用户明确说出的**唯一目的**（「通道打通是为了以后轮询拿最新」）。
没有这个能力，331 个适配器只是「一次性脚本」，价值大幅缩水。
**这一条不做，整个项目就没有达到用户的原始意图。**

**Independent Test**: 挑 3 个通道，各跑两次增量轮询 ——
第一次跑完后记录水位，人为在源站找到新条目，再跑第二次，
**验证第二次只落盘了新增条目，且水位前移**。

**Acceptance Scenarios**:

1. **Given** 某通道已采完存量并记录了水位，
   **When** 用户执行一次轮询命令，
   **Then** 系统只请求水位之后的内容，落盘条数 ≈ 该时段新增量，且总条数增加但不重复
2. **Given** 某通道连续两次轮询之间源站无更新，
   **When** 执行第二次轮询，
   **Then** 落盘 0 条，且**不产生任何重复记录**
3. **Given** 某通道的轮询中途失败，
   **When** 再次执行，
   **Then** 从上次成功的水位继续，**不丢数据也不重复**
4. **Given** 全部通道需要轮询一遍，
   **When** 用户执行一条总命令，
   **Then** 产出「每个通道新增多少条」的汇总报告

---

### User Story 2 - 覆盖完整性：每个行政区都有来源且深度达标 (Priority: P2)

用户要求「所有省、所有市」。现在省级面全但深度差 134 倍，市级从未系统盘点过。

**Why this priority**: 数据要做「全国分析」，覆盖不均衡会直接污染结论。
但比 P1 次一级 —— 因为数据已经能用了，只是不够好。

**Independent Test**: 产出一张「覆盖销号表」，
逐个列出每个省级行政区 / 地级行政区的**来源数、落盘量、是否达标**，
人工抽验若干行与实际数据一致。

**Acceptance Scenarios**:

1. **Given** 全国 31 个省级行政区 + 333 个地级行政区，
   **When** 查看覆盖销号表，
   **Then** 每个单位都有明确的「有来源 / 无来源 / 深度不足」状态
2. **Given** 某个省级行政区落盘量低于设定下限，
   **When** 查看销号表，
   **Then** 它被标红并给出「还差多少」
3. **Given** 用户想补某个薄弱地区，
   **When** 查看销号表，
   **Then** 能直接看到该地区**还没有来源的渠道清单**（而不是只知道"数据少"）

---

### User Story 3 - 数据可用性：标签可信、字段完整 (Priority: P2)

用户要求「把内容的标签分好」。现在标签覆盖 100%，但**准确率是模型自评的 78.9%**，
且存在「question 为空」这类静默缺陷。

**Why this priority**: 标签不可信 ⇒ 按类型做的分析全错。与 US2 同级。

**Independent Test**: 人工抽检 200 条记录（覆盖各标签、各来源），
核对标签是否正确、问题与答复是否非空，算出**真实准确率**。

**Acceptance Scenarios**:

1. **Given** 全库记录，**When** 跑字段体检，
   **Then** 能列出每个字段的非空率，且**没有「整列全空」的静默缺陷**
2. **Given** 人工抽检 200 条，
   **When** 核对标签，
   **Then** 真实准确率 ≥ 设定阈值（否则需改分类器或改标注体系）
3. **Given** 某条记录的 `question` 为空但 `answer` 非空，
   **When** 跑体检，
   **Then** 该异常被单独列出并可定位到来源

---

### User Story 4 - 自愈与可观测：出问题能自己发现 (Priority: P3)

用户要求「可运维」。可运维的核心不是「功能多」，而是**出问题能被发现、能定位**。

**Why this priority**: 前三项是「数据本身好不好」，这项是「系统能不能长期跑」。
必要但不紧急 —— 因为已经有基础（闸门 + 追踪日志）。

**Independent Test**: 人为制造 3 类故障（删一个数据文件、塞一条重复 id、注册一个空适配器），
验证体检工具能在**一次运行内全部检出**并给出可定位的信息。

**Acceptance Scenarios**:

1. **Given** 系统处于健康状态，**When** 跑一次总体检，
   **Then** 全部判据绿灯，且耗时在可接受范围（秒级，不拖垮轮询）
2. **Given** 数据被意外删除/损坏，**When** 跑体检，
   **Then** 立即报红并指出**哪个文件**
3. **Given** 某适配器连续失败，**When** 跑轮询，
   **Then** 该通道被标记为「故障」但不影响其他通道继续
4. **Given** 用户想知道「现在能不能用」，**When** 跑一条命令，
   **Then** 得到一句话结论（可用 / 不可用 + 原因）

---

### Edge Cases

- **源站改版**：适配器依赖的页面结构变化 ⇒ 采集返回 0 条。系统应**区分「真的没数据」和「解析失败」**，后者要报警而不是静默成功。
- **并发写**：多个采集进程同时写同一文件 ⇒ 重复 id。系统应保证**同一个站同时只有一路在采**。
- **中途中断**：进程被杀 ⇒ 该轮已采数据丢失。系统应做到**中断只损失当前块**。
- **水位丢失**：水位文件损坏 ⇒ 必须能**安全地退化为全量重采**，而不是漏数据。
- **极慢的源**：单站需数小时 ⇒ 必须**分块**，否则永远跑不完。
- **空壳源**：源站返回大量结果但答复正文为空（如某些 IGI 站）⇒ 应被识别并剔除，不污染语料。

## Requirements *(mandatory)*

### Functional Requirements

**增量轮询（US1）**

- **FR-001**: 系统 MUST 为每个通道维护一个「水位」（上次采到的时间点或游标）
- **FR-002**: 系统 MUST 支持「只取水位之后的内容」的增量采集模式
- **FR-003**: 系统 MUST 在增量采集后原子更新水位（失败不得前移水位）
- **FR-004**: 系统 MUST 支持「全部通道轮询一遍」的单条命令，并输出每通道新增量
- **FR-005**: 系统 MUST 保证增量模式下的**幂等性** —— 同一条数据重复采集不得产生重复记录
- **FR-006**: 系统 MUST 在水位缺失/损坏时安全退化为全量采集，不得漏数据

**覆盖完整性（US2）**

- **FR-007**: 系统 MUST 产出覆盖销号表，逐条列出每个省级行政区的来源数与落盘量
- **FR-008**: 系统 MUST 产出覆盖销号表，逐条列出每个地级行政区的来源数与落盘量
- **FR-009**: 销号表 MUST 标注每个单位的达标状态与缺口
- **FR-010**: 系统 MUST 能列出某个地区**尚未建立来源的渠道**（而不只是"数据少"）
- **FR-011**: 系统 MUST 支持按「缺口大小」排序，指导补采优先级

**数据可用性（US3）**

- **FR-012**: 系统 MUST 为每条记录提供规范化的类型标签
- **FR-013**: 标签体系 MUST 是**封闭集合**，且每个标签有明确定义
- **FR-014**: 系统 MUST 能报告标签的真实准确率（基于人工抽检，非模型自评）
- **FR-015**: 系统 MUST 能检出「关键字段为空」的记录并定位到来源
- **FR-016**: 系统 MUST 保留原始标签与规范化标签的对应关系，支持回溯

**自愈与可观测（US4）**

- **FR-017**: 系统 MUST 能在一次运行内检出：数据倒退、重复 id、空适配器、标签覆盖不足
- **FR-018**: 体检 MUST 用**纯 ASCII 机器可读格式**输出判定结果（避免本地化文本做接口）
- **FR-019**: 系统 MUST 记录每次体检的执行轨迹（时间、解析值、结论），供事后定位
- **FR-020**: 系统 MUST 区分「采到 0 条」与「采集失败」
- **FR-021**: 系统 MUST 支持单通道故障隔离 —— 一个通道失败不影响其他通道

### Key Entities

- **通道（Channel）**：一个可采集的数据来源。属性：唯一标识、名称、层级（省/市/部委/人大/第三方）、入口地址、自报总量、上次落盘量、**水位**、健康状态。
- **水位（Watermark）**：某通道上次成功采集到的位置。属性：通道标识、位置值（时间戳/游标/页码）、更新时间、上次成功采集的条数。
- **记录（Record）**：一条问答。属性：来源、唯一标识、问题、答复、提问时间、答复时间、部门、渠道、原始类型标签、规范化类型标签、标签来源。
- **覆盖单元（Coverage Unit）**：一个行政区或机构。属性：名称、层级、下属通道列表、落盘总量、达标状态、缺口、**未覆盖的渠道清单**。
- **体检报告（Health Report）**：一次自检的结果。属性：时间、各判据状态、异常清单、耗时。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 用户执行一条命令，即可在 **10 分钟内**完成全部通道的增量轮询，并得到「各通道新增多少条」的报告
- **SC-002**: 连续两次轮询之间源站无更新时，第二次轮询落盘 **0 条新增且 0 条重复**
- **SC-003**: 增量轮询中断后重跑，**不丢数据、不产生重复**
- **SC-004**: 全国 **31 个省级行政区 + 333 个地级行政区**，每一个都能在销号表里查到「来源数 + 落盘量 + 达标状态」
- **SC-005**: 落盘量低于下限的行政区，**100% 被标红并给出缺口数值**
- **SC-006**: 任意薄弱地区，用户能**直接查到它尚未覆盖的渠道清单**，无需人工排查
- **SC-007**: 全库标签覆盖率 **100%**，且人工抽检 200 条的真实准确率 **≥ 80%**
- **SC-008**: 全库**不存在**「问题与答复同时为空」的记录；存在「问题为空」的记录时能被单独列出并定位到来源
- **SC-009**: 人为制造的数据故障（删除文件 / 重复 id / 空适配器），体检**一次运行内全部检出**
- **SC-010**: 体检本身的耗时 **≤ 60 秒**（不能拖垮轮询）
- **SC-011**: 用户执行一条命令，即可得到「系统当前可用/不可用 + 原因」的一句话结论
- **SC-012**: 单通道采集失败时，**其他通道的轮询不受影响**（故障隔离）

## Assumptions

- **目标用户是数据使用者本人**：不做多租户、不做权限体系、不做 Web 界面。
  交付形态是**命令行工具 + 文件产物**，因为用户的工作方式是「我要拿数据做分析」。
- **源站不会提供 API**：绝大多数政务站是 HTML 抓取，因此「水位」多数是**页码或时间戳**，
  而非增量 API 的游标。这决定了增量采集必然依赖「翻到已知位置为止」的策略。
- **数据以本地文件为唯一事实来源**：`data/*.jsonl` 是权威存储，git 是备份与审计手段。
  不引入数据库 —— 当前规模（36 万条）用文件完全够用，引入数据库会增加运维负担。
- **增量轮询按「天」为粒度即可**：政务问答不是实时数据，日更已足够。
  因此水位精度到「天」即可，不需要秒级。
- **「达标」的定义需要用户确认下限**：本 spec 暂定省级 ≥3,000 条、
  地级 ≥500 条为达标线，这两个数字是**假设**，需要用户确认或调整。
- **标签体系沿用现有 9 分类**（咨询/建议/投诉/举报/求助/表扬/申诉/反馈问题/其他），
  不重新设计 —— 因为已有 11.5 万条真实站方标签作为锚点。
- **两个 agent 并行工作的现状保持不变**：本特性不解决「多 agent 协作」问题，
  但所有工具必须**对并发安全**（不产生重复 id、不互相覆盖）。

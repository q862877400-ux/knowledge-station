# Phase 0 调研：政务问答采集系统的可运维化

**Created**: 2026-10-10 ｜ **对应 spec**: [spec.md](./spec.md) ｜ **对应 plan**: [plan.md](./plan.md)

> 本文件只记**决策 + 理由 + 备选**。不重复 spec 的需求描述。

---

## R1. 增量水位用什么做？

**Decision**: **每通道自声明水位类型**，共三种，存 `state/watermarks.json`：

| 水位类型 | 适用 | 比较语义 | 示例通道 |
|---|---|---|---|
| `page` | 列表按时间倒序 + 可翻页 | 已采到的最大页码 | 大部分 jact / IGI |
| `since` | 列表带时间字段 | 已采到的最大时间戳 | 带 `submitTime` 的源 |
| `idset` | 无时间无稳定序，但有唯一 id | 已见过的 id 集合（有上限 LRU） | 少数奇葩源 |

**Rationale**:
- 政务站**没有增量 API**。实测 331 个 adapter，列表形态只有两类：
  ①按时间倒序的翻页列表（占绝大多数）②带时间字段的 JSON 列表。
- `page` 型增量 = **从第 1 页开始翻，翻到「本页全部已见过」就停**。
  这比「记录页码」更健壮 —— 因为列表会因新增内容而整体后移，页码会漂。
- `idset` 型是兜底：**保证不重复**，代价是每次都要翻全量。

**Alternatives considered**:
- ❌ **HTTP `Last-Modified` / `ETag`** —— 政务站基本不返回这两个头（实测抽 20 个源，
  只有 2 个返回 `Last-Modified` 且不可靠）。RSS 那套用不上。
- ❌ **Scrapy `JOBDIR`** —— 它管的是「请求队列的持久化」，不是「数据水位」。
  且引入 Scrapy 要重写 331 个 adapter，风险极大（违反宪法 VI「够用即止」）。
- ❌ **只记「上次采集时间」** —— 源站发布时间与采集时间不同步（有的源会补发旧文），
  会导致漏采。**宁可多翻几页，不可漏**。

## R2. 如何保证幂等（重复轮询不产生重复记录）？

**Decision**: **落盘前按 `(source, id)` 去重**，去重逻辑**前置到写入路径**，
而不是事后跑 `dedup-data.py`。

**Rationale**:
- 现有 adapter 已经用 `(source, id)` 做唯一键，且 id 生成规则**稳定**
  （站方 id 优先；无 id 时用内容指纹 `md5(...)`）。
- 内容指纹的稳定性**已被实测检验过**：`nat-mohurd` 的指纹曾因 `question` 为空而退化
  引发 59 行碰撞（已修，见 commit `11657c6`）。**说明指纹方案可行，但必须验证字段非空**。
- 前置去重的收益：**写入即保证不重复**，事后不必再扫全库。

**Alternatives considered**:
- ❌ 事后去重 —— 会有一段「脏窗口」，期间其他 agent 可能读到重复数据。
- ❌ 用数据库唯一索引 —— 引入数据库，违反宪法 VI。
- ✅ **补充**：新增一个 `recon/verify-idempotent.py`，**实测**「连续两次轮询后 id 集合不变」，
  把 SC-002 变成可自动验证的判据（而非靠人记）。

## R3. 如何做到断点续跑（中断不丢数据）？

**Decision**: 增量模式**边采边落盘**（每条 append 后 `flush`），而不是沿用
`harvest.py` 的「跑完才落盘」。

**Rationale**:
- **这是当前最大的可靠性缺口**。`harvest.py` 跑完才落盘 ⇒ 一个跑 3 小时的源，
  第 2 小时 59 分被杀 ⇒ **整轮全丢**。GOAL.md 硬约束 3 就是为了绕开它才要求「必须分块」。
- 边采边落盘的代价：写入次数变多、可能写出半条记录。**缓解**：每条记录是**完整一行 JSON**，
  原子 append（`O_APPEND`），不存在半条。
- 已采条数记在落盘时同步更新水位，**中断后重跑从水位继续**。

**Alternatives considered**:
- ❌ 沿用「跑完才落盘 + 分块」—— 分块是**人工预先切分**，切错了就白跑。
  边采边落盘让「分块」这个约束**变得不必要**。
- ❌ 写临时文件再 rename —— 对 append 型日志无必要，且 rename 会丢已 append 的内容。

## R4. 覆盖销号表的「达标下限」怎么定？

**Decision**: 采用 **省级 ≥3,000 条 / 地级 ≥500 条** 作为**默认下限**，
但**做成参数可调**，且表里同时给出「相对全国中位数」的比值。

**Rationale**:
- 当前分布：重庆 32,580 / 天津 630,595（含异常）vs 云南 84。**绝对阈值会被极端值带偏**。
- 补一个「相对中位数」的视角，能看出**结构性不均衡**而不只是「谁没到 3000」。
- ⚠ **这两个数字是假设**，spec 的 Assumptions 已标注需用户确认。
  做成参数的好处：用户改主意不用改代码。

**Alternatives considered**:
- ❌ 只按绝对阈值 —— 会被「天津 63 万」这种源带偏，掩盖真实的结构问题。
- ❌ 只按中位数 —— 用户看不懂「为什么是 0.3 倍中位数」，不如「还差 2,916 条」直观。
- ✅ **采用两者并列**：绝对缺口给「还差多少」（可执行），比值给「结构位置」（可判断）。

## R5. 机器可读输出为什么必须纯 ASCII？

**Decision**: 所有**给程序读**的输出一律 `KEY=VALUE` 纯 ASCII；
中文只出现在**给人看**的输出里。

**Rationale**:
- **这不是理论担忧，是实测踩了 4 次坑**（2026-10-10 闸门排查）：
  1. `sed` 匹配中文 ⇒ locale 失配 ⇒ 解析成 `?`
  2. 无条件的自愈步骤打满 300s hook 超时
  3. `joblib` 缓存因嵌套函数 `PicklingError` 失效
  4. Python 打印中文 ⇒ hook 环境 stdout 非 UTF-8 ⇒ `UnicodeEncodeError`
- **四层里有两层是同一个病**：拿中文当程序间接口。跨环境（bash / PowerShell / hook）时，
  编码与 locale 一变就崩。

**Alternatives considered**:
- ❌ 强制 `PYTHONIOENCODING=utf-8` —— 治标。调用方的环境不可控（hook 是外部拉起的）。
- ❌ 只用英文输出 —— 对人不可读，违反宪法 I「说人话」。
- ✅ **两套输出并存**：`--quiet` / `--gate` 给机器，默认给人。

## R6. 是否需要引入数据库？

**Decision**: **不引入**。继续用 `data/*.jsonl` + `state/watermarks.json`。

**Rationale**:
- 规模：36 万条 × ~1KB ≈ 360MB。文件完全够用。
- 现状痛点不是「查询慢」，而是「**增量能力缺失**」。引数据库不解决这个。
- 引入数据库的代价：要装服务、要管备份、要处理并发 —— **与「可运维」的目标背道而驰**。
- 现有工具链（`audit-coverage.py --gate` 全库扫描 **1.8 秒**）**证明性能不是瓶颈**。

**Alternatives considered**:
- ❌ SQLite —— 看起来「零运维」，但会引入 schema 迁移问题，且现有 331 个 adapter
  都是「写 jsonl」的，改造面太大。
- ❌ DuckDB —— 适合分析，但同样要改写入路径。
- ✅ **将来若需要**：jsonl 可直接被 DuckDB / pandas 读，**不锁定**。所以现在不引不亏。

## R7. 与并行 agent 的并发安全怎么做？

**Decision**: 三层防护：
1. **水位文件加锁**（文件锁 + 短超时，抢不到就跳过该通道，不阻塞整轮）
2. **数据写入前按 id 去重**（R2）
3. **同一个源只允许一路在采**（GOAL.md 硬约束 4，用锁文件保证）

**Rationale**:
- 本目录**确实有并行 agent**（2026-10-10 实测：它在做 IGI 轮次续采，数据量几分钟内
  从 355,795 涨到 357,818）。
- 之前已因并发产生过 60 行重复 id（`nat-mohurd` 59 + `tj-enorth` 1）。
- **不能假设「只有一个 writer」** —— 这是实测结论，不是假想。

**Alternatives considered**:
- ❌ 让两个 agent 分工约定 —— 不可靠，无法强制。
- ✅ **用锁把「约定」变成「机制」**：抢不到锁就跳过，下一轮再采。

## 调研小结

| # | 决策 | 一句话 |
|---|---|---|
| R1 | 每通道自声明水位类型（page/since/idset） | 政务站没增量 API，只能靠「翻到已知位置为止」 |
| R2 | 落盘前按 id 去重 + 新增幂等验证脚本 | 把 SC-002 从「靠人记」变成「可自动验」 |
| R3 | 增量模式边采边落盘 | 修掉「跑 3 小时被杀就全丢」这个最大可靠性缺口 |
| R4 | 绝对阈值 + 相对中位数并列 | 绝对缺口可执行，比值可判断结构 |
| R5 | 机器接口纯 ASCII，中文只给人看 | 已踩 4 次坑，其中 2 次同病 |
| R6 | 不引入数据库 | 性能不是瓶颈，增量能力才是 |
| R7 | 三层并发防护（锁 + 去重 + 单路） | 并行 agent 是实测事实，不是假想 |

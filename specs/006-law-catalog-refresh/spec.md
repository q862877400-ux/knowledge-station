# Feature Specification: 法规目录补齐与定时刷新 + 历次版本链

**Feature Branch**: `006-law-catalog-refresh`

**Created**: 2026-10-10

**Status**: Draft

**Input**: 业主指令「从 std-law-watch 项目里把能用的提取出来，融入我们现在的 ks 项目中」「自动下载要保留，a」「全部按照你的推荐，你设置好目标，全自动按照 spec 的规则推进」

---

## 背景：为什么需要这个特性

`D:/AI/std-law-watch` 是一个独立 Agent 于 2026-10-10 建成的法规/标准采集项目
（64 站注册表、185 条候选台账、flk 全量索引 29,994 条）。它的**技术发现**对 KS 有用，
但它的**代码形态**（独立引擎 + 自建 Stop hook 闸门 + 无版本控制）与本仓规范不兼容。

Lead 的独立诊断（本 spec 的事实依据，全部实测）确认了一处**真实的存量缺陷**：

| 项 | 值 | 来源（实测命令） |
|---|---|---|
| KS `law_catalog` 行数 | **29,764** | 真库 `%APPDATA%\KnowledgeStation\database\knowledge.db` |
| flk 远端空条件 total | **30,910** | `flk_client.search("", …)` |
| **KS 缺失** | **1,187** | 按 `bbbs` 差集 |
| 缺失集中在 | 2026-07 缺 **438**、2026-08 缺 **676** | 按 `gbrq` 年月分组 |
| KS 8 月只有 | **26** 条（flk 同月 702 条） | 同上 |
| `updated_at` 全部 | **2026-08-25** | `GROUP BY updated_at` |
| `gbrq` 最大值 | **2026-08-10** | `MAX(gbrq)` |
| `law_manifest.json` | 28 个分类**全部 `done=true`** | 账本 |

**根因**：不是抓不到，是**抓完那一次就再没跑过**。
`src/core/update/` 里 `law_catalog` / `refresh_catalog` / `check_law_updates` 命中 **0 行**；
`scheduler.py` 提到 `law` **0 行**。8-25 那次 28 个分类全标完成，此后 6 周无任何刷新机制。

**分片覆盖是完整的**（排除"抓漏"这个解释）：28 个叶子分类 `total` 之和 = **30,909**，
空条件 total = **30,910**，只差 1。

### ⚠ 比"缺失"更严重：库里有 1,130 条时效状态是**错的**

按 `bbbs` 逐条比对两库的时效字段（`law_catalog.sxx` vs flk 现况），**实测**：

| 方向 | 条数 | 性质 |
|---|---|---|
| KS「有效」→ flk「**已修改**」 | **864** | 状态过期 |
| KS「有效」→ flk「**已废止**」 | **147** | ⚠ **在库中标着"现行有效"，实际已废止** |
| KS「已修改」→ flk「已废止」 | **60** | 状态过期 |
| KS「尚未生效」→ flk「有效」 | 58 | 时间推移，正常演进 |
| KS「已修改」→ flk「有效」 | 1 | 异常 |
| **合计不一致** | **1,130** | 其中 **1,071** 条是 8-25 之后真的变了 |

**为什么这条更严重**：KS 是合规工具，「现行有效 / 已废止」直接决定引用能不能用。
库里 147 条标着"有效"实际已废止 —— **这是会误导使用的正确性缺陷，不只是"少了几条"**。

**同一根因**：8-25 之后无任何刷新 ⇒ 既漏新增（1,187），也让存量状态烂掉（1,130）。
**一次刷新同时修两件事**，这也是把刷新机制列为 P1 的原因。

**取证示例**（同名法规在两边并存，可复核）：

```
绍兴市大气污染防治条例
  KS  bbbs=4028abcc612777930161280e0b9c4e77  gbrq=2016-10-19  sxx=3（有效）
  FLK bbbs=4028abcc612777930161280e0b9c4e77  gbrq=2016-10-19  status=已修改
  FLK bbbs=ff8081819ff54ab801a06b37cbc33373  gbrq=2026-08-10  status=有效   ← KS 没有这条
  FLK bbbs=ff8081819ff54a6401a056dc1f7676d6  gbrq=2026-08-04  status=有效   ← KS 没有这条
```

⇒ 同一部法规，KS 只存了 2016 年那版并标"有效"，**官方早已标"已修改"，
且 2026 年有两版新的**。这正是用户口径里「更新」的语义，也正是本特性 US2 要解决的。

### 关于「自动下载」的口径（先讲清，避免与台账冲突）

`docs/NOT-DOING.md` #20 禁止的是「**缺标准**自动下载」——即答案引用了库中没有的标准时
系统自行下载入库（动的是知识库内容，故必须人批）。本特性**不触碰**该条。

本特性涉及的自动下载是**既有 `auto_ingest` 能力**（设置页有开关、服务端默认开），
其对象是**官方源（flk / gov.cn）白名单内**的法规目录与全文。二者不是同一件事。

**⇒ 本特性 MUST NOT 修改 `NOT-DOING.md` #20，MUST NOT 放宽「必须人批、无旁路」纪律。**

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 法规目录不再断档，且以后自己保持最新 (Priority: P1) 🎯 MVP

作为使用者，我打开法规目录查一部 8 月新发布的法规，现在**查不到**——
因为目录停在 8 月 10 日。我要它补齐，并且**以后每天自动跟官方对一次**，
新发布的法规自己进来，不用我记着让人跑。

**为什么最优先**：这是唯一的**真实数据缺陷**（1,187 条缺失），其余两条是增强。
且它直接决定「法规目录」这个功能今天可不可信。

**Independent Test**：取一部已知在 8-25 后改过状态的法规（如「绍兴市大气污染防治条例」，
KS 记 `sxx=3` 有效、官方实为「已修改」），刷新后断言其 `sxx` 变为 2；
再触发一次增量刷新，重复执行不产生重复行（幂等）。

**Acceptance Scenarios**:

1. **Given** 目录停在 2026-08-25（29,764 行），**When** 执行一次全量刷新，
   **Then** 行数 ≥ 30,900 且 2026-08 的条数从 26 升到 ≥ 600。
2. **Given** 库里有 1,130 条时效与官方不一致（含 147 条标"有效"实为"已废止"），
   **When** 执行一次全量刷新，**Then** 不一致条数降到 **0**
   （仅统计两库都有、且官方 `sxx` 非空的 `bbbs`）。
3. **Given** 刚跑完全量刷新，**When** 立即再跑一次（无官方变更），
   **Then** 写库行数为 0（增量跳过）、总行数不变（幂等）。
4. **Given** 引擎启动、刷新周期已到，**When** 后台循环跑一拍，
   **Then** 自动执行增量刷新，无需人工调用。
5. **Given** 官方接口某分类临时失败，**When** 跑刷新，
   **Then** 该分类记 warning 并跳过，其余分类照常入库，整体不中断（断点续传）。

### User Story 2 - 能看到一部法规改过几次、什么时候废止的 (Priority: P2)

作为使用者，我查「中华人民共和国审计法实施条例」，现在只能看到「当前有效」，
**看不到它 2010 年发布、2026 年修订过**。我要能看见这条历次版本链，
这样"更新"这件事对我才是可解释的。

**为什么第二优先**：用户口径里「发布 / 更新 / 废止」是核心语义，而
`lsyg`（历史沿革）是官方**原生字段**——std-law-watch 挖到了，KS 里**没有任何代码读它**
（`git grep lsyg` 在 `src/` 命中 0 行，只有 `channel_seed.json` 一句备注）。

**Independent Test**：取一个已知有多版本的 `bbbs`，调详情接口，
断言返回的版本链长度 ≥ 2 且按日期降序；再断言端点对无 `lsyg` 的法规返回空链而非报错。

**Acceptance Scenarios**:

1. **Given** 一个有历次版本的 `bbbs`，**When** 查询该法规的版本链，
   **Then** 返回 ≥ 2 个版本，每个含 `bbbs` / `title` / `gbrq`，按 `gbrq` 降序。
2. **Given** 一个无 `lsyg` 字段的 `bbbs`，**When** 查询版本链，
   **Then** 返回空列表且 `status=ok`（不报错、不猜）。
3. **Given** 官方接口不可达，**When** 查询版本链，
   **Then** 返回明确错误码，MUST NOT 返回空列表冒充"无版本"。

---

### User Story 3 - 那个项目挖到的接口知识能省下一次重新摸索 (Priority: P3)

作为维护者，官方站点改版时我要能查"上次是怎么摸出来的、哪些路已经判死"，
而不是从零再试一遍。

**为什么第三优先**：纯文档，风险为零，但它防止未来重复劳动。
当前 KS **不知道**这些事实（`highSearch` 在 `src/` 命中 0 行）：

- `highSearch` 端点（std-law-watch 的主力端点）KS 从未使用；
- 翻页 offset 上限 **30,000** 这堵墙；
- `flfg_code_id` 传的是 **`codeId` 不是 `id`**；
- 文号藏在详情接口的 `xgzl`（相关资料）里，列表接口没有该字段。

**Independent Test**：`git grep` 上述四个事实的关键词，在归属文档中均命中。

**Acceptance Scenarios**:

1. **Given** 本特性完成后，**When** 查 `docs/LAW-SOURCE-PLAN.md`，
   **Then** 能找到 `highSearch` 端点、30,000 墙、`codeId≠id` 三条的记载与出处。
2. **Given** 判死结论（全文下载、采标国标等），**When** 查文档，
   **Then** 有"已判死 + 证据"条目，且**明确标注与 KS 现有结论的冲突**（见下）。

---

### Edge Cases

- **KS 现有结论与 std-law-watch 相反**：对 `download/pc` 全文下载，
  KS 记为「主路径」（`flk_client.py` 注释 + `ENCYCLOPEDIA.md` 写"实测返回 SPA 首页"），
  std-law-watch 记为「判死」。**本特性 MUST NOT 单方面采信任一方**；
  必须在文档中**并列记录冲突**并标注"未实测仲裁"。
- 刷新中途进程被杀：账本是 DB 的镜像承诺，下次运行重来该分类，upsert 幂等兜底。
- `enum_data` 结构变更导致解析不出叶子分类：`refresh_catalog` 已 `raise RuntimeError`，保持。
- 同一 `bbbs` 出现在多个分类（实测存在，如"修改、废止的决定"有 4 个 code）：
  按 `bbbs` 去重，`category` 取首次写入值。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 提供一次可重跑的法规目录刷新，把 `law_catalog` 补齐到官方全量
  （当前 29,764 → ≥ 30,900）。
- **FR-001a**: 刷新 MUST 同时修正**存量时效漂移**——已入库但官方 `sxx` 已变的条目
  MUST 被更新（当前 1,130 条不一致，含 147 条标"有效"实为"已废止"）。
  即：增量判据 MUST 比较 `sxx`，MUST NOT 只看"该 `bbbs` 是否已存在"。
- **FR-002**: 刷新 MUST 幂等——已入库且 `title`/`sxx` 未变则跳过写库；
  重复执行 MUST NOT 产生重复行。
- **FR-003**: 刷新 MUST 支持分类级断点续传；单分类失败 MUST 记 warning 并继续，
  MUST NOT 中断整体。
- **FR-004**: 系统 MUST 在引擎启动时拉起一个后台刷新循环，按配置周期自动触发，
  MUST NOT 要求人工调用。
  **（2026-10-10 更正）** 原写"接入既有 `src/core/update/scheduler.py`"，
  实测该调度器**在生产中从未被启动**（`start()` 全仓无人调用）⇒ 接进去等于刷新永不执行。
  改为照抄 `server.py` 既有先例 `write_queue_bootstrap.start_write_worker()` 的
  daemon 线程模式，在 `run()` 里启动。
- **FR-005**: 刷新周期 MUST 是可配置项（deployment-varying），
  MUST NOT 是插件内硬编码常量。
- **FR-006**: 系统 MUST 提供法规历次版本链查询（读 flk 详情接口的 `lsyg`），
  返回版本列表（含 `bbbs` / `title` / `gbrq`），按 `gbrq` 降序。
- **FR-007**: 版本链查询 MUST 区分「无版本」（空列表）与「查询失败」（明确错误），
  MUST NOT 用空列表冒充失败。
- **FR-008**: 系统 MUST 暴露版本链的 HTTP 端点（挂在既有 `/api/v1/laws/*` 族下）。
- **FR-009**: 本特性 MUST NOT 修改 `NOT-DOING.md` #20 或放宽「采集必须人批、无旁路」纪律。
- **FR-010**: 文档 MUST 记录 std-law-watch 的四条接口事实
  （`highSearch` / 30,000 墙 / `codeId≠id` / `xgzl` 文号）及其出处。
- **FR-011**: 文档 MUST 并列记录 `download/pc` 全文下载的**结论冲突**，
  标注"未实测仲裁"，MUST NOT 单方面采信任一方。
- **FR-012**: 所有新增网络请求 MUST 经 `law_source/http.py` 的域白名单出口
  （`fetch_json` / `download_file`），MUST NOT 绕过。
- **FR-013**: 本特性 MUST NOT 引入 `std-law-watch` 的 64 站注册表到 KS
  （KS 白名单只允许 5 个官方域；并入会破坏来源纪律）。

### Key Entities

- **law_catalog 行**：一部法规的目录条目。关键属性：`bbbs`（官方主键）、`title`、
  `flxz`（法律性质）、`sxx`（时效）、`category`、`gbrq`（公布日期）、`sxrq`（施行日期）。
- **law_manifest（账本）**：刷新进度。关键属性：分类级 `done` / `fetched`、法规级
  `title` / `sxx` / `fetched_at`。语义是 DB 的镜像承诺（写库成功后才记账）。
- **版本链条目**：一部法规的历次版本。关键属性：`bbbs`、`title`、`gbrq`、`highLight`
  （官方标记的当前版本）。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: `law_catalog` 行数从 29,764 升至 **≥ 30,900**，
  且 2026-08 条数从 26 升至 **≥ 600**（对齐官方 702）。
- **SC-001a**: 时效不一致条数从 **1,130 降到 0**
  （口径：两库都有、官方 `sxx` 非空的 `bbbs` 逐条比对 `sxx`）。
- **SC-002**: 连续两次全量刷新，第二次写库行数 = **0**、总行数不变（幂等可测）。
- **SC-003**: 法规刷新在**引擎启动后自动触发**（有测试断言：启动循环 + 注入假时钟到期
  ⇒ 确实调用了刷新；未到期 ⇒ 不调用）。
- **SC-004**: 版本链端点对一个已知多版本法规返回 **≥ 2** 个版本且日期降序。
- **SC-005**: 版本链端点对官方不可达返回**非 200 语义**，MUST NOT 返回空列表。
- **SC-006**: `pwsh -File scripts/run-gates.ps1 -Quick` **exit 0**，测试基线只涨不跌。
- **SC-007**: 四条接口事实 + 一条结论冲突在归属文档中可 `grep` 到。

## Assumptions

- flk 官方接口（`search/list`、`flfgDetails`）在 2026-10-10 实测可用
  （`search` 返回 `code=200 total=30910`）；官方改版会导致刷新失败并明确报错。
- 既有 `refresh_catalog` 的分片逻辑（28 个叶子分类）覆盖完整
  （实测各分类 total 之和 30,909 vs 空条件 30,910，差 1）⇒ 本特性**不改分片策略**。
- 巡检调度器（`scheduler.py`，2 秒轮询 `app_config`）是既有可用基础设施 ⇒ 复用而非新建。
- `std-law-watch` 目录**保留只读**（内含 `_diag/` 原始证据，删除后无法复验）；
  本特性只并入**知识**，不并入**代码**。

## R5 ⚠ 额外发现：`UpdateScheduler` 在生产中是**死代码**（本轮只登记，不修）

**发现经过**：原 plan 打算把法规刷新接进 `UpdateScheduler.tick()`。
动手前核"这个调度器在生产里到底跑不跑"，实测结论是**不跑**。

**证据链**（逐层追调用者）：

| 层 | 位置 | 调用者 |
|---|---|---|
| `tick()` | `scheduler.py:165` | 只被 `_run()` 调用（`scheduler.py:104`） |
| `_run()` | `scheduler.py:98` | 只被 `start()` 拉起（`scheduler.py:88`） |
| `start()` | `scheduler.py:82` | **全仓无人调用** |

`git grep -n UpdateScheduler -- src` 只命中两处，且都不是实例化：
- `src/core/update/scheduler.py:70` —— 类定义自身
- `src/core/update/__init__.py:37,53` —— re-export

其余全部命中在 `tests/test_update_inspector.py`（531/541/1237/1295/1312/1327/1334 行）。
`server.py` 的 `run()`（唯一的生产启动点，`:3286-3313`）里只启动
`start_write_worker()`，**没有任何地方启动 `UpdateScheduler`**。

**⇒ 结论**：定时巡检建批（`trigger='scheduled'`）这条路径
**在生产中不可达**；实际只有"手动一键检查更新"
（`POST /api/v1/update/check`，`routes_update.py:68` 用 `trigger="manual"`）会建批。

**为什么这是本轮必须记的事**：它正是本仓纪律「**工具正常返回 ≠ 工具是对的**」
的又一实例——调度器代码完整、6 条测试全绿、注释写着"每 tick 检查 app_config"，
但**生产路径上没人拉它**。若不核这一步，本特性的 SC-003（自动触发）
会以"接进了 tick()"为满足，而**刷新永远不会执行**。

**处置：本轮只登记，不修**。理由：
1. 修它 = 启动一个"每 7 天自动建巡检批、进日预算池"的行为，
   这是业主**没要求**的行为变更；
2. 与法规目录刷新**无关**——法规刷新不需要 `bulk_import_batch`；
3. 本仓纪律：**跨轮次的额外发现只登记，不在当轮顺手实施**。

**建议后续**（不在本特性范围）：要么在 `run()` 里启动它（明确接受自动建批），
要么删掉它并在文档里说明"定时巡检未启用、只支持手动一键"。
**两种都要业主定**，本轮不擅自选。

**对方案的影响**：plan D2 已**就地更正**为"自建轻量后台线程"，
spec FR-004 与 tasks T012/T012a 同步更正（错话与更正都留在原文里，未悄悄删）。

## R6 ⚠★ 反爬挑战页：HTTP 200 + HTML（本特性的最大障碍，已修）

**发现经过**：第一次真跑刷新（T020）时，**12 个分类**报
`Expecting value: line 1 column 1 (char 0)`（JSONDecodeError）。

### 症状与误判风险

直接探测官方端点，返回的是：

```
HTTP 200  len=36819  ctype=text/html
body: <!DOCTYPE HTML><html><head><meta charset="utf-8"></head>
      <body><noscript><h1><strong>Please enable JavaScript and refresh the page.
```

**⚠ 这个形状特别坑**：`HTTP 200` 让 `raise_for_status()` **放行**，
只有 `resp.json()` 抛错 ⇒ 挑战被当成"普通网络错误"，
而 `http.py` 原来只用 `0.8s / 1.6s` 退避 ⇒ **必然失败**，
且错误信息里**看不出是被挡了**。

### 实测读数（2026-10-10 本机）

| 实验 | 结果 |
|---|---|
| 每 0.6s 一页连打 | 第 **33** 页起被挡 |
| 被挡后每 60s 探一次 | **1 分钟内自愈** |
| 带自适应退避（失败退避 20–120s）连打 **120** 页 | **0 次被挡** |
| 换全浏览器头（`Sec-Fetch-*` / `Origin` / `Accept-Language`） | **无效** |
| 换 GET 首页预热（std-law-watch 记的"坑 1：首访 307 挑战"） | **无效** |
| 直连 vs 走本机代理 `127.0.0.1:7897` | **一样被挡**（与代理无关） |
| **持续猛打多轮后** | 封禁**变长**：>73s（5/10/30/60s 退避共 4 次）仍未解；后拉到 10/30/60/120s（5 次）仍偶发失败 |

**⇒ 判读**：这是**突发限速**（阈值可变、分钟级自愈、猛打会加长），
**不是**封 IP、**不是**头指纹、**不是**代理问题。
**唯一有效对策是拉长退避**。

### 本仓的修法

`src/core/knowledge/law_source/http.py`：
- 新增 `AntibotChallenge`（RuntimeError 子类）+ `_looks_like_antibot()`；
- **判据以 `Content-Type` 为主**：`fetch_json` 的契约就是"拿 JSON"，
  **声明不是 JSON 的响应**本身就说明没拿到数据 ⇒ 一律走长退避；
- `_ANTIBOT_BACKOFF = (10.0, 30.0, 60.0, 120.0)`、`_ANTIBOT_TRIES = 5`。

⚠ **第一版判据只查特征串**（`"Please enable JavaScript"`），实测**漏判**：
站点有时返回**另一种** HTML 页（正文里没有该串）⇒ 已改成 Content-Type 优先。
⚠ **第一版退避只有 5/20/45s**，实测**不够**（猛打后封禁 >73s）⇒ 已拉长。

**取证**：`tests/test_law_source_http_antibot.py`（10 条，含两条变异验证）。

### 诚实边界

- 上表是**本机、当天**的读数；阈值会随站点策略变。
- 「120 页 0 次被挡」那次是**单轮**实测，未在多轮猛打后复现。
- **未能拿到稳定的"幂等实跑"读数**（SC-002 的活体验证）：连续猛打后站点
  进入长封禁，第二轮 `refresh_catalog` 在 `enum_data` 处就失败。
  ⇒ SC-002 目前**由单元测试覆盖**（`test_skips_when_not_due` +
  既有 `test_law_catalog.py` 的增量跳过用例），**活体读数明确未做**。
  **✅ 收口轮已补上**：见 R7。

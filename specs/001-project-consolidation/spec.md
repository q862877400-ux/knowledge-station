# Feature Specification: 项目整理与接手文档体系

**Feature Branch**: `001-project-consolidation`

**Created**: 2026-10-05

**Status**: Draft

**Input**: User description: "我的目标是让项目文件干净清爽，没有多余的无用的东西，各种历史备份也分门别类放好，项目文件本地干净清爽，各种命名啊分类啊都有统一规范，然后还有一套逐步递进的wiki一样的文档清晰描述项目具体情况，比如一个大map展示各类文件怎么归档什么功能，然后每套组件都有详细描述和规范契约，然后别的agent接手的时候，一套文档一读玩就对这个项目的目标和现状完全了解清楚了，至于历史和备份就知道在哪找就像需要的时候才去看。"

**补充确认（业主 2026-10-05 逐条选定）**：
清理程度 = **搬 + 删明确无用的**；归档位置 = **仓内 `docs/archive/`**；文档形态 = **仓内 md 分级**；
组件契约范围 = **分层（1 张大 map + 每子系统 1 篇 + 关键接口契约）**；
命名 = **先出新旧名称对应表，再全量重命名（含代码内部引用）**；
现有总览文档 = **改造成那套 wiki**；`var/` = **算在"本地干净"范围内**。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 定名字：命名与分类规范落定并全量执行 (Priority: P1)

项目里同一类东西有四种叫法（中文名 `wenjianmulu/`、大写 `B3A-REPORT.md`、kebab `gen-doc-index.py`、
带日期后缀 `NEXT-DEV-PLAN-2026-09-28.md`）。接手者无法从名字判断一个文件是"当前真源"还是"历史归档"。

业主先拿到一份**新旧名称对应表**（每一行：现名 → 新名 → 归属分类 → 为什么），确认后由执行方
**一次性全量重命名**，并把因此受影响的**全部引用同步改正**（文档间链接、代码里引用的文档路径、门禁脚本里的断言），
最后跑门禁验证没有改坏。

**Why this priority**: 名字是一切后续工作的地基。清理和 wiki 都以"找到并指向某个文件"为基础；
若先做清理和 wiki 再改名，这两样的成果会立刻过期。

**Independent Test**: 只做这一条也能交付完整价值——名字统一后，接手者仅凭文件名即可判断
"这是当前真源 / 这是历史 / 这是研究笔记"。测试方式：随机抽 20 个文件，只看路径，
判断其分类，与对应表的归属一致即通过。

**Acceptance Scenarios**:

1. **Given** 仓库尚未有命名规范，**When** 规范落定，**Then** 存在一份文档，明确给出
   目录命名规则、文件命名规则、分类归属规则，且每条规则有反例说明。
2. **Given** 规范已落定，**When** 生成对应表，**Then** 表中每一行都给出
   现名、新名、归属分类、改名理由；且**覆盖全部需要改名的对象**（不遗漏、不静默跳过）。
3. **Given** 对应表已确认，**When** 执行全量重命名，**Then** 全仓**断链数为 0**
   （文档互相引用、代码引用文档、门禁断言三类都无残留旧名）。
4. **Given** 重命名已完成，**When** 跑门禁，**Then** 门禁通过，测试基线不下降。
5. **Given** 某个文件被多个门禁脚本或测试硬编码引用，**When** 它被改名，**Then**
   该处引用被同步改正，且改动被明确列出（不靠"碰巧没坏"）。

---

### User Story 2 - 归位：清理杂物并把历史分门别类归档 (Priority: P2)

接手者打开仓库看到的是干净的结构：顶层每一项都能说出它是什么、属于哪一类；
历史记录、旧计划、调研过程、备份全部在归档区按类归好；本地目录（`var/`）也不再是杂物堆。

**Why this priority**: 清理是 wiki 能在稳定地基上写的前提；同时它本身直接满足业主"干净清爽"的首要诉求。

**Independent Test**: 只做这一条也能交付价值——仓库根目录每一项都能在归档说明里找到归属，
临时产物与重复件消失。测试方式：列出仓库顶层条目，逐条说出归属；说不出归属的即失败。

**Acceptance Scenarios**:

1. **Given** 仓库存在散落文件（如根目录的报告类 md、名字来历不明的目录），
   **When** 清理完成，**Then** 每个顶层条目都能在归档说明中查到归属，无"说不出是什么"的条目。
2. **Given** 存在一批历史文档（旧计划、旧调研、过程记录），**When** 归档完成，
   **Then** 它们位于归档区且按类分目录，并有一份索引可查"哪类历史在哪"。
3. **Given** 存在重复件与明确无用的文件（临时产物、已被取代且无人引用的全文、生成物残留），
   **When** 清理完成，**Then** 它们被移除，且**移除前存在可恢复路径**（可从版本历史或归档区找回）。
4. **Given** 归档区已建立，**When** 需要查历史，**Then** 从仓库入口按"历史在哪"的指引能在
   **不超过 3 步**内到达目标归档文档。
5. **Given** 本地目录 `var/` 下有多个混杂目录，**When** 整理完成，**Then**
   每个子目录有明确用途说明；业务资料不被误删；明显的临时产物被清掉。

### User Story 3 - 读懂：分级 wiki 使接手者读完即了解项目 (Priority: P3)

一个新接手的 agent（或人）打开仓库，按一份递进式文档读下去：
先看**一张大 map**（各类文件怎么归档、各自什么功能）→ 再看**每个子系统的描述与契约**
（它负责什么、对外提供什么、依赖什么、明确不做什么）→ 读完即能回答
"这个项目的目标是什么、现在做到哪了、这块代码是干什么的、我要改某处该动哪个文件"。

**Why this priority**: 这是业主诉求的最终价值，但它建立在 P1（名字定死）和 P2（结构归位）之上；
前置不稳会让 wiki 写完就过期。

**Independent Test**: 找一个**从未读过本仓**的 agent，只给它 wiki 入口，让它回答一组关于
项目目标与现状的问题；答对率达标即通过。

**Acceptance Scenarios**:

1. **Given** 接手者从未见过本仓，**When** 只读 wiki 入口，**Then** 能说出项目的目标、
   当前阶段、主要子系统各是什么。
2. **Given** 接手者要改某个功能，**When** 查 wiki，**Then** 能在 wiki 内定位到
   负责该功能的子系统文档，而不需要先读代码。
3. **Given** 大 map 已存在，**When** 接手者看它，**Then** 能说出仓库每一类文件放在哪、用来干什么。
4. **Given** 每个子系统都有描述与契约，**When** 接手者读其中一个，**Then** 能说出
   它的职责边界、对外接口、依赖关系、以及它明确**不做**什么。
5. **Given** wiki 与代码不一致时，**When** 有人发现不一致，**Then**
   wiki 的归属与更新责任是明确的（知道该改哪一份）。
6. **Given** 项目已有若干份总览性质文档，**When** wiki 建成，**Then**
   同一主题**只有一处**说全文，其余位置只链接（不出现两套重叠的总览）。

### Edge Cases

- **别人的未提交改动**：仓库里存在其它会话正在进行、尚未提交的文件。
  整理过程 MUST NOT 触碰它们；若它们恰好落在要清理的范围内，MUST 跳过并登记。
- **重命名撞车**：两个不同文件按新规范算出同一个新名。MUST 停下来报告，MUST NOT 静默加后缀。
- **被重命名对象正被别的进程使用**（如正在跑的复核用某棵树）。MUST 先确认无人使用再动。
- **改名后出现断链但门禁扫不到**（门禁只覆盖部分文件）。MUST 用独立的全仓链接检查补上，
  MUST NOT 只凭"门禁绿了"就宣布无断链。
- **历史文档里引用了自己**（自引用路径）。归档移动后 MUST 修正。
- **明确无用 vs 拿不准**：拿不准的 MUST 归入归档，MUST NOT 删除。
- **`var/` 下的业务资料**（如用户存放的原始资料）与临时产物外观相似。MUST 按内容判断，MUST NOT 按目录名判断。

## Requirements *(mandatory)*

### Functional Requirements

**命名与分类（P1）**

- **FR-001**: 系统 MUST 提供一份命名与分类规范文档，规定目录命名、文件命名、分类归属三类规则，
  每条规则 MUST 附反例。
- **FR-002**: 系统 MUST 产出一份新旧名称对应表，每行含现名、新名、归属分类、改名理由。
- **FR-003**: 对应表 MUST 覆盖全部需改名对象，MUST NOT 静默跳过（跳过项 MUST 显式列出并说明原因）。
- **FR-004**: 系统 MUST 执行全量重命名，且同步改正全部受影响引用：文档间链接、代码引用、门禁断言。
- **FR-005**: 重命名后，全仓文档链接断链数 MUST 为 0；MUST 用独立的全仓检查验证，
  MUST NOT 仅凭门禁结果断言。
- **FR-006**: 重命名后 MUST 跑门禁，测试基线 MUST NOT 下降。

**清理与归档（P2）**

- **FR-007**: 仓库顶层每一个条目 MUST 在归档说明中有明确归属；MUST NOT 存在"说不出是什么"的条目。
- **FR-008**: 系统 MUST 建立归档区，历史文档按类归入，并 MUST 提供一份归档索引
  （说明哪类历史在哪、怎么查）。
- **FR-009**: 明确无用的文件（临时产物、生成物残留、已被取代且无人引用的全文）MUST 被移除，
  且移除前 MUST 存在可恢复路径。
- **FR-010**: 拿不准归属的文件 MUST 归入归档区，MUST NOT 删除。
- **FR-011**: 仓库 MUST NOT 包含本机专有、与项目无关的状态目录；此类目录 MUST 被排除在版本控制外。
- **FR-012**: 本地目录 `var/` 的每个子目录 MUST 有用途说明；明显临时产物 MUST 被清理；
  业务资料 MUST NOT 被删除。

**接手文档体系（P3）**

- **FR-013**: 系统 MUST 提供一张大 map，覆盖仓库每一类文件的归档位置与功能。
- **FR-014**: 系统 MUST 为每套组件提供描述与契约，含职责、对外提供什么、依赖什么、明确不做什么。
- **FR-015**: wiki MUST 分级递进：入口 → 大 map → 子系统 → 契约，且每级 MUST 能从上一级到达。
- **FR-016**: 接手者 MUST 能只读 wiki 就回答：项目目标、当前阶段、某功能由哪个子系统负责。
- **FR-017**: 同一主题 MUST 只有一处说全文，其余位置只链接。
- **FR-018**: 系统 MUST 明确 wiki 的更新责任（改了代码该改哪份文档），使 wiki 不随代码漂移。
- **FR-019**: 项目已有的总览性质文档 MUST 被改造或并入 wiki，MUST NOT 留下与 wiki 重叠的第二套总览。

**约束**

- **FR-020**: 整个过程 MUST NOT 触碰其它会话的未提交改动；
  若某目标落在其中，MUST 跳过并在报告中登记。
- **FR-021**: 任何改动 MUST NOT 破坏既有门禁；每次改动 MUST 可追溯到一次提交。
- **FR-022**: 任何历史留痕 MUST 遵循"错话+更正就地保留、作废的删全文只在开发史留一句"的既有纪律。

### Key Entities

- **命名规范**：目录/文件/分类三类规则，每条带反例。
- **名称对应表**：现名 → 新名 → 归属分类 → 理由；是重命名的唯一依据。
- **归档区**：历史文档的分类存放地，附索引。
- **大 map**：仓库文件类别 × 归档位置 × 功能 的对照。
- **组件契约**：单个子系统的职责、接口、依赖、明确的非目标。
- **归档索引**：回答"哪类历史在哪"的单一入口。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 全仓文档互相引用、代码引用文档、门禁断言三类引用中，指向旧名的残留数为 **0**。
- **SC-002**: 随机抽 **20** 个文件，仅凭路径判断其分类，与对应表归属的一致率 **100%**。
- **SC-003**: 仓库顶层条目中，无法在归档说明中找到归属的数量为 **0**。
- **SC-004**: 一个从未读过本仓的 agent，只读 wiki，对"项目目标/当前阶段/某功能归属"三类问题
  的回答正确率 **≥ 80%**。
- **SC-005**: 从仓库入口到任一历史归档文档，步数 **≤ 3**。
- **SC-006**: 每套子系统组件都有描述与契约，覆盖率 **100%**。
- **SC-007**: 门禁在本特征完成后通过，测试基线**不低于**开工前。
- **SC-008**: 文档总体积相比开工前下降（去重与归档后），且当前真源类文档**无一被删除**。
- **SC-009**: 其它会话的未提交改动，开工前后**逐字节一致**（零触碰）。

## Assumptions

- **使用者是 agent 与人**：wiki 的首要读者是接手的 coding agent，其次是人；因此以仓内 md 为主，
  不依赖任何需要构建、联网或专用阅读器的形态。
- **归档 ≠ 删除**：历史迁入归档区后仍受版本控制，可被搜索到，只是不再出现在"当前真源"的路径上。
- **有版本控制作为安全网**：受版本控制的文件被删除后可从历史找回；
  **未受版本控制的文件（如 `var/` 下的产物）不享有这个安全网**，因此对它们 MUST 先移动到可恢复位置而非直接删除。
- **门禁覆盖不完全**：门禁只扫部分面，因此断链检查 MUST 独立于门禁单独做。
- **`specs/` 目录是本特征引入的新结构**，与既有 `docs/` 并存；其边界 MUST 在命名规范中写清。
- **不存在"一次改完"**：分阶段推进，每阶段结束都在可交付、门禁绿的状态上停下。
- **依赖**：本特征的执行依赖既有门禁脚本可用、既有测试基线可复现。

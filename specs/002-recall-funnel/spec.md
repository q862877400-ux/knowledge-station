# Feature Specification: 召回漏斗诊断与第一轮改进

> **给业主看的版本（大白话）→ [读我-大白话版.md](读我-大白话版.md)**　—— 本文是技术文档，业主不必读。

**Feature Branch**: `002-recall-funnel`

**Created**: 2026-10-06

**Status**: Draft

**Input**: User description: "不再扩展技术方向，直接进入一个 7～10 天的「召回诊断 → 第一轮改进 → 决策」周期。核心原则：先把「第一跳为什么丢」测清楚，再决定是修表示、修查询、修索引，还是训练。"

## 背景（为什么现在做这个）

项目开发**已暂停在基础层**（见 [`../../docs/archive/research-process/PROJECT-STATUS-2026-10-05.md`](../../docs/archive/research-process/PROJECT-STATUS-2026-10-05.md)）。

**卡点**：用大白话提问时，**一半以上根本找不到正确条文**。手上只有几个**互相独立、口径未确认**的数字（53% 零重合 / 按字 6.8% / 按意思 5.8% / 命中集合 41.6% → 前二十 24.5% → 前五 11.8%）。

**⇒ 现在的问题是【不知道该修哪里】**：可能是文档表示不对、可能是提问表达不对、可能是检索通道不够、也可能是索引本身把答案丢了。**这四种的修法完全不同，而现有数字分不出来。**

**⇒ 本规格要交付的不是"更高的命中率"，是【一个能指出问题出在哪一层的答案】。**

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 看清正确条文是在哪一步被丢掉的 (Priority: P1)

业主拿一批**已经人工确认过正确答案**的问题，逐个跑过各个检索角度，得到一张表：**每条问题在每一步是"还找得到"还是"已经丢了"**。

> **⚠ 2026-10-06 更正（事后实测，"四个检索角度"作废，原话留痕）**
>
> **原话**：四个角度 = ① 按字找 ② **语义·精确**（按意思找，但用精确计算、不经过任何近似）
> ③ **语义·近似**（按意思找，走现在实际在用的那套索引）④ 合并后。
>
> **实测**：`clause_vec` 是 `vec0(clause_revision_id TEXT PRIMARY KEY, embedding FLOAT[512])`，
> `sqlite-vec` 在本仓**只做暴力精确扫描、没有近似索引** ⇒ **②与③是同一次计算**，
> "精确 vs 近似"这条分界线**不存在**。
> 同时本仓的检索**不是四路而是六条通道**（A 条款号精确 / B FTS5 全文 / C 向量 / D 模态 /
> E 法理要素 / F 行为客体），且**其中四条在"外行用大白话提问"这条路上不触发**
> （A 要提问含条款号、D 要含模态词、E/F 需要调用方传筛选条件而生产不传）。
>
> **更正后**：角度按**实际实现**定 —— 从"四个视角"改为
> **"六条通道 × 各自取回上限 + 融合后"**，并且每条通道都要**分别记名次**。
> 判读规则与结论种类见 [contracts/funnel.schema.md](contracts/funnel.schema.md)（已同步更正）。

**更正后的角度（六条通道 + 融合后）**：

| # | 角度 | 生产会触发吗 | 取回上限 |
|---|---|---|---|
| 1 | A 条款号/法条号精确 | 只在提问含条款号时 | 无上限 |
| 2 | B FTS5 全文（**按字**） | 恒 | `LIMIT 20` |
| 3 | C sqlite-vec 向量（**按意思**） | 恒 | `k = 20` |
| 4 | D 模态 | 只在提问含模态词时 | 无上限 |
| 5 | E 法理要素 | **恒不触发** | 无上限 |
| 6 | F 行为客体 | **恒不触发** | `LIMIT 20` |
| 7 | **融合后**（RRF + 时效过滤） | 恒 | `cap` |

**Why this priority**：**这是后面所有决策的前提。** 没有它，任何改动都是猜；有了它，"该修哪一层"是读出来的，不是想出来的。

**Independent Test**：拿 20 条已知答案的问题跑一遍，能说清每条是在哪一步丢的。**这一步不需要改任何检索代码即可完成。**

**Acceptance Scenarios**：

1. **Given** 一批人工确认过答案的问题，**When** 逐个跑各个角度，**Then** 每条问题都有一行记录，标明各角度各自"命中/未命中"
2. **Given** 跑完的结果，**When** 按"丢在哪一步"归并，**Then** 能得出**三种**结论之一：**前 1000 名里都没有**（`not-any`）/ **只有融合丢**（`fusion-only`）/ **多个环节都丢**（`multi-stage`）。
   **⚠ 2026-10-06 更正**：原写的是**四种**，多一个「只有近似索引丢」—— 本仓无近似索引 ⇒ 该结论**结构性不可达**，已删除。
   **另新增一种**：**被取回上限截断**（`truncated`，前 1000 名里有但每路前 20 名里没有）——
   它是"改上限就能拿回来"的一类，**与"表示能力"无关，必须单独一档**。
3. **Given** 得出的结论，**When** 对照预设的判读规则，**Then** 直接指出下一步该修哪一层（或指出"表示能力本身不够"）

### User Story 2 - 有一份可复跑的"改动前"基线 (Priority: P2)

业主把**当前系统的状态**固定下来：它现在用什么配置、在这批问题上表现如何、每条问题的原始结果是什么。**以后任何改动，都能拿它当"改前"对照。**

**Why this priority**：没有它，改动之后**无法证明是变好了还是变坏了**；而且现有那几个数字口径不明，不能当基线用。

**Independent Test**：同一套配置连跑两次，两次结果一致；换一套配置，结果能看出差别。

**Acceptance Scenarios**：

1. **Given** 当前系统，**When** 盘点并记录它的关键配置，**Then** 得到一份可读的配置记录（用了什么模型、有没有按字检索、索引怎么配的、取多少条、在什么机器上跑）
2. **Given** 现有那几个数字，**When** 找到产出它们的统计代码，**Then** 每个数字的确切定义（分母是什么、算的是"排在前几"、还是"有没有被找到"）被写清楚
3. **Given** 冻结好的基线，**When** 用同一套配置重跑，**Then** 结果与首次一致

---

### User Story 3 - 能用同一批问题比较"改了一处"带来的变化 (Priority: P3)

业主改**某一个环节**（比如换一种文本表示、或加一条检索通道），**其他环节一律不动**，在同一批问题上重跑，看出这一处改动带来了多少变化。

**Why this priority**：只有一次只改一处，才能知道**是哪一处起了作用**；同时改多处，即使数字变好也不知道为什么。

**Independent Test**：只改一个环节、其他全部固定，在同一批问题上跑出改前/改后两组数。

**Acceptance Scenarios**：

1. **Given** 冻结的基线，**When** 只改一个环节，**Then** 其余配置与提问文本**逐项不变**（可逐条核对）
2. **Given** 改前/改后两组数，**When** 对照**预先定好**的止损线，**Then** 得出结论：**放弃 / 保留观察 / 值得推广**
3. **Given** 任何一个结论，**When** 追溯，**Then** 都能挂回具体数据，而不是印象

### Edge Cases

- **一条问题有多个正确答案**（同一术语在多份文件里各有定义）⇒ 命中其中任意一个即算命中；必须支持记多个答案。
- **正确答案其实不在库里**（提问依赖库外资料）⇒ 这类必须能被单独标出并剔除，**不能算系统失败**。
- **短条款占 36.8%**（<40 字的条款）⇒ 分析时必须能按这个子集切片看。
- **字面零重合的问题占多数**（971/1832）⇒ 分析时必须能按这个子集切片看。
- **提问里带明确标准号**（如 "GB 50016"）⇒ 这类要能单独切片，它们是"引用型通道"的适用对象。
- **口径冲突**：新指标与旧数字口径不同时**不得混比**；旧数字只能在口径确认后使用。

## Requirements *(mandatory)*

### Functional Requirements

**诊断准备**

- **FR-001**: 系统 MUST 能盘点并记录当前检索链路的六项关键配置：所用的语义模型及其维度、是否具备按字检索通道、**向量索引的类型与关键参数**、当前截取的候选数量、运行所在机器的 CPU/内存/是否有 GPU。
  **⚠ 2026-10-06 更正**：原写的是「**近似索引**的类型与关键参数」。实测本仓**没有近似索引** ——
  `clause_vec` 是 `vec0`、`sqlite-vec` 只做暴力精确扫描。该项已改为「向量索引的类型与关键参数」，
  并 MUST 如实记为"`vec0` 暴力精确扫描、无 ANN"。（产出见 `eval/recall-funnel/config-inventory.md`。）
- **FR-002**: 系统 MUST 能找到产出既有那几个数字（53% / 6.8% / 5.8% / 41.6% / 24.5% / 11.8%）的统计代码，并把每个数字的**确切定义**写清楚（分母、截断位置、"被找到"的判定）。
- **FR-003**: 既有数字在口径确认前 MUST NOT 被用作任何技术决策的依据。

**基准集**

- **FR-004**: 系统 MUST 支持建立一份 **150～200 条**的问题基准，每条包含：提问原话、**经人工确认的**正确条文标识（**允许一条问题对应多个正确条文**）。
- **FR-005**: 基准 MUST 支持为每条问题标注难度子集：短条款、字面零重合、带标准号、普通。
- **FR-006**: 基准 MUST 支持标记"答案不在库内"的问题，并在统计时排除。

**漏斗测量**

- **FR-007**: 系统 MUST 能对基准中每条问题，分别输出它在**每一条实际存在的召回通道**各自的前 1000 条里**是否包含正确条文**，以及正确条文的名次。
  **⚠ 2026-10-06 更正**：原写「四个检索角度」；实测是**六条通道**（A–F），且 MUST 区分
  「该通道**未触发**」与「触发了但没命中」——前者不是"丢了"，是"这条路没开"。
- **FR-008**: 系统 MUST 能输出四个截断位置各自的命中率：前 20 / 前 100 / 前 1000，以及至少一个更靠后的截断位置，用于判断"是不是排得太靠后"。
- **FR-009**: 系统 MUST 能按 FR-005 的每个子集分别给出命中率，而不只是全体平均。
- **FR-010**: 系统 MUST 把"哪一步丢的"归并成可判读的结论，并对照预设规则指出下一步该动哪一层。

**基线与实验**

- **FR-011**: 系统 MUST 能冻结一份可复跑的基线，至少包含：配置、指标、每条问题的原始结果。
- **FR-012**: 基线 MUST 可复跑且结果稳定（同一配置两次结果一致）。
- **FR-013**: 任何改进实验 MUST 只改变一个环节，其余配置逐项冻结并可核对。
- **FR-014**: 每个改进实验 MUST 在开跑前定好止损线（放弃阈值 / 观察阈值 / 推广阈值）。
- **FR-015**: 第一个改进实验 MUST 只改**文档送给模型理解时所用的文本**（原文、页码、坐标等**一律不动**），并保留分字段存储以便后续单独调权。
- **FR-016**: 诊断完成前，系统 MAY NOT 改动任何检索算法。

### Key Entities

- **基准问题**：一条提问原话 + 一个或多个正确条文标识 + 难度子集标签 + 是否"答案在库外"。
- **基线快照**：一次冻结下来的系统状态 —— 配置记录 + 各项指标 + 每条问题的原始返回结果。以后所有实验都以它为对照。
- **漏斗记录**：一条问题在四个检索角度、各个截断位置上的命中情况。
- **改进实验**：改动了哪一个环节 + 改前/改后指标 + 是否达到止损线 + 结论。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: **能明确说出问题出在哪一层** —— 结论必须落在**三档之一**（`not-any` 够不着 / `truncated` 被取回上限截断 / `fusion-only` 只有融合丢），另加"多环节都丢"作为兜底，**不接受"好像哪都不行"这类结论**。
  **⚠ 2026-10-06 更正**：原写「四种之一（仅近似索引有损 / 仅合并有损 / 多环节有损 / 连精确计算都找不到）」。
  本仓无近似索引 ⇒「仅近似索引有损」**结构性不可达**，已删；并**新增** `truncated` 一档
  （实测它占 171 条里的 **48 条 / 28.1%**，是**"改上限就能拿回来"**的一类，不许与"够不着"混为一谈）。
- **SC-002**: 基线**可复跑**：同一配置连跑两次，各项指标完全一致。
- **SC-003**: 基准集达到 **150～200 条**，且**每条的答案都经人工确认**（不是自动生成后未经确认）。
- **SC-004**: 第一个改进实验在**预设止损线**内给出明确结论（放弃 / 保留观察 / 推广），**且改动面可逐项核对只限于一处**。
- **SC-005**: 全部结论**可追溯** —— 每个结论都能挂回具体的原始数据，不依赖印象或转述。
- **SC-006**: 交付周期落在 **7～10 天**内；且**诊断（第 1～3 天）完成前不发生任何检索算法改动**。

## Assumptions

- **语料规模冻结在现状**：库里现有 522,021 条条文；本周期**不做扩容**，也不按千万级做分布式改造（架构上按可扩容设计，但不实做）。
- **提问候选已有现成来源**：`eval/lay-phrasing/` 的 1,832 条外行说法可当**提问候选**；但**它们只是候选，不是答案** —— 正确答案必须人工确认。
- **已有部分评测资产**：`eval/golden/` 的 96 条是"防倒退尺子"，**不是难度尺子**，本周期**不改它的用途**。
- **单机环境**：全部实验在一台机器上跑完，不涉及集群。
- **`gen-V2.jsonl` 是只读基准**：它是既有那批数字的唯一来源，**只读不改**。
- **每轮改动走仓库既有纪律**：小提交 + 快照 + 门禁，提交信息写清"改了什么 / 为什么 / 边界"。

## 明确不做（本周期）

- 全面重写切分器
- 引入图数据库 / 知识图谱
- 全库上多向量（late interaction）方案
- 全库上视觉模型
- 自训基础模型
- 完整的 Agent 式多轮检索
- 同时更换语义模型 + 切分方式 + 重排器
